## 1. Project outcome and governing decisions

Build a native PlayStation 2 implementation of *Halo: Combat Evolved* using:

- Selected portable gameplay implementation from `halo-64` and `halo-ce-universal`.
- PS2-specific rendering, platform services, and conversion infrastructure adapted from `halo-ps2`.
- Offline conversion of user-supplied Xbox retail data.
- A fixed 30 Hz gameplay simulation.
- PS2-native VIF, VU1, GS, IOP, and SPU2 services.
- Reproducible native Linux and container build environments.

The complete target includes:

1. All 13 original Xbox multiplayer maps.
2. One-to-four-player local split screen.
3. Stock multiplayer game types and team variants.
4. Weapons, equipment, vehicles, HUD, effects, and audio.
5. Multiplayer bots.
6. All ten campaign missions, including scripts, encounters, dialogue, cinematics, checkpoints, and saves.
7. Two-player local cooperative campaign.
8. An OPL-compatible standalone image.
9. Subsequent optical-disc and physical-console validation.

Networking, System Link, online multiplayer, four-player campaign, PAL support, and 60 fps rendering are outside the initial delivery requirements.

Development remains private. Retail assets, converted packs, BIOS files, recordings containing retail material, and data-bearing images remain outside tracked source.

### First major success

The first major architectural success is a **hybrid proof**:

> Selected original Halo gameplay modules execute on R5900, drive visible object state through a narrow interface, and coexist with the PS2 renderer without introducing simulation dependence on rendering.

A successful textured triangle alone does not satisfy this gate. Cross-compiling gameplay code without executing it does not satisfy it either.

### Fidelity and performance priorities

Apply optimizations in this order:

1. Remove redundant work and improve data layout.
2. Improve visibility, batching, caching, and streaming.
3. Reduce texture resolution, render distance, effect density, and visual complexity.
4. Improve scheduling without changing gameplay outcomes.
5. Consider gameplay changes only through an explicit design revision supported by measurements.

Do not inherit N64-specific gameplay reductions merely because they already exist in `halo-64`.

### 2.5 Memory contract

Restore the original research allocation. Its arithmetic was already correct: **26.5 MiB committed plus 5.5 MiB reserve equals 32 MiB**.

| Region | Initial allocation |
|---|---:|
| System and kernel reservation | 1.5 MiB |
| ELF code, constants, static tables | 2.0 MiB |
| Resident gameplay and tag data | 6.5 MiB |
| Current BSP, collision, portals, path data | 6.0 MiB |
| RAM texture and lightmap cache | 4.0 MiB |
| Dynamic simulation and effects | 2.5 MiB |
| DMA and render command buffers | 1.0 MiB |
| Streaming and decompression | 1.5 MiB |
| Checkpoint storage | 0.5 MiB |
| Audio staging | 0.5 MiB |
| Frame scratch | 0.5 MiB |
| Uncommitted reserve | 5.5 MiB |
| **Total** | **32.0 MiB** |

Treat these as initial engineering allocations. Any transfer between regions requires recorded measurements and a versioned budget change.

Count stacks, allocator metadata, alignment padding, executable sections, loaded IOP-related EE buffers, and temporary overlap during loading. Do not count the same allocation under multiple categories.

Measure GS framebuffer and depth-buffer requirements before assigning the remaining texture window. Do not assume the approximate window in the research is the exact usable allocation.

Git’s recursive update initializes missing nested repositories and checks out the commits recorded by their parent repositories. ### Local-fork restoration

1. Keep canonical upstream URLs in tracked submodule metadata during the local-only phase.
2. Before introducing a fork-only commit into a gitlink, create a complete private bundle containing that commit and its necessary history.
3. Verify the bundle and record its checksum and advertised references.
4. During bootstrap, initialize submodule configuration, restore local fork repositories, and apply local URL overrides before checkout.
5. If synchronization updates URLs from `.gitmodules`, reapply the local fork overrides afterward.
6. Allow local transport only for the explicit local-fork operation; do not change global Git transport policy.
7. Fail clearly if a required fork commit is unavailable. Do not silently substitute its upstream ancestor.

Git bundles provide an offline mechanism for transferring repository objects and references; full bundles must be independently restorable. [Git bundle documentation](https://git-scm.com/docs/git-bundle)

### Acceptance tests

- All eight top-level repositories are real submodules.
- Recursive initialization completes.
- Gitlinks and lock-manifest commits agree.
- Re-running bootstrap leaves source pins unchanged.
- A fresh parent checkout can restore fork-only commits from the private bundle set.

- Dirty submodule worktrees are preserved rather than reset automatically.

## 27. Cross-cutting regression and update procedures

### Dependency updates

For every proposed upstream update:

1. Fetch into a local fork without changing the current build pin.
2. Review source and dependency changes.
3. Replay or merge project adaptations on a dedicated update branch.
4. Run affected upstream tests.
5. Run parent host tests and build-parity checks.
6. Run the relevant emulator scenarios.
7. Run hardware regressions for changes affecting platform behavior.
8. Update fork bundles and lock metadata.
9. Update parent gitlinks only after the required checks pass.

### Pack or converter changes

1. Identify affected sections and consumers.
2. Update format documentation when compatibility changes.
3. Run synthetic malformed-input tests.
4. Reconvert affected retail inputs privately.
5. Compare reports and hashes.
6. Run loader and visual regressions.
7. Reject old incompatible packs clearly.

### Gameplay changes

1. Identify the behavior and reference scenario.
2. Preserve the failing replay or observation.
3. Apply the smallest source or compatibility change.
4. Compare discrete outcomes and declared numerical tolerances.
5. Test rendering independence.
6. Update evidence links and limitations.

### Milestone closure

Close a milestone only after its deliverables exist, its required checks have run, and unresolved conditions are accurately recorded. If external prerequisites remain unavailable, preserve useful completed work and leave dependent acceptance pending.

1. Review the milestone's deliverables and acceptance criteria against actual evidence. Leave the milestone `INCOMPLETE` if any required gate remains pending.
2. Run the relevant validation and record commands, dependency/tool identities, results, artifact locations, and remaining limitations in the milestone evidence.
3. For any modified submodule, commit its scoped changes in its local fork, preserve the fork commit in its private bundle, and update the parent gitlink and dependency manifest together.
4. Mark the milestone `COMPLETE` in this plan's tracker and milestone section, and update `docs/milestones.md` in the same change.
5. Review the staged diff and create a dedicated local parent-project commit with a message such as `M03: Complete reproducible PS2 toolchain validation`. Include only changes belonging to that milestone and its required evidence; exclude unrelated user changes, retail assets, private bundles, and generated build outputs.
6. Record the resulting commit ID in the next execution record or milestone handoff, then proceed to the next eligible milestone. Do not amend a commit merely to insert its own hash into itself.
7. Keep partial-work checkpoints explicitly labeled as such. A checkpoint commit does not complete a milestone. If several milestones become eligible together, close and commit them separately. Local commits do not authorize pushing or publishing.

## 28. Assumptions and unresolved external prerequisites

The following are established project defaults:

- Full Xbox ISO or map data will be supplied locally.
- xemu is the behavioral reference environment.
- Initial development and fork storage remain private and local.
- Both native and container builds are supported equally.
- Real PS2 access is not currently assumed.
- Gameplay implementation reuse is conditional on compatibility and behavior gates.
- A failed compatibility probe triggers documentation and replanning rather than automatic replacement.
- Later subsystem specifications are frozen at their milestone entry using audited source and measured evidence.

The following must be resolved through environment access rather than guessed:

- Writable parent Git metadata.
- Reliable access to dependency repositories and archives.
- Actual full commit pins.
- Current buildable branches of the two foundation projects.
- Availability and location of user-supplied retail data and emulator prerequisites.
- Compatible REA providers for specific artifact investigations.
- Physical-console configuration and operator availability.

No milestone may invent these facts or treat their absence as a successful validation.
