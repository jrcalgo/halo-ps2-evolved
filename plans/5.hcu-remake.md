# Halo CE Universal PS2 Gameplay Migration

**Status:** plan authored and committed on branch `port/halo-ce-universal-remake`; M0 is in progress (source ownership decision recorded; compile-closure and ABI gates remain open).

## 1. Objective and locked decisions

Move the authoritative Halo gameplay simulation into the pinned `halo-ce-universal` fork, as Halo-64 did for its platform, while retaining this repository as the PlayStation 2 machine, renderer, pack pipeline, and integration layer. This is a source-ownership migration, not a replacement of the PS2 renderer or a change to the product scope.

The governing target remains all 13 Xbox multiplayer maps, one-to-four-player local split screen, stock multiplayer modes, vehicles, bots, ten campaign missions, scripts, AI, checkpoints, two-player co-op, and OPL delivery. Online play, System Link, four-player campaign, PAL, and 60 fps remain out of scope ([project scope](0.native-ps2-halo-hybrid-port.md#L67), [exclusions](0.native-ps2-halo-hybrid-port.md#L79)). The CE simulation remains fixed at 30 Hz.

The PS2 parent keeps the GS/VU1/DMA renderer, HP2/world/stream readers, offline asset conversion, fixed-memory bootstrap, pad, timer, and future SPU2 playback. HCU owns authoritative objects and datums, physics and collision, player/unit movement, weapons, projectiles, damage, local game rules, AI, HaloScript, effect simulation, HUD decisions, and first-person weapon simulation. Parent `sim/objects`, `sim/skeleton`, and `sim/fpview` become read-only snapshot consumers. A gameplay collision query has one owner: HCU.

Special-weapon decisions:

- **Fuel rod:** the pinned HCU source has generic tag-driven weapon/projectile/damage behavior, not a dedicated fuel-rod code path. Its weapon-set comment says the Xbox maps it reflects had no fuel rod ([generic firing](../submodules/halo-ce-universal/source/items/weapons.c#L2863), [generic projectile update](../submodules/halo-ce-universal/source/items/projectiles.c#L665), [weapon-set note](../submodules/halo-ce-universal/source/game/game_engine.c#L7902)). The supplied map audit does include the CE `weapons\\fuel rod gun\\fuel rod` tag ([inventory](../docs/combat.md#L23)); route it through HCU's generic tag path, without adding a bespoke branch unless new source/tag evidence requires one.
- Remove the parent fuel-rod gameplay and the borrowed Halo 2/rocket-launcher view pose. The tag audit says the fuel rod has no first-person model/graph; HCU draws a first-person weapon only when the tag supplies a first-person animation reference ([HCU draw condition](../submodules/halo-ce-universal/source/interface/first_person_weapons.c#L498), [current parent fallback](../src/game/play_fp.c#L848)). Thus the accepted fallback is arms-only, not a synthesized fuel-rod model or pose.
- **Energy sword and gravity rifle:** retain both as supported weapons. Any weapon-specific gameplay extensions belong in marked HCU fork code, reusing CE's generic object, damage, and projectile paths where possible. Preserve their accepted Halo 2-derived sword/carbine orientations only as PS2 presentation adaptation; do not retain duplicate gameplay in parent `src/game` ([current pose mapping](../src/game/hold_pose.h#L9), [path dispatch](../src/game/hold_pose.h#L31), [M13 gravity-rifle requirement](0.native-ps2-halo-hybrid-port.md#L916), [M13 sword requirement](0.native-ps2-halo-hybrid-port.md#L917)).

## 3. Milestones

### M0 — Freeze ownership and measure the compile closure

1. Update `docs/source-audit.md`: HCU becomes production gameplay source; Halo-64 remains a behavioral/portability reference; `halo-ps2` remains the machine/renderer reference. Record the exact HCU source commit and fork provenance.
2. Create a source/owner table for every gameplay, presentation, and platform subsystem. Require each HCU source departure to have a `port:` comment and use `HALO_PS2` for platform-specific conditionals ([HCU source-edit rules](../submodules/halo-ce-universal/AGENTS.md#L115)).
3. Generate a reproducible compile/link closure report rooted at local-game startup, map initialization, one simulation tick, player control, object lifecycle, collision, combat, AI, scripts, effects, HUD, and sound decisions. Report live relocations and classify each as simulation, data, PS2 service, render, or excluded feature.
4. Do not adopt `port/linux/port.json` as the PS2 source manifest: it gathers the broad game tree together with desktop source and SDL-oriented libraries ([manifest](../submodules/halo-ce-universal/port/linux/port.json#L3)). Do not use Halo-64's big-endian prefix or empty-stub policy: its prefix targets big-endian MIPS and its stub generator describes omitted AI, sound, networking, and renderer systems ([N64 prefix](../submodules/halo-64/port/n64/include/halo_n64_prefix.h#L4), [stub policy](../submodules/halo-64/tools/n64_stubs.py#L6)).
5. Freeze one collision owner (HCU) and one identity owner (HCU datum/object state). The parent object table must not remain a competing simulation database.

**Exit gate:** reviewed closure report; source/owner matrix; no unresolved simulation symbol classified as a harmless stub.

### M1 — Establish the R5900 PS2 port layer

1. Add a dedicated HCU `port/ps2` manifest, prefix, declarations, and local-game startup. Build for little-endian MIPS ILP32, with 32-bit pointers/`long`, 16-bit `wchar_t`, and only required MSVC/XDK compatibility semantics. Explicitly reject `HALO_N64` and `HALO_LINUX` in this target.
2. Add compile-time ABI assertions for pointer/`long`/`wchar_t`, tag references and blocks, datum headers, object records, and weapon/projectile records. Confirm layout under host ILP32 and R5900 compilers before adding larger source groups.
3. Compile in narrow layers: C runtime/math and memory; tag/datum services; object/physics/collision; player/game tick; then weapons/projectiles/damage. For each layer record compiler flags, source hashes, unresolved symbols, and live relocations. The existing combat probe is useful closure evidence only; it explicitly uses N64 capacity macros as compile placeholders and is not a PS2 runtime ([probe disclaimer](../tools/probe_combat_source.py#L1), [probe flags](../tools/probe_combat_source.py#L138)).
4. Replace Xbox shell/main startup with a PS2 façade that starts a local game. Keep local player/mode logic; exclude online/System Link transport and desktop UI/platform implementation. Implement a minimal local-session service only where source local-game code requires host/session state.
5. Supply explicit declarations for rendering/snapshot submission, pad, time, files, profiling, logging, and sound requests. Simulation services must be implemented; render-only callbacks may be empty only after the M0 call-graph audit proves they cannot change simulation state.

**Exit gate:** a minimal R5900 ELF links and boots the CE-owned local-game lifecycle without Direct3D, DirectSound, Bink, or online-netcode relocations.

### M2 — Fixed memory and a runtime tag image

1. Inventory every allocation path used by the selected source closure, including `match_malloc`, `game_state_malloc`, datum arrays, memory pools, temporary tags, and map transitions. Route them through the parent boot allocation's fixed sub-arenas; preserve CE datum handles/generation behavior ([datum allocation](../submodules/halo-ce-universal/source/memory/data.c#L225), [pool creation](../submodules/halo-ce-universal/source/memory/memory_pool.c#L124)).
2. Treat current capacities as strict budgets, not proof of fit: 32 MiB total, `dynamic_simulation` 2,621,440 bytes, `resident_gameplay` 6,815,744 bytes, and the existing reserve unspent absent measured approval ([budget](../config/memory-budget.json#L4)). Resolve the current world-arena overrun before assigning CE tag/collision allocations; the recorded high-water exceeds `current_bsp` ([arena findings](../docs/memory.md#L45)).
3. Extend the offline converter to emit a versioned, checksummed, little-endian CE tag image with bounded tag/reference tables and validated relocation data. Keep render geometry/bitmap payloads in PS2 packs. Keep collision BSP accessible to CE collision while accounting its bytes with the map/BSP region.
4. Load the runtime tag image through HP2 sections using existing bounds, alignment, codec, and CRC validation ([HP2 section layout](../submodules/halo-ps2/engine/src/stream/hp2.h#L25), [HP2 validation](../submodules/halo-ps2/engine/src/stream/hp2.c#L18)). Map load must fail closed on malformed references, overflow, unsupported fields, or budget exhaustion.
5. Add deterministic converter fixtures for a small synthetic tag set and the supplied Blood Gulch map. Verify byte-identical outputs, valid cross-tag references, correct endianness/layout, and that render vertices/bitmap pixels are not duplicated into the gameplay image.

**Exit gate:** map load/unload returns to a stable arena baseline; no steady-state heap allocation; measured high-water fits the assigned regions and preserves the reserve.

### M3 — CE player, object lifecycle, movement, and collision

1. Initialize through CE `game_initialize` and advance the original `game_tick` at the existing 30 Hz cadence, retaining source ordering for units, AI, first-person update, game rules, scripts, and objects ([initialization](../submodules/halo-ce-universal/source/game/game.c#L277), [tick](../submodules/halo-ce-universal/source/game/game.c#L330)). Do not replace it with the parent diagnostic play loop.
2. Wire tick-indexed input from the existing DualShock pad service into CE player control; support the parent’s 1–4 local players. Preserve existing dead-zone/button behavior only where it matches the locked control contract ([pad poll](../submodules/halo-ps2/engine/src/platform/pad.c#L40)).
3. Use CE object datums as the sole state/identity across ticks. Preserve generation-safe handles in any parent-side render records. Convert `sim/objects`, `sim/skeleton`, and `sim/fpview` to consume-only readers, not object/animation/first-person simulation ([render-table contract](../submodules/halo-ps2/engine/src/sim/objects.h#L1)).
4. Route player sweeps, BSP tests, object collision, actor collision, and projectile tests through CE physics/collision. Retire parent `collide.c`/`collpack.c` only after parity fixtures pass; no duplicate collision authority ([CE pill/BSP query](../submodules/halo-ce-universal/source/physics/collision_bsp.c#L1130)).
5. Add a PS2 snapshot builder after each completed CE tick. It publishes immutable object transforms, node palettes, cameras/first-person pose, HUD work, and render-only effect requests. The parent renderer may skip/delay rendering without mutating the snapshot or simulation.

**Exit gate:** real player movement and collision use CE records and collision; test traces match with zero, one, or multiple render passes between ticks.

### M4 — Replace M13 duplicate combat

1. Link CE weapon, projectile, damage, and grenade lifecycles to the converted tag system and M3 collision owner. Preserve source ordering, ownership, deterministic random state, material/region selection, and AoE filtering. Keep parent combat modules as comparison fixtures during this milestone; do not delete them before equivalence is demonstrated.
2. Close the parent M13 ledger for all 23 audited `weap` paths, grenade equipment/projectiles, objective items, actor weapons, and vehicle/turret origins—not just the current player-camera diagnostic path ([scope](../plans/0.native-ps2-halo-hybrid-port.md#L894), [runtime acceptance ledger](../plans/0.native-ps2-halo-hybrid-port.md#L904)).
3. Fuel rod: instantiate the supplied CE tag through generic HCU weapon/projectile/damage paths; delete the parent bespoke fuel-rod combat profile and borrowed viewmodel path. Test its tag-derived trigger, ammo semantics, projectile air/water values, ownership, collision response, detonation/AoE, and failure behavior. Assert no Halo 2 pose/model fallback; the current tag’s missing first-person graph means arms-only presentation.
4. Energy sword: retain its special melee/lunge arbitration, tag-backed damage, and accepted animation/presentation behavior in HCU plus the PS2 presentation adapter. Gravity rifle: retain its weapon-specific behavior on its tagged flame-projectile route and the accepted carbine-relative presentation; do not equate it with flamethrower behavior.
5. Add actor-target fixtures and source-backed replay tests for cadence, reload, trigger release/charge, collision materials/regions, damage/shields/death, projectile exhaustion, simultaneous explosions, and render-schedule invariance. Diagnostic sphere passes remain smoke evidence, not acceptance.

**Exit gate:** every M13 ledger row passes integrated actor/vehicle/object tests and source-reference comparisons in both PCSX2 interpreter and recompiler, with identical normalized simulation traces.

### M5 — Integrate AI, scripts, effects, HUD, local modes, and sound decisions

1. Expand the source closure to full AI/pathfinding, HaloScript runtime, scenarios, devices, and cutscenes. Keep actor decisions and scripts active; `actors_update` performs perception, decisions, movement, and combat, while `hs_update` runs the script runtime ([actor update](../submodules/halo-ce-universal/source/ai/actors.c#L4200), [script update](../submodules/halo-ce-universal/source/hs/hs.c#L13544)).
2. Retain effects simulation and tag logic; submit only their render representation to PS2. Keep CE HUD decisions for shields, ammo, motion sensor, and messages, and translate draw calls into bounded quads/glyph requests.
3. Keep sound choice/priority in CE. Replace DirectSound with parent sound requests containing event/tag identity, owner, position, and playback parameters; SPU2 later owns voice allocation, ADPCM upload, and mixing. Sound delivery must not feed results back into simulation ([sound-to-platform seam](../submodules/halo-ce-universal/source/sound/sound_manager.c#L1279)).
4. Preserve local Slayer/CTF/Oddball/King/Race and other stock local modes, split-screen player state, and campaign script/encounter support. Omit network transport, Bink, and desktop presentation only; do not stub game rules or campaign systems.
5. Add representative multiplayer and campaign maps as resource/behavior fixtures. Measure AI, script, effects, tag, and actor pool high-water on both dense combat and scripted/cinematic scenes.

**Exit gate:** gameplay logic remains CE-owned for the full planned local multiplayer and campaign features, with PS2 rendering/audio backends consuming requests only.

### M6 — Resource/performance qualification and retire the duplicate path

1. Produce an auditable per-map report for static ELF, permanent tags, BSP plus collision, dynamic simulation, streaming, audio staging, and frame scratch. Enforce the 32 MiB budget and keep the 5.5 MiB reserve unchanged until measured end-to-end data supports a budget revision.
2. Profile CE tick, AI, collision, combat, and snapshot work with the EE timer at 30 Hz. Target the full 33.3 ms tick budget; record phase timings and worst-case actors/projectiles/effects. PCSX2 results are regression evidence, not physical EE timing. Do not reduce simulation frequency or AI/effect populations by assumption ([EE timer](../submodules/halo-ps2/engine/src/platform/timer.h#L1)).
3. Run deterministic scenario replays across render schedules and both emulator CPU modes. Hash CE gameplay state in stable datum order (handles/generations, transforms/velocities, weapons/ammo, projectiles, health/shields, random state, tick); exclude render/audio-only work.
4. Once parity and budget gates pass, remove parent `src/game` gameplay modules from the production link and retire their duplicate behavior/tests. Retain the PS2 renderer, world readers, HP2 packs, fixed allocator, platform services, snapshot adapter, and sword/gravity-rifle presentation exceptions. Remove the fuel-rod pose adapter entirely. `src/game` must not grow with further weapon, projectile, damage, or movement semantics ([current duplicate link list](../tools/ee-world.mk#L43), [current play loop imports](../src/game/play_ee.c#L1)).
5. Record the final HCU source commit/gitlink, source closure, ELF hash, test traces, arena high-water, emulator configurations, and remaining physical-hardware work. Physical PS2 RAM/CPU qualification remains a separate release gate.

**Exit gate:** production gameplay is HCU-only; CE parity, emulator determinism, bounded allocation, and measured memory gates pass; physical-console claims are explicitly left open until hardware testing.

## 4. Interfaces, tests, and failure policy

The parent/HCU boundary is a small `port/ps2` façade with these contracts:

- Startup/shutdown and map load/unload operate on caller-owned fixed arenas and return explicit errors; no source path may fall back to heap allocation.
- Each simulation call consumes tick-indexed commands for local player slots and invokes one CE tick. CE datum handles are authoritative; no parent-side object identity is invented.
- Snapshot production is read-only and bounded. It carries the render data needed by GS/VU1, HUD/effect draw requests, and first-person presentation; render code cannot call back into gameplay state mutation.
- Sound requests are one-way presentation events to SPU2. They may be dropped/culled by the audio backend under bounded-resource pressure but cannot alter gameplay outcomes.
- Platform-only omissions are classified by call site. Missing tag, collision, object, AI, script, or gameplay services are fatal to map/game startup rather than silently stubbed.

Required verification includes ABI/layout tests; converter corruption/bounds/CRC tests; allocator exhaustion and map reload tests; CE-source host fixtures; all M13 actor/vehicle/object scenarios; source-state hashes across render schedules; R5900 link and size reports; PCSX2 interpreter/recompiler parity; and eventual physical-PS2 measurement under the parent M23 gate. The existing parent build links bespoke gameplay modules today ([play target](../tools/ee-world.mk#L43)), and `play_ee.c` currently imports them and performs runtime `malloc` ([imports](../src/game/play_ee.c#L1), [allocation](../src/game/play_ee.c#L423)); both are explicit migration targets, not patterns for the final architecture.

Failure policy: preserve the last known-good branch and HCU pin; do not delete the parent comparison path before its replacement passes the same fixture; do not expand a failed source closure with broad zero-return stubs; reject over-budget maps/records rather than corrupt memory; and document any behavior divergence as a port-specific exception with a source citation and regression test.
