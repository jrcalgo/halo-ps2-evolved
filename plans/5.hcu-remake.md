## 1. Objective and locked decisions

Move the authoritative Halo gameplay simulation into the pinned `halo-ce-universal` fork and compile that CE `source/` for the PlayStation 2, inside the machine's R5900, 32 MiB EE RAM, 4 MiB GS eDRAM, 2 MiB IOP RAM, and 2 MiB SPU2 RAM, while retaining this repository as the machine, renderer, pack pipeline, and integration layer. Pinned `halo-64` (`17541f4444baabb47d1a0deb917f26ccb7b6bc5c`) is the example of this method: it implements Halo on the Nintendo 64, hardware the Xbox game was not written for, by compiling Halo CE `source/` and replacing the Xbox platform underneath it. This is a source-ownership migration, not a replacement of the PS2 renderer or a change to the product scope.

The governing target remains all 13 Xbox multiplayer maps, one-to-four-player local split screen, stock multiplayer modes, vehicles, bots, ten campaign missions, scripts, AI, checkpoints, two-player co-op, and OPL delivery. Online play, System Link, four-player campaign, PAL, and 60 fps remain out of scope ([project scope](0.native-ps2-halo-hybrid-port.md#L67), [exclusions](0.native-ps2-halo-hybrid-port.md#L79)). The CE simulation remains fixed at 30 Hz.

The PS2 parent keeps the GS/VU1/DMA renderer, HP2/world/stream readers, offline asset conversion, fixed-memory bootstrap, pad, timer, and future SPU2 playback. HCU owns authoritative objects and datums, physics and collision, player/unit movement, weapons, projectiles, damage, local game rules, AI, HaloScript, effect simulation, HUD decisions, and first-person weapon simulation. Parent `sim/objects`, `sim/skeleton`, and `sim/fpview` become read-only snapshot consumers. A gameplay collision query has one owner: HCU.

Special-weapon decisions:

- **Fuel rod:** the pinned HCU source has generic tag-driven weapon/projectile/damage behavior, not a dedicated fuel-rod code path. Its weapon-set comment says the Xbox maps it reflects had no fuel rod ([generic firing](../submodules/halo-ce-universal/source/items/weapons.c#L2863), [generic projectile update](../submodules/halo-ce-universal/source/items/projectiles.c#L665), [weapon-set note](../submodules/halo-ce-universal/source/game/game_engine.c#L7902)). The supplied map audit does include the CE `weapons\\fuel rod gun\\fuel rod` tag ([inventory](../docs/combat.md#L23)); route it through HCU's generic tag path, without adding a bespoke branch unless new source/tag evidence requires one.
- Remove the parent fuel-rod gameplay and the borrowed Halo 2/rocket-launcher view pose. The tag audit says the fuel rod has no first-person model/graph; HCU draws a first-person weapon only when the tag supplies a first-person animation reference ([HCU draw condition](../submodules/halo-ce-universal/source/interface/first_person_weapons.c#L498), [current parent fallback](../src/game/play_fp.c#L848)). Thus the accepted fallback is arms-only, not a synthesized fuel-rod model or pose.
- **Energy sword and gravity rifle:** retain both as supported weapons. Any weapon-specific gameplay extensions belong in marked HCU fork code, reusing CE's generic object, damage, and projectile paths where possible. Preserve their accepted Halo 2-derived sword/carbine orientations only as PS2 presentation adaptation; do not retain duplicate gameplay in parent `src/game` ([current pose mapping](../src/game/hold_pose.h#L9), [path dispatch](../src/game/hold_pose.h#L31), [M13 gravity-rifle requirement](0.native-ps2-halo-hybrid-port.md#L916), [M13 sword requirement](0.native-ps2-halo-hybrid-port.md#L917)).

### Halo-64: compiling CE source for unintended hardware

Pinned `halo-64` is the method example for this migration. The PS2 work follows that shape inside the HCU fork. The EE link does not include Halo-64 objects, and HCU `source/` is the simulation that gets compiled.

1. Compile the CE simulation with the target toolchain, and keep the platform layer separate. Halo-64's build takes the project's own `source/` and compiles it for the console ([N64 build](../submodules/halo-64/tools/n64_build.py#L11)).
2. Select those sources with a port manifest, and force-include a prefix that reproduces the MSVC/XDK environment the sources assume ([manifest](../submodules/halo-64/port/n64/port.json#L11), [prefix](../submodules/halo-64/port/n64/include/halo_n64_prefix.h#L3)). Leave the Xbox shell in the link, with `main` renamed so the machine entry can call it ([shell rename](../submodules/halo-64/port/n64/port.json#L56), [game entry](../submodules/halo-64/port/n64/src/n64_main.c#L449)).
3. Replace Xbox SDK calls in a platform layer type-checked against the declarations the game sees. Keep the machine SDK on the other side of that layer ([platform split](../submodules/halo-64/port/n64/src/platform.h#L4)).
4. Put session, memory-map, and cache-file replacements in a file compiled as a game unit. Halo-64 starts a local game there and substitutes the Xbox physical memory map and disk cache with a map image converted ahead of time ([game-side port](../submodules/halo-64/port/n64/game/n64_game.c#L3), [local setup](../submodules/halo-64/port/n64/game/n64_game.c#L195), [memory map](../submodules/halo-64/port/n64/game/n64_game.c#L734)). Local play is the CE `_game_connection_local` path, up to four players ([local-connection notes](../submodules/halo-64/port/n64/NOTES.md#L8)).
5. Keep simulation results independent of the machine renderer. Halo-64 records that the simulation does not read render results, and that a few calls which look like rendering still advance HUD timers and particle lifetime, so those calls have to run ([render seam](../submodules/halo-64/port/n64/NOTES.md#L33)).

`halo-ps2` remains the PlayStation 2 machine, GS/VU1/DMA renderer, and pack format.

These N64 consequences stay on the N64: the big-endian VR4300 ABI ([prefix target](../submodules/halo-64/port/n64/include/halo_n64_prefix.h#L15)), the pools sized for 8 MB ([limits](../submodules/halo-64/port/n64/include/halo_n64_limits.h#L4)), the manifest's omission of AI, HaloScript, sound, cutscenes, and the Xbox renderer ([excluded directories](../submodules/halo-64/port/n64/port.json#L11)), the generated zero-return stubs for those omissions ([stub policy](../submodules/halo-64/tools/n64_stubs.py#L6)), and the separate campaign experiment ([campaign experiment](../submodules/halo-64/port/n64/game/n64_campaign.c#L4)). The parent scope still requires AI, scripts, campaign, and sound decisions. Those systems are kept by fitting them to the PlayStation 2, not by adopting the N64 cuts or the Xbox pool sizes.

### PlayStation 2 hardware and memory are binding

Every milestone abides by the machine and by budget version 2. A feature that does not fit is reduced in presentation, deferred, or rejected. It does not receive a larger store, a heap fallback, or a spend of the reserve.

The Emotion Engine is a 294.912 MHz in-order R5900 with 32 MiB of RDRAM, a 16 KiB instruction cache, an 8 KiB data cache, no L2, and a 16 KiB scratchpad. Its FPU is single precision and is not IEEE, so the port uses no `double`. DMA moves 16-byte quadwords. VU1 has 16 KiB of micro memory and 16 KiB of data memory, and runtime geometry goes through VU1. The GS has 4 MiB of eDRAM, one texture per primitive, and no DXT compression. The IOP is a 36.864 MHz R3000A with 2 MiB of RAM. SPU2 has 48 ADPCM voices and 2 MiB of sound RAM ([EE](../submodules/halo-ps2/docs/01-ps2-architecture.md#L32), [EE RAM](../submodules/halo-ps2/docs/01-ps2-architecture.md#L46), [VU1](../submodules/halo-ps2/docs/01-ps2-architecture.md#L59), [GS](../submodules/halo-ps2/docs/01-ps2-architecture.md#L97), [IOP](../submodules/halo-ps2/docs/01-ps2-architecture.md#L145), [SPU2](../submodules/halo-ps2/docs/01-ps2-architecture.md#L155)).

EE RAM, GS eDRAM, IOP RAM, and SPU2 RAM are four separate stores. The active EE contract is budget version 2: 27,787,264 bytes committed and 5,767,168 bytes reserved, totaling 33,554,432 bytes ([budget](../config/memory-budget.json#L4), [region table](../docs/memory.md#L9), [memory contract](0.native-ps2-halo-hybrid-port.md#L211)). The 5.5 MiB reserve stays unspent until a measured, versioned revision. GS VRAM is not one of the EE regions ([GS store](../docs/memory.md#L24)). The split in `halo-ps2` `docs/02-specs.md` is historical design guidance; budget version 2 is the account.

- Every live byte has one region: kernel and stacks, ELF static, resident gameplay, current BSP, texture cache, dynamic simulation, DMA commands, streaming, checkpoint, audio staging, or frame scratch. Count alignment padding, allocator metadata, IOP/EE buffers, and bytes that overlap during a load. A byte claimed twice fails the account ([memory contract](0.native-ps2-halo-hybrid-port.md#L233)).
- Steady state uses the boot arenas. A `malloc` after map load, including the allocation in `play_ee.c`, is a migration defect ([allocation](../src/game/play_ee.c#L423)).
- Xbox pool sizes, OpenCE `HALO_PORT_MAXIMUM_*` macros, and Halo-64's `HALO_PORT_GAME_STATE_CPU_SIZE` are foreign capacities. A PS2 pool size is a high-water measurement that fits its assigned region.
- The recorded world-arena high water already exceeds `current_bsp`, and the stream-viewer ELF already exceeds the 2,097,152-byte `elf_static` region ([arena findings](../docs/memory.md#L45), [ELF findings](../docs/memory.md#L27)). Close those overruns before adding CE tag, collision, AI, or effect bytes on top of them.
- The 30 Hz tick has 33.3 ms. The EE phase splits in the PS2 specs are targets until the EE timer measures them; PCSX2 timings are regression evidence ([frame budget](../submodules/halo-ps2/docs/02-specs.md#L77)). Report a tick that does not fit. Leave the simulation at 30 Hz, and leave AI and effect populations in place, until a measurement supports a change.
- When the GS texture window, a DMA chain, an SPU2 voice, sound RAM, or a particle sprite pool is exhausted, the backend drops or coalesces that presentation. Health, ammo, position, scripts, and the simulation hash stay unchanged.

For each row, name the Halo-64 port file or manifest entry that shows the method, or mark the N64 behavior as non-transferable. Require each HCU source departure to have a `port:` comment and use `HALO_PS2` for platform-specific conditionals ([HCU source-edit rules](../submodules/halo-ce-universal/AGENTS.md#L115)).
3. Generate a reproducible compile/link closure report rooted at local-game startup, map initialization, one simulation tick, player control, object lifecycle, collision, combat, AI, scripts, effects, HUD, and sound decisions. ### M1 — Establish the R5900 PS2 port layer

1. Add a dedicated HCU `port/ps2` manifest, prefix, declarations, and machine entry, in the shape Halo-64 uses for the N64: a force-included prefix for the environment the CE sources assume, a platform side that replaces XDK calls, and a game-side file compiled as a game unit ([N64 prefix](../submodules/halo-64/port/n64/include/halo_n64_prefix.h#L3), [platform split](../submodules/halo-64/port/n64/src/platform.h#L4), [game-side port](../submodules/halo-64/port/n64/game/n64_game.c#L3)). Build for little-endian MIPS ILP32, with 32-bit pointers/`long`, 16-bit `wchar_t`, and only required MSVC/XDK compatibility semantics. Define `HALO_PS2`. Leave `HALO_N64` and `HALO_LINUX` unset.
2. Add compile-time ABI assertions for pointer/`long`/`wchar_t`, tag references and blocks, datum headers, object records, and weapon/projectile records. Confirm layout under host ILP32 and R5900 compilers before adding larger source groups. Assert single precision only, 16-byte alignment of every DMA-visible record, and no `double` ([FPU](../submodules/halo-ps2/docs/01-ps2-architecture.md#L42), [DMA quantum](../submodules/halo-ps2/docs/01-ps2-architecture.md#L75)).
3. Compile in narrow layers: C runtime/math and memory; tag/datum services; object/physics/collision; player/game tick; then weapons/projectiles/damage. For each layer record compiler flags, source hashes, unresolved symbols, and live relocations. The existing combat probe is useful closure evidence only; it explicitly uses N64 capacity macros as compile placeholders and is not a PS2 runtime ([probe disclaimer](../tools/probe_combat_source.py#L1), [probe flags](../tools/probe_combat_source.py#L138)).
4. Enter the CE shell the way Halo-64 does: compile `shell_xbox.c` with `main` renamed, start the PS2 machine services, then call that shell ([shell rename](../submodules/halo-64/port/n64/port.json#L56), [call](../submodules/halo-64/port/n64/src/n64_main.c#L451)). Start the local session from the game-side port file on `_game_connection_local`, for the parent's one-to-four local players ([local setup](../submodules/halo-64/port/n64/game/n64_game.c#L195), [local-connection notes](../submodules/halo-64/port/n64/NOTES.md#L8)). Leave online/System Link transport and the OpenCE desktop UI out of the link. Supply host/session state only where the CE local-game path reads it.
5. Supply explicit declarations for rendering/snapshot submission, pad, time, files, profiling, logging, and sound requests. Simulation services must be implemented. Halo-64's render notes are the check for an apparently empty callback: the simulation does not read pixels, but `render.frame_index`, the per-window camera, and `interface_draw_screen` still advance particle lifetime and HUD timers ([render seam](../submodules/halo-64/port/n64/NOTES.md#L33)). A callback may be empty only after the M0 call-graph audit shows it cannot change simulation state.

**Exit gate:** a minimal R5900 ELF links and boots the CE-owned local-game lifecycle without Direct3D, DirectSound, Bink, or online-netcode relocations. Its allocated ELF bytes are reported against the 2,097,152-byte `elf_static` region. A link that boots and still has no region for its static data does not pass.

### M2 — Fixed memory and a runtime tag image

1. Inventory every allocation path used by the selected source closure, including `match_malloc`, `game_state_malloc`, datum arrays, memory pools, temporary tags, and map transitions. Follow Halo-64's replacement of the Xbox physical memory map and disk cache: the port owns the base addresses, and the map image is produced ahead of time ([memory map](../submodules/halo-64/port/n64/game/n64_game.c#L734), [cache replacement](../submodules/halo-64/port/n64/game/n64_game.c#L11)). Route those bases through the parent boot allocation's fixed sub-arenas, and preserve CE datum handles/generation behavior ([datum allocation](../submodules/halo-ce-universal/source/memory/data.c#L225), [pool creation](../submodules/halo-ce-universal/source/memory/memory_pool.c#L124)).
2. Treat the version-2 capacities as strict budgets, not proof of fit: 33,554,432 bytes total, `elf_static` 2,097,152, `resident_gameplay` 6,815,744, `current_bsp` 6,291,456, `texture_cache` 4,194,304, `dynamic_simulation` 2,621,440, `dma_commands` 1,179,648, `streaming` 1,572,864, `checkpoint` and `audio` 524,288 each, `frame_scratch` 393,216, and the 5,767,168-byte reserve unspent absent measured approval ([budget](../config/memory-budget.json#L4)). Resolve the current world-arena overrun and the stream-viewer ELF overrun before assigning CE tag or collision allocations ([arena findings](../docs/memory.md#L45), [ELF findings](../docs/memory.md#L27)). Account GS eDRAM, IOP RAM, and SPU2 RAM separately from these EE regions.
3. Extend the offline converter to emit a versioned, checksummed, little-endian CE tag image with bounded tag/reference tables and validated relocation data. Keep render geometry/bitmap payloads in PS2 packs. Keep collision BSP accessible to CE collision while accounting its bytes with the map/BSP region.
4. Load the runtime tag image through HP2 sections using existing bounds, alignment, codec, and CRC validation ([HP2 section layout](../submodules/halo-ps2/engine/src/stream/hp2.h#L25), [HP2 validation](../submodules/halo-ps2/engine/src/stream/hp2.c#L18)). Map load must fail closed on malformed references, overflow, unsupported fields, or budget exhaustion.
5. Add deterministic converter fixtures for a small synthetic tag set and the supplied Blood Gulch map. Verify byte-identical outputs, valid cross-tag references, correct endianness/layout, and that render vertices/bitmap pixels are not duplicated into the gameplay image.

**Exit gate:** map load/unload returns to a stable arena baseline; no steady-state heap allocation; measured high-water fits each assigned EE region and preserves the reserve; GS, IOP, and SPU2 bytes are reported in their own stores.

### M5 — Integrate AI, scripts, effects, HUD, local modes, and sound decisions

1. Expand the source closure to full AI/pathfinding, HaloScript runtime, scenarios, devices, and cutscenes. Halo-64's manifest drops `source/ai/`, `source/hs/`, `source/sound/`, and `source/cutscene/` to fit the N64 ([excluded directories](../submodules/halo-64/port/n64/port.json#L11)); those directories stay in the PS2 closure. Keep actor decisions and scripts active; `actors_update` performs perception, decisions, movement, and combat, while `hs_update` runs the script runtime ([actor update](../submodules/halo-ce-universal/source/ai/actors.c#L4200), [script update](../submodules/halo-ce-universal/source/hs/hs.c#L13544)).
2. Retain effects simulation and tag logic; submit only their render representation to PS2. Effect and particle records stay inside `dynamic_simulation`. Their sprites stay inside the GS texture window and a bounded sprite count. Keep CE HUD decisions for shields, ammo, motion sensor, and messages, and translate draw calls into quads and glyphs that fit the 4 MiB GS store beside the framebuffers ([GS VRAM](../submodules/halo-ps2/docs/01-ps2-architecture.md#L133)).
3. Keep sound choice and priority in CE. Replace DirectSound with parent sound requests containing event/tag identity, owner, position, and playback parameters. Those requests stage inside the 524,288-byte `audio` region. SPU2 later owns voice allocation, ADPCM upload, and mixing, within 48 voices and 2 MiB of sound RAM ([SPU2](../submodules/halo-ps2/docs/01-ps2-architecture.md#L155)). IOP transfer buffers stay inside the IOP's 2 MiB. Sound delivery does not feed results back into simulation ([sound-to-platform seam](../submodules/halo-ce-universal/source/sound/sound_manager.c#L1279)).
4. Preserve local Slayer/CTF/Oddball/King/Race and other stock local modes, split-screen player state, and campaign script/encounter support. Omit network transport, Bink, and desktop presentation only; do not stub game rules or campaign systems.
5. Add representative multiplayer and campaign maps as resource/behavior fixtures. Measure AI, script, effects, tag, and actor pool high-water on both dense combat and scripted/cinematic scenes, including the overlap of resident tags, the current BSP, dynamic simulation, streaming, and audio staging. A map whose measured peak exceeds its regions is rejected.

**Exit gate:** gameplay logic remains CE-owned for the full planned local multiplayer and campaign features, with PS2 rendering and audio backends consuming bounded requests only, and each measured pool inside its assigned EE, GS, IOP, or SPU2 store.

## 4. Interfaces, tests, and failure policy

The parent/HCU boundary follows Halo-64's split between a machine platform layer and a game-side port file ([platform split](../submodules/halo-64/port/n64/src/platform.h#L4), [game-side port](../submodules/halo-64/port/n64/game/n64_game.c#L3)). The PS2 façade has these contracts:

- Startup, shutdown, and map load/unload operate on caller-owned fixed arenas and return explicit errors. No source path falls back to heap allocation. A request that would pass an EE region, the GS texture window, IOP RAM, or SPU2 RAM fails closed.
- Each simulation call consumes tick-indexed commands for local player slots and invokes one CE tick. CE datum handles are authoritative; no parent-side object identity is invented.
- Snapshot production is read-only and bounded. It carries the render data needed by GS/VU1, HUD/effect draw requests, and first-person presentation; render code cannot call back into gameplay state mutation.
- Sound requests are one-way presentation events to SPU2. They may be dropped/culled by the audio backend under bounded-resource pressure but cannot alter gameplay outcomes.
- Platform-only omissions are classified by call site. Missing tag, collision, object, AI, script, or gameplay services are fatal to map/game startup rather than silently stubbed.

Required verification includes ABI/layout tests; converter corruption/bounds/CRC tests; allocator exhaustion and map reload tests; CE-source host fixtures; all M13 actor/vehicle/object scenarios; source-state hashes across render schedules; R5900 link and size reports; PCSX2 interpreter/recompiler parity; and eventual physical-PS2 measurement under the parent M23 gate. The existing parent build links bespoke gameplay modules today ([play target](../tools/ee-world.mk#L43)), and `play_ee.c` currently imports them and performs runtime `malloc` ([imports](../src/game/play_ee.c#L1), [allocation](../src/game/play_ee.c#L423)); both are explicit migration targets, not patterns for the final architecture.

Failure policy: preserve the last known-good branch and HCU pin; keep the parent comparison path until its replacement passes the same fixture; treat a missing simulation symbol as a closure failure. Halo-64's stub generator fills omitted AI, sound, networking, and renderer calls with zero-return stand-ins ([stub policy](../submodules/halo-64/tools/n64_stubs.py#L6)); the PS2 closure does not. An overrun of an EE region, the GS texture window, IOP RAM, or SPU2 RAM fails the map or the milestone. It does not spend the 5.5 MiB reserve, allocate from the heap, or corrupt adjacent records. Document any behavior divergence as a port-specific exception with a source citation and regression test.
