## What was being implemented when work paused

The main unresolved C1.4 issue is connecting the HCP profile data to actual live consumers while respecting storage and renderer ownership. The existing HCP currently validates and provides chunks, but the normal map service mounts the legacy HP2 CTAG/CRNG/CBIX source. Merely registering a profile view does not publish its normalized CE tag indices, CBSP payloads, resource ranges, or bitmap bindings into the runtime namespace. A complete HCP mounting path is being added in bounded, source-pinned pieces.

### Existing frame and bitmap path

- `src/stream/hcu_bitmap_dispatch.[ch]` implements a real native path from CE `interface_draw_bitmap` capture through queue consumption, HCP bitmap/TEXS reads and hash checks, shared `tc_t` acquisition, GS upload, and quad emission. It holds backing-store and cache leases until an explicit paired GPU completion callback.
- `src/stream/hcu_bitmap_frame.[ch]` owns the per-frame queue/dispatcher/profile/bindings/generation. It starts once per frame, sets per-player views, and requires a fence query that confirms both chains completed before releasing leases. The unit fixture tests do not simulate a real GS fence.
- The HCU-side PS2 frame callback hooks and request queue view setter are in `submodules/halo-ce-universal/port/ps2/`. They can call the actual CE HUD producer. A real producer descriptor was added to the real `source/interface/interface.c` translation unit so a generated stub cannot claim readiness.
- The actual HCU HUD body is linked from `source/interface/interface.c`. `ui_widget.c` is excluded by `port.json`, so there is no real widget producer; the path must fail closed for widgets and cannot claim pregame widget support.
- Parent renderer observations show two private geometry chains (32,768 QW each) and two upload chains (4,096 QW each), together using the full 1,179,648-byte DMA allocation. `bsp_render_kick` waits for upload completion and launches geometry; `bsp_render_poll` records VIF1 and GS FINISH observations. `bsp_render_wait_gpu` alone checks only the GS-seen condition and must not be treated as the paired fence.
- No snapshot DMA allocation can be overlaid on those chains. The target needs a safe suballocation/binding into the renderer's actual idle resources or a design change backed by the C2 memory budget. Do not claim the new frame-owner adapter is wired into production just because the standalone adapter compiles.

### HCP profile mounting and metadata

- `src/stream/hcu_profile_mount.[ch]` is being implemented by the native-corpus agent. Its API is currently drafted and reported stable: read-only `prepare`, then `load` only after the previous map is unpublished, and `unload` that unpublishes CE before caller memory can be released.
- The mount consumes `hcu_profile_cbsp_binding` (source extent, media chunk ID, source-map SHA, chunk SHA) and `hcu_profile_resource_range` (output datum, source offset, size). It validates the CE root chunk, target capacity, CTAG/relocations, exact CBSP catalog extents, and immutable table/profile/catalog snapshots. It installs actual PS2 cache CTAG/CBSP visitors and checks resource reads against an explicit whitelist. UI may be validated against its real source map; multi-source survival is not qualified by faking a single source-map length.
- `src/stream/hcu_profile_metadata.[ch]`, `tools/build_hcu_runtime_metadata.py`, and `tests/test_hcu_profile_metadata.py` have just been added by the metadata agent. They define/emit HCM1 little-endian runtime tables and decode them into caller-owned storage after checking exact length, expected profile ID, and an externally supplied full-file SHA-256. The reported initial UI metadata is 21,616 bytes, with 368 bitmap bindings, one CBSP binding, and 75 resource ranges; its first reported digest begins `0c978cf9`. These are early agent results, to be rechecked after the agent finishes and the files stop changing.
- The metadata parser/generator is a small-input and identity mechanism. It is not a runtime consumer proof, CE mount proof, target fit result, or permission to set `runtime_admitted` true.
- Root had not yet modified `src/stream/hcu_map_service.[ch]` or `src/stream/hcu_main.c` when the handoff was requested. These are the next integration points: register the caller-owned metadata/package/profile runtime, preflight it without touching the live owner, mount HCP CE/CBSP only after CE unpublishes the prior owner, retain the HCP reader and metadata tables through all readers, and tear them down only after frame/GPU leases drain. Existing legacy UI behavior and failure safety need regression coverage.
