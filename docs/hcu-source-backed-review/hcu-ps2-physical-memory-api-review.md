# M0 PS2 physical-memory provider API review

**Disposition scope:** `physical_memory_allocate`, `physical_memory_get_game_state_base_address`, `physical_memory_get_tag_cache_base_address`, `physical_memory_get_tag_cache_size`, `physical_memory_get_structure_bsp_cache_base_address`, `physical_memory_get_structure_bsp_cache_size`, and `physical_memory_get_sound_cache_base_address`.

The authoritative implementations are the PS2 provider in [`ps2_memory.c`](../submodules/halo-ce-universal/port/ps2/src/ps2_memory.c#L113) and its API declarations in `source/cache/physical_memory_map.h`. `physical_memory_allocate` is an idempotent commit of caller-configured spans into the provider's physical table; it does not malloc or silently claim the parent arena. In standalone builds it may select the explicitly declared bootstrap arrays; `HALO_PS2_NO_BOOTSTRAP_MEMORY` uses only caller-owned spans. The getter APIs expose committed base addresses and capacities to CE cache/tag-validation callers, with the tag-cache size retaining the documented 2 MiB bootstrap limit only before free and only in a bootstrap build. A missing optional BSP span remains null/zero until the parent binds it.

The contract is exercised in both bootstrap and `HALO_PS2_NO_BOOTSTRAP_MEMORY` modes by [`test_ps2_memory_binder_tracks_caller_owned_capacity`](../tests/test_hcu_ps2_closure.py#L57), which compiles the real HCU provider and parent binder with [`hcu_ps2_memory_main.c`](../tests/hcu_ps2_memory_main.c). The fixture checks idempotent allocation, bound base/size reads, bootstrap behavior, release behavior, and the parent v2 arena binding. The current R5900 closure compiles and links the same provider, and the current PCSX2 optical profile passes CE startup readiness. These checks establish API behavior and integration but do not independently prove that every retail-map working set fits a region; that remains M2/M6.

`physical_memory_verify` is a state adapter rather than an implementation of Xbox page-protection queries. The original CE body walks every 4 KiB tag-cache page and the game-state verification span and requires `XQueryMemoryProtect(...) == PAGE_READWRITE` (`source/cache/physical_memory_map.c:96-118`). PS2 has no Xbox virtual-memory protection contract for these caller-owned EE spans; `ps2_memory.c` therefore does not emulate that query. In the accepted combined entry, the parent binds every required span, calls `physical_memory_allocate`, and requires `physical_memory_ready()` to succeed before entering `halo_shell_main` (`src/stream/hcu_main.c:95-134`). CE calls `shell_platform_verify` at the end of shell initialization (`source/shell/shell.c:73`), so it cannot precede that gate on this path. `physical_memory_ready` checks allocation state and minimum game-state, tag, texture, sound, malloc, and validator-claims capacities. This is a documented platform-equivalent startup validation, not a runtime physical-memory protection test.

The remaining `physical_memory_get_texture_cache_base_address` and size APIs have no rooted external in this closure; do not add ledger rows for unrooted symbols. Retail map capacity, BSP extent capacity, and allocation-failure/unload lifecycle remain M2/M6 concerns, not approved by these API dispositions.

The same source/test pass also reviews `GlobalAlloc` and `LocalFree`, which are not physical-map APIs but are owned by this provider. CE `system_malloc`/`system_calloc` and `system_free` call them directly (`source/cseries/cseries_windows.c:172-190`). PS2 allocations are aligned, monotonic, bounded to the prebound arena, and fail closed on exhaustion; `GMEM_ZEROINIT` is honored. `LocalFree` intentionally cannot reclaim this monotonic arena but returns Win32's null success result; allocations made before arena binding are sent to the PS2SDK allocator and freed by the CRT wrapper. `tests/hcu_ps2_memory_main.c` now exercises these exact GlobalAlloc/LocalFree behaviors along with bootstrap and external-only provider configurations. `GlobalReAlloc` remains pending: its current implementation copies the requested new size without knowing the old allocation size, so growth can overread; do not approve or rely on it until allocation metadata/copy bounds are fixed or every live caller is proven not to grow.
