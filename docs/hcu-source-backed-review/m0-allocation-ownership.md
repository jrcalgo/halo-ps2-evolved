The v2 arena capacities total 24,117,248 bytes and are carved by the halo-ps2 implementation in [`engine/src/core/mem.c:62-95`](../../submodules/halo-ps2/engine/src/core/mem.c). `hcu_main.c` charges the ELF NOBITS span to `resident_gameplay`, allocates the remaining arena backing, and calls the parent binder. It avoids charging `.bss` twice in the boot allocation's logical v2 sum. The current link-only lower-bound headroom before the reserve is 30,577 bytes. `hcu_main.c` now logs and checks every arena's physical base/capacity/used/high-water against the actual boot backing and pairwise overlaps. It also queries `GetThreadId`/`ReferThreadStatus`, logs the actual current-thread stack interval, and rejects a stack outside the high kernel reservation. Here `arena.used/high` describe the parent arena allocator's own cursor; they do not include allocations made directly by CE providers after a span is bound. The boot harness requires nine complete, unique, non-overlapping arena records and a valid stack/kernel interval when physical placement is requested. These checks are target-linked but not yet observed in the guest: actual malloc pointer/metadata and current-image kernel bounds remain unverified. The M0 gate reports nine checks passed and zero errors; the separate guest-placement gate remains open.

The link probe records the single PT_LOAD interval, exact `.bss`/NOBITS bounds, `_end`, `_heap_size`, `_stack`, and `_stack_size`. The pinned startup linkfile sets `_heap_size` and `_stack` to `-1` and `_stack_size` to 128 KiB; the ELF alone therefore cannot reveal runtime heap/stack bounds. `docs/memory.md:122-139` supplies a prior emulator-measured kernel split (low 1 MiB plus high 512 KiB, with the 5.5 MiB reserve immediately below the high interval), but the new entry obtains the actual current-thread stack through `ReferThreadStatus` and asserts it lies in that high reservation. ## Engine ownership boundary observed in this image

- `halo-ce-universal` owns the compiled CE simulation/gameplay closure, object and game-state records, tag validation/cache semantics, input-frame semantics, and HCU PS2 memory-provider contracts. Its `port/ps2` code is the platform contract implementation, not the GS renderer.
- `halo-ps2` and the parent own the EE boot/memory allocator, pad/video/timer services, FileXio/HP2/streaming bridges, GS/VU/DMA renderer, and the PS2-specific render/world packs. The HCU entry and binder are parent glue that binds CE providers to those arenas.
- The current parent link also retains legacy `sim/objects.c`, `sim/skeleton.c`, and `sim/fpview.c` units. Per `plans/5.hcu-remake.md`, their intended future role is reading a post-tick CE snapshot; they must not become a competing object, animation, or first-person simulation owner. That snapshot/render boundary is not yet proven by this link.
- OPL is an unmodified, read-only reference submodule; OPL launch/device operation is not proven by this host-profile ELF.

## High-water evidence and gaps

The machine-readable `high_water_evidence` in [`hcu-ps2-memory-map.json`](../../config/hcu-ps2-memory-map.json) gives all twelve budget regions exactly one classification: link-measured `elf_static`; host-fixture-measured `streaming` and `frame_scratch`; reserved-and-unused `uncommitted_reserve`; and explicitly unknown production peaks for the remaining eight. The M0 gate now reports nine checks passed and zero errors. It rejects missing records, numeric peaks claimed for unknowns, out-of-capacity fixture values, and a consumed reserve. The exact current link audit assigns 2,066,232 allocated file-backed bytes to `elf_static`; older candidate totals in prior prose are superseded by the hash-bound audit.

Recorded values in this ledger are explicitly labeled as link-map byte count, fixed allocation capacity, actual retail-UI integration fixture peak, or unknown production peak. The retail UI test reaches 1,550,356 / 1,572,864 bytes in the map-mount path and 1,550,484 / 1,572,864 in the complete map-service path; it checks cleanup returns `used` to baseline. It does not measure full retail maps. HCU's bump compatibility allocator tracks `malloc_used` internally but has no published high-water accessor/log in the combined machine output. Texture/audio provider usage, parent DMA-chain peak under this entry, and physical EE allocator overhead are likewise unknown. The logical owner ledger is complete without promoting unknown peaks into measured values; those unknowns remain M1/M2 runtime acceptance gaps. M2 still needs full-map working-set and transaction evidence.

The essential M0 decision is now made without double counting: `game_state` includes the current object pool, while the HCU compatibility allocator is bound to `dynamic_simulation`; `ps2_memory.c:70-74` deliberately allows SDK heap use before provider allocation, so CRT/libc/PS2SDK bootstrap use must be accounted in the ELF/boot physical-placement ledger and must not be silently charged to the dynamic arena.
