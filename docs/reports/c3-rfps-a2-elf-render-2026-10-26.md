# C3 multi-view FPS audit: A2 ELF and renderer

## Scope and identity

Read-only analysis of the `baseline-v4` ELF identified in `build/c3/perf/object-sharing-ab-20261025-r1/baseline-v4/desktop-launch.json`:

- ELF: `build/c3/perf/object-sharing-ab-20261025-r1/baseline-v4/play/bloodgulch-realtime-timing.elf`
- SHA-256: `2f6b99a2c0fbc34df55b7fa0a8bcf4b9bce2050d3b2c92d04b11bbd42dad4d23` (matches manifest)
- Package: `23d41d49c5e755da415f068e6420745eca8d51a71474d40c7335cca834273aac`
- Relevant pinned source hashes match the manifest: `bsp_render.c` `d90b0cb8…2666`, `obj_render.c` `8c7299ab…48f5`, `hcu_main.c` `e903dee0…17ed2`.
- Build flags include `HCU_C3_OBJECT_PREPARE_CACHE=0`; optimized comparison's prepare cache is enabled. Other immutable tuple, package, source-pin, settings and pixel-parity checks are exact per `report.json`.

REA accepted and hashed the ELF, but its available Ghidra profile explicitly rejects this MIPS/EE variant (`architecture_unsupported`; machine-specific MIPS variants need a supported processor profile); Hopper likewise rejects MIPS. No REA function pseudocode, function evidence IDs, or runtime address correlation was produced. I used only the already installed EE `nm`/`objdump` to confirm ELF symbols and inspect emitted code; the disassembly is static evidence, not a timing profile. I did not execute the ELF on the host. REA target session was closed.

There is no stable optimization win in the paired results: FPS deltas are -0.027% at 2 views, +2.025% at 3, and -0.244% at 4. Four-view optimized build time is 23.891 ms and its view total 20.705 ms (baseline 25.620 / 21.718); callback is slightly worse (35.803 vs 35.280 ms), and present time differs by 2.25 ms (8.659 vs 6.409). Sample count is five, so these small shifts do not identify a cause. All pairs are pixel exact, and all runs report zero new drops. The 30 FPS target is not qualified at any split count.

The report indicates `visibility`, `clip`, `sky`, `objects/fx`, and `world` as CPU phases; in the 4-view row, clip/gather/group and sky each cost about 5.5–5.9 ms, objects/fx 7.0 ms, and visibility 1.5 ms. These are measured phase totals, not proof which individual function or operation consumes those cycles. The coarse clip phase includes `gather_clipped` and `group_clipped`; the sky phase is the configured sky callback. Current data does **not** show a positive BSP or video GPU wait. Present is a separate ~4–8 ms interval and includes `graph_wait_vsync`, but its exact wait-vs-swap split is unmeasured.

## Actionable experiments for the implementor

Prioritize changes that reduce repeat CPU work per view while preserving the same generated geometry and ordering. For each experiment compare split counts 1–4 under the same workload, report per-phase medians and tails (rather than sparse means alone), and require exact per-view RGB, canonical snapshot, queue semantics, and zero fence/pin/canary/overflow errors.

1. **Break down clipping and sky before replacing algorithms.** `bsp_render.c:1137–1146` times clip gathering plus grouping as one interval; `s_stats.clip_ms` at 1139–1142 isolates only `gather_clipped`, so expose both that and `group_clipped(0)` as separate existing internal costs and add work counters (visible batches/polygons/vertices in, clipped polygons/vertices out). At four views the combined interval is 5.493 ms. For sky, phase boundaries are `bsp_render.c:1169–1180`; add sky polygon/triangle/vertex counts per view to distinguish expensive projection/clipping from DMA-chain packet writes. If clip-pack math dominates, optimize the existing clip/pack path and retain identical vertex/order output. If gather dominates, first add conservative bounds rejection that is demonstrably equivalent; do not drop visibility or clipping checks.
2. **Reduce per-object repeated queries and LOD table scans.** `obj_render.c:239–258` loops all objects in every view, transforms a center, computes distance/sphere rejection, estimates pixel diameter and resolves a LOD. `pick_lod` at 131–147 walks per-region LOD part ranges to find available geometry. `light_at` does a cluster lookup at 203–215 for every visible object. Build a compact immutable per-model/per-permutation LOD availability table at world preparation time, then resolve the same `pick_lod` answer by lookup; cache only data keyed by model generation and permutation/region identity, and invalidate on world change. Separately measure/candidate-cache `bsp_find_cluster` only where the quantized cell is proven equivalent to its existing lookup. Static EE `nm` locates `obj_render_pass` at `0x147f90` and `draw_model` at `0x1476bc`; disassembly shows `obj_render_pass` reserves an 8,624-byte stack frame, which is a static compiler/codegen observation—not evidence that stack traffic is a runtime bottleneck. The measured 4-view objects/fx phase is 6.976 ms and falls to 6.156 ms in the optimized run without a stable whole-frame FPS gain.
3. **Tune object budgets from measured demand, preserving fairness.** `obj_render.c:224` selects `max_batches`; `draw_model` skips a whole part if its batches exceed remaining budget (`169–170`) and emits model batches while checking chain space (`100–128`). Existing quarter-frame LOD policy is active. Do not assume an LOD change guarantees 30 FPS or lower current LOD blindly. Record per-view visible/culled objects, chosen LOD, requested/emitted/skipped batches and chain refusals; then sweep a bounded batch budget or LOD bias as a controlled quality/perf test, checking that all views retain UI/foreground models and no view starves.
4. **Investigate material and texture work only after counts.** `bsp_render.c:1150–1165` performs material counting/grouping and qsort each view; measured sort is only 0.23–0.33 ms at 2–4 views, below clip/sky/object totals. `bsp_render.c:1191–1195` resolves a base texture for each used material, and `obj_render.c:170–175` resolves object bindings/textures per part. Existing residency (`resident_tex0`) may avoid upload but not callback/key lookup. Count callback calls, cache hits/misses, uploads and bytes per view before considering a view-local resolved-binding memo keyed to the pinned world/material generation. This is a hypothesis about avoidable CPU lookup work, not a measured texture bottleneck. Preserve texture pin lifetime until the exact upload kick's VIF1 and GS fence has been observed.
5. **Separate present pacing from CPU work; keep fence semantics.** `video.c:94–99` calls `graph_wait_vsync()` before changing framebuffer; `hcu_main.c:2691–2707` orders prior-kick wait, present, then frame-end submission. The measured explicit `bsp-wait` and `video-wait` fields are 0, while `present` varies 4.076–8.310 ms. Add a non-invasive sub-timer around `graph_wait_vsync` versus framebuffer select, and report completed-kick/fence state at the same sample. Do not remove or bypass vsync or the prior-kick check as a blind speedup: that can change tearing/pacing and can clear GS FINISH before source retirement. Keep the two-buffer chain/upload reset checks (`bsp_render.c:963–1013`) and VIF1+GS retirement (`1404–1468`) intact.
6. **Consider viewport-scaled work only with a pixel contract.** Every active view presently executes visibility, clipping, sky, world and object passes (`hcu_main.c:2642–2676`); rectangle size changes the clip matrix (`bsp_render.c:1099–1108`) but not the pipeline. Existing sub-pixel clutter rejection uses a 3-pixel projected diameter in `obj_render.c:250–252`; further threshold or view-size scaling is a quality choice and needs dedicated image acceptance, not a correctness-preserving optimization claim. A pixel-preserving candidate is to precompute view-independent immutable world/material/LOD data once at world bind, then retain exact per-view camera-dependent clipping and output.

## Suggested next profiling patch (not implemented)

Add narrowly scoped counters/timers to the existing opt-in C3 timing build: split `gather_clipped` and `group_clipped`, count input/output clip vertices and sky geometry, split present wait from framebuffer programming, and include per-view object visible/culled/LOD/batch/texture callback/cache statistics. Use an 8+ sample repeated warm window for the 2-, 3- and 4-view rows. This should identify whether the next code change belongs in clipper, sky emission, object traversal or pacing. Keep diagnostic printing sparse because serial output distorts time; preserve asynchronous DMA and all source pins/fences.

## Evidence ledger and limits

- **Runtime measurements (observed):** `build/c3/perf/object-sharing-ab-20261025-r1/report.json` and `report.md`; 2–4 view baseline and paired optimized values above. They establish phase totals in the measured workload only.
- **Binary identity (observed):** manifest and `sha256sum` match the ELF digest listed above. REA `open_binary` accepted ELF/MIPS and reported that digest. REA `binary_session` says selected Ghidra and Hopper do not support this MIPS target; therefore no function-level REA result or address-based runtime trace is available.
- **Static symbol/disassembly (observed, installed EE binutils):** `nm -C` resolves `obj_render_pass=0x147f90`, `draw_model=0x1476bc`, `vis_run=0x1693c4`, `cmp_key=0x140a0c`, `group_clipped=0x140af8`, `emit_clipped=0x141264`, `emit_view=0x144008`, `bsp_render_kick=0x143304`, `resident_tex0=0x143c4c`, and `video_present=0x1409a8`. The disassembly of `obj_render_pass` shows its prologue reserves 8,624 bytes. This does not rank runtime costs.
- **Source locations:** `bsp_render.c` lines 1099–1278, 1404–1476; `obj_render.c` lines 100–147, 149–200, 203–215, 217–283; `video.c` lines 89–105; `hcu_main.c` lines 2580–2587, 2642–2707, 2728–2738.
- **Unknown:** no EE hardware or guest profiling run was performed in this audit. Emulator phase values may not rank the same way on hardware. The isolated time inside `graph_wait_vsync`, per-function cycle costs, polygon/object counts, clip output and texture callback hit rates are not present in the retained report. `video.c` is not listed among this case's source pins, so its source locations are a repository cross-check, not a separately pinned source identity.
- **Safety boundary:** no builds, guest execution, active-process interaction or source edits were performed. REA's opened ELF was closed.
