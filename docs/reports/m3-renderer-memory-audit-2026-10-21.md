# M3 parent renderer memory and display ownership audit

Date: 2026-10-21  
Scope: report-only review of M3 Step 13 / first visible-frame integration. This audit covers GS eDRAM versus EE RAM, DMA/VIF command storage, allocation/lifecycle ownership, current snapshot and boot arenas, and Halo-64 as a bounded comparison. It does not change code or approve an arena resize.

## Executive finding

The PS2 renderer has a real display path in `halo-ps2`: `video_init()` allocates the two color buffers and Z buffer in GS VRAM, configures the CRTC, and `video_present()` waits for vblank and switches the displayed GS framebuffer ([`video.c:9-40,94-105`](../../submodules/halo-ps2/engine/src/platform/video.c#L9)). This VRAM is the PS2 GS's separate 4 MiB eDRAM store; those color/Z allocations are not allocations from the 32 MiB EE RAM budget. At the current 512×448 mode, the nominal pixel payload is 917,504 bytes for two 16-bit color buffers plus 917,504 bytes for one 32-bit Z allocation, 1,835,008 bytes total before GS page/alignment and allocator effects. The renderer reports the remaining texture window separately ([`video.c:28-45`](../../submodules/halo-ps2/engine/src/platform/video.c#L28), [`video.h:9-18,34-37`](../../submodules/halo-ps2/engine/src/platform/video.h#L9)).

That does **not** mean renderer integration is free in EE RAM. DMA chains, staging/upload chains, VIF payloads, packet metadata, world visibility/material data, and source texture/lightmap bytes are EE-readable inputs and need explicit EE owners. Current integration has a concrete aliasing hazard: HCU binds its 4,128-byte matrix-VIF payload to the beginning of the complete `dma_commands` arena, without carving that interval from the arena; the standalone renderer separately allocates two 512 KiB geometry chains and two 64 KiB upload chains with `memalign()` ([`hcu_main.c:245-266`](../../src/stream/hcu_main.c#L245), [`bsp_render.c:25-28,104-111,152-171`](../../submodules/halo-ps2/engine/src/render/bsp_render.c#L25)). The four renderer chains total exactly 1,179,648 bytes—the full configured `dma_commands` capacity—before the HCU matrix payload or any packet2 objects. The capacities are documented in [`core/mem.c:62-70`](../../submodules/halo-ps2/engine/src/core/mem.c#L62) and [`memory-budget.json:14-19`](../../config/memory-budget.json#L14).

Consequently, Step 13 can validly prove immutable CPU snapshots and correctly aligned packet construction, but **must not claim GS/VIF submission or rendered output** until a single EE-side allocation/lifetime design reserves disjoint storage for the snapshot VIF batch, full geometry/upload chains, packet2 control blocks, texture upload source data, and any overlays. The renderer also needs one owner-controlled init/teardown and a DMA/GS fence before reusing a chain or freeing/releasing its source data. Existing parent renderer calls and allocation helpers are not wired into `hcu_main.c`; no current M2 UI marker implies they ran.

## Store boundary: EE RAM, GS eDRAM, DMA, and source data

| Resource | Physical/semantic owner | Current evidence and consequence |
|---|---|---|
| Color framebuffers, Z buffer, GS texture pages | 4 MiB GS eDRAM (VRAM) | `graph_vram_allocate()` in `video_init()` allocates both framebuffers, depth, and a texture page; `graph_set_framebuffer_filtered()` sets the scanout buffer. These bytes do not consume `resident_gameplay`, `current_bsp`, or the 5.5 MiB EE reserve. Capacity still needs measured page-rounded allocation results and texture-cache high-water. |
| GS register state / display mode | GS/CRTC state, controlled by PS2 machine layer | Current engine selects interlaced NTSC, 512×448 field output; `video_present()` blocks on vblank before selecting the buffer and flipping. This call is essential to visible pixels even after geometry reaches GS. |
| VIF1 and GIF chain bytes | EE RAM readable by DMA (with required address/cache semantics) | Static BSP renderer currently allocates uncached buffers via `memalign(64, bytes)` then sets the KSEG1 alias and uses `dma_channel_send_chain_ucab()` / `dma_channel_send_chain()`; this is not GS VRAM. It must be carved from `dma_commands`, given a named permanent renderer owner, or the budget must be revised from measured usage without overlap. |
| CE-to-parent snapshot banks | EE `frame_scratch` | The HCU snapshot records are fixed-width/pointer-free and double-buffered. Header defines 2,048 object records and 64 first-person matrices; one bank is 134,488 bytes and aligned bank storage is 134,496 bytes, so two banks consume 268,992 bytes of the 393,216-byte arena, leaving 124,224 bytes for the current section-scratch tail. This matches the boot marker and the plan’s current UI-only evidence. |
| HCU compact VIF matrix payload | EE `dma_commands`, current base address | `hcu_render_snapshot_bind()` stores `dma_commands` itself as `s_dma_words`, and requires only 4,128 bytes. The packer writes a VIF UNPACK header and up to 64 4×4 matrices, but exposes no submission function; it is not a complete VIF1/GIF chain and no DMA can be inferred from `snapshot-dma qwords=5`. |
| Render source textures/lightmaps, BSP data, visibility and material arrays | EE RAM plus destination texture residency in GS | `bsp_render_set_world()` allocates visibility/material structures in its passed arena; texture callback data is read on EE and uploaded into GS. The source image lifetime must span cache misses/reuploads; a GS texture residency record does not make the source image or map-independent metadata resident in eDRAM. |
| Packet2 state and startup allocations | PS2SDK/EE heap unless explicitly overridden | `packet2_create()` allocates packet objects in BSP initialization/draw paths. `memalign()` for chain arrays is a separate EE allocation call path. Neither allocation is currently visibly carved through the parent `arena_t` API. Must inspect actual libc/newlib wrapping and memory profile at integration; do not count them both in an arena and heap. |

### Arithmetic and collision proof

The memory-budget file assigns exactly 1,179,648 bytes to `dma_commands`. Renderer constants are `CHAIN_QW=32768` and `UPLOAD_QW=4096`, two buffers each, at 16 bytes/qword ([`bsp_render.c:25-28,158-161`](../../submodules/halo-ps2/engine/src/render/bsp_render.c#L25)). Thus:

```text
2 * 32768 * 16 = 1,048,576 bytes (geometry chains)
2 *  4096 * 16 =   131,072 bytes (texture/lightmap upload chains)
renderer chain total = 1,179,648 bytes (entire dma_commands region)
HCU matrix VIF payload = 4,128 additional bytes if separately reserved
```

This is an exact capacity collision, not proof that the renderer currently overruns the arena: current renderer allocations use a separate `memalign()` path rather than the HCU bound pointer. It proves the existing ledger cannot honestly assign those allocations to the same DMA region until the allocator path is unified and one of the allocations is redesigned, reduced from measurements, or assigned to a distinct valid EE region without violating that region’s existing ownership. Since the DMA chain payload is uncached after alias conversion, a disjoint carve must preserve the library’s expected alignment, physical address, uncached alias and D-cache rules. Merely adding 4,128 bytes to the nominal arena or moving the snapshot payload pointer is not enough; `packet2_t` descriptors and temporary packets also need an allocation policy.

Likewise, GS eDRAM capacity is not a substitute for EE command buffers. GS cannot execute arbitrary VIF/DMA command memory or service CE’s ordinary pointers to cache/tag/BSP data. Conversely, framebuffer/Z buffers should not be charged against EE arena totals. Keep these storage ledgers separate and record each transfer’s source EE extent, destination GS block/page, DMA completion fence, and cache-coherency operation.

## Current code and integration gaps

1. **No production display initialization/submission is called from HCU boot.** `hcu_main.c` binds the snapshot and map loader and then enters `halo_shell_main()` ([`hcu_main.c:245-296`](../../src/stream/hcu_main.c#L245)). It does not invoke `video_init()`, `bsp_render_init()`, `bsp_render_set_world()`, `bsp_render_build()`, `bsp_render_kick()`, or `video_present()`. The PS2 renderer code is available but not connected to the HCU loop; the direct-ELF UI stage consequently cannot be interpreted as visual rendering.
2. **The snapshot cap is a fixed policy, not a 1–4-view proof.** One bank has 2,048 object entries and one node-palette slice. The top-level snapshot has only one camera/local-player slot; there is no array of 4 views or per-view offsets. Thus Step 13’s explicit one-through-four-view requirement is not met by merely exercising the existing single-view banks. The camera record has viewport/window bounds, but commit validation currently verifies finite pose/FOV/near/far only; it does not reject zero, inverted, or out-of-display viewport bounds ([`hcu_render_snapshot.c:112-151`](../../src/stream/hcu_render_snapshot.c#L112)).
3. **Object identity needs generation semantics.** Snapshot object entries copy datum index, definition index, type, flags, and transform ([`halo_ps2_render_snapshot.h:30-36`](../../submodules/halo-ce-universal/port/ps2/include/halo_ps2_render_snapshot.h#L30)). Datum index alone may be reused after object deletion; the current entry does not carry a generation. A parent consumer holding the entry beyond that published bank’s lifetime could bind old transform/palette data to a new object. Either consume synchronously while the bank is protected, or add a CE-derived generation/token validated against the same published datum lifetime; do not manufacture a generation in the parent.
4. **Two-publication lifetime conflicts with current static frame pipeline unless fenced.** Header says readers finish before two later publications ([`halo_ps2_render_snapshot.h:53-54`](../../submodules/halo-ce-universal/port/ps2/include/halo_ps2_render_snapshot.h#L53)). That is a CPU-side protocol, not automatically a GS/DMA fence. If DMA reads the bank or VIF payload after the call returns, the producer must not overwrite it until VIF1 completion; and any texture/lightmap source slices must remain valid until the corresponding GIF transfer completes. The renderer currently explicitly overlaps frame build with prior GS drawing and uses ping-pong chain/upload banks ([`bsp_render.h:1-4`](../../submodules/halo-ps2/engine/src/render/bsp_render.h#L1), [`main.c:256-274`](../../submodules/halo-ps2/engine/src/main.c#L256)). A correct adapter should bind snapshot bank sequence to a submitted chain generation and retire it only after VIF/GIF and GS completion appropriate to that data.
5. **Existing renderer lifetime does not match the HCU one-boot-arena API yet.** Standalone `main.c` calls one `malloc()` for the map/level arena ([`main.c:135-146`](../../submodules/halo-ps2/engine/src/main.c#L135)); renderer initialization then calls `memalign()` for two geometry and two upload chains, and `packet2_create()` for program/state chains ([`bsp_render.c:85-99,104-111,152-171`](../../submodules/halo-ps2/engine/src/render/bsp_render.c#L85)). HCU boot instead creates one bounded v2 backing allocation and wrapper-binds CE malloc to `dynamic_simulation`; the current code does not give `bsp_render_init()` an arena parameter ([`core/mem.h:1-4,15-27`](../../submodules/halo-ps2/engine/src/core/mem.h#L1), [`hcu_main.c:150-185`](../../src/stream/hcu_main.c#L150)). Before integrating renderer, decide whether static chain buffers are a named permanent suballocation from `dma_commands` (preferred accounting model), and define where `packet2_t`/startup descriptors go. Ensure arena rebinding/unbinding cannot invalidate live DMA or renderer globals.
6. **Map teardown must include renderer/source teardown.** `bsp_render_set_world()` stores a BSP pointer and texture callbacks; its render buffers and texture-cache state are coupled to the loaded map ([`bsp_render.h:70-80`](../../submodules/halo-ps2/engine/src/render/bsp_render.h#L70)). Before M2 releases `current_bsp`, map/texture source arenas, or scratch, caller must stop snapshot publication, wait for all VIF/GIF/GS consumers, clear the renderer world/callback, and invalidate any cache metadata that identifies source images. `bsp_render_clear_world()` documentation already requires GPU waits before clearing arena-backed world data ([`bsp_render.h:73-75`](../../submodules/halo-ps2/engine/src/render/bsp_render.h#L73)). A GS-resident cached texture may outlive its EE source, but it may not outlive or be reused across map identity changes without a cache invalidation/generation policy.
7. **GS allocator results and total residency need runtime validation.** `video_init()` currently stores `graph_vram_allocate()` return values but does not check a documented allocation-failure sentinel; it hardcodes `s_vram_used` by pixel arithmetic and assumes the rest is texture capacity ([`video.c:12-29,43-45`](../../submodules/halo-ps2/engine/src/platform/video.c#L12)). An integration gate should verify addresses/ranges/page non-overlap and report actual allocator positions. The 4 MiB texture window competes with UI/font, lightmaps and material textures, not EE RAM. Report peak page usage per loaded scenario and cache behavior across map changes.

## Safe architecture and sequence constraints

Do not enlarge `frame_scratch`, reduce object limits, shrink chain sizes, spend reserve, or reuse `dynamic_simulation` speculatively. The following is a safe implementation seam for M3 Step 13, subordinate to the plan:

1. **Freeze the payload contract first.** Keep CE datum authoritative. Snapshot only fixed-width copies needed by renderer (per-view camera/viewport, frame/tick sequence, object identity token and world transforms, first-person pose/nodes, explicit HUD/effect records). Specify whether a field is critical or optional; over-capacity rejects the snapshot rather than publishing a partial world. Explicitly decide if local split-screen is in scope for this renderer slice; the required four-player input contract does not itself prove four-view snapshot support.
2. **Measure the exact compiled capacities.** Add `sizeof`/alignment assertions or a target-generated size report for all snapshot records, `video_t`, packet descriptors, and renderer chain payload. Assert two snapshot banks fit the `frame_scratch` carve while preserving the existing map-section scratch tail; report actual 16-byte/64-byte/padded extents rather than just logical struct bytes.
3. **Introduce one PS2 EE allocator interface for render DMA objects.** At boot, permanently partition `dma_commands` into non-overlapping intervals for renderer geometry chains, texture upload chains, HCU matrix payload (or eliminate duplicate packet by building the final chain in renderer-owned buffer), packet2/static control blocks, guard/canary bytes, and any diagnostic chain. Check all start/end addresses, alignment and sum against 1,179,648 bytes. Existing exact chain totals leave no room for extra areas, so the design must reduce/stream/pipeline these buffers based on measured worst-case chain use or justify another EE owner with a reconciled global ledger. It may not alias the snapshot's current DMA base with chain byte zero.
4. **Make allocation failure and cleanup transactional.** Renderer init should return a checked error when VRAM or any EE allocation fails; no null `packet2_t` use. On any failure, release packet metadata and chain reservations to the original arena marks, leave HCU’s provider bindings intact until their owning shutdown, and report the named owner. Shutdown order: stop rendering/snapshot producers -> wait for VIF1/GIF/GS -> clear map/world callbacks and texture-source references -> release renderer EE allocations -> stop display/blank if required -> unbind snapshot -> only then release the v2 boot backing. Current `hcu_main.c` unbinds snapshot after shell shutdown and then frees provider/backing, but does not currently call renderer teardown because it never initializes one ([`hcu_main.c:296-305`](../../src/stream/hcu_main.c#L296)).
5. **Implement the actual display sequence in the parent loop.** One production frame should be: input/frame boundary -> zero-or-more CE ticks -> CE stateful render-adapter/snapshot publication -> resolve source records through a render bridge (no CE pointer retained) -> build a complete GS/VU1/GIF/VIF command submission -> submit only when the chosen buffer is idle -> poll/wait DMA and GS at defined ownership points -> vblank -> framebuffer switch. The CPU snapshot marker and VIF payload qword count precede, and do not imply, any of the latter operations.
6. **Use independent tests per boundary.** First unit-test eDRAM address allocations/overlap and mode setup with injectable GS allocator results; next test bounded EE arena carve and cache-line alignment/canaries; next fake DMA that records chain ranges and rejects overlap/lifetime violations; then host CE snapshot immutability and zero/one/two build schedule; then PCSX2 screenshot/readback verifying a deterministic clear/color test actually reaches framebuffer; then target/PCSX2 UI render; finally a capacity-qualified gameplay map with BSP, objects, HUD, and post-unload retry. PCSX2 passing a DMA test does not substitute for physical EE instrumentation/cache-coherency evidence on hardware where applicable.

### Minimal acceptance evidence for a first visible pixel (not full M3 completion)

- Exact parent/HCU/halo-ps2 pins and ELF hash; current source and memory-budget hashes recorded.
- `video_init()` reports three unique valid GS ranges (two framebuffers plus Z), followed by a deterministic GS clear triangle or rectangle and a successful `video_present()`; screenshot/readback hash differs from black/BIOS and matches expected colors.
- EE map documents every renderer-owned range including packet metadata and DMA buffers, all intervals disjoint from ELF/BSS, boot allocator metadata, HCU frame snapshots, map/gameplay arenas, each other, and protected system/reserve ranges.
- Instrumented max chain/upload bytes are bounded by their owners; send/complete sequencing proves the CPU never mutates chain or source bytes while DMA may read them; all GS texture blocks are in range and non-overlapping.
- Test init failure for each EE/GS allocation, DMA timeout, map unload during pending frame, renderer shutdown/reinit, and sequence wrap; no leak, stale map pointer, canary corruption, or post-unload submission.
- PCSX2 proves a rendered pixel, not just a successful shell/map marker. Record PCSX2 settings, interpreter/recompiler result, log and screenshot hashes, and distinguish emulator evidence from EE hardware qualification.

## Halo-64 comparison and non-transferable cuts

Halo-64 is useful as evidence that renderer-owned buffers can fail under constrained RAM and that teardown ownership must be explicit. Its history records an N64 crash screen failing to allocate its own display from the map's already-consumed CPU heap ([`HISTORY.md:48-61`](../../submodules/halo-64/port/n64/HISTORY.md#L48)). That is a valid warning to test OOM/error display paths and not borrow a live map arena opportunistically. It is **not** evidence that PS2 framebuffers consume EE RAM: PS2 color/Z buffers here are allocated from GS eDRAM with `graph_vram_allocate`, while EE command lists use separate EE addresses. Halo-64's 8 MiB CPU/RSP/RDP topology, N64 limits, rasterization backend, and feature/pool cuts must not be copied into this 32 MiB R5900 + 4 MiB GS design. The transferable principle is strict accounting and failure/lifecycle tests; the storage numbers and cuts are not.

## Recommendation to the M3 implementer

Treat this as a **hard unresolved dependency before claiming visible rendering**, not a cosmetic renderer hookup. First create the global render-memory ledger and a single arena-backed DMA allocator with explicit disjoint ranges. The present sizes show that the planned `dma_commands` pool is fully consumed by existing halo-ps2 worst-case ping-pong geometry/upload chains alone, and the HCU snapshot payload currently aliases its base independently. Until a deliberate, measured chain redesign reconciles that exact collision, do not initialize the full BSP renderer against HCU arenas or call the resulting pipeline memory-safe. A minimal clear-screen path can prove GS display/present separately because it uses tiny command data, but it does not qualify BSP/VU1 render memory or campaign map capacity.
