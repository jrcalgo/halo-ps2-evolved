# Independent M2 animation-data lease feasibility review

**Disposition: report-only; no code or tag-format change is authorized by this review.** A typed lease is a plausible way to remove selected `animation.data` bytes from the resident CTAG image, but the present evidence does not establish a safe cache size, active pin high-water, media-read deadline, or a complete memory fit. It is a candidate experiment—not a capacity credit and not M2 acceptance.

This review independently inspected the current HCU animation readers, tag-schema validator, tick call order, retail range artifacts, and the Halo-64 animation stream implementation as a comparison. It ran `python3 -m pytest -q tests/test_animation_data_ranges.py` on 2026-10-21: **2 passed**. It did not modify implementation or regenerate source artifacts.

## 1. Findings from current CE/HCU source

### 1.1 The four direct runtime access points are not the whole integration boundary

The public `animation_get_frame_data()` obtains the base of `animation->data` with `tag_data_get_pointer()`, then returns a raw pointer to either the compressed blob or an uncompressed frame. There is no acquisition token, release, pin, or ownership marker in this API ([`model_animation_definitions.c:500-515`](../../submodules/halo-ce-universal/source/models/model_animation_definitions.c#L500)). The pointer helper itself performs bounds checks and returns pointer arithmetic from `data->address` ([`tag_groups.c:91-114`](../../submodules/halo-ce-universal/source/tag_files/tag_groups.c#L91)).

The source search regression currently finds these four runtime access sites:

| Path | Read behavior | Evidence |
|---|---|---|
| `animation_get_frame_data()` | Returns a raw pointer into `animation.data` for a selected uncompressed frame or the compressed-data region. | [`model_animation_definitions.c:500-515`](../../submodules/halo-ce-universal/source/models/model_animation_definitions.c#L500) |
| Compressed rotation keyframe helper | Directly gets the compressed base at `compressed_data_offset`, then reads header/default/keyframe/index ranges. | [`model_animations.c:2145-2185`](../../submodules/halo-ce-universal/source/models/model_animations.c#L2145) |
| Compressed translation keyframe helper | Same direct base acquisition and direct indexed reads. | [`model_animations.c:2289-2322`](../../submodules/halo-ce-universal/source/models/model_animations.c#L2289) |
| Compressed scale keyframe helper | Same direct base acquisition and direct indexed reads. | [`model_animations.c:2424-2456`](../../submodules/halo-ce-universal/source/models/model_animations.c#L2424) |

`tests/test_animation_data_ranges.py` asserts one `tag_data_get_pointer(&animation->data, ...)` use in `model_animation_definitions.c`, three in `model_animations.c`, and one `animation->data.address` use in the schema validator ([test lines 11-39](../../tests/test_animation_data_ranges.py#L11)). This is useful regression coverage, but it is a textual inventory, not a semantic call graph. New aliases, casts, generic accessors, copied descriptors, or new pointer arithmetic could evade its regular expressions; any lease project should replace or augment it with source-aware inventory and runtime instrumentation.

### 1.2 Pointer retention inside callers constrains the lease scope

These functions retain one or more returned pointers while decoding:

* `animation_get_node_orientations()` retains the selected frame pointer while walking node flags and decoding the entire node array ([`model_animations.c:843-999`](../../submodules/halo-ce-universal/source/models/model_animations.c#L843)). It also separately reads `default_data`; that field is not interchangeable with `animation.data`.
* The continuous overlay path retains current and next frame pointers together ([`model_animations.c:1332-1342`](../../submodules/halo-ce-universal/source/models/model_animations.c#L1332)).
* `aiming_screen_apply()` acquires four frame pointers (`data00`, `data10`, `data01`, `data11`) before entering its node loop, then consumes them during interpolation ([`model_animations.c:1756-1888`](../../submodules/halo-ce-universal/source/models/model_animations.c#L1756); decoding continues through at least [`:1957`](../../submodules/halo-ce-universal/source/models/model_animations.c#L1940)). The four frames all belong to the same `struct animation`; the minimum safe lease need not allocate four independent cache slots if one whole-record view pins their common backing.
* `animation_get_root_velocity()` calls the pose decoder for current and previous frames serially, writing results into stack-local orientation arrays ([`model_animations.c:813-838`](../../submodules/halo-ce-universal/source/models/model_animations.c#L813)).
* Replacement, ordinary overlay, and scaled overlay paths each retain a selected frame pointer across their node walk ([`model_animations.c:1023-1095`](../../submodules/halo-ce-universal/source/models/model_animations.c#L1023), [`:1101-1192`](../../submodules/halo-ce-universal/source/models/model_animations.c#L1101), and [`:1197-1294`](../../submodules/halo-ce-universal/source/models/model_animations.c#L1197)).

The model callers include world-object pose construction ([`objects.c:2525-2534`](../../submodules/halo-ce-universal/source/objects/objects.c#L2525)) and first-person weapon pose, including a second pose for fractional interpolation ([`first_person_weapons.c:1233-1269`](../../submodules/halo-ce-universal/source/interface/first_person_weapons.c#L1233)). These are active game presentation/update paths, not merely offline conversion or a renderer upload.

Persistent animation state does **not** appear to retain frame pointers: `struct animation_state` contains only animation index and frame index ([`objects.h:235-247`](../../submodules/halo-ce-universal/source/objects/objects.h#L235)). That narrows the known lifetime problem to decode scopes, but does not establish a measured maximum set of simultaneously pinned records.

### 1.3 Schema validation is an additional direct reader and publication boundary

Before a validated animation graph is published, `animation_data_problem()` checks the declared node count and, for compressed animations, directly reads `animation->data.address + compressed_data_offset`; it then parses the compressed header, defaults, node headers, keyframes, and frame-index tables ([`tag_schema_models.c:862-927`](../../submodules/halo-ce-universal/port/linux/game/tag_schema_models.c#L862)). `animation_check()` invokes that validation and corrects malformed data to a no-node animation ([`tag_schema_models.c:930-950`](../../submodules/halo-ce-universal/port/linux/game/tag_schema_models.c#L930)). The animation schema declares `frame_info`, `default_data`, and `data` separately as `TAG_SCHEMA_DATA`, followed by this check ([`tag_schema_models.c:1197-1216`](../../submodules/halo-ce-universal/port/linux/game/tag_schema_models.c#L1197)).

Consequently, replacing only `animation_get_frame_data()` is insufficient. A viable external provider must present the same logical bytes to schema validation before tag publication, preserve CE acceptance/correction behavior, and also route all three compressed keyframe helpers through the same logical-view contract. `frame_info` and `default_data` are separate data claims and must remain independently owned unless separately audited; for the narrow `animation.data` candidate they should stay in the tag image.

`animation_data_contains()` uses `animation->data.size` as the logical bound and checks offsets/counts without relying on pointer arithmetic ([`model_animations.c:2558-2602`](../../submodules/halo-ce-universal/source/models/model_animations.c#L2558)). The external descriptor therefore must retain the original logical size even when its backing bytes are elsewhere.

### 1.4 Execution is presently ordered, but an async exclusion is not proven

The observed CE `game_tick()` order calls units, AI, first-person updates, game engine, scripts, recorded animations, objects, HUD, and effects in a sequential function body ([`game.c:331-399`](../../submodules/halo-ce-universal/source/game/game.c#L331)). `first_person_weapons_update()` loops over local players sequentially and calls each update synchronously ([`first_person_weapons.c:869-895`]). This supports the limited finding that the inspected model-animation decode calls are reached from ordinary ordered update functions and that no persistent animation-state field stores their data pointers.

This is **not** proof that every production access is single-threaded. Render/update scheduling, PS2 thread configuration, future callbacks, and any calls from platform or loading workers must be checked against the exact production build. The lease must either be thread-safe with explicit pin accounting or document and assert an owner-thread contract. Map unload must not invalidate a record while any lease remains active. A cache miss must not recursively enter code that can evict a record currently held by the caller.

## 2. Retail-derived range evidence and its limits

The extractor walks schema-recognized in-image records and records exact source extents, payload digests, map identity, gap, and overlap information; its own docstring disclaims runtime cache or memory claims ([`audit_animation_data_ranges.py:1-7`](../../tools/audit_animation_data_ranges.py#L1)). Extraction selects `animation.data`, validates source bounds, hashes payload bytes, and sorts by source offset ([`audit_animation_data_ranges.py:27-74`](../../tools/audit_animation_data_ranges.py#L27)). The checked-in range artifact is tied to schema ELF SHA-256 `2fba411b7244b20fdf31f0b1e540fc2b6f5598891f53a64f8b12f850a0cda0aa`; its report hash is `92a1d32f79f77a83ce1125dddb9b73c5a3c57ec94632ad0963e3602018b4f47a` (the report records this identity at [`m2-animation-data-contract-feasibility.md:5-7`](m2-animation-data-contract-feasibility.md#L5)). Do not join those values to a different schema ELF or retail-map set without regenerating and hashing the entire tuple.

The 24-map range audit reports **12,590 records** and **60,788,194 payload bytes** across the map set; the largest record is **167,560 bytes** in d40, while the highest per-map payload sum is **4,971,464 bytes** in c10. c10's source extent is **9,420,696 bytes**, including **4,449,232 bytes of gaps**. These are byte-layout facts, not concurrent residency facts ([`m2-animation-data-contract-feasibility.md:38-81`](m2-animation-data-contract-feasibility.md#L38)). The current small checked-in retail fixture validates Blood Gulch's 343 records, 1,440,988-byte sum, 41,000-byte maximum, nonoverlap, and source bounds ([`test_animation_data_ranges.py:41-65`](../../tests/test_animation_data_ranges.py#L41)).

The schema permits a theoretical maximum `animation.data` block of `2048 × 64 × 24 = 3,145,728` bytes, with separate maxima for `default_data` and `frame_info` ([`tag_schema_models.c:59-64`](../../submodules/halo-ce-universal/port/linux/game/tag_schema_models.c#L59)). Observed retail maximum record size is much lower, but the schema maximum remains relevant to malformed or future assets and to cache failure tests.

The 1,572,864-byte `streaming` region can hold one observed maximum record, but cannot hold c10's complete animation payload sum. A one-record fit is not a cache-capacity proof: the active set, co-residency, cache metadata, alignment, validation staging, and target read timing are not measured. Likewise, mapping the data to some other EE span without eviction saves packaging bytes only; it does not reduce EE residency.

The independent capacity lower-bound review assumes the most favorable possible case—every animation payload byte removed with zero bytes charged for cache, metadata, staging, texture, dynamic simulation, DMA, audio, scratch, or transition overlap. Even then, the tightest map leaves **2,404,132 bytes** for every omitted EE owner and all animation pins; the d20 residual is **2,751,784 bytes** ([`m2-capacity-viable-design-review-2026-10-21.md:37-52`](m2-capacity-viable-design-review-2026-10-21.md#L37)). The same report notes that the configured `dynamic_simulation` capacity is **2,621,440 bytes**, before other named runtime functions ([`m2-capacity-viable-design-review-2026-10-21.md:68-74`](m2-capacity-viable-design-review-2026-10-21.md#L68)). This comparison is a strong warning that animation externalization alone may not be sufficient. It is still only a lower-bound screen: the final answer must come from actual per-phase owner high-water and valid physical placement, not by mechanically adding nominal arena capacities or treating startup-zero regions as free.

## 3. Minimum stable lease contract (proposal, not implementation)

If diagnostic evidence shows animation data is a viable capacity contributor, the minimum safe first prototype should use a **whole-record scoped lease**, not a frame-slot pointer cache:

1. **Stable identity.** Key each external record by a source-manifest identity that survives conversion and runtime loading: retail source-map hash, tag datum/index identity, animation-graph identity, animation block element index, and field (`animation.data`). Store and verify the original logical byte size and payload digest. Include enough animation metadata to validate the descriptor's relation to `frame_count`, `frame_size`, node count, flags/compression, and `compressed_data_offset`. Names alone are not stable identities.
2. **Exact logical view.** `acquire(animation identity)` returns an immutable contiguous EE view of exactly the original logical `animation.data` bytes (or a provider object with identical indexed-read semantics). A compressed helper must not perform media I/O per node or keyframe. The view must preserve the meaning of frame offsets and `compressed_data_offset` exactly.
3. **Explicit lifetime and non-eviction.** Acquisition returns a lease token plus pointer/span; eviction is forbidden until every token for that entry is released. For an initial implementation, acquire once at the outer public decode scope and pass the leased view down to frame and compressed-keyframe helpers. Release after the outer decode has copied all required values into caller output. Never return a pointer that can be silently recycled while any caller may still read it.
4. **Multi-frame behavior.** The four pointers in `aiming_screen_apply()` can be derived from one whole-record lease because they belong to one animation record; continuous overlays similarly require both frame views during one decode. The contract must also handle nested/reentrant same-record acquisition and any two-record nested use without prematurely releasing the backing. Do not assume all future call patterns match this narrow observation.
5. **Validation and publication.** Make the external provider available to the schema validator before `animation_check()` runs. Validate the same byte sequence with the same compressed/uncompressed rules and correction behavior as the in-image provider. Report corrupt resource, unavailable media, short read, digest mismatch, invalid logical extent, lease exhaustion, and unload-with-live-lease as distinct deterministic failures. Do not publish a usable animation graph whose required bytes have not passed validation.
6. **Separate fields and unload.** Keep `frame_info` and `default_data` in the current tag-image contract for this prototype. On map unload, stop new acquisitions, wait for or reject outstanding leases at a documented safe point, invalidate all tokens, close provider handles, then release the map/arena. Failed map load/retry must not leave provider state associated with the wrong map hash.
7. **Keep an in-image oracle.** Retain the current CE in-image reader as the reference provider. The lease provider must be semantically interchangeable for valid and malformed payloads; no scope reduction, pose approximation, frame dropping, or change in animation scheduling is part of this proposal.

This redesign can preserve the logical byte contract and resulting CE pose behavior. It cannot preserve the original promise that every `animation.data.address` raw pointer remains valid for the entire tag-image lifetime; all code that reads such pointers must be converted or explicitly confined to the resident provider. Describe it as a behavior-preserving API migration only if the full consumer audit and parity fixtures pass.

## 4. Evidence required before selecting a cache size or counting savings

The following data are absent and must be gathered before sizing a lease cache:

* **Stable per-record manifest:** extend extraction/conversion to emit the exact map hash, tag datum/index, graph and animation-block element identity, field, logical size, source offset, payload hash, frame count/size, node count, flags/compression, and compressed offset. Test duplicate names, aliases/shared extents, deterministic IDs under map-load-order changes, missing records, and corrupted extents. Current range rows include offset/size/hash but lack the stable graph/tag/element identity needed to bind a runtime descriptor ([`audit_animation_data_ranges.py:45-73`](../../tools/audit_animation_data_ranges.py#L45)).
* **Complete access instrumentation:** instrument schema validation, the public frame accessor, and all three compressed direct helpers. Record call site/phase, map and record identity, frame, bytes touched, lease begin/end, cache hit/miss, evictions attempted/blocked, provider read bytes/seeks/latency, unique resident bytes, and peak simultaneous distinct records/bytes. Include unsuccessful accesses and failure/retry paths.
* **Workload coverage:** all ten campaign maps, adversarial largest-BSP scenarios and BSP switches, authored campaign encounters at actor high-water, world-object animations, first-person weapons, fractional/palindromic current/next frame paths, four-frame aiming interpolation, and 1–4 local players. Multiplayer stock maps should be included if their animation records are in the M2 capacity scope. The workload must prove worst observed pin high-water rather than sum all records in a map.
* **Timing and media profile:** cold and warm reads from actual supported DVD/optical and OPL USB, SMB, and internal-HDD paths; record number of reads/seeks, bytes per miss, latency distribution and worst latency, requests/misses per tick, maximum blocked tick, and 30 Hz deadline misses. Test fragmented extents and source errors. PCSX2 interpreter/recompiler establish functional behavior and reproducibility, not physical EE latency qualification.
* **Memory ledger:** per map and phase, count reduced CTAG resident bytes, complete active lease cache and metadata, validation/staging memory, claims bitmap, CE game state, active BSP/collision data, parent render/visibility packs, texture staging/cache, dynamic simulation, DMA, streaming, checkpoint, audio, scratch, and old/new map overlap. Each EE byte must have one physical owner; GS, IOP, and SPU2 remain separate stores. Preserve the 5.5 MiB reserve.
* **Failure/lifetime:** deliberately undersize cache capacities (including 1, 2, 4 entries and byte-based limits); force eviction while pointers are live; exercise all four aiming pointers; nested/reentrant calls; overlapping access from two records; unload with leases outstanding; absent device/root, short read, corrupt hash, and cache exhaustion; failed map switch and retry. Assert no stale pointer, premature eviction, use-after-unload, altered pose, leaked pin, or partially published tags.

Parity must cover validator accept/reject and correction, every frame's decoded rotations/translations/scales for representative compressed and uncompressed records (including c10, d40, b40, and Blood Gulch), root transform/velocity, replacement and all overlay forms, four-corner/interior aiming interpolation, world-object and first-person pose, and repeated/current/next frame access. Compare against the same exact in-image provider; use bitwise float comparison where deterministic and a documented tolerance otherwise. Preserve separately owned `frame_info` and `default_data` bytes.

## 5. Halo-64 comparison—limited relevance

Halo-64 demonstrates a port-specific animation-data seam, not a PS2 capacity or lifetime answer. Its `animation_get_frame_data()` branches under `HALO_N64` to `n64_animation_frame()` while the regular pointer path remains the fallback ([`model_animation_definitions.c:498-523`](../../submodules/halo-64/source/models/model_animation_definitions.c#L498)). The N64 implementation moves frame bytes into per-graph cartridge files and exposes each frame through a 16-entry, 4-KiB LRU cache (64 KiB total) ([`n64_anim.c:1-12,22-24`](../../submodules/halo-64/port/n64/src/n64_anim.c#L1), [`:108-177`](../../submodules/halo-64/port/n64/src/n64_anim.c#L108)). Its notes describe N64-specific media and map constraints, including the 2.8 MiB Sidewinder allocation issue ([`NOTES.md:65-75`](../../submodules/halo-64/port/n64/NOTES.md#L65)).

That comparison confirms that source-level accessors can be adapted when the target's storage model differs. It must **not** be copied as the design here: N64's cartridge DMA, uncompressed asset distribution, 8 MiB/94 MHz constraints, and LRU pointer behavior differ from PS2's EE memory, DVD/OPL file I/O, and current CE four-pointer interpolation/validation requirements. In particular, an evictable frame LRU does not by itself prove that four live pointers or a nested decode remain valid. Use Halo-64 as a seam/reference only; derive PS2 lifetimes and sizing from HCU source plus measured EE profiles.

## 6. Conclusion and M2 disposition

Current evidence supports **no-change to the production animation tag contract**. Keep `animation.data` as in-image `TAG_SCHEMA_DATA` until a complete record identity, validator/runtime lease conversion, peak pin and I/O measurement, lifecycle/failure contract, full pose parity, and physical memory ledger exist. A whole-record typed lease is the least-complex credible experiment because it accommodates the observed multi-pointer consumers while avoiding per-node media reads. Whether it materially closes the map-capacity shortfall remains unproven; even the impossible zero-cache/all-bytes-removed lower bound leaves too little residual to claim a complete PS2 runtime fit.

This report closes no M2 acceptance gate. It does not establish a retail gameplay map load, a rendered scene, target EE timing, an animation active set, a production cache size, or that animation externalization alone solves memory. Any implementation or capacity proposal must be reviewed against exact source/map/ELF hashes and the complete requirements above.
