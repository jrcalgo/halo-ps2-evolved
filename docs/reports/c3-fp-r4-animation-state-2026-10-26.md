# C3 first-person animation/state audit (R4) — 2026-10-26

## Scope and conclusion

Audited CE first-person state initialization, equip switching, game-tick animation advancement, render-time pose building, PS2 callbacks/stubs, and available Halo-64 integration sequence. This does not identify a state-machine defect that explains a permanently off-right gun. The retained tick-2 pose is too early to characterize the steady state. The next discriminating evidence is the pose worker's planned state/frame/root trace at ticks 0–300, correlated with the exact active weapon resource and callback freshness.

The first-person data is initialized per map with unit index `NONE` (`source/interface/first_person_weapons.c:443-459`). For each local player, `first_person_weapons_update` detects unit changes, switches weapon if absent, then runs the state update (`:1099-1128`). Switch clears animation indices, timers, recoil, and interpolation count, validates gun and hands remapping tables, then deliberately enters idle via `first_person_weapon_set_state(...idle, TRUE)` (`:1967-2069`). If either remapping table is invalid, `weapon_index` remains `NONE` and subsequent update retries switching; that is a visible missing-pose case rather than a plausible persistent translated pose.

Each active game tick calls `first_person_weapons_update` from `game_tick` (`source/game/game.c:388`). State animation progression uses `animation_update_render_only`, transitions only on restart boundary, and separately advances the movement animation from unit throttle (`first_person_weapons.c:2182-2310`). For ordinary non-PAL tags, `pal_tags_first_person_advance` returns true; PS2's local implementation is documented as matching that contract (`port/ps2/src/ps2_network_local.c:269-271`, Linux implementation `port/linux/game/pal_tags.c:408-436`). Thus the PS2 compatibility function's FALSE return is not an unconditional frozen-animation bug: it is only false for PAL cadence fractions. No evidence found that CE's tick/update protocol was omitted in the C3 trace setup.

Normal render sequencing is also explicit: after setting `render.local_player_index` and camera, `first_person_weapon_render_update` sets visibility and calls `first_person_weapon_build_node_matrices` for an equipped first-person weapon (`first_person_weapons.c:659-680`; general CE ordering in `render/render.c:322-340`). That builder applies state, movement, interpolation, and overlay layers. The C3 snapshot path sets per-view context then calls this render update before copying palettes on successful bitmap callbacks (`port/ps2/src/ps2_render.c:349-357, 486-489`). An already identified exception remains the bitmap preflight/begin/partial-view failure path, where snapshot publication can reuse old matrices; see R3. This is pose freshness, not a bad animation-state transform.

## Candidate exclusions and unresolved hypotheses

- The 41-node parent inverse-bind/camera composition agreement and the I1 FOV math rule out those stages for the captured configuration, subject to the R3 caveat that the optional CE viewmodel-projection hook has not been recorded directly.
- The early root forward vector `(0.596, 0.090, 0.798)` points largely upward and is compatible with a transient raise/equip animation; no frame-zero state was logged in the prior trace. It cannot justify an axis or offset correction.
- Idle/ready, raise animation selection, and animation frame decoding remain unproven for the *steady* capture. `first_person_weapon_set_state` resolves the requested first-person animation slot to a graph animation index and starts it at frame zero (`first_person_weapons.c:1278-1360`). For a decisive trace, log numeric state, animation type/slot, resolved animation index/frame/count, restart event, movement index/frame, overlay index, and root graph node transform at each sample. Also record unit/weapon datum and selected first-person model/graph resource IDs, plus whether weapon/hands remapping tables validated. Compare ticks 0, 1, 2, 6, 15, 30, 60, 120, 300.
- Search found no `render_interpolation_update` symbol in this CE tree; first-person interpolation is updated explicitly in its own builder/state code. Therefore the task's named interpolation phase should not be assumed to be a separate missing call without a concrete equivalent in the local fork.
- The port configuration notes C3-specific visibility/copy stubs: `ps2_config.c:67-105` says `viewmodel_is_visible` and `first_person_weapon_copy_render_models` are wired to C3 implementations; shield visibility remains a generated FALSE stub because the C3 publisher never draws the shield flare. That shield gate affects an effect, not the gun/hands palette. Confirm the actual C3 copy implementation is linked in the capture, but a zero-return shield/viewmodel-render gate does not explain the observed populated offscreen matrices.

## Halo-64 comparison boundary

Halo-64 has a separate port/runtime and a different model representation (node-space vertices pretransformed by inverse default pose, then scaled for N64; R3 documents converter/draw sites). I found no evidence that its sequencing can be transplanted to PS2 as an animation fix. The comparable CE contract is tick advancement followed by render-context selection and pose construction; C3 follows it on successful views. A Halo-64-specific update cadence or axis interpretation would be insufficient evidence to change CE state handling.

## Recommended next check

Use the already planned fresh steady-state trace. First establish that by tick 300 the state is idle (or record actual state), root basis/translation has settled, and the same pose is built for each render view. If settled CE-native weapon vertices still project wholly right with a settled idle root and valid remaps, inspect the selected animation graph/resource and matrix convention at the graph-to-model remap boundary. If CE-native pose moves into frame but the snapshot does not, investigate C3 publication freshness. Do not alter state timing, animation speed, or authored pose until that comparison identifies a divergence.
