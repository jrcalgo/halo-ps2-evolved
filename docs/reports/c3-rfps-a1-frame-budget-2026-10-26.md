Read-only source/runtime investigation of the current four-view PCSX2 workload. Source is pinned to `2a8a0836893c31bf80b12fa37e28edb99b97135e`; this report uses the retained object-sharing A/B report and its logs. No code, binaries, or tests were changed or run for this investigation.

Four-view mean `render-callback-ms` is 35.280 (5 samples), `view-build-ms` 25.620, and inner `c3-view-perf total-ms` 21.718. In the same samples `c3-publication-perf total-ms` is 20.118. ## Exact scheduling and timing boundaries

In [CE main loop](../../submodules/halo-ce-universal/source/main/main.c), the realtime scheduler converts elapsed host time into 30 Hz steps, caps catch-up at four and counts excess whole ticks as drops ([scheduler implementation](../../submodules/halo-ce-universal/port/ps2/include/halo_ps2_scheduler.h)). If no tick is due, the Windows host loop calls `Sleep(1)` (main.c:4227–4257). For each due step it executes input sampling/abstraction, `player_control_update(1/30)`, input end, `game_time_update(1/30)`, increments tick counters, then calls scheduler-progress telemetry (main.c:4267–4293).

After all steps in that batch, it calls `main_game_render(1/30)` once to publish the newest CE frame snapshot (main.c:4295–4303), then synchronously calls `hcu_c3_render_tick` and `hcu_c3_snapshot_tick` (main.c:4383–4384). Therefore a wall-clock batch contains scheduler polling/sleep, 1–4 simulation ticks, one CE publication, one HCU callback, snapshot capture work, and loop overhead. At steady state with 30 ticks/s and ~10 host renders/s, this implies roughly three simulation ticks per render on average; it does not mean three renders share a publication. Actual per-batch step distribution is not logged in the standard timing path.

The callback timer begins at function entry and ends after `bsp_render_frame_end`/`hcu_render_frame_end`; it covers view setup/build, waits, video present, and kick. `view-build-ms` begins after frame setup and ends before waits. The separately reported `c3-view-perf total-ms` comes from BSP phase counters inside that build; it is nested and must not be added to build/callback totals. Callback wait fields and present/kick fields partition later callback portions (see [callback timing code](../../src/stream/hcu_main.c:2589)); the log’s four-view means show ~0 ms BSP/video waits, ~6.409 ms present and ~3.199 ms frame-end kick. The 20.118 ms CE publication timing occurs before callback entry and is not in `render-callback-ms` (main.c:4301–4303; hcu_main.c:1215–1229, 2771–2773).

The 30 Hz game counter and dropped-tick counter are meaningful scheduler health signals, not measures of host frame throughput. `hcu_c3_scheduler_progress` samples at tick boundaries and reports interval wall time/rates, with `renders` derived from HCU frame deltas (hcu_main.c:3112 onward). The existing benchmark scores host FPS from scheduler tick timestamps, so it includes all serial phases and any scheduler idle/pacing. The current report does not expose per-batch work-phase durations or scheduler polling/sleep time.

The four-view callback of 35.3 ms alone cannot explain ~100 ms per host frame. Publication (~20 ms) plus callback (~35 ms) is ~55 ms before simulation, scheduler/host overhead, snapshot/capture tasks, and idle/pacing. This is a lower bound on identified serial work, not a full additive budget because timings are means from periodic samples and may not match the host-FPS interval sample-for-sample. Source A/B gives a direct target: exact-pixel-preserving object prep reuse did not consistently improve FPS, so a next change should first target a separately measured dominant phase.

## Recommended next instrumentation

One new low-overhead aggregate timing row at the realtime parent batch boundary should report: wall interval from previous batch, due `steps`, aggregated simulation time, `main_game_render` publication time, HCU callback time, snapshot/capture time, and scheduler dropped ticks. Add sparse samples and distributions (median/p95/max) rather than noisy per-step logging. Within simulation, initially split player-control and game-time totals; only add deeper phase points if one is dominant. Maintain the current callback’s own phase rows for attribution, and clearly label nested counters as nested.

This instrumentation makes the speed gap actionable without altering pixels. PCSX2 measurements can rank hypotheses and confirm exact-output parity, but they cannot qualify native PS2 frame rate or hardware-specific GS/presentation behavior.
