# M2 animation-tag live-set access inventory

Date: 2026-10-21  
Scope: source-backed audit of Halo CE animation `tag_data` reads for the M2 capacity experiment. This is report-only; it does not propose N64 content cuts or change runtime code.

## Findings in brief

CE has three animation tag-data blobs that matter to the capacity experiment: `animation.data`, `animation.default_data`, and `animation.frame_info`. The main frame accessor is `animation_get_frame_data()`, but it is not a complete interception point. Three compressed-keyframe helpers bypass it and call `tag_data_get_pointer(&animation->data, animation->compressed_data_offset, 0)` directly (`source/models/model_animations.c:2152,2296,2431`). The uncompressed default pose bypasses `tag_data_get_pointer()` too: the macro `animation_get_default_data()` returns `animation->default_data.address`, and `animation_get_node_orientations()` walks it (`source/models/model_animation_definitions.h:61-62`, `source/models/model_animations.c:862-998`). Frame-info also has a bulk direct-address walk in `animation_get_x_offsets()` in addition to its indexed accessor (`source/models/model_animations.c:387-439`).

The common accessor does not establish one safe or complete streaming/cache boundary. Any live-set experiment must observe all four paths—frame data, compressed subranges, defaults, and frame-info—before it can claim animation-byte coverage. It should attribute reads to the phase/caller and graph/animation, and separately report distinct bytes touched and simultaneous residency: repeated reads of one resident tag blob are not the same quantity as a cache working set.

Halo-64 is useful only as a contrast: it adds cartridge streaming in the two public accessors, while CE has ordinary resident tag pointers. Its N64-specific converter and capacity choices are not PS2 requirements. In particular, a PS2 experiment must preserve CE's full graph and animation semantics and measure the actual R5900 memory/IO behavior rather than importing N64 cuts.

## Definitions and sources

`struct animation` holds three independent `struct tag_data` descriptors: `frame_info`, `default_data`, and `data` (`submodules/halo-ce-universal/source/models/model_animation_definitions.h:53-88`). `MAXIMUM_FRAMES_PER_ANIMATION` is 2,048 and `MAXIMUM_NODES_PER_ANIMATION` is 64 (`.../model_animation_definitions.h:19-25`). The parser/loader's tag relocation makes each descriptor address usable by runtime; the code below consumes those addresses synchronously. The inventory is based on exact source-level callers and accesses, not aggregate relocation/string searches.

### Other forms of access

The compressed path also reads defaults stored within `animation.data`: for example `animation_get_node_orientations()` uses offsets from the compressed header to select per-node default rotations and translations, while scale may default to `1.0f` (`model_animations.c:883-984`). Those are not `default_data` accesses; their bytes belong to the compressed blob and are checked with `animation_data_contains()`.

`animation_frame_valid()` and `animation_data_contains()` inspect `frame_count`, `frame_size`, flags, offsets, and sizes, but do not themselves load the byte payload. Count these as metadata validation, not payload bytes. `animation_get_frame_data()` also has pointer-arithmetic postcondition assertions in its consumers; repeated accessor calls inside those assertions should be counted separately from payload decodes if the instrumentation counts calls, but must not inflate distinct-byte totals.

No other CE source-level `tag_data_get_pointer()` access to `animation.data`, `animation.default_data`, or `animation.frame_info` was found beyond the sites listed here. In particular, the three direct compressed fetches and the default-data macro/direct frame-info walk are the bypasses that a single-accessor audit would miss.

## Caller and phase classification

The bytes are consumed at several engine phases; “animation is render data” is not a valid classification.

The same routine is called from object creation/update paths (`objects.c:3410,3629,3786,3810,3860,3904,5042`). | Can be reached while creating/updating objects, independent of whether final scene drawing succeeds. ## Instrumentation points recommended for the M2 capacity experiment

Implement the instrumentation in a separate measured build, preserving retail behavior and using fixed-size counters/buffers (no runtime heap growth). Record the build hash, CE/parent source pins, map/tag identity, and run scenario with every report.

1. **Central indexed-frame hook:** instrument `animation_get_frame_data()` (`model_animation_definitions.c:500`) with animation graph/tag index, animation index, type, frame index, compressed flag, byte offset, requested extent, and current phase/caller. For uncompressed frames, report `[frame * frame_size, frame_size]`; for compressed frames, report the compressed base and defer exact subrange accounting to step 2. Do not count accessor assertion probes as decoded payload reads.
2. **Compressed bypass hook:** instrument all three direct `tag_data_get_pointer(&animation->data, compressed_data_offset, 0)` sites at `model_animations.c:2152,2296,2431`, or route them through a side-effect-free measured helper. The helper should report the exact header/default/keyframe extents already checked by `animation_data_contains()`, including invalid reads separately. Do not omit these just because most uncompressed reads route through `animation_get_frame_data()`.
3. **Default-data hook:** instrument before `animation_get_default_data()` is consumed in `animation_get_node_orientations()` (`model_animations.c:862-998`). Derive the true cursor range by measuring cursor advancement, and retain the declared `default_data.size` and computed required size. A `tag_data_get_pointer()` hook will not observe this macro.
4. **Frame-info dual hook:** instrument both `animation_get_frame_info()` (`model_animation_definitions.c:518`) and the direct bulk loop in `animation_get_x_offsets()` (`model_animations.c:387-439`). The bulk record must include type, frames scanned, total validated bytes, and whether size validation rejected the scan.
5. **Phase attribution at callers:** push/pop a small phase enum (load/validation, object create/update, unit movement/pose, melee, device/vehicle, first-person tick, first-person render, sky/camera/cinematic, other) around the source-backed call sites enumerated above. Prefer call-site phase scopes over inferring phase from the PC or helper name; helpers are shared across gameplay and presentation.
6. **Report two different memory numbers:** (a) unique animation payload bytes ever touched per map/scenario; (b) maximum simultaneous live bytes and working-set window, grouped by graph and tag. Add total resident bytes for all animation `data/default_data/frame_info` blobs from tag metadata. A sum of per-frame reads or accessor call counts is neither a resident-size total nor a cache-capacity result.
7. **Bound the instrumentation itself:** fixed-size open-addressed per-animation counters or a pre-sized table in an explicitly accounted scratch/diagnostic arena; count dropped records/overflow. Do not keep raw pointers beyond the callback. Output a compact summary after the scenario rather than printing on each node/frame read, which would distort EE performance.
8. **Exercise representative paths:** campaign actors (idle/movement/damage/death), player first-person firing/reload, melee timing, seat enter/exit, animated devices/vehicles, sky/cinematic path, and continuous overlays. Include repeated render schedules for first-person/render-sampled paths and compare simulation state hashes to ensure instrumentation is observational only.

## Halo-64 contrast (not a PS2 prescription)

Halo-64 adds a `HALO_N64` branch to `animation_get_frame_data()` and `animation_get_frame_info()` to route data flagged as streamed to `n64_animation_frame()` (`submodules/halo-64/source/models/model_animation_definitions.c:498-537`). Its N64 converter describes per-animation graph streams and cartridge-backed animation frame data (`submodules/halo-64/tools/n64/convert.py:84-104`). This demonstrates that the two public accessors are natural integration seams for a platform whose animation payload is external.

However, Halo-64's `model_animations.c` still directly fetches compressed data in the three keyframe helpers (`submodules/halo-64/source/models/model_animations.c:2031,2143,2246`); an accessor-only port would therefore not cover every compressed access. Halo-64 also has N64-specific map conversion/streaming and memory/content decisions. The PS2 port has a different 32 MiB memory/store topology and must keep CE campaign AI, scripts, effects, full animations, and gameplay semantics in scope. Use Halo-64 to identify where a streaming design can hook and what bypasses remain—not to remove animation content, reduce update cadence, or copy N64 pool limits.

## Caveats and acceptance boundary

- This inventory is static source evidence. It does not report a measured campaign animation high-water mark or prove that streaming is required.
- `animation_get_frame_data()` returns a raw pointer, and some consumers use two or four frame pointers while interpolating. A future staged decoder must honor those simultaneous ranges; one-frame-at-a-time eviction may be invalid even if individual frame reads fit.
- `animation.data.size` is one payload range but compressed content has sparse internal reads; `frame_count * frame_size` is not a safe estimate for compressed animations.
- The live-set result must be tied to the exact PS2 build and scenario. PC host instrumentation can validate accounting coverage but cannot establish EE CPU cost, IOP/DVD stall behavior, or PS2 peak memory.
- No M2 capacity gate is closed by this report alone. The next step is measured instrumentation and representative guest scenarios, followed by an explicit capacity decision.
