# M2 Step 7 — PVS and game-sound query follow-up

**Disposition: useful next host slice identified; Step 7 remains partial.** The retail package fixture already calls CE's PVS and sound-distance accessors, and counts both set and clear non-self PVS bits. It does not yet bind named visible/hidden cluster pairs to an independent expected value, run CE's actual `compute_sound_obstruction()`, or qualify an EE map. The shortest soundly scoped improvement is a deterministic visible/hidden PVS pair oracle over the currently published relocated BSP. A second, more integrated slice can execute CE's sound-obstruction function while keeping the same package transaction and BSP publication.

## Current evidence and the precise hole

`plans/7.hcu-remake-m2-m4.md` says Step 7 must preserve collision, cluster, surface, PVS, and sound-cluster data and tie any removal to a bounded replacement test (Step 7 text around lines 590–595). The current package transaction now proves significantly more than a raw envelope round trip: the CE schema validators and `scenario_switch_structure_bsp()` run over retail `a30` and `a50`; CE collision-BSP queries hit material-bearing surfaces and resolve leaves to clusters; every relocated PVS row includes self; and every sound-distance pair is bounded, symmetric, and unchanged. The current qualification report documents the package hashes, host ILP32 fixture, and limits in [`m2-step7-retail-consumer-query-qualification-2026-10-21.md`](m2-step7-retail-consumer-query-qualification-2026-10-21.md).

The missing PVS assertion is narrower than earlier plan text implies. `tests/hcu_scenario_bsp_switch_main.c:685-720` does inspect every row through CE's `structure_bsp_get_cluster_pvs()` and `BIT_VECTOR_TEST_FLAG()`, and requires at least one visible and one hidden non-self pair. However, the fixture does not identify the pair(s), print their indices, or compare those bits with an independently-derived expected value from the source BSP/package. It therefore catches all-zero/all-one rows, but cannot prove a specific row/bit survived relocation correctly if the payload is corrupted in a way that still leaves both kinds of bit.

CE's data/accessor contract is small and favorable for this fixture:

- [`structure_bsp_get_cluster_pvs()`](../../submodules/halo-ce-universal/source/structures/structure_bsp_definitions.c#L35) returns the row at `cluster_data.address + cluster_index * row_stride`, after index/count/extent guards (`structure_bsp_definitions.c:35-68`). Its return type is `unsigned long *`; the host fixture uses ILP32, matching CE's 32-bit bit-vector word.
- The actual render visibility traversal uses that row to gate portal traversal with `BIT_VECTOR_TEST_FLAG(cluster_pvs, neighbor_cluster_index)` in [`structure_visibility.c:1653-1666, 1762-1775`](../../submodules/halo-ce-universal/source/structures/structure_visibility.c#L1653). CE player PVS aggregation also reads these rows in `source/game/players.c:1832,1844,1867`.
- The game-sound behavior is available as a directly callable CE function, [`compute_sound_obstruction(short local_player_index, struct sound_source *source, real distance)`](../../submodules/halo-ce-universal/source/sound/game_sound.h#L96), implemented at [`game_sound.c:950-1047`](../../submodules/halo-ce-universal/source/sound/game_sound.c#L950). It combines the CE sound-distance and PVS accessors and, for a reachable/PVS-visible pair, calls CE `collision_test_vector()` with structure, media, object, scenery, and machine flags (`game_sound.c:985-1034`).

## Recommended first implementation: deterministic visible/hidden PVS pairs

This is the smallest useful next commit and does not require pulling player-control or renderer-global logic into the transaction fixture.

1. In the existing `assert_relocated_cluster_queries()` path, select at least one ordered `(from_cluster, to_cluster)` pair whose non-self PVS bit is set and one whose bit is clear. Keep the current all-row scan and self-bit check; add explicit selected-pair fields and report them with the package/BSP identity. Do not assume PVS symmetry unless a separate source/tag audit establishes it.
2. Add an independent expected-pair oracle in the Python runner. Derive the expected two bit values from the exact input source map/schema data (or a small checked-in generated record keyed by source-map SHA, package SHA, CBIX entry, and CBSP image SHA). The oracle must not read `global_structure_bsp->cluster_data` after CE materialization; that would compare the accessor with the same relocated bytes and be circular. The expected record should include cluster count, row byte stride, pair indices, expected set/clear values, and identities for both `a30` and `a50`.
3. Pass the selected pair indices/expected values to the C fixture through a generated header or bounded command-line fixture input. At runtime call the real `structure_bsp_get_cluster_pvs()` and CE's `BIT_VECTOR_TEST_FLAG()` against the active published structure, assert the exact expected bits, and assert both selected indices are in range. Retain the current pointer-in-span checks and before/after payload immutability checks.
4. Emit a machine-readable row for each queried BSP: map/package/source hashes, section tag and CBSP image hash, cluster count, visible pair, hidden pair, raw observed values, and active `global_structure_bsp_index`. The Python test should reject missing or duplicate rows and match them to the expected oracle; no success-by-count-only check.
5. Run the existing package-backed native ILP32 test for `a30` and `a50`, then run the non-package focused tests. The runner already uses the real CE scenario and PS2 materializer with host-owned overprovisioned arrays; label this as host semantic evidence only. Do not claim PVS renderer output, a production-fit map, EE memory qualification, or visible pixels.

This directly covers the plan's “visible/hidden cluster” consumer subcheck and provides a fast, deterministic regression test for row offsets, bit numbering, and relocation preservation. It still does not execute the complete `structure_visibility` portal/frustum traversal or player PVS aggregation. The distinction matters: a PVS bit means a cluster is potentially visible to CE; actual screen visibility additionally depends on portal hull/frustum traversal and renderer state.

## Optional second slice: call the real CE game-sound obstruction routine

If extending Step 7 beyond the PVS gate, prefer a narrow wrapper around CE `compute_sound_obstruction()` rather than invoking the entire audio update/mixer. The source function's exact decision path is unusually testable:

- If either cluster is `NONE`, it retains initial `obstruction=0.6`, `occlusion=1.0`.
- For valid clusters, it reads the symmetric packed sound distance via `structure_bsp_get_cluster_encoded_sound_distance()` (`structure_bsp_definitions.c:232-267`). If distance is unreachable/outside the maximum, it keeps the initial values.
- For reachable distance and a clear PVS bit, it skips the geometric collision call and calculates occlusion from the encoded cluster distance plus the supplied source distance.
- For reachable distance and a set PVS bit, it sets obstruction to `0.45`, computes camera-to-source vector, and runs `collision_test_vector()`. A no-hit result sets both obstruction and occlusion to zero; otherwise the reachable-distance attenuation is applied (`game_sound.c:985-1034`).

Suggested bounded fixture structure:

1. Keep the same package transaction fixture and invoke the probe only after a real CBSP has been published; query `global_structure_bsp_get()` so no duplicated test-local BSP object is substituted.
2. Avoid re-declaring CE's private `struct sound_source` layout. A test-only translation unit can include the CE `game_sound.c` implementation and expose a tiny fixture wrapper in the same translation unit, constructing the private source record and calling the production `compute_sound_obstruction()`. Alternatively, add a narrowly `HALO_PS2_TEST`-guarded wrapper if including the source proves impractical. Do not copy the decision code into the test.
3. Supply only machine-boundary adapters that are required by the function: deterministic `observer_get_camera(local_player_index)`, monotonically advanced `game_time_get()`, the live BSP getter, `vector_from_points3d()`, and a collision-user stack initialized with its required pre-existing depth. `compute_sound_obstruction()` itself pushes `_collision_user_sounds` and asserts the depth remains above the caller's entry depth on return (`game_sound.c:971-1047`); assert stack depth and entries are restored after every case.
4. Use oracle-selected package pairs: a reachable hidden pair to exercise the no-PVS branch and a reachable visible pair to enter collision. Assert exact output floats with a documented tolerance and recompute the CE attenuation formula from exact encoded distance and input `distance`. For the visible case, first use a deterministic collision adapter to distinguish “PVS branch selected” from “PVS branch skipped”; then, if claiming actual geometric occlusion, link and execute CE `collision_test_vector()` over the package-backed collision BSP and use source-derived camera/source endpoints with independent expected hit/miss. A fake collision callback is not evidence of wall occlusion.
5. Advance game time for each test vector. CE's static 128-entry cache in `game_sound.c:929-969` keys by game tick, local player, and source position; it does not key on the test's cluster pair or supplied distance. Reusing a tick/position can silently return the previous answer and invalidate branch coverage. Include a same-tick repeat case only as an explicit cache contract check.
6. Assert sound source fields, no writes to relocated PVS/sound payload, cache replay behavior, collision stack balance, and unchanged BSP publication. Record the linked test ELF/map and symbols resolved by shims so the fixture cannot quietly grow into an unreviewed game/audio port.

The include-source method plus function/data sections and linker garbage collection should keep the initial link narrow, but the exact rooted symbol closure must be measured before committing to that route. Linking real `collision_test_vector()` may pull much more CE object/BSP state than the current low-level `collision_bsp_test_vector()` fixture; measure the map and enumerate each remaining adapter. It is reasonable to first land the visible/hidden PVS test, then decide whether a sound wrapper is still an efficient Step 7 slice.

## Limits, dependencies, and comparisons

- These probes remain host semantic tests. Step 8 has not produced a lossless, physically qualified BSP+CTAG ownership topology; the existing `a30`/`a50` harness arrays exceed PS2 capacity. Do not run a campaign map on target or claim target memory acceptance until that dependency is resolved.
- A real CE sound-obstruction function result is not audible audio output. It does not verify tag selection, sound playback, SPU2 voices, or sound encoding; those remain separate sound/runtime work (M14 in the overarching plan).
- Keep all schema-owned payloads. A successful PVS or sound query is positive evidence that these fields are needed, not permission to strip them.
- Halo-64 is useful only as adapter-boundary context: its [`port/n64/NOTES.md:33-55`](../../submodules/halo-64/port/n64/NOTES.md#L33) explicitly preserves CE CPU-side frame/camera/first-person/HUD state even when drawing is excluded. That supports retaining CE simulation/query state behind the PS2 renderer boundary, but offers no PVS semantics, PS2 memory sizing, or permission to cut features.
- REA is **not applicable** to this slice. There is no disputed shipped executable whose behavior must be recovered; the question is whether current CE source queries relocated retail package bytes correctly. Source inspection, exact package identity, and the host ILP32 transaction fixture are the appropriate evidence. If a later mismatch arises only in a retail binary, REA could be considered for that concrete artifact then.

**Recommendation to the integrator:** add the deterministic pair oracle first. The current test already proves both categories exist, so the added code is small and immediately addresses a real Step 7 hole. Treat full `game_sound.c` execution as an optional follow-up with an explicit collision-link budget; do not hold the small PVS regression on the wider sound/audio closure.
