# M2/M3 Steps 7–8 documentation audit: implementation decisions

Date: 2026-10-22  
Scope: stock 13-map multiplayer set plus UI; multiplayer players, bots, and co-op are in product scope. Campaign is excluded. This is a source-cited decision memo, not a plan/status or code change.

## Decision summary

1. **Do not strip CE BSP members based on the PS2 `BSPS` converter schema.** Keep the CE `structure_bsp` image complete until the member ledger links every field to CE readers, relocated ownership, and a parity test. The PS2 renderer's `BSPn` is a distinct converted representation, and its own documentation lists omitted/uncertain fields. Continue validating the CBSP transaction before CE publication; all-13 late-visitor failure/retry evidence proves rollback behavior, not complete consumer correctness.
2. **Do not accept or resize the candidate 10 MiB map/texture owner from map-query or static-section totals.** The 6,470,832 B tag+BSP / 4,014,928 B texture profile is a test-only host/PCSX2 candidate. Owner high-water must include real concurrent renderer texture use/staging and live match state, while respecting guards and explicit ownership. Current production v2 regions put a 16-byte canary between `current_bsp` and `texture_cache`; a production recarve requires a deliberate layout/binder/guard change.
3. **Treat game-state/object pools and `dynamic_simulation` as separate owners.** Existing CE object-pool and game-state allocations route to resident game-state memory; `dynamic_simulation` is the PS2 compatibility malloc arena. Measure each independently, including actual failures and peak/cursor reset. Never sum a nested object pool twice or infer bot/co-op byte demand from static map inventory.
4. **No N64-derived limits or cuts.** Halo-64 is useful as evidence that explicit pool/arena and workload measurements matter, not as a source of PS2 capacities, bot limits, update throttles, or accepted compromises.

## Step 7: BSP relocation and consumer correctness

The actionable rule is **preserve first, classify by actual consumer, then consider a measured replacement**. The grouped CE ledger already identifies collision traversal/material/leaf results; PVS/player aggregation; PAS/sound obstruction; fog/weather/location/wind; sound environments; visibility surfaces/portals; materials/lightmaps; breakables; precache; and Xbox buffer handles. It explicitly says this is not yet exhaustive for nested decal, detail-object, pathfinding, marker, and sound-scenery members ([current field audit, lines 33–49 and 63](m2-step7-field-inventory-current-audit-2026-10-21.md#L33)). That gap is the next concrete Step 7 work, not an invitation to infer dead fields from a converted pack.

For each remaining BSP member, record: serialized location/type/count; validation and relocation action; every rooted CE read/write site; owner/lifetime; exact test oracle; disposition (`preserve`, `copy/relocate`, or only after proof `replace/omit`). The PS2 `BSPS` doc is a useful uncertainty checklist, but its own unreferenced-surface inference and undocumented node/fog/marker cases are expressly uncertain. Keep source surface IDs when comparing to converted output.

The package-backed host fixture now injects a late `B000` visitor failure at cycle zero across the 13-map matrix, verifies rollback of published scenario/BSP/collision/game/tag-cache state and parent-service release, then retries successfully ([late-failure report, lines 1–39](m2-step7-mp-cbsp-late-failure-atomicity-2026-10-22.md#L1)). Existing 13-map host reports also exercise collision, PVS, fog, weather/wind, location, sound/PAS and sound-environment slices. These are meaningful consumer qualifications, but they do not amount to a complete field→consumer proof, full collision wrapper closure, live audio playback, or PS2-target BSP parity. Keep CBSP publication failure-atomic and expand the member ledger plus missing render/surface/material and nested-reference tests before any source-data reduction.

## Step 8: capacity, ownership, and target evidence

**Current candidate evidence:** the aligned candidate is 6,470,832 B tag+BSP plus 4,014,928 B texture (10 MiB total). The provider-bound all-13 host run passed 26 load/query/unload rows, with texture owner peak 2,144,672/4,014,928 B and CRC rollback transient peak 2,550,720 B ([provider-bound rerun](mp-step8-provider-bound-combined-rerun-2026-10-22.md#L1)). Separate PCSX2 Blood Gulch and Sidewinder probes load/query/unload under candidate capacities; Sidewinder's resident BSP payload has only 24 B margin. These are query/loader evidence, not a playable match, renderer residency, or max-workload qualification ([Blood Gulch](step8-mp-bloodgulch-pcsx2-query-2026-10-22.md#L1), [Sidewinder](step8-mp-sidewinder-pcsx2-query-2026-10-22.md#L1)).

**Ownership/layout decision:** do not reinterpret the current adjacent-looking capacities as one store. The production v2 carve places a 16-byte guard between the `current_bsp` and `texture_cache` owners. A test-only guarded combined-owner variant validates a proposed topology and provider alignment, but does not change or validate the production carve/binder. Any implementation must explicitly replace the two regions and their guard policy, maintain all other owners/canaries, and show no overlap. Count decoded/retained sections, source/decode overlap, texture upload staging, live pins/eviction, GS eDRAM residency, and DMA independently; don't add alternative catalog totals as simultaneous demand.

**Gameplay ownership decision:** the source-backed pool audit finds `dynamic_simulation` is a 2,621,440 B compatibility malloc arena, while the 1 MiB CE object payload pool is allocated by `game_state_memory_pool_new()` from game-state storage inside resident gameplay; actor/prop/swarm arrays use `game_state_data_new()`. These are distinct owners and current occupancy is unknown ([dynamic pool report](mp-step8-dynamic-pool-pressure-2026-10-22.md#L1)). Diagnostics should attribute bytes/failures at actual owner boundaries, reset at well-defined bind/reinitialize lifecycle points, and prove arena reset/reload behavior. Do not double-count object-pool bytes against `dynamic_simulation` unless code is deliberately rehomed.

The all-13 content closure and static render inventory are offline conversion/source inventories, not runtime capacity: scenario-selected object texture sections undercount weapon-held, bot/co-op, HUD/effects and first-person content; custom Energy Sword and Fuel Rod roots are absent from stock maps and need a separate source provision. Conversely, summed sections across alternative maps are not concurrent residency ([content closure](m2-step8-mp-match-time-content-closure-2026-10-22.md#L1), [static inventory](m2-step8-mp-static-render-asset-inventory-2026-10-22.md#L1)).

**Acceptance evidence still needed:** a real match fixture that initializes and reports the intended supported 1–4 player, bot, and co-op mix; traverses weapons/first-person assets, vehicles, projectiles and representative effects; and captures per-owner current/high-water/failure plus transitions/unload reset. Run each of the 13 MP maps where the supported scenario can differ, on PCSX2 interpreter and recompiler, then retail R5900 when available. Include render texture loads/pins/eviction and UI; preserve CE simulation cadence/parity. Do not report a four-player/bot/co-op pass unless the fixture actually creates and runs that configuration. Compare the resulting measured owners against the actual HCU memory map and guards; the separate halo-ps2 design table and N64 limits are not substitutes.

## Implementation order

1. Finish the CE field→consumer ledger, including render/surface/material and currently unclosed nested blocks; preserve all fields pending proof.
2. Keep the tested relocation validation-before-publication transaction; extend failure injection only where a new validation/publication boundary is added.
3. Resolve and review production arena topology/guard ownership before transferring any capacity between map and texture.
4. Add separate diagnostic accounting for dynamic malloc, game-state allocation, and fixed object-pool capacity; assert no double counting and define reset semantics.
5. Build the actual multiplayer workload fixture; measure renderer and game-state owners together. Only then make PS2 capacity/admission decisions and run target qualification.

The existing broad [submodule documentation audit](m2-step7-step8-submodule-documentation-audit-2026-10-21.md) remains the deeper reading index. This memo narrows it to the current gates and the evidence already available; it changes neither implementation nor plan status.
