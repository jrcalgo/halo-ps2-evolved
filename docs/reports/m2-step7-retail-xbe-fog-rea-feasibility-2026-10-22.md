Therefore this pass produced no disassembly, pseudocode, or runtime observation of the bot-fog routine.

## Next authoritative path

The XBE must first be parsed with a format-aware XBE section reader; preserve its section table, raw file extents, virtual addresses, executable flags, entry point, and digests. Then extract only a verified executable section into REA's explicitly selected `raw-binary` x86 mode at that section's actual virtual base, preserving the derived-file relationship and exact source digest. Even if the section opens, identifying the correct function still requires a defensible XBE-to-CE correspondence (symbols, known call/data anchors, controlled retail execution, or equivalent), not a guess based on function order. If that mapping cannot be established, keep the fog algorithm blocked and gather controlled output vectors from retail Halo CE on MP cases instead of inventing a formula.

Querying that exact address in the current raw-XBE-`.text` REA session did not resolve a function entry there: Ghidra resolved the containing function as `FUN_0017de80`, with observed body `0x0017DE80–0x0017DF05`; the instruction at `0x0017DEE0` is `PUSH ECX` inside that body, and the body has a different four-argument operation/call structure from CE's three-argument fog helper.
