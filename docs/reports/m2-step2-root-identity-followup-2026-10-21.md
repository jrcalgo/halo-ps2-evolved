## Which changes must stay on the M2 production path?

Do not revert the entire root to 0645 or omit all later HCU source changes just to regain an old tested identity. Several changes are production behavior for current map/lifecycle paths:

- The PS2 cache implementation owns CTAG mount, bounded stream validation, BSP extent/load setup, and map-owner release. The current manifest identifies that replacement as the M2 cache path and says HP2/retail map support is still incomplete ([`port.json`](../../submodules/halo-ce-universal/port/ps2/port.json)). These cache/CTAG/CBSP implementation updates are required for the M2 UI load and upcoming map transaction steps, not M0-only accounting.
- CE `scenario_tags_unload()` now clears `cache_file_globals.tag_header` after unregistering its consumers ([`cache_files.c:647-657`](../../submodules/halo-ce-universal/source/cache/cache_files.c#L647)). That is a production teardown invariant: the parent may reuse the fixed tag-cache span after the CE owner has been released, so a retained CE header pointer would become stale. It must not be dropped from the ordinary path merely to match an older root.
- HaloScript edits include validation/refusal and R5900 stack-alignment behavior ([`hs.c:13031-13077`](../../submodules/halo-ce-universal/source/hs/hs.c#L13031), [`hs_runtime.c:955-976,1412-1426,2885-2932`](../../submodules/halo-ce-universal/source/hs/hs_runtime.c#L955)). Changes that fix target faults or malformed-script handling are not diagnostic tracing and must be preserved unless separately disproven by parity tests.

In contrast, lifecycle orchestration and animation-trace calls are compile-time diagnostics; keeping the test-specific code in the HCU tree for its dedicated acceptance profile does not require executing it in an ordinary image. The current ordinary build already passes both test macros as zero. The trace source's zero-sized normal-profile object is evidence that its helper module adds no ordinary code/data at present, though `port.json` and closure/ledger identity still include the source input. Removing it from the manifest is not necessary for ordinary behavior and would create another manifest/root identity requiring re-audit.

Do not mark M0 complete by citing the older 0645 review or by comparing only the external count. M0's ownership audit is an evidence gate; it does not authorize excluding required M2 production code.

## Recommendation

Keep ordinary UI/map code changes that implement current M2 behavior. Keep lifecycle orchestration and animation tracing opt-in; the build already provides separate switches for that. Rebuild the ordinary image after resolving its PT_LOAD overage, then qualify that exact hash in both PCSX2 modes. In parallel, refresh M0's root-bound ledger/review to the exact production `rooted.o` rather than attempting to backport current behavior to the stale 0645 image. Until then, 03670 is valid evidence for its own historical source snapshot only, and the current 147f ordinary UI state is unqualified.
