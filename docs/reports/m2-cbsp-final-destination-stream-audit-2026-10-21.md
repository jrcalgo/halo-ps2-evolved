# M2 CBSP final-destination streaming audit (2026-10-21)

**Disposition: a bounded Longest B000 final-destination stream is arithmetically feasible under the already-tested boot split, but it is not implemented or runtime-qualified.** With the Longest diagnostic split (4,477,120-byte tag cache + 1,814,336-byte BSP cache, same 6,291,456-byte `current_bsp` owner) and the frozen Longest B000 (374,784-byte CE image, 214 relocation rows), a split-view CBSP visitor needs 98,304 bytes of HP2 decode workspace plus 2,604 bytes for the fixed CBSP header and relocation rows. That is 100,908 payload bytes before alignment/parser state, below a 124,224-byte scratch budget; conservative 64-byte arena alignment adds at most 126 bytes for the two leases, leaving about 23 KiB. The actual v2 `frame_scratch` cap remains 393,216 bytes.

This conditional arithmetic **does not** mean current production can load Longest: the default tag span remains 2 MiB and cannot hold its 4,263,624-byte CTAG image. The 4,477,120/1,814,336 split is an opt-in, boot-bound diagnostic with memory-placement evidence only. Nor does it establish a complete gameplay-map budget, CE BSP validation, collision/rendering, or a visible scene. M2 remains open.

## Production call path and ownership

1. **Map mount owns metadata, not the final BSP.** After CE has unloaded the previous map, `map_loader()` mounts the verified HP2 source with the streaming map arena as `owner` and `service->section_scratch` as `bsp_scratch` ([`hcu_map_service.c:129-135`](../../src/stream/hcu_map_service.c#L129)). `map_service_init()` defaults that scratch to `frame_scratch` ([`hcu_map_service.c:179-199`](../../src/stream/hcu_map_service.c#L179)). `ctag_mount_hp2_internal()` keeps the whole CTAG and CRNG section allocations in the map owner; the catalog variant additionally keeps CBIX there and installs a BSP extent loader ([`ctag_mount.c:112-173,225-270`](../../src/stream/ctag_mount.c#L112)). Preflight separately whole-loads HMAP/CTAG/CRNG/CBIX into `streaming`, validates them, then rewinds its mark ([`hcu_map_service.c:283-323`](../../src/stream/hcu_map_service.c#L283)). Non-UI maps remain rejected by the current `capacity-not-qualified` check ([`hcu_map_service.c:248-252`](../../src/stream/hcu_map_service.c#L248)).
2. **CE asks for the BSP through its normal cache read.** During `scenario_switch_structure_bsp()`, CE disconnects/unloads the old BSP and clears the current index before attempting the requested BSP; only after a successful read and `structure_bsp_port_verify()` does it publish `global_structure_bsp`, collision pointers, and the new BSP index ([`scenario.c:1101-1135,1141-1184`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L1101)). `scenario_structure_bsp_load()` eventually calls `cache_file_read()` with `tag_index == NONE`, the source map file offset/size from the scenario BSP reference, and the fixed BSP-cache base ([`cache_files.c:1410-1435`](../../submodules/halo-ce-universal/source/cache/cache_files.c#L1410), [`cache_files.c:492-534`](../../submodules/halo-ce-universal/source/cache/cache_files.c#L492)).
3. **The PS2 adapter resolves the exact extent before reporting success.** `cache_file_read()` starts with the failure completion sentinel, recognizes BSP requests only when the output pointer is the fixed BSP-cache base, clears a mounted CBSP if it describes a different extent, then synchronously calls the registered `bsp_loader` for the requested offset/size ([`ps2_cache.c:375-404`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L375)). It sets completion true only after materialization and the CE-specific removal of Xbox vertex/index buffer fields; failure leaves the sentinel false and CE rejects the read ([`ps2_cache.c:417-447`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L417), [`cache_files.c:1428-1450`](../../submodules/halo-ce-universal/source/cache/cache_files.c#L1428)).
4. **Current BSP loader stages the complete encoded section.** `ctag_mount` confirms that the exact `(file_offset,file_size)` exists in CBIX, rejects overlap with the tag-data extent and CRNG resource intervals, releases any previous mounted BSP, then calls `load_section()` with `bsp_scratch` as the decoded-output owner. It retains that allocation until the backend unmount/release callback ([`ctag_mount.c:67-104`](../../src/stream/ctag_mount.c#L67)). The PS2 cache `ps2_cache_mount_cbsp_for_extent()` then calls `ps2_cbsp_open()` on the complete contiguous envelope, checks the CBIX expected extent, raw source size/image-size equality, source-file bounds and non-overlap with CTAG, and stores a view into that retained payload ([`ps2_cache.c:236-267`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L236)).
5. **Materialization copies and rebases to the final cache.** On the same `cache_file_read()` call, `ps2_cbsp_materialize()` copies the contiguous image into the fixed BSP destination and applies its two relocation domains; then the cache adapter empties Xbox vertex/index buffer references, sets completion true, and releases the retained CBSP envelope ([`ps2_cache.c:417-442`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L417)). The mount's BSP release path first unmounts the backend/view and only then rewinds the scratch lease ([`ctag_mount.c:54-60`](../../src/stream/ctag_mount.c#L54)).

### Current CBSP and HP2 constraints

`ps2_cbsp_open()` currently requires one contiguous decoded CBSP payload. It validates minimum header length, `CBSP` v1, image size and relocation limit, exact `36 + image + rows` layout, zero reserved field, source-file extent, `psbs` image signature, image CRC, and each 12-byte row's zero padding, domain, aligned/in-range strictly ordered field, matching stored target, and internal target range ([`ps2_cbsp.c:62-128`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cbsp.c#L62)). `ps2_cbsp_materialize()` checks the final capacity and 32-bit/alignment/disjoint address bounds; validates each domain-1 CTAG string target is in range and NUL-terminated within at most 256 bytes; rejects overlap between the complete payload and destination; copies the image; and applies base+offset relocations ([`ps2_cbsp.c:131-187`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cbsp.c#L131)).

The parent HP2 visitor already supplies the required bounded codec primitive: one retained-reader section parse, 64 KiB LZ4 history + 16 KiB input + 16 KiB output, ordered sink writes, and final raw-section CRC before `HP2_OK` ([`section.c:79-138`](../../submodules/halo-ps2/engine/src/world/section.c#L79), [`hp2.c:260-354`](../../submodules/halo-ps2/engine/src/stream/hp2.c#L260)). A sink can receive a prefix before an I/O/decode/CRC error. Therefore BSP-cache writes during the visitor must be treated as untrusted private staging; the CE load must not publish success until every outer/inner check and fixup is complete. The existing full-buffer loader remains allocation-first: it allocates the entire decoded `raw_size`, then a 98,304-byte workspace and rolls the output allocation back on any failure ([`section.c:141-235`](../../submodules/halo-ps2/engine/src/world/section.c#L141)).

## Longest B000 fixed-owner and scratch arithmetic

The already qualified **placement-only** split is:

```text
tag cache                                  4,477,120
BSP cache                                  1,814,336
                                            ---------
current_bsp total                          6,291,456
Longest CTAG image                         4,263,624
tag-span slack after CTAG                    213,496
Longest B000 CE image                        374,784
BSP-span slack after one B000              1,439,552
```

Both CE images fit their respective fixed spans in this one-map diagnostic. The same split produces the current claims size because `tag_span + bsp_span` is unchanged: `ceil(6,291,456 / 32) * 4 = 786,432` bytes in `resident_gameplay`. Nothing is enlarged and the reserve is not used. This does **not** fix default 2 MiB tag-cache configuration or prove the split is viable for another map.

For a CBSP direct-to-final-image stream, use the frozen B000 counts and current decoder values:

```text
CBSP fixed header                            36 bytes
relocation rows                             138 + 76 = 214 rows
row width                                   12 bytes
retained relocation bytes                   214 * 12 = 2,568 bytes
header + relocation storage                 36 + 2,568 = 2,604 bytes
HP2 history + input + output workspace       65,536 + 16,384 + 16,384 = 98,304 bytes
known simultaneous scratch payload           2,604 + 98,304 = 100,908 bytes
requested design scratch budget             124,224 bytes
raw headroom before alignment/parser state    23,316 bytes
```

The header/rows may be held in a single 64-byte-aligned scratch lease before calling the visitor; the visitor then allocates its 98,304-byte lease at 64-byte alignment and rewinds only to its entry mark. If both leases begin at arbitrary offsets, two 64-byte alignment steps cost at most 126 bytes, so this concrete layout uses no more than about 101,034 bytes before optional small parser state, leaving about 23.2 KiB of the 124,224-byte working budget. The actual arena is 393,216 bytes and 124,224 is a stricter proposed simultaneous-work limit, not a current config value. Header/table/view metadata can be stack/local state; if allocated from scratch, charge it explicitly. This arithmetic assumes no concurrent user of `frame_scratch` and no 262,144-byte source-hash buffer overlapping the call; `verify_source_hash()` does allocate up to that amount but releases it before the map mount/BSP request ([`hcu_map_service.c:25-52`](../../src/stream/hcu_map_service.c#L25)). EE timing, call-stack high-water, cache coherency and same-frame scratch contention remain unmeasured.

By contrast, the whole-buffer path's Longest encoded section is 377,388 bytes, and the section loader requires another 98,304-byte scratch lease. With production `bsp_scratch == section_scratch == frame_scratch`, same-arena raw+decode demand is at least `377,388 + 98,304 = 475,692` bytes (plus allocation alignment), which exceeds the 393,216-byte arena by at least 82,476 bytes. It therefore cannot load B000 through the current whole-section path, even though the envelope alone is smaller than frame scratch. The direct sink removes the full-envelope staging requirement; it does not reduce the 374,784-byte final BSP image or its fixed owner.

## Bounded final-destination design that fits the current call shape

The existing `bsp_loader(context, offset, size)` callback is invoked synchronously inside the CE cache read and currently receives no destination argument. A streaming implementation can either add the fixed destination pointer/capacity to that callback contract or safely obtain them through the same `physical_memory_get_structure_bsp_cache_*()` calls used in `ps2_cache.c`; it must continue to bind the operation to the exact fixed BSP base and CBIX extent.

1. At the start of an exact CBIX row load, preserve the existing extent/path/resource-overlap checks and release the old BSP lease only after CE has called `scenario_structure_bsp_unload()`. Mark the candidate destination invalid/unpublished. Reserve bounded scratch for the 36-byte CBSP header and bounded relocation table, with checked `count * 12`, fixed maximum row count, and 64-byte alignment accounting.
2. Call `world_visit_section_with_scratch()` on the single selected `B000` section. Its sink validates monotonically increasing exact output offsets and expected raw section length. Route bytes `[0,36)` into the header record; route only the declared CE image bytes into `bsp_cache_base + image_offset`; route the remaining 12-byte rows into the scratch row array. Reject gaps, duplicate/out-of-order callbacks, section-size disagreement, image/table overrun, unexpected output bytes, and any mismatch between decoded length and `CBIX` section raw size. There is no complete decoded CBSP envelope allocation.
3. After, and only after, visitor `HP2_OK`, parse the split header/parts and run every existing `ps2_cbsp_open()` rule: CBSP magic/version, image and exact payload sizes, relocation bound/table position, reserved fields, `source_file_offset/source_file_size` equal to the CE request and CBIX record, `source_file_size == image_size`, source file bounds, non-overlap with CTAG/resource extents, `psbs` signature, inner CBSP image CRC, ordered/aligned relocation rows/domains/padding, row target equals its original image word, and internal-target bounds.
4. Validate all domain-1 tag-name pointers against the currently materialized fixed tag-cache image and bound exactly as today (target in image; NUL within 256 bytes). Validate every final `base + target` pointer address for overflow **before writing the first fixup**. The existing materializer checks address overflow during its write loop and rejects any source/destination overlap, so a new split-view validator and `ps2_cbsp_rebase_in_place()`-style routine are needed; do not try to call `ps2_cbsp_materialize()` with a fabricated contiguous payload or ignore its overlap rejection.
5. Rebase the BSP image in place only after all structural, CRC, target and address checks pass. Preserve domain-0 null pointers; domain-0 non-null targets become `bsp_base + target`; domain-1 targets become `tag_base + target`. Then perform the current PS2 cache normalization of CE Xbox vertex/index buffer fields, flush the final BSP span with the appropriate `SyncDCache`, register/commit the active CBSP lease if needed, and only then set CE's completion flag to `TRUE`. CE's ordinary header/schema/`structure_bsp_port_verify()` checks must still run before global BSP/collision pointers are published.
6. On HP2 read/decoder/CRC failure, CBSP-format/CRC failure, invalid row/name/address, no scratch, wrong extent, or sink error: keep the completion sentinel false; never publish a CBSP view or CE BSP globals; clear/poison the destination signature and any private mounted-part view; release the scratch lease and source descriptor exactly once; return failure so CE follows its normal failed BSP-load behavior. Scenario switch already clears the old BSP and attempts to reload it after a candidate failure; if that reload also fails CE goes to the main menu ([`scenario.c:1141-1169`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L1141)). Test this exact fallback path instead of promising preservation of the overwritten old BSP bytes.

Do not leave a mounted CBSP view pointing at scratch after the visitor returns if the rows/header scratch were released. Either keep that small lease until CE's cache read finishes and the release callback fires, or complete all validation/rebase inside the loader and publish a one-shot “exact requested BSP is materialized” acknowledgement for `cache_file_read()`. The latter must avoid running the existing copy materializer a second time and must be invalidated on any offset/size/buffer mismatch.

## Halo-64 comparison

Halo-64 is not directly needed to validate CBSP parsing, but it is a useful architectural comparison for why the final destination and callback lifetime must be explicit: its N64 port places cartridge-backed resources behind port-specific interfaces while the game continues to hold ordinary simulation pointers. That is not evidence that this CBSP image can be evicted or that a 124,224-byte PS2 scratch lease is target-safe. Here the CE synchronous `cache_file_read()` completion flag and fixed BSP address define the commit boundary; keep Halo-64's memory limits and feature cuts out of this PS2 design.

This audit changes no implementation, plan status, memory capacity, default split, or campaign map admission. It is supplemental evidence for M2's CBSP/owner/lifecycle work.

## Implementation addendum — split parser/rebase primitive

After the report was completed, the first parser-only slice was implemented in the HCU PS2 port: [`ps2_cbsp_open_parts()`](../../submodules/halo-ce-universal/port/ps2/include/ps2_cbsp.h) accepts separate header, image, and relocation spans; it retains the existing envelope, CRC, source-extent, ordered-row, domain, and target checks and rejects overlapping spans. [`ps2_cbsp_rebase_in_place()`](../../submodules/halo-ce-universal/port/ps2/include/ps2_cbsp.h) requires the destination to be exactly the validated image span, requires the relocation table to be disjoint, validates every cross-image string and effective address before writing the first fixup, then applies the same domain-0/domain-1 address mapping as the full-buffer oracle. The existing `ps2_cbsp_open()` and `ps2_cbsp_materialize()` remain intact as the compatibility/oracle path.

[`tests/ps2_cbsp_main.c`](../../tests/ps2_cbsp_main.c) now compares full-buffer output with split-span in-place output and tests a malformed final relocation entry, overlapping relocation storage, and invalid CTAG-name targets without image mutation. [`tests/test_cbsp.py`](../../tests/test_cbsp.py) additionally runs this C path against the frozen Longest package and checks the expected 374,784-byte B000 image and all 214 relocation rows against the Python output.
