# M3 Steps 11–14: CE tick, pad boundary, snapshot and render-consumer audit

Date: 2026-10-21  
Scope: report-only review of the current M3 Steps 11–14 implementation. No source, test, or plan files were changed by this audit. The worktree contains unrelated edits; findings below describe the present files and must be rebound to exact source/artifact hashes before they are used as release evidence.

## Executive finding

The implementation has useful separated proofs, but no single fixture currently composes the production CE scheduler/tick with the PS2 input boundary and `render_frame()` snapshot adapter, then proves simulation-state invariance across different render counts. That is the most actionable test gap that can be advanced without editing M2 map-service code. It is also the direct unmet requirement in the M3 exit text: equivalent authoritative traces with zero, one, and multiple render passes between ticks.

The other hard boundary is clear: the PS2 `render_frame()` adapter commits and CPU-packs a matrix VIF payload, but no production parent consumer submits that payload to VIF1/GS or presents a CE-derived scene. A separate blue-clear diagnostic proves GS video/present only. Do not interpret the snapshot marker or the clear test as scene rendering.

## Current evidence and what it proves

### Step 11 — tick ordering and determinism

- The plan records source-extracted CE `game_tick()` and `game_time_update()` fixtures, scheduler multiplicities 0/1/3/capped-7, source-order checks, repeatable stubbed state/RNG hashes, and one real `units_update()` timer phase. Those checks support scheduler and phase-order claims, but not full integrated gameplay determinism ([M3 plan, Steps 11–12](../../plans/7.hcu-remake-m2-m4.md#L387-L412)).
- CE's actual `game_tick()` executes unit, AI, pre-player, effects, first-person weapon, game-engine, HaloScript, object, post-player, HUD and player-effect phases in a fixed order ([`game.c:334-410`](../../submodules/halo-ce-universal/source/game/game.c#L334)). The PS2 port's trace counter is advanced at tick entry ([`game.c:348-351`](../../submodules/halo-ce-universal/source/game/game.c#L348)); that counter alone does not certify the state mutation performed by the phases.
- The CE scheduler can run zero or more fixed ticks for an outer frame; the main loop updates player control before `game_time_update()`, then may draw afterward ([`main.c:3688-3738`](../../submodules/halo-ce-universal/source/main/main.c#L3688)). Thus polling once per frame and simulation tick multiplicity are separate semantics, and both must be composed in parity evidence.
- Current tick fixtures source-extract substantial control-flow bodies but leave almost all stateful simulation callbacks stubbed. The added real unit timer phase is meaningful, but is only one small phase and is not a player, object, movement, AI, collision, projectile, or weapon state trace. This limitation is already acknowledged by the plan and remains valid.

### Step 12 — input boundary

- The real CE `input_frame_begin()` calls `ps2_input_poll_devices()` before `input_get_device_states()` and marks the frame active afterward ([`input_xbox.c:710-723`](../../submodules/halo-ce-universal/source/input/input_xbox.c#L710)). The parent-to-CE bridge and tests cover four logical pad samples plus press/held/release/disconnect/reconnect transitions, according to the current plan entry ([`plans/7.hcu-remake-m2-m4.md:404-408`](../../plans/7.hcu-remake-m2-m4.md#L404)).
- The production main loop calls `input_frame_begin()` once before per-frame control and later calls the scheduler ([`main.c:3613-3618`](../../submodules/halo-ce-universal/source/main/main.c#L3613), [`main.c:3692-3708`](../../submodules/halo-ce-universal/source/main/main.c#L3692)). This establishes the sampled-input boundary in source. It does not prove a real hardware or PCSX2 pad transition was consumed by CE gameplay during catch-up ticks; no guest/device capture is recorded in the plan.
- Halo-64's frame adapter is a useful structural comparison: it keeps CE-facing frame/camera/first-person/HUD state in an adapter while actual drawing lives in a distinct N64 renderer ([`n64_render_game.c:2-8`](../../submodules/halo-64/port/n64/game/n64_render_game.c#L2), [`n64_render_game.c:517-546`](../../submodules/halo-64/port/n64/game/n64_render_game.c#L517)). Its N64 decisions and cuts are not PS2 requirements; the useful precedent is explicit separation of CE state adaptation and platform drawing.

### Steps 13–14 — snapshot producer/consumer and immutability

- The PS2 CE adapter advances `render.frame_index`, selects the first valid non-console window, updates first-person pose, copies camera and object matrices into a bounded pointer-free snapshot, commits it, and calls `hcu_render_snapshot_publish_dma()` ([`ps2_render.c:94-124`](../../submodules/halo-ce-universal/port/ps2/src/ps2_render.c#L94), [`ps2_render.c:126-216`](../../submodules/halo-ce-universal/port/ps2/src/ps2_render.c#L126)). It captures only one selected camera/window per call; multi-view rendering is not implemented by this adapter.
- The parent owns two caller-backed banks and a DMA payload. Commit validates bounds/finite transforms and publishes a monotonically increasing sequence, while the producer rejects over-capacity object/node counts ([`hcu_render_snapshot.c:28-65`](../../src/stream/hcu_render_snapshot.c#L28), [`hcu_render_snapshot.c:112-157`](../../src/stream/hcu_render_snapshot.c#L112), [`ps2_render.c:191-215`](../../submodules/halo-ce-universal/port/ps2/src/ps2_render.c#L191)). The matrix packing path makes a bounded VIF `UNPACK V4-32` payload ([`hcu_render_snapshot.c:197-265`](../../src/stream/hcu_render_snapshot.c#L197)).
- `tests/test_hcu_render_frame_invariance.py` compiles the exact extracted `render_frame()` body with immutable CE-shaped mock object records/matrices. It runs zero, one, and two render calls, checks two mock object transforms and source bytes, and confirms CPU DMA packing. It does not execute CE's actual object array/iterator or tick, deletion/reuse, map unload, a target chain, or GS rendering ([`test_hcu_render_frame_invariance.py:32-44`](../../tests/test_hcu_render_frame_invariance.py#L32), [`test_hcu_render_frame_invariance.py:165-201`](../../tests/test_hcu_render_frame_invariance.py#L165)).
- Separate snapshot tests validate matrix conversion and storage/binding. They do not jointly prove that a published bank remains unchanged while a renderer reads it through the supported lifetime, that a stale bank/generation is rejected, or that render cadence leaves a game-tick state hash invariant. The two-bank contract says consumers may retain a pointer only until two later frames; there is no consumer-side lease/fence API in the present public interface ([`hcu_render_snapshot.h`](../../src/stream/hcu_render_snapshot.h), [`hcu_render_snapshot.c:49-81`](../../src/stream/hcu_render_snapshot.c#L49)).
- No production consumer currently reads snapshot data and submits it as a BSP/object render chain. The plan and render reports correctly say that the `snapshot-dma qwords=5` guest marker proves CPU preparation only. The existing visual clear diagnostic initializes video and presents a blue clear but is not a CE scene consumer ([`plans/7.hcu-remake-m2-m4.md:417-435`](../../plans/7.hcu-remake-m2-m4.md#L417)).
- Halo-64 further demonstrates that the adapter boundary includes more than transforms: its frame adapter gathers visible objects once for views, updates camera/window state, invokes per-view rendering, first-person drawing and particles, and calls the HUD adapter ([`n64_render_game.c:314-325`](../../submodules/halo-64/port/n64/game/n64_render_game.c#L314), [`n64_render_game.c:517-546`](../../submodules/halo-64/port/n64/game/n64_render_game.c#L517), [`n64_render_game.c:669-686`](../../submodules/halo-64/port/n64/game/n64_render_game.c#L669)). The PS2 port need not copy its renderer or resource budgets, but it should explicitly enumerate which CE state must cross the PS2 snapshot boundary and which remains platform-owned.

## One concrete, non-overlapping next slice

Add a test-only integration harness and report (no M2 service changes) that composes the existing test mechanisms:

1. Reuse the source extraction in `test_hcu_game_tick_fixture.py` and `test_hcu_game_time_scheduler.py`, but replace a small, deliberately selected set of stubs with actual CE owners that can be initialized without a retail map. At minimum, include real tick counter/timing state and one stable CE object datum whose authoritative transform is mutated by the chosen actual phase; document every remaining stub rather than calling the result full gameplay.
2. Feed one deterministic `input_frame_begin()` sample through the existing PS2 pad bridge, then request a controlled scheduler sequence. Record canonical hashes and named counters after each requested tick; zero scheduled ticks must leave simulation state unchanged, and N scheduler ticks must execute the selected actual phase exactly N times.
3. Between the same tick checkpoints, call the extracted production `render_frame()` zero, one, or multiple times, with changing render-only camera/window data. Hash only authoritative CE simulation state (object datum, tick-owned gameplay fields, RNG) separately from presentation state. The simulation hashes must match across the three schedules; snapshot sequence/frame data may differ as expected.
4. Read and checksum the previously published bank immediately after the next commit, then after the second subsequent commit. Assert the documented two-bank lifetime precisely: no mutation before it expires; on expiry require callers not to hold the pointer (or add a generation/lease mechanism in a later implementation task). Include empty-object, maximum-object, overflow-rejection, invalid-matrix, and unbound-snapshot cases with clear expected publication/sequence outcomes.
5. Keep this as host integration evidence, not an EE/guest pass. Follow it only after M2 admits a retail gameplay BSP; then repeat the same canonical trace on the exact combined ELF in PCSX2 with deterministic pad injection and capture the state/hash markers. Do not bypass Step 10's capacity/load gate to obtain a visual result.

This is a focused advance because it touches only the M3 harness/tests and does not alter map-service ownership, M2 capacity, CE simulation ordering, or PS2 renderer allocation. It closes the most direct evidentiary seam between Steps 11/12 and 13/14 while preserving the plan's dependency order. A later, distinct renderer task must solve the `dma_commands` allocation/fencing issue, create a real snapshot consumer, and render an accepted gameplay BSP; those changes are not part of this test slice.

## Risk and acceptance notes

- Do not equate render-time first-person pose update with tick-time weapon simulation. CE `game_tick()` has a seeded-RNG lock around first-person weapon update ([`game.c:385-389`](../../submodules/halo-ce-universal/source/game/game.c#L385)); PS2 `render_frame()` separately invokes `first_person_weapon_render_update()` after camera selection ([`ps2_render.c:142-146`](../../submodules/halo-ce-universal/port/ps2/src/ps2_render.c#L142)). Tests should hash the intended authoritative/tick-owned state separately from render pose state.
- Existing Step 13 diagnostics establish a working video/GS clear path, not a normal-game output path. A black UI map viewport remains unsurprising while no scene consumer and gameplay BSP are present.
- M3 still depends on M2's accepted gameplay-BSP residency before collision parity and rendered-scene acceptance. Halo-64 is comparison evidence for adapter structure only; do not transplant its N64 limits, reduced AI/scripts, or renderer.
