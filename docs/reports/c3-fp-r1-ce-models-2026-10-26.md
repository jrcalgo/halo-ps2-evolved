# C3 first-person weapon / hands model path audit (R1) — 2026-10-26

## Finding (revised after R2 runtime palette evidence)

R1's camera-space/world-space claim is **retracted**. The independent retained-runtime audit in [`c3-fp-r2-depth-contract-2026-10-26.md`](c3-fp-r2-depth-contract-2026-10-26.md) parsed all eight canonical snapshots (82,912-byte v5 structure). The view camera is at `(105.026, -162.209, 0.641)` with non-identity forward and vertical FOV `0.5779`; the weapon palette root stays near identity basis, scale `1`, translation `(0.176, -0.047, -0.036)`, while the hands root is independently near origin. These observations establish camera-local palette values for the retained C3 captures. The existing `hcu_render_first_person_world` camera transform is therefore appropriate; do not remove it.

The most concrete model-pose defect candidate is **missing inverse-bind application**. PS2 MODL vertices are explicitly documented by `tools/halo2ps2/modelconv.py` as bind-pose model-space vertices, with skin transform `world(node, pose) * inverse(world(node, default pose))`. The parent renderer's standalone pose helper applies the model node's inverse bind after animation, at `halo-ps2/engine/src/sim/objects.c:103-117`; CE model rendering also multiplies each posed node matrix by the model node inverse at `halo-ce-universal/source/models/models.c:1028-1038`. In contrast, active CE first-person export remaps graph `node_matrices` directly to each model's node order (`first_person_weapons.c:874-974`, helper at `:2581-2608`), and HCU's `pose_fn` installs each resulting matrix as both `out->skin` and `out->world` (`src/stream/hcu_render_objects.c:1464-1470`). There is no per-model inverse-bind multiplication in that active FP branch. This is a strong, minimal, falsifiable candidate for giant/intersecting deformation where the graph pose matrices are absolute posed-node transforms rather than already bind-relative skin transforms.

It remains a candidate rather than a proven runtime cause: the CE publisher's remap helper is assignment-only, but R2's local-looking root alone does not prove whether the node matrix array was converted earlier to bind-relative matrices. Before changing it, capture palette nodes 1–2 and compare `exported_node` to `posed_model_node * model.runtime_default_inverse_matrix` and to the current exported matrix, for both arms and gun. Forcing a second inverse-bind when the CE nodes are already bind-relative would be wrong. No actual MODL node inverse matrices, per-vertex ranges, or source retail asset bytes were available in this audit.

A separate projection candidate has now been checked against the actual stock projection contract and ruled out for the retained configuration. CE's Xbox model renderer wraps first-person model geometry with `viewmodel_projection_begin/end` (`rasterizer_xbox_models.c:615-654`), but the hook changes the FOV only for an explicit `display.viewmodel_fov` override or a widened `display.fov`; its default path leaves the camera unchanged (`port/linux/game/view_fov.c:196-234`). The stock PS2 hook is pass-through (`port/ps2/src/ps2_render.c:1269-1277`) and this snapshot has no viewmodel FOV override field. Its `0.5779` value is vertical (33.111 degrees), matching CE's 50-degree observer angle after `2*atan(.75*.85*tan(observer_fov/2))`. CE's projection builder and HCU's vertical-to-horizontal conversion yield the same coefficients: at the 4:3 view aspect, CE `x/y = (2.52296197, 3.36394929)` and HCU/PS2 `x/y = (2.52296197, 3.36394929)`. Thus the same corrected model vertices project identically under the CE stock view and current parent world camera; projection mismatch does not account for the oversized/off-right capture. See the detailed equations in [`c3-fp-i1-pose-2026-10-26.md`](c3-fp-i1-pose-2026-10-26.md). R2 owns the separate near/far/depth/wall-clipping implementation guidance.

The CE-to-snapshot wire conversion itself preserves `scale`, axes and translation without a multiplier; captured root scales are 1.0. There is no evidence for a global numeric scale fix or a weapon-specific offset. Keep the weapon and hands models as independent palettes and retain the parent camera transform.

## Active CE producer and palette construction

- `submodules/halo-ce-universal/source/interface/first_person_weapons.c:653-673` calls `first_person_weapon_build_node_matrices` during render update.
- `:1283+` samples CE graph node orientations and calls `animation_graph_node_matrices_from_orientations(..., &render.camera.position, &render.camera.forward, &render.camera.up)` at `:1696-1703`. Although this helper signature appears world-rooted, R2 snapshots show the matrices copied into the FP palettes are camera-local; source call alone is insufficient to infer final palette contract.
- On PS2, `submodules/halo-ce-universal/port/ps2/src/ps2_render.c:1321-1337` makes `render_interpolation_first_person` a no-op; no interpolation rewrite should explain scale.
- `first_person_weapon_copy_render_models` (`source/interface/first_person_weapons.c:874-974`) preserves CE visibility/equipped weapon/animation decisions, obtains weapon `first_person_model`, independently obtains scenario `hands`, validates node counts, then invokes `model_remap_node_matrices_to_match_animation_graph` separately for each model. This is the correct shape of a two-model pose export; do not merge hands and gun into one offset/root.
- `submodules/halo-ce-universal/port/ps2/src/ps2_render.c:1032-1104` appends gun and hands palettes to separate ranges in `halo_ps2_frame_snapshot.palette`, records each tag resource slot independently, and sets first-person view flag.
- Parent selection at `src/stream/hcu_render_objects.c:322-376` resolves each slot against resource generation, model identity and exact model node count. Model misses or node-count mismatch fail closed; no evidence of silently reusing a world weapon pose.

## Active parent consumer and transform

- `hcu_render_objects_select_first_person` reads two independent first-person resource/palette ranges (`src/stream/hcu_render_objects.c:342-348`).
- Per-model submission at `:1910-1970` builds root from palette node zero, sets `SKINNED | CAMERA_LOCAL`, and runs `obj_render_pass` once per model. `pose_fn` (`:1423-1466`) applies `hcu_render_first_person_world` to **every node in that model's palette**, then assigns converted matrix to both skin/world node arrays. Weapon and arms are separate submissions, same camera and function.
- `hcu_render_first_person_world` (`:589-619`) computes left = camera up × forward, uses camera F/L/U as axes, transforms local basis and position, preserving `local.scale`. It is a camera-local-to-world composition. R2 runtime palettes validate this use for captured runs; retain it.
- `hcu_render_snapshot_matrix_from_ce` (`src/stream/hcu_render_snapshot.c:146-176`) copies CE `{scale, forward, left, up, position}` to the parent `mat4`, multiplying basis by scale once and leaving translation unchanged. No 1024↔1 world/model unit factor appears here.
- The renderer `mat_from_snapshot` similarly maps each basis row and position; first-person-specific code does not introduce a global scalar. `mi.radius * palette[0].scale` is for projected LOD/culling only, not vertex transforms.

## Halo 64 comparison and limits

Halo 64's `port/n64/src/n64_render.c:3570-3576` converts CE-style matrix basis by `axes = m[0] * (WORLD_SCALE / MODEL_SCALE)`, then translations by `WORLD_SCALE`. `WORLD_SCALE=64`, `MODEL_SCALE=1024` (`:39`, `:334`). Its model-space vertex pipeline therefore explicitly pairs vertices stored in model units ×1024 with matrix scale and world units ×64. Parent PS2 MODL rendering converts decoded chunk positions / matrices under its own `model.c` and must honor corresponding MODL units; this audit found no project evidence that the current PS2 loader is applying the halo-64 scalar to a differently normalized model format. The existence of that conversion is a reason to inspect vertex and bind-pose units in actual models, not proof of a 16× error.

Halo 64 renders first-person under an explicit first-person viewport (`n64_render_first_person_begin` near `:3257`, perspective near `:3273`, first-person flag before phase draw). It avoids world-object distance culling for FP (`render_object` skips that block when `renderer.first_person`) but still converts nodes with the same model/world scale. This is relevant context; separate pass depth/FOV requirements are owned by the other research report.

## Implementor-ready minimal plan

1. Capture CE source graph node matrices and the published weapon/hands palettes at nodes 0, 1, 2, plus each MODL node's default inverse matrix, names/parent indices and captured model id. For each model test whether `published[i]` already equals `posed_model_node[i] * inverse_bind[i]`.
2. If capture shows the palettes are raw posed-node matrices, apply the matching model-order inverse-bind matrix exactly once while exporting/consuming each model palette. Keep the CE camera-local root and parent `hcu_render_first_person_world` composition. Do not apply a second inverse-bind if the published matrix is already relative.
3. Capture MODL vertex AABB from decoded batch positions and skin influence node ids/weights, and compare with CE vertex/tag bounds where available. Do not patch vertex/model scale absent a numeric mismatch.
4. Separately compare current 33.1° snapshot FOV and CE authored viewmodel FOV at same viewport/aspect; use the same camera-local pose and asset, measure screen-space weapon/hands bounds. Treat this as projection investigation, not pose correction. Wall depth/near clipping is separate R2 work.

## Fixtures and capture tests

- Bind-pose fixture: build a 2-node model with non-identity bind translation/rotation; use non-bind pose node matrices. Verify expected skin matrix is `posed_world * inverse(default_world)` and maps a bind-space test vertex to its expected posed position. Include identity bind pose to prove no accidental extra inverse.
- Palette contract fixture: root and nodes must be camera-local, scale 1; applying parent camera composition once must match expected screen/world matrices for camera origin/yaw changes. Include non-origin camera and yaw ±90°.
- Scale invariant: node 0/child scale 1 and orthonormal basis; adapter retains scale exactly once. Inject scale 2 to confirm no squared factor.
- Two-model fixture: weapon node count N and hands count M with distinct node ordering, distinct remap table, and separate first/count ranges; assert parent selection binds each MODL resource and exactly the matching palette count and no cross-range overlap.
- Capture matrix across at least neutral camera, yaw ±90°, pitch, non-origin camera, weapon switch, reload/sway animation, and two-player split views. Record weapon and arms projected bounding boxes separately; compare CE authored bounds/tag hashes and exported matrices. Acceptance: orientation/scale stable across camera motion, weapon/hands remain independently animated, no topology or transform jump on switch.
- Do not accept a single map/gun fixed offset as a correction. Test multiple stock weapons that have valid FP model+graph and at least one arms model.

## Evidence boundary

This remains a source audit. R2 supplies actual camera-local palette evidence across eight canonical snapshots. `docs/reports/c3-object-sharing-ab-2026-10-25.md` reports giant/intersecting FP geometry in both arms of its cache A/B; that isolates away the world-object cache toggle, not the FP cause. The leading pose hypothesis is missing inverse bind, to be checked against captured CE palettes and private model metadata; the projection mismatch is plausible but unmeasured. No specific numeric model unit/scale or weapon offset is justified.
