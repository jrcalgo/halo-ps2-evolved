# M2 CE UI unload/reload diagnostic: build seam and lifecycle recommendation

## Finding

The safest implementation is an explicitly selected, compile-time diagnostic variant of the *combined gameplay machine ELF*. Gate the CE test helper with a dedicated define such as `HALO_PS2_M2_UI_LIFECYCLE_TEST`; never put that define in the normal `port.json` profile and never change the memory-map capacities for this test. Compile the variant into a separate closure/output directory, pass its `rooted.o` and PS2 port objects into the parent-link probe, and emit a dedicated lifecycle marker only after the full unload/reload checks pass. The default production/diagnostic build remains unchanged.

Run the test after the initial local-game/menu setup has completed and before the steady main loop begins. The CE path already has a same-map unload/reload protocol: `main_load_ui_scenario()` preflights the UI map, unloads the old map and disposes its map state, then loads the UI scenario through the normal CE path. The HCU parent service explicitly stages a same-map reload request before release and performs full package/source validation again after the owner has been released. This exercises the relevant production lifecycle rather than a synthetic call into the loader.

The test should prove CE state *and* parent-owner state at each boundary. `game_map_loaded()`, `global_scenario_try_and_get()`, and `cache_files_precache_map_loaded()` can establish CE map/tag publication state, but they cannot prove the parent arena returned to its boot baseline or that the retained source reader/descriptor has the expected lifetime. Add diagnostic-only state reporting at the parent map-service boundary (map-arena `used`/`high`, `mount.active`, `source.active`, reader descriptor, staged/reload flags; optionally outstanding file-bridge slots). Do not infer a baseline from the success marker alone.

This is M2 UI lifecycle evidence only. It does not qualify gameplay-map capacity, visible scene rendering, or the M2 exit gate.

## Source-backed lifecycle path

1. The combined EE entry initializes the map service and then calls CE’s shell entry. `hcu_main()` calls `halo_shell_main()` after memory, pads, storage, map service, and asset-probe setup; the CE shell starts `main_loop()`. See [`src/stream/hcu_main.c`](../../src/stream/hcu_main.c#L220-L275) and [`submodules/halo-ce-universal/source/shell/shell_xbox.c`](../../submodules/halo-ce-universal/source/shell/shell_xbox.c#L105-L135).
2. `main_loop()` calls `game_initialize()`, then `main_setup_connection()`, then `main_initialize_time()` before entering the loop. On a fresh local-menu launch, `main_setup_connection()` selects the menu and `main_menu_load()` loads the UI map. This makes the post-setup/pre-loop point a deterministic, non-recursive place for a test-only round trip. See [`main.c`](../../submodules/halo-ce-universal/source/main/main.c#L2838-L2865) and [`main.c`](../../submodules/halo-ce-universal/source/main/main.c#L3430-L3458).
3. `main_menu_load()` loads the UI scenario only when `main_menu_scenario_loaded` is false, then loads menu-shell resources and restarts the map-time/script runtime. `main_menu_unload()` stops menu music, deactivates the menu, and clears that loaded flag. See [`main.c`](../../submodules/halo-ce-universal/source/main/main.c#L1118-L1144).
4. `game_unload()` calls `scenario_unload()` only for a loaded map. `scenario_unload()` first unloads tags and clears CE scenario/BSP globals; only after those pointers have been unpublished does it call `ps2_cache_release_map_owner()`. Then `game_unload()` clears `map_loaded`. `game_dispose_from_old_map()` releases per-map subsystem state and sets the CE game inactive. See [`game.c`](../../submodules/halo-ce-universal/source/game/game.c#L741-L773), [`scenario.c`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L364-L389), and [`game.c`](../../submodules/halo-ce-universal/source/game/game.c#L933-L973).
5. The reload enters `main_load_ui_scenario()`. Its PS2 preflight runs before teardown. For the exact already-mounted UI package, `hcu_map_service_preflight()` stages `reload_pending` without overwriting the live arena. The subsequent CE unload invokes the parent unloader; after release, `map_loader()` reopens/revalidates the source before remounting. This is the intended preflight → unload → owner release → validate/remount sequence. See [`main.c`](../../submodules/halo-ce-universal/source/main/main.c#L1913-L1957), [`hcu_map_service.c`](../../src/stream/hcu_map_service.c#L81-L149), [`hcu_map_service.c`](../../src/stream/hcu_map_service.c#L152-L167), and [`hcu_map_service.c`](../../src/stream/hcu_map_service.c#L202-L236).
6. `ctag_mount_unload()` unmounts the cache before closing its retained reader and returning the owner arena to its recorded mark. Its sequence is the owner-level behavior to observe, not alter. See [`ctag_mount.c`](../../src/stream/ctag_mount.c#L277-L290). The PS2 cache’s `cache_files_precache_map_loaded()` reports whether the named UI map is actually mounted, and the CE `game_load()` emits `m2-ui-map-loaded` only after `scenario_load()` succeeds. See [`ps2_cache.c`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L287-L294) and [`game.c`](../../submodules/halo-ce-universal/source/game/game.c#L609-L645).

## Minimal change surface

Keep the implementation narrow and diagnostic-only:

- **CE lifecycle test helper:** in `submodules/halo-ce-universal/source/main/main.c`, under `#if defined(HALO_PS2) && defined(HALO_PS2_M2_UI_LIFECYCLE_TEST)`, add a helper called once after `main_setup_connection()` and `main_initialize_time()` in `main_loop()` and before the loop begins. Do not call `main_load_ui_scenario()` recursively and do not manually unload before preflight. For two bounded cycles, validate the loaded UI state, call `main_menu_unload()`, then call `main_menu_load()`. This is the important production ordering: `main_menu_load()` invokes `main_load_ui_scenario()` when the menu flag is false; that function preflights *while the old UI owner is still mounted*, then performs `game_unload()` and `game_dispose_from_old_map()`, and only then remounts. Validate successful UI reload, initialized map state, and the same fixed region bases/capacities after each call. Let the helper’s compile-time guard make the normal build a no-op with no added runtime branch.

Use it before release, after release, and after remount. The harness currently knows `playable`, `m3-memory-ready`, `m1-boundary`, and `m2-ui`; it does support an explicit success-marker override, but a named stage yields clearer, stable evidence metadata. Keep the ordinary `m2-ui` marker semantics unchanged. See [`test_hcu_boot.py`](../../tools/test_hcu_boot.py#L45-L51) and [`test_hcu_boot.py`](../../tools/test_hcu_boot.py#L354-L397).
- **Tests:** add host tests for profile routing/manifest and output isolation, test-helper compile guards and cycle assertions, parent snapshot state transitions, and harness stage parsing. Run them without disturbing the standard build outputs. Then run the exact combined lifecycle ELF in PCSX2 interpreter and recompiler, binding both results to ELF/source/asset/settings hashes.

The test define has to reach HCU’s source compile in the closure tool.

## Evidence and exit checks

The diagnostic build must fail closed and must not claim success if any assertion fails. At minimum, retain a per-cycle trace with:

| Boundary | CE state expected | Parent owner state expected |
|---|---|---|
| Start | `game_map_loaded()` true; menu-scenario flag true; scenario getter non-null; UI cache reports loaded | mounted owner true; map arena used/high captured; source reader active with a valid descriptor |
| During each unload, before remount | `game_map_loaded()` false; scenario/BSP pointers null; UI cache reports not loaded | `mount.active == 0`; source inactive/descriptor closed; map arena `used` restored to its pre-mount mark; the same-map deferred request may remain staged until the validated reload completes |
| After reload | all start-state checks restored; successful `m2-ui-map-loaded` for this load | same base/capacity; used equals the stable UI map footprint; high-water does not climb on identical reloads; descriptor count is bounded and stable |

Use an unchanged `config/memory-budget.json` and memory-map hash. No arena-capacity edit is needed: the test loads the same UI assets and exercises existing owner release/reuse. If current per-cycle state is not observable through public APIs, add only read-only test diagnostics at the owning layer; do not expose parent arena internals by making HCU authoritative over those arenas.

For execution, build the distinct combined image, confirm its hash and source pins in the probe result, then run it in both PCSX2 modes using `--stage m2-ui-lifecycle`, the test ELF, and the UI data root/ISO. Require both the completion marker and a fault-free stability interval afterward. Confirm every cycle marker occurs the expected number of times and no failure marker appears. Do not accept `m2-ui-map-loaded` by itself as the lifecycle pass; do not require a rendered image here. The project-plan context already marks CE-global unload/reload as absent/required for M2 Step 2 and warns that the black UI capture is not rendering proof: [`plans/7.hcu-remake-m2-m4.md`](../../plans/7.hcu-remake-m2-m4.md#L181-L195) and [`plans/7.hcu-remake-m2-m4.md`](../../plans/7.hcu-remake-m2-m4.md#L458-L495).

## Hazards to avoid

- Do not set `HALO_PS2_M2_UI_LIFECYCLE_TEST` in the normal manifest defines or HCU prefix. That turns a supposedly opt-in diagnostic into default boot behavior.
- Do not reuse `all-no-bootstrap-memory` for a differently compiled `main.c`. Its `rooted.o`, `result.json`, and object hashes would become ambiguous, and `hcu_parent_link_probe.py` could combine test and default inputs.
- Do not invoke `main_load_ui_scenario()` directly twice: its assertion requires `main_menu_scenario_loaded == FALSE`, it runs game-engine transitions, and it is normally orchestrated by `main_menu_load()`. Call `main_menu_unload()` then `main_menu_load()` so the normal PS2 preflight occurs before `game_unload()` and owner release.
- Do not call `game_unload()` after changing the parent arena or before CE unpublishes scenario/tag globals. Existing `scenario_unload()` deliberately clears globals before releasing their CTAG owner.
- Do not forcibly clear `reload_pending`, remount over an active owner, or manually rewind an arena. The parent service intentionally rejects an active-owner reload and validates again only once CE has released the owner.
- Do not treat the full CTAG mount footprint as a leak: require `used` to return to its recorded baseline after unload, and compare the post-reload footprint/high-water against the first successful UI load. `high` is a high-water measure and is expected to remain elevated after release.
- Do not infer descriptor closure from `hcu_file_bridge` slot count alone. The map mount keeps a `ctag_map_source` reader context until owner unmount; instrument/check that ownership path separately.
- Do not interpret a passing lifecycle marker as visible rendering or as proof that Blood Gulch/other retail maps fit current EE regions. M2 still requires a qualified gameplay map and its measured high-water/capacity plan.

## Recommendation

Proceed with a separate closure profile and combined gameplay ELF; place the opt-in test hook after successful initial connection setup and before the first normal main-loop iteration. Prefer two real UI unload/reload cycles to a direct synthetic mount test, because that reaches the same CE lifecycle and HCU owner protocol while remaining well within the existing UI-only memory envelope. Add owner snapshots before coding the test, since the current CE-visible getters alone cannot demonstrate the required parent arena/descriptor baseline. Keep the default ELFs and arena capacities untouched, run the dedicated variant through both PCSX2 modes, and label the result strictly as UI lifecycle evidence.

## Dated addendum: M2 Step 10 next capacity slice (2026-10-21)

### Decision in brief

The successful Step 9 UI lifecycle round-trip is now useful evidence for the *owner transition* (two cycles pass in both PCSX2 modes), but it does not remove any gameplay-map capacity blocker. The smallest defensible production slice is a **Longest-only, fail-closed vertical loader path** that keeps the configured regions and reserve unchanged, keeps the non-UI catalog guard closed by default, and is enabled only in a separately identified capacity-test profile. It must remove full-payload staging for both CTAG and the selected CBSP, retain only bounded CRNG/CBIX metadata, and use the existing fixed CE tag-cache/BSP destinations. There is no safe one-file or one-buffer tweak that makes a gameplay map fit: CTAG and CBSP are independent staging bottlenecks, and the renderer's map assets remain unaccounted.

Treat all figures below as candidate bounds, not proof of a loaded or rendered map. The current `current_bsp` region is 6,291,456 bytes (`config/memory-budget.json:12`); the boot binder partitions it into a tag span followed by the BSP tail (`src/stream/hcu_memory_bind.c:41-56`), while `hcu_main.c` still requests a 2 MiB tag cache (`src/stream/hcu_main.c:16-18,174-183`). A Longest-only split needs at least the 4,263,624-byte complete CTAG image and 374,784-byte raw active BSP, rounded/aligned with canaries and loader-owned metadata measured separately. The reviewed 4,477,120-byte tag / 1,814,336-byte BSP split is a more conservative *two-map arithmetic candidate* for Longest plus Blood Gulch, not an accepted topology; it still does not solve campaign missions or runtime assets (`docs/reports/m2-next-capacity-design-review.md`, “Provisional boot-fixed tag/BSP split,” especially rows at lines 194-207). Do not change `config/memory-budget.json`, spend its 5,767,168-byte reserve, shrink CE data, or imply full product support.

### Exact state and source-backed gap

The latest on-disk combined gameplay ELF is SHA-256 `ec3a127f3afc867645fc7c2ddb7b11fa68e0b9fe1e62a5cd68efd5ed59febbf8`; the exact parent/HCU/halo-ps2 commit pins are `70e2ed0cf2145a45d23aa07414a3a88c05155d4c`, `6933490b2d16bb1c637295b6a0f3880ba23a7d56`, and `71183bb0a9adc586cd267b2780c82bbc12cfd95b`. This is the ordinary UI-capable ELF, not a gameplay-map run. The exact `memory-budget.json` SHA remains `67ef6d6085de71c22e3998a355cb2f79a8123837b7b14e89593a0d497de21b74`.

One important refinement to the earlier streamed-CTAG design: the current `halo-ps2` section loader already reads/decodes HP2 data with a bounded history/input/output workspace (64 KiB + 16 KiB + 16 KiB), so it no longer needs a full `stored_size` staging buffer. It still reserves the **entire `raw_size` output** in the owner arena and writes the decoded section there (`submodules/halo-ps2/engine/src/world/section.c:57-106,129-146`). Therefore it is bounded in decoder scratch, but not in section output residency. A CTAG sink/visitor API is still necessary to direct the compact tag image to the fixed CE cache instead of retaining multi-megabyte raw CTAG in `streaming`.

The actual runtime call graph makes this separation explicit:

1. `hcu_map_service_preflight()` still rejects non-UI maps as `capacity-not-qualified`, then decodes whole HMAP, CTAG, CRNG, and CBIX outputs into `streaming` before validating them (`src/stream/hcu_map_service.c:202-295`, rejection at `:214-224`). This must remain fail-closed until the vertical slice passes.
2. `ctag_mount_hp2_internal()` retains full decoded CTAG and CRNG buffers in the map-owner arena for the mount lifetime (`src/stream/ctag_mount.c:112-173`); the BSP-catalog wrapper similarly retains decoded CBIX (`src/stream/ctag_mount.c:199-235`). The resource index/source lifetime is real CE cache behavior, so these payloads cannot just be released without replacing them with validated compact records/descriptors.
3. CE already requests tag bytes at the final fixed tag-cache pointer, and `ps2_cache.c` materializes CTAG there before completing the synchronous read (`submodules/halo-ce-universal/port/ps2/src/ps2_cache.c:358-397`). CTAG validation/fixups belong in HCU's PS2 cache/tag adapter; CE continues to own the published tag state and its validation. The cache must not report read success until stream CRC, CTAG validation, relocations, and destination bounds all pass (`submodules/halo-ce-universal/source/cache/cache_files.c:1260-1329`).
4. `ctag_mount.c:67-104` currently asks the shared `world_load_section_with_scratch()` to load a complete CBSP payload into `frame_scratch` before CE materialization. The new loader additionally needs 98,304 bytes of decoder work, so even the Longest 377,388-byte CBSP envelope cannot coexist with its 393,216-byte scratch region using the current whole-output API. Blood Gulch's raw B000 is 1,303,092 bytes and is a stronger negative case (`docs/reports/m2-step7-retail-cbsp-validation.md:10-17`). Separate CBSP stream validation/materialization is mandatory; CTAG streaming alone cannot get to gameplay BSP publication.
5. The same-map unload/reload protocol now has a passing clean-cycle trace, but it is destructive after the old map releases the one fixed destination: source I/O or validation failure during post-unload materialization must result in an explicit no-map/menu-safe state and retry, not restoration of overwritten old tag bytes (`src/stream/hcu_map_service.c:99-149,152-172`; `scenario_unload()` ordering in `submodules/halo-ce-universal/source/scenario/scenario.c:364-406`).

`docs/reports/m2-streamed-ctag-destination-design.md` remains the API design evidence: it identifies the HP2 visitor, CTAG no-write verify pass, CE fixed-destination materialize pass, CRC/relocation obligations, and separate CBSP work. Its claims are design recommendations, not implementation proof. Also keep the reproducibility warning in `docs/reports/m2-next-capacity-design-review.md:20-31` in view: the report's schema ELF identity was historically different from the ELF at its recorded path. Before a target capacity run, regenerate or reconcile the CTAG/schema/BSP/package report bundle against one retained schema ELF and exact retail input hashes. Do not inherit mixed-hash size rows as an acceptance ledger.

1. **Freeze a map-specific evidence bundle before changing the path.** Rebuild the Longest HP2 package and all dependent CTAG image/schema, resource-index, CBSP catalog/materialization, and renderer pack audits against a single retained schema ELF and the exact `longest.map` hash. Record parent/HCU/halo-ps2 commits *and dirty source-file hashes*, package hashes, converter parameters, and the new combined ELF hash. Preserve stable bases after CE allocation; no late rebinding is allowed (`src/stream/hcu_memory_bind.c:41-71`; HCU PS2 memory bind contract in `submodules/halo-ce-universal/port/ps2/src/ps2_memory.c:91-110,147-155`). 6. **Add the CBSP streaming materializer as a separate owner path.** Verify the selected CBSP envelope and complete raw CRC before publishing; stream bytes into the unpublished fixed BSP destination with a bounded scratch window; validate CBSP image/relocation domains, bounds and CTAG string references with the existing C materializer as oracle (`submodules/halo-ce-universal/port/ps2/src/ps2_cbsp.c`, `ps2_cache.c:380-418`; `tools/cbsp.py`). ### Acceptance tests, risks, and prerequisites

**Prerequisites:** (a) one coherent retained map/schema/package artifact set; (b) passing host streamed-decoder parity and CTAG/CBSP failure-atomicity tests; (c) a reviewed boot-time tag/BSP split whose total remains inside current `current_bsp` and whose claims allocation remains in its existing owner; (d) measured compact CRNG/CBIX high-water; (e) full Longest parent renderer pack and audio/animation inventory; and (f) an isolated build profile and guest harness that bind all results to one ELF and pins. Step 9's UI lifecycle pass satisfies only the lifecycle-order prerequisite for a clean reload; it does not satisfy the gameplay/fault branch.

**Must-pass host and target tests:** byte-for-byte old/new HP2 decode parity for real UI/Longest/Blood Gulch sections; every existing CTAG/CBSP rejection branch; no destination writes during validation-only rejection; partial-write and late-CRC/relocation failure leaves CE completion false and no tag/BSP globals published; a full retry works; CRNG/CBIX extents match the legacy parsers; canaries and arena marks recover after every failure; simultaneous peak ledger includes source-hash scratch and decoder scratch without overlap. On guest, run same ELF/package in interpreter and recompiler, validate `structure_bsp_port_verify` and real CE query consumers, tick gameplay, and inspect parent snapshot/map identity. These are explicit gates, not tasks that host emulation can waive.

**Main risks:** fixed in-place destinations make post-unload failures destructive; two-pass verify/materialize can increase disc/USB reads and CPU time; SIF/FileXio short reads or source mutability between passes can invalidate preflight; changing tag:BSP split changes CE validation-claims size unless their sum stays fixed; large tag cache can leave a BSP too small; map-specific splits can make future map transitions impossible unless they are fixed at boot or all required maps share the same contract; CBSP pointer-domain fixups must keep CTAG-owned strings valid; one-map acceptance says nothing about campaign c20 or the 24-map set; and parent-render packs may dominate remaining EE/GS memory even after the CE tag path is streamed.

**Explicit non-claims:** this addendum does not assert that Longest fits; that a Longest CTAG/CBSP stream implementation exists; that any gameplay map loads in CE; that the parent renderer has Longest assets; or that anything is visible in PCSX2. It recommends a smallest testable path and its gates only. M2 Step 10 stays open and non-UI maps stay rejected until that evidence exists.
