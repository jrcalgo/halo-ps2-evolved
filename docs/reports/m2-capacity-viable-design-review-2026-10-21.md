# M2 capacity viable-design review — campaign residency

**Disposition:** No implementation-ready, evidence-backed design currently proves that every stock campaign map fits the PS2 EE budget while preserving current CE raw-pointer semantics, retaining all required behavior, and leaving the 5.5 MiB reserve untouched. A lossless typed lease for selected tag-data is the strongest measurable *experiment*, especially for `animation.data`; it is not an approved capacity solution. Its optimistic arithmetic leaves only about 2.4 MiB for all other live EE owners in the hardest post-externalization map, before any animation pages are pinned. Peak simulation/render/audio working sets and the animation active set are not measured, so fit is unknown and cannot be inferred.

This is strictly report-only. `plans/5.hcu-remake.md` governs scope and acceptance; `plans/7.hcu-remake-m2-m4.md` governs execution. No runtime/source, tests, budget, or shared plan were edited.

## Scope, current image, and per-map peak interpretation

The product remains all ten campaign missions, all thirteen stock multiplayer maps, local split screen, campaign AI/scripts/effects, and the stated cooperative scope; neither a reduced map set nor Halo-64/N64 pool policy is permitted ([`plans/5.hcu-remake.md`](../../plans/5.hcu-remake.md#L233-L269)). The M2 exit calls for stable load/unload baseline, no steady-state heap growth, measured per-region high water, untouched reserve, and a gameplay-map load after a valid capacity design; UI-only load is not sufficient ([`plans/7.hcu-remake-m2-m4.md`](../../plans/7.hcu-remake-m2-m4.md#L181-L189)).

The static per-map peak below means **one complete compact CTAG image plus the largest one-at-a-time raw CE BSP** for that map. It is a lower bound for supporting every referenced BSP, not a measured live-process peak. CE's scenario switch has one active BSP, while the entire tag image remains published; source review documents unload/load and global-pointer changes but no BSP demand paging ([`m2-2026-10-21-tag-residency-options.md`](m2-2026-10-21-tag-residency-options.md#L28-L38)). Encoded CBSP and CTAG are separate transient inputs; bounded HP2 decode may reduce that overlap but not the destination image.

The following calculation is intentionally optimistic. It assumes every measured `animation.data` payload byte can be removed from the compact EE CTAG image without changing its logical CE value, charges the reduced capacity-derived claims bitmap, and assumes **zero bytes** for an animation cache, metadata, page tables, staging, texture/lightmap residency, dynamic simulation, DMA, streaming, checkpoint, audio, frame scratch, parent packs, and transition overlap. The fixed subtotal is kernel/system `1,572,864` + ELF file bytes `2,086,532` + ELF `.bss` `2,114,588` + CE game-state `3,428,352` = `9,202,336` bytes ([budget review](m2-2026-10-21-budget-repartition-review.md#L19-L25), and its d20 bound at [L48-L72](m2-2026-10-21-budget-repartition-review.md#L48)). Claim bytes are recomputed from aligned tag and BSP capacities using CE's implementation, `ceil((tag_capacity+BSP_capacity)/32)*4` on PS2 ILP32 ([`tag_validate.c`](../../submodules/halo-ce-universal/port/linux/game/tag_validate.c#L244-L283)). “Headroom” below is the residual against the **entire** committed budget, so it is the maximum all-other-owner-plus-cache amount if no other bytes were omitted.

## Direct-pointer semantics: what is and is not pageable today

* `struct tag_data` and `struct tag_block` contain direct address fields. `tag_data_get_pointer()` validates bounds and returns pointer arithmetic from `data->address`; fast block access returns `block->address + index * element_size` ([`tag_groups.h`](../../submodules/halo-ce-universal/source/tag_files/tag_groups.h#L64-L145), [`tag_groups.c`](../../submodules/halo-ce-universal/source/tag_files/tag_groups.c#L91-L114)). Other CE paths dereference `.address` directly, so changing a central helper alone would not intercept all access.
* Cache loading reads the complete tag-data image to the bound contiguous cache, performs header and schema validation, then publishes `tag_header` and `global_tag_instances` ([`cache_files.c`](../../submodules/halo-ce-universal/source/cache/cache_files.c#L1258-L1310)). A partial page set cannot be published as a normal CE cache image under this contract.
* Scenario BSP load validates a complete BSP extent at the bound base, materializes internal and CTAG-name relocations, then installs `global_collision_bsp` and structure globals; switching unloads/loads complete BSP records ([`scenario.c`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L1120-L1183), [`ps2_cache.c`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L405-L457)). BSP3D, materials, leaves, PVS, paths, fog/weather, and sound cluster data feed gameplay/runtime; field report finds no whole BSP field family safely removable today ([`m2-step7-bsp-consumer-disposition.md`](m2-step7-bsp-consumer-disposition.md#L23-L79)).
* No transparent disk-backed raw-pointer path is evidenced. The PS2 FileXio reader seeks and copies bounded chunks into caller-provided EE buffers (`submodules/halo-ps2/engine/src/stream/file.c:143-169`, summarized with source citations in [`m2-2026-10-21-tag-residency-options.md`](m2-2026-10-21-tag-residency-options.md#L58-L66)). R5900 TLB mapping would not make DVD/IOP bytes directly CPU-addressable; data must be transferred to an EE buffer and cannot be evicted while a raw pointer remains live.
* Animation is the best quantified CE-owned tag-data candidate, but is not drop-in. `animation.data` is `_tag_schema_data`, and compressed validation reads its address before graph publication. Runtime uncompressed and compressed readers include `animation_get_frame_data()` and three direct calls in rotation/translation/scale helpers. Four-frame aiming-screen interpolation can retain four pointers simultaneously; `frame_info` and `default_data` are separate and must stay resident unless independently audited ([`animation-data-pointer-audit.md`](animation-data-pointer-audit.md#L1-L56), source lines in [`tag_schema_models.c`](../../submodules/halo-ce-universal/port/linux/game/tag_schema_models.c#L862-L933), [`model_animations.c`](../../submodules/halo-ce-universal/source/models/model_animations.c#L1867-L1888)). Across maps the audit counts 12,590 records / 60,788,194 bytes, maximum per-map payload 4,971,464 bytes in c10, and largest record 167,560 bytes, but does not measure a live set ([`m2-animation-data-contract-feasibility.md`](m2-animation-data-contract-feasibility.md#L38-L99)).

Therefore preserving every original raw pointer simultaneously is incompatible with paging these candidate bytes. A viable *behavior-preserving* architecture would require converting every pointer consumer into a typed lease or bounded whole-record view, while retaining current CE logical bytes, validation outcomes, and unload semantics. That can preserve Halo CE behavior, but it is not unchanged pointer semantics. Do not call it transparent streaming.

## Candidate assessment

### Strongest experiment: lossless `animation.data` lease

This candidate is strongest because its bytes are individually enumerated with source offsets and payload hashes, a complete field consumer list exists, and individual record maximum is bounded (167,560 bytes). It has up to 2.55–4.97 MiB/map of arithmetic candidate savings in campaign CTAG, enough to materially affect tag-image size if those bytes can stay off EE. The existing external resource mechanism proves only bounded byte reads for `TAG_SCHEMA_FILE_DATA`; `animation.data` is schema-owned in-image data, so conversion, schema validator, runtime readers, and cache lifecycle all need a new contract. Source-backed feasibility report explicitly rejects choosing a cache size from the largest record or stream arena capacity.

For the hardest residual map a10, complete animation externalization reduces the tag+BSP+claims+fixed-owner subtotal to 25,383,132 bytes, leaving 2,404,132 for all other owners and all simultaneously pinned animation data. This is **not enough evidence to fit**: the current named dynamic-simulation capacity alone is 2,621,440 bytes, and texture, DMA, streaming, audio, and scratch have nonzero roles, although their true simultaneous high-water/reclaimability is unknown. For d20 the corresponding residual is 2,751,784. Any runtime cache lowers these residuals further. The project must measure actual owner peaks rather than add nominal capacities mechanically or declare them unused.

Required risks to close: schema checks must parse compressed payloads from the same logical bytes before publishing tags; four interpolation pointers cannot be invalidated; multi-actor and 1–4 player simultaneous records may dominate the hot set; page-source I/O cannot stall the 30 Hz tick; cache eviction cannot occur while any derived pointer exists; file-source failure/corruption must preserve CE's deterministic failure behavior. This candidate is not presently supported as sufficient.

### BSP render-data replacement

The new `d20_hangar` mapping experiment shows all 49,859 source rendered surfaces matched to a generated triangle with 149,577 compared corners, but it finds position quantization and diffuse-UV outliers. Candidate source-surface mapping is 199,436 bytes. The BSPS section is 3,876,512 bytes versus 3,311,136 bytes of the source compressed-vertex field; if additional EE-resident this is at least **764,812 bytes larger** before remaining CE data/staging. If the parent renderer already owns BSPS, it is not charged twice, but neither its same-lifetime EE ownership nor equivalence for CE CPU consumers has been proven ([`m2-d20-hangar-render-mapping-audit.md`](m2-d20-hangar-render-mapping-audit.md#L17-L48)). CE uses source vertices/UVs/normals/radiosity in visibility, collision-hit-to-surface/material/barycentric queries and object lighting ([`m2-bsp-compressed-vertices-parity-audit.md`](m2-bsp-compressed-vertices-parity-audit.md#L20-L63)). This is a good differential consumer experiment, not present-day capacity credit.

### Loader streaming and region reuse

The current HP2 stream visitor can decode through bounded codec scratch, but `world_load_section_with_scratch()` still reserves the full raw output; CE cache publication still needs stable complete CTAG/BSP images ([`section.c`](../../submodules/halo-ps2/engine/src/world/section.c#L79-L190), [`ps2_cache.c`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L375-L457)). Direct-to-final decode is valuable and likely required to stop duplicate staging, but it cannot solve campaign final residency under current pointer assumptions. Temporal arena sharing is possible only for proven nonoverlapping lifetimes; UI-only peaks are not evidence for campaign/actor/render peaks. A candidate cannot shrink a named owner until production-phase canaries/high-water and consumer lifetimes show it is safe.

GS (4 MiB), IOP RAM (2 MiB), and SPU2 RAM (2 MiB) are distinct stores, not CPU backing for CE pointers. A texture/model draw representation may be GS-resident after upload, but CE simulation/tag/collision remains on EE. The project’s machine-split table explicitly treats those stores independently ([`hcu-ps2-memory-map.json`](../../config/hcu-ps2-memory-map.json#L101-L105); hardware constraints in [`plans/5.hcu-remake.md`](../../plans/5.hcu-remake.md#L259-L267)). Halo-64 demonstrates source-porting and machine-glue patterns only; its N64 pools, scheduling, and omitted AI/scripts are not acceptable PS2 capacity policies ([`plans/5.hcu-remake.md`](../../plans/5.hcu-remake.md#L245-L257)).

## Concrete experiment to prove or disprove the strongest candidate

Run a source-backed **animation live-set / lease prototype** before attempting to resize any production owner:

1. Freeze a coherent tuple of retail source-map hashes, exact schema ELF, dirty HCU/halo-ps2 patch hashes, converter/CTAG/animation sidecar hashes, production closure/ELF, toolchain, budget and memory map. The existing reports use matching `2fba…` artifacts, but the full runtime source worktrees are dirty and must be hashed into the experiment.
2. Add diagnostic-only instrumentation (not yet a migration) at every identified `animation.data` validator/runtime read path. Record `(map hash, tag index/datum, animation index, frame, phase, pointer interval, begin/end)` with per-frame unique resident bytes, overlap/pin high-water, hit/miss, and I/O bytes/latency. Ensure direct compressed readers and schema validation are instrumented in addition to `animation_get_frame_data()`.
3. Exercise all campaign maps’ maximum-BSP scenarios, campaign encounters at actor-count high-water, first-person weapons, object animations, interpolation/aiming-screen paths and 1–4 local players. Keep identical CE resident data as oracle. Record worst simultaneous lease set and worst tick cost; do not sum payload bytes across a whole map and call that the active set.
4. Prototype one typed whole-animation lease with stable identity `(map hash, tag identity, graph/block element, field, logical size, payload digest)`. The provider returns an exact contiguous EE view valid until release. Move only `animation.data`; keep `frame_info` and `default_data` unchanged. Modify schema validation to validate the same logical compressed data before publication, route all direct runtime readers through leases, and fail closed on stale/short/corrupt/exhausted requests. Forced four-pointer and reentrancy tests are mandatory.
5. Run dual-provider parity fixtures over compressed and uncompressed records: validator accept/reject, keyframes, scale/translation/rotation, root motion, 4-way aiming interpolation, object/first-person pose, retries, map unload, cache pressure and read failure. Compare exact decoded outputs against in-image CE.
6. Produce a **net resident byte ledger per map/phase**: reduced CTAG, active leases/cache, identity tables, provider buffers, claims, CE state, largest active CE BSP, renderer/visibility packs, texture staging/residency, DMA, dynamic simulation, audio, decoder, scratch, and old/new-map transition. Count each physical EE byte once and report GS/IOP/SPU2 separately. For a10, the entire post-externalization residual before all other owners/cache is only 2,404,132 bytes; a passing ledger must demonstrate actual simultaneous all-owner peaks within it (or evidence-backed reduction of a specific unnecessary EE owner) with reserve untouched.
7. Measure cold/warm DVD, OPL USB/SMB/HDD and cache behavior on EE hardware when available; use PCSX2 interpreter/recompiler as functional integration checks, not EE timing qualification. Require no missed 30 Hz ticks from synchronous data fetch, no pointer escape after release, no owner overlap, correct failure rollback/retry, and all stock map/BSP identities.

**Disproof condition:** if the measured animation pin set plus all required simultaneous EE owners exceeds the residual in any mission/encounter, this field alone cannot close capacity. Then evaluate a second individually audited representation (for example, reusing already-required PS2 BSP render bytes only after CE surface/light/visibility parity) or conclude that no fixed-budget design is supported. Do not use compressed file size, nonresident media capacity, zero-startup use, or N64 behavior cuts as savings.

## Acceptance gate and current conclusion

An implementable strategy is supported only when it has: (1) complete CE consumer and pointer-lifetime coverage; (2) a lossless logical-byte contract and CE validator parity; (3) per-map and per-phase actual active-set/owner high water including all required local actors/players; (4) exact physical EE placement with canaries and nonoverlap; (5) PS2 I/O/tick latency evidence; (6) gameplay, BSP-switch, unload/reload, failure/retry, and rendering/query fixtures; (7) unchanged all-map scope and reserve; and (8) a reproducible current artifact tuple. Current evidence has static input sizes and partial UI/lifecycle/map parser tests only; there is no capacity-qualified campaign map, no active animation lease measurement, and no production BSP query/render scene run. M2 remains open.
