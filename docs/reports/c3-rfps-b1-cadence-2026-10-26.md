# C3 frame cadence and interpolation research (B1) — 2026-10-26

## Scope and evidence boundary

Read-only cadence/render-path analysis for the question of exceeding 30 presented frames/s while retaining the fixed 30 Hz gameplay simulation and current graphical fidelity. No implementation, build, or runtime test was performed. The parent worktree and `halo-ce-universal` submodule have concurrent uncommitted instrumentation edits; source observations below use the checked-out submodule baseline where possible and established documentation/contracts. The active uncommitted `src/stream/hcu_main.c` is explicitly not treated as baseline behavior.

This is a feasibility and experiment plan, not evidence that >30 fps is achieved on either PCSX2 or a physical PS2. Existing retained evidence in the 30 fps review shows 30.0096 gameplay ticks/s and 14.9648 rendered frames/s in a prior workload; quiet emulator observations at 29.97 FPS / 59.94 VPS describe that run/configuration only. The separate performance report has lower rates as view count increases. Emulator speed, VPS, repeated display fields, and an uncapped guest loop are not equivalent to distinct game frames per second, nor do they prove console throughput.

## Current CE cadence

The realtime CE scheduler advances fixed 1/30-second simulation steps from elapsed time, with bounded catch-up (up to four steps) and dropped-tick accounting. It samples input and applies `player_control_update(1/30)` and `game_time_update(1/30)` for each due step. After the entire batch, it calls `main_game_render(1/30)` once to publish the latest CE frame snapshot, then synchronously invokes the parent renderer/snapshot consumer. Thus the simulation is independent of a slow render, but presentation is currently coupled to one publication/render opportunity per scheduler batch. Faster presentation requires a separately paced render loop that can reuse/interpolate between published tick states; speeding simulation or changing its delta is not an acceptable route.

The standalone `halo-ps2` viewer is not the active CE loop. Its `main.c` explicitly ticks objects at 30 Hz (every frame at 30 fps, every other frame at 60), and `video_present` waits for vsync and changes the displayed framebuffer. This supports the architectural feasibility of a distinct render cadence, but is not proof the integrated CE path works at that cadence.

## Snapshot and interpolation readiness

The integrated design direction is already recorded in `halo-ps2/docs/03-engine-architecture.md` and ADR-002/ADR-023: keep the 30 Hz tick, present at 60 fps by interpolating previous/current immutable snapshots, and accept one-frame latency. The planned interpolated values include object transforms, camera, animation node matrices, and particle positions; input is sampled at presentation rate and applied at tick boundaries with look deltas accumulated. ADR-023 defers this stretch until content budgets justify it and cites console-side renderer risk.

**Active C3 path distinction:** when `HCU_C3_FRAME_SNAPSHOT` is enabled, `src/stream/hcu_main.c` allocates/binds `hcu_snapshot_bank` v2 storage in `frame_scratch`; this replaces, rather than accompanies, the legacy `hcu_render_snapshot` two-slot store. `hcu_c3_views_begin()` pins the published v2 `halo_ps2_frame_snapshot`; C3 view setup and object preparation consume that pinned frame snapshot, and `hcu_c3_views_end()` releases the reader. The three-slot bank refuses writes to the published slot or any reader-pinned slot. Therefore the legacy two-slot no-reader-pin lifetime is **not** an active-C3 blocker. Two consecutive tick snapshots can in principle remain resident in the three slots while the third is used for publication, but exact pin overlap, parent render completion, and CE publication ordering must be proven before relying on that arrangement.

The measured cache-OFF frame owner uses 262,608 of 393,216 bytes, leaving 130,608 bytes; cache-ON uses 360,928 bytes and is excluded from FPS conclusions because its comparison mixed frame rates. The existing 82,912-byte derived snapshot-copy workload indicates a candidate copy may fit in the cache-OFF slack, but that is not yet an allocation/layout proof: alignment, guards, renderer workspace, actual target run high-water, and lifetime all matter. Prefer first testing endpoint retention with the existing three pinned banks; consider a bounded derived copy only if ownership and measured slack are verified for the exact configuration. Do not add another bank or assume unused budget without a guarded owner audit.

### Exact CE interpolation path and current PS2 behavior

CE already contains a separate presentation interpolation subsystem, but its active PS2 implementation is deliberately disabled. `game_time_update()` calls `render_interpolation_tick()` after each `game_tick()` and brackets `game_frame()` with interpolation frame begin/end. CE object drawing asks `render_interpolation_object_node_matrices()`, camera setup calls `render_interpolation_camera()`, and first-person weapon drawing calls `render_interpolation_first_person()`. The PC/Linux implementation in `port/linux/game/render_interpolation.c` maintains tick/render state and supplies interpolated poses; the PS2 `port/ps2/src/ps2_render.c` stubs return the direct observer, return `NULL` for node matrices, no-op tick/frame hooks, and explicitly leave first-person CE matrices unchanged. This is the CE animation/pose path to investigate for future integration.

The C3 path instead runs CE fixed ticks, calls `main_game_render()` after a due-tick batch to publish the frame, and the parent consumes that publication through HCU-owned snapshots. This is not the standalone halo-ps2 `objects_tick`/`fpview_tick` loop, and parent animation must not be added as a second clock. A sound first milestone is presentation of the same latest HCU snapshot more often (even if duplicate images), then a separately owned render interpolation view derived from adjacent immutable HCU publications. Re-enabling the generic PS2 CE interpolation stubs wholesale is not automatically correct: the headless publisher and snapshot boundary may not retain all CE live pose state needed by the original draw hooks.

## Fidelity and ownership contracts

- Keep simulation exactly 30 Hz with the same tick ordering and per-tick time delta. Parent rendering must be a read-only consumer; interpolation must not advance CE objects, animation, particles, HUD timers, or weapon state.
- Retain two completed, generation-compatible HCU v2 bank publications at a defined post-tick boundary. The active three-slot reader-pinned bank may hold both endpoints without allocating another bank, but only if reader-pins, publication order, and DMA/GS consumer lifetimes are demonstrated. Interpolate a presentation-only derived view with a clamped alpha derived from the scheduler accumulator. Define behavior at map changes, pause, spawn/delete, discontinuous teleport, camera cuts, and missing/late publication. Never blend across unrelated map generations or reused object handles.
- Interpolate positions/transforms, camera orientation (shortest-arc rotation), and node palettes consistently. Discrete fields (visibility, weapon/effect state, HUD text, resource identity) need an explicit endpoint/selection rule. Any first-person pose or camera smoothing must preserve input response and avoid introducing a second animation clock.
- Tick-owned sound/event emission must occur once per simulation tick even if there are two presentations. Presentation-side HUD/effect work needs classification: Halo CE `game_frame` includes particle/contrail/widget/sound and rasterizer updates; the snapshot-render auditor notes that skipping or multiplying render calls can change presentation state. Move state advancement to a defined tick/update boundary or publish presentation state; do not duplicate events to make frames look smoother.
- Input can be sampled at render cadence for responsive camera control, but apply accumulated gameplay commands only at fixed tick boundaries, preserving deterministic replay and tick hashes. Define button edge handling so a press cannot be lost or repeated across multiple renders.
- Preserve GS/DMA completion, source leases, and snapshot reader pins through the final consuming kick/fence. More frequent frames increase publication frequency and can overlap more reads; no fence removal or bank reuse is justified by host timings.
- Preserve the current framebuffer format, resolution, assets, draw passes, LOD/visibility rules, and required content. A higher frame rate obtained by disabling geometry/effects, changing resolution, dropping objects, or reducing fidelity does not answer the stated question.

## Present path and PS2 limits

The `halo-ps2` video path allocates two CT16S color buffers and a Z buffer, configures interlaced NTSC field output, and `video_present()` waits for vsync before selecting the rendered buffer and flipping the back index. At 60 Hz field cadence this creates a potential one-presentation-per-field schedule, while CE ticks remain 30 Hz. It does not establish that the integrated C3 work per frame fits the ~16.7 ms presentation interval or that all intended native modes behave identically. The C3 prior review specifically warns that PCSX2 immediate-present timing does not qualify native GS/presentation cost.

Consequently, >30 distinct renders/s is architecturally plausible and explicitly documented as a stretch path, but cannot be claimed achieved or safe on hardware from this source audit. In particular, two half-frames may repeat a frame if the render misses a field; report distinct render sequence IDs and flip intervals rather than relying on emulator FPS/VPS counters.

## Guarded experiment for the implementor

1. First establish a 30-tick/s baseline and record source/config/ELF identity. For cache-OFF (the only cited frame-owner profile), log owner current/high-water, exact v2 bank slots/sequences/pin counts, CE publication duration, parent render duration, GS waits, and field/present intervals. The stated 262,608 used / 130,608 spare must be verified against this exact build/config before relying on it.
2. Add an opt-in cadence switch that changes only presentation scheduling: baseline versus a 60 Hz target; simulation remains fixed at 30 Hz. Keep a deterministic 30 Hz command stream and per-tick state hash. Before interpolation, run repeated presentation of the latest pinned HCU frame snapshot to isolate render throughput and presentation cost. Repeated frames are a cadence diagnostic, not evidence of 60 distinct rendered frames or success.
3. Add endpoint retention using the active three-bank v2 store. Pin the previous published snapshot while the current one is published and consumed; prove the writer selects only the third unpinned/nonpublished slot, and verify no pin survives past its consumer fence accidentally. If endpoint aliasing/pin pressure prevents this, measure a bounded derived 82,912-byte view against exact cache-OFF owner/slack and canaries before adding it. Do not route this experiment through legacy `hcu_render_snapshot` or parent animation.
4. Add interpolation only after ownership is proven. Render from a scratch-derived view, never mutate CE datums or either publication. Use same input/tick stream for comparison. Track bank sequences, map generation, reader pins, endpoint IDs, alpha and distinct present IDs; require valid alternation and no write refusals/pin leaks.
4. Compare matched 30 Hz and 60 Hz runs at equal simulation ticks and captured camera/input checkpoints. Require identical simulation hashes, event/sound counts, object/animation tick counts, map/resource generation, draw-content counters and framebuffer composition at tick-aligned alpha=0 checkpoints. For midpoint frames, review expected smooth intermediate transforms and verify no discontinuity, HUD/effect duplication, stale resource reads, or changed visibility/content.
5. Gate each mode on no warm dropped simulation ticks, no snapshot write refusals or invalid reads, bounded memory/chain high-water, completed GS/DMA fences, and sustained distinct presented frames. Measure median/p95/max frame intervals and render cost; if 16.7 ms is missed, classify the limitation by EE preparation versus GS completion/present. Do not claim hardware support from emulator alone.
6. Qualification matrix: 1/2/3/4 local views; interpreter and recompiler PCSX2 for determinism/resource checks; NTSC physical PS2 for actual performance if available; idle/quiet and representative high-object/effect scenes; steady movement/look/fire plus pause, spawn/delete, camera cut, map transition, and late-frame stress. A hardware row remains “not measured” until a physical console capture/log exists.

## Recommendation

Proceed only as a guarded, opt-in feasibility experiment after cadence instrumentation establishes time and memory margins. The active C3 three-slot reader-pinned HCU frame bank is a plausible endpoint source; the legacy two-slot renderer snapshot is inactive in this configuration. First prove two-endpoint retention and pin/fence behavior, then investigate an HCU-owned derived interpolation view. CE's original interpolation logic has explicit PS2 no-op stubs and should be treated as a separate source/reference path, not presumed active or suitable for the headless publication flow. The native GS frame budget and presentation-frequency side effects remain unproven, so a production default change or claim of lossless >30 fps is premature. The key question remains whether the complete same-fidelity pipeline sustains distinct 60 Hz presents on physical PS2; PCSX2 validates logic and regressions but not that hardware performance.
