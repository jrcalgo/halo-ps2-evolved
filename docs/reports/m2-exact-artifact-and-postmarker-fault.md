## Asset/package comparison

The ISO contains `/maps/ui.map` (33,582,080 bytes), SHA-256 `8556b647b82742d07282fe4e6db0cf847b542c046484e91e71ec31fea5f5fd7e`, and `/maps/ui.hp2` (282,624 bytes), SHA-256 `c5b4760afa3b3e8484dc232b2332fb6855d52c0ca271c4427e29c745eec7b51c`. The extracted UI map and `build/hcu-parent-link-probe/maps/ui.map` are byte-identical to the ISO's MAP. The original HP2 has CTAG, CRNG, and HMAP sections.

The working generated `build/hcu-parent-link-probe/maps/ui.hp2` is 286,720 bytes, SHA-256 `a83ded5049128dc0287b975af9c17f4224e467ad5e10ffa079468934e6241e90`; it adds B000 and CBIX to CTAG/CRNG/HMAP. The guest log confirms B000 reads as 2,288 bytes and the generated CBIX is consumed. The boot result hashes the ISO, not the separately opened host-profile HP2; therefore the run manifest alone cannot prove which on-disk HP2 bytes the bridge served. This is a provenance gap to close in the boot manifest or file-bridge trace before declaring the package identity fully reproducible.

No evidence shows a malformed source `ui.map`: the retail map bytes are identical. Earlier reports found the source syntax roots/records in range and normal CE postprocessing rebinds syntax data. The immediate new failure is different from the old out-of-range `hs_syntax_data` assertion, so the two should not be collapsed into one root cause.

## Guest observations

The rebuilt interpreter result reaches `game-initialize-done`, `m1-ui-map-request`, successful HMAP/CTAG/CRNG/CBIX preflight, UI mount, a successful 2,288-byte B000 read, and `m2-ui-map-loaded` at about 30.4076 seconds. At about 30.6689 seconds it reports unaligned stores to `0x7d2cc6` and `0x7d2cca`, followed by unaligned loads at `0x7d2cc6`, then `branch delay!!`. It does not log `hs-invalid-node` or the prior `ring_loop`/datum-get assertion in this run. It shows repeated `Unknown device 'd'` and `'z'` diagnostics before and after the marker; their causal relationship to the trap is unproven.

With `--stable-seconds 10`, a fresh interpreter replay again failed after the marker at `[31.3045] Address Error, addr=0x7d2cc6 [store]`. Its result/log hashes are `0703a0fa6a12794ddcf4c215d53e4ca6dd20306dad9a193f70faaa01237aab9c` / `4864579398edc757e378854f92fbb2355f5f843969e478462cb3f0fda149af46` in run `emulator-m1-interpreter-54469ec2c5604d2895667abe6ed7cc7b`. A fresh recompiler run on the same ELF reached the marker at about 18.3672 seconds and logged no `Address Error` or `branch delay!!` for the full 10.03-second observation window; result/log hashes are `0e58b6b6e09b17273cee2d36e8de17229f5e3fd81522cabf1e5a149ac96ea250` / `c6866dd05e0613e7e6c32730fe06fe790666ec7a95cfb267036a1b7fc6867615` in run `emulator-m1-recompiler-d5d33708efbd4357bce0ac04aa8fa53d`. This is a concrete mode divergence for the observed window, not proof of interpreter root cause, a stable full session, or visible rendering. PCSX2 terminates the guest when the observation window ends.

The early BIOS `Address Error, addr=0x1ff [store]` predates CE startup. Treat it as emulator/BIOS noise for the later M2 stage; only faults after the stage marker should invalidate that stage. The late faults are guest-visible. The old PCSX2 captured viewport was black, and this new log has no rendering-success marker. UI scenario load is not a visible scene.

`0x7d2cc6` and `0x7d2cca` are data addresses, not the faulting instruction PC. The current exact-run memory report maps both into the CPU subrange of CE `game_state` in `resident_gameplay`, not the tag cache/current BSP. `hcu_memory_bind_parent_v2` allocates that game-state span first, size `0x345000`, before the tag-cache allocation ([`hcu_memory_bind.c`](../../src/stream/hcu_memory_bind.c:33), [`halo_ps2_limits.h`](../../submodules/halo-ce-universal/port/ps2/include/halo_ps2_limits.h:16)). This narrows the destination owner but does not identify the code or datum responsible. PCSX2's current text log does not include EPC/call stack for these accesses, so the data addresses cannot be resolved with `addr2line` as if they were code locations. Capture EPC/register state or instrument the suspect lifecycle/access before changing game semantics; the independent [`m2-guest-exception-capture.md`](m2-guest-exception-capture.md) has a debugger procedure and SDK exception-frame fallback.

## REA and code/data inspection

REA's shipped-artifact flow fingerprinted the exact MIPS ELF, but its available decompiler providers do not support this MIPS/R5900 variant (Ghidra processor profile unavailable; Hopper unsupported; IDA not configured). The data ISO is not a supported executable binary input for REA. Thus no REA pseudocode/decompilation claim is made. Standard readelf/nm/map tools, xorriso extraction, the project's HP2/CTAG schema walkers, and CE source inspection supplied the evidence above.

`readelf` identifies an ELF32 little-endian MIPS executable with `5900` and `abi2` flags. This does not itself indicate an error: [`port.json`](../../submodules/halo-ce-universal/port/ps2/port.json:5) explicitly declares 32-bit pointers/long and `mabi: n32`, and [`hcu_ps2_link.py`](../../tools/hcu_ps2_link.py:387) passes `-mabi=n32`. Do not flip this to o32 based solely on the shorthand “ILP32.” Halo-64 is a useful source comparator, but its N64 prefix and omissions (including HaloScript/effects changes documented in [`port.json`](../../submodules/halo-ce-universal/port/ps2/port.json:1) and its N64 notes) are not PS2 fixes to import; preserve CE HS runtime behavior and the PS2 machine ABI.

Source review also highlights `hs_node_gc` deleting every non-permanent node (`hs.c:13555-13569`), while CE runtime advances scripts and calls GC periodically. GC/lifetime interaction is a plausible investigation lead only; no current fault PC or node diagnostic ties these data-address faults to GC. The added `hs_syntax_get_checked` diagnostic at [`hs_runtime.c`](../../submodules/halo-ce-universal/source/hs/hs_runtime.c:560) was not invoked in the latest run. The changed root-validation logic in `hs.c` did not eliminate the crash. Do not land a byte-order patch, disable `ring_loop`, or alter GC based on timing correlation alone.

## Harness correction and test result

`tools/test_hcu_boot.py` previously called a 2-second stage-marker observation “passed” without checking PCSX2 `Address Error`/`branch delay!!` lines during that window. The harness now identifies these as post-boundary guest faults and polls immediately after the marker; the pre-marker BIOS `0x1ff` line remains outside the M2 failure boundary. `tests/test_hcu_boot_physical.py` adds tests for pre-marker noise, post-marker address errors, branch-delay traps, and missing markers.

Verification: `python3 -m pytest -q tests/test_hcu_boot_physical.py` → **8 passed**. Replaying the exact rebuilt ELF using the corrected harness in interpreter mode fails at the first post-marker guest fault. The updated result is `build/hcu-ps2-closure/emulator-m1-interpreter-0da9209b68cf495db52cf4f1fd49b7a2/result.json` and preserves the exact fault line. This fixes false-positive test classification; it does not fix the guest.

## Follow-up: PS2 HaloScript stack alignment and fresh dual-mode runs (2026-10-21)

The independent layout review in [`m2-hs-thread-unaligned-access-audit.md`](m2-hs-thread-unaligned-access-audit.md) corrected the target interpretation: the original bad effective address lies at `hs_thread_datum.stack_data[0x22]`, but it did not yet explain the writer. Review of the actual R5900 layout exposed a concrete alignment hazard in `hs_stack_allocate`: the interpreter stores typed `long *`/`real *` values into a byte-oriented stack, while `hs_stack_frame.data` is at offset `0x0e` even though `sizeof(hs_stack_frame)` rounds to `0x10`. The first PS2-only attempt rounded `frame->size` relative to `data`; its ELF (`343ce7c7c5c85f10c8ec652ebce19e0bb5438d8df2cb6268aac46d2901696a19`) still faulted at allocation-relative `+0x72`, demonstrating that the *actual pointer* must be aligned. The exact source layout and R5900 disassembly show the `data` base at frame+`0xe`; no EPC was captured, so the exact issuing instruction/caller remains unobserved.

The corrected `HALO_PS2` branch in `hs_stack_allocate` aligns the returned `frame->data + offset` address itself (using `uintptr_t`) and includes padding in `frame->size`; `hs_stack_push` keeps subsequent frame headers word-aligned. Non-PS2 builds retain the original tightly packed behavior. Current edited `hs_runtime.c` SHA-256 is `008fca1e333d74598a398f6d058cad8be09e4e5b8cbc6c8b8ab09c3aa3f9a174`. This is a source-backed PS2 fix at the CE interpreter scratch-stack boundary, not a claim that PCSX2 exposed the fault EPC.
