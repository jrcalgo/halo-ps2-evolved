## What is now actually covered

### L0–L3: service staging, source, owner, cache publication

The parent map service keeps preflight staging distinct from mount publication. `map_loader()` refuses deferred reload while the old mount/source is still active, revalidates after owner release, and clears staged state on failure ([`hcu_map_service.c:125-204`](../../src/stream/hcu_map_service.c#L125)). `map_unloader()` releases the parent mount/source and clears preflight state ([`hcu_map_service.c:211-231`](../../src/stream/hcu_map_service.c#L211)). Parent mount stores a mark, stages CTAG/CRNG, calls the cache backend, and only then marks the mount active; later CBIX or callback-registration failure goes through teardown ([`ctag_mount.c:152-213`](../../src/stream/ctag_mount.c#L152), [`ctag_mount.c:239-330`](../../src/stream/ctag_mount.c#L239)).

The UI service fixture exercises missing paths, malformed required sections, short reads, changed data after preflight/unload, a late capacity refusal at the actual cache-adapter boundary, and retained-source resource EOF followed by same-owner retry. The parent/service snapshots include arena identity/capacity/cursors, active mount/source and staged state, descriptor/open-close counts, public cache-loaded state, and in newer cases hashes of the complete tag/BSP destination arrays. This is strong evidence for the specific UI host seams described in plan lines 335–347; it is not a single full CE/service snapshot at each L0–L3 fault.

The current real resource-read EOF test proves `cache_file_read()` leaves its completion flag failed when a CRNG-authorized source returns one byte then EOF, and proves a subsequent callback read returns the exact expected bytes ([`ctag_mount_main.c:754-791`](../../tests/ctag_mount_main.c#L754)). It does **not** run the CE resource consumer that received the partial destination buffer, nor prove that consumer discards the prefix before a complete map retry.

### L4: CTAG read and CE tag publication

CE poisons the tag destination, calls its exact cache read callback, checks completion, verifies the tag header, and runs `tag_validate_tags()` before setting `tag_header`/`tags_loaded` ([`cache_files.c:1262-1314`](../../submodules/halo-ce-universal/source/cache/cache_files.c#L1262)). The host lifecycle fixture invokes real `scenario_tags_load()` against a mounted UI package and corrupts the final CTAG relocation row. The current whole-buffer CTAG materializer rejects before copying, CE keeps the tag globals unpublished, and a corrected retry on the same mount succeeds. The fixture also forces the real CE tag-schema validation seam to reject after the payload has been read; `scenario_load()` then calls the PS2 teardown path, clears CE state before releasing parent ownership, and a fresh same-process scenario load succeeds ([`hcu_ce_map_lifecycle_main.c:116-213`](../../tests/hcu_ce_map_lifecycle_main.c#L116)).

This is real CE lifecycle execution in a host ILP32 fixture, but it has host-only oversize arrays and claims storage. It does not validate a streamed CTAG callback: the production CTAG read still requires the complete CTAG payload in the parent owner's staging path and then materializes to the fixed tag cache. Whole-image CTAG capacity remains a hard gameplay-map gate.

### L5: CBSP and BSP-switch rollback

The current tree contains a production direct visitor path, so older notes saying no HCU CBSP visitor calls the split parser are superseded. Parent `visit_bsp_extent()` checks catalog/extent exclusion and calls the registered section visitor ([`ctag_mount.c:108-145`](../../src/stream/ctag_mount.c#L108)). HCU `stream_cbsp_for_read()` routes decoded chunks into the exact fixed BSP destination, keeps only the small envelope header and relocation rows arranged in that destination, validates the full visitor result, invokes split CBSP validation/rebase, and only then normalizes the cache header ([`ps2_cache.c:407-564`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L407)). `cache_file_read()` initializes completion to failure and sets it true only after the visitor/materializer succeeds ([`ps2_cache.c:566-649`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L566)).

The a50 retail host transaction injects two late, distinct failures in B001 while B000 is live: (1) bad stored HP2 CRC after more than the 36-byte envelope reached the candidate destination, and (2) a bad inner CBSP image CRC after the HP2 visitor completed. In both cases, real CE `scenario_switch_structure_bsp()` rejects the candidate, rematerializes B000, compares the *entire B000 destination extent* and CE pointers/indices/owner/scratch snapshot, then successfully retries B001→B000 without process/mount restart ([`hcu_scenario_bsp_switch_main.c:919-957`](../../tests/hcu_scenario_bsp_switch_main.c#L919)). Existing package-backed cases also cover candidate read, CE schema/port-verifier rejection, candidate-plus-old-BSP failure to safe-null/menu, and retry ([fixture lines 986–1060](../../tests/hcu_scenario_bsp_switch_main.c#L986)).

The UI lifecycle fixture separately injects an initial B000 visitor failure after decoded bytes have reached the actual BSP destination; `scenario_load()` fails, `scenario_unload()` clears tag/scenario/BSP globals before owner release, owner/scratch returns to baseline, and a valid same-process retry passes ([`hcu_ce_map_lifecycle_main.c:399-428`](../../tests/hcu_ce_map_lifecycle_main.c#L399)). Thus it is no longer accurate to say all initial-BSP post-write rollback is missing. It is a UI host test with a test wrapper around the visitor callback, not a target guest failure run or campaign BSP.

Important safety distinction: direct CBSP writes are not byte-atomic. A visitor/CRC/rebase error can leave candidate bytes in the fixed BSP destination, but completion remains false and CE has already unpublished the old BSP before attempting replacement. On candidate failure, CE tries loading the old BSP by its source identity; if that also fails, it must clear all BSP pointers and go to the menu ([`scenario.c:1116-1169`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L1116)). The tests establish restoration/safe-null for selected host faults; they do not justify calling the candidate destination itself rolled back. Keep the distinction between logical unpublication, old-BSP rematerialization, and physical byte restoration explicit.

### L6: final publication/commit

The current UI runtime has successful map-loaded/snapshot markers, but there is no single transaction object or generation that atomically joins map-service preflight, mounted CTAG/cache callback, CE tag validation, selected CE BSP publication, and render-snapshot publication. The successful lifecycle and the failure fixtures each prove their own transitions; they do not prove a single L6 commit boundary or a successful gameplay-map/render commit. The L6 concern in [`m2-step9-l0-l6-current-state.md`](m2-step9-l0-l6-current-state.md#L27) remains valid.

## Next smallest useful slice

Do not start another parser or standalone rollback test. Add one **test-only end-to-end state/snapshot scenario around the existing UI lifecycle fixture**, because the remaining highest-value gap is the seam between the already-strong parent-service snapshot and real CE publication state:

1. Before successful `scenario_load()`, capture CE scenario/tag/BSP globals and indices, `cache_file_globals` publication/header identity, `hcu_map_service` staged/mount/source fields and descriptor, arena base/cap/used/high, complete fixed tag/BSP destination digests, and cache completion/public-load state. Keep a separate expected snapshot for the active old UI map and for safe-null after teardown; historical `high` is monotonic and must not be required to rewind.
2. While that UI scenario is active, request each catalog entry that must be rejected before unload (the production UI-only capacity gate) and assert byte-for-byte/state-for-state preservation, not merely return false. Also exercise the same-map preflight contract (pending identity only; no second open or live-owner mutation).
3. After explicit CE unpublish/owner release, inject one deterministic failure at each already-existing production callback boundary in sequence: source reopen/short read; required-section/CRC; actual cache-adapter refusal; CTAG read/schema; direct CBSP visitor failure after a destination write; and post-CE BSP verifier rejection. After every failure assert the documented post-unload state (safe-null/menu or rematerialized previous BSP when switching inside the still-mounted same map), owner/source/callback cleanup, completion false where applicable, and a valid same-process retry after removing the one-shot fault.
4. Reuse the production UI package and existing wrappers first; do not admit a gameplay catalog entry, enlarge an arena, or use reserve RAM. Treat this as lifecycle/failure semantics only. Keep full a50 direct CBSP switch as its separate host regression, because the current guest/physical-memory capacity design does not qualify a50.
5. Record exact package and executable hashes and run the host ILP32 fixture outside the SIGSYS-restricted sandbox. Then run the matching opt-in diagnostic image in PCSX2 interpreter and recompiler only if its exact ELF passes the physical-placement gate. Guest acceptance should be narrowly named (UI scenario failure/retry), never called gameplay-map acceptance.

This is deliberately a test-only composition slice; the biggest product blocker remains Step 8 capacity. It advances proof of transaction semantics without pretending the 24-map lower bound fits or that current committed code is target-qualified.
