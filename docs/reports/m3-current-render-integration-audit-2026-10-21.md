# M3 current render integration and BSP payload audit

Status: report-only investigation. No production source, test, or plan was changed. This report distinguishes (a) CE render-facing state and CPU BSP consumers, (b) the parent halo-ps2 BSP renderer and its `BSPn` pack input, and (c) the current HCU adapter/guest path. It is not a rendered-scene acceptance result.

## Executive finding

The ordinary HCU guest can have a valid CE viewport/camera and a committed matrix snapshot while showing a black game viewport. The current adapter's `render_frame()` increments CE render state, updates the first-person pose, copies camera/object/node matrices, and packs a small VIF UNPACK payload; it does not call the CE render pipeline or the parent BSP renderer, and the production `hcu_main.c` path does not call `video_init()`/`video_present()`. The GS clear diagnostic is separately compile-gated and presents one blue clear; it is not the production frame loop or a scene.

There is also a real data-contract boundary: CE visibility and some world-light/surface queries read source `structure_material.compressed_vertex_data`; halo-ps2's HP2 `BSPn` is a useful expanded/quantized VU render representation but does not preserve all CE source surface identity and vertex semantics. It may replace or supply *render-only* geometry only after a source-to-batch mapping, exact package provenance, and parity evidence. It cannot be presumed to replace collision-to-surface/material lookup, diffuse/lightmap sampling, or CPU normal/radiosity access. See the prior detailed record at [`m2-bsp-compressed-vertices-parity-audit.md`](m2-bsp-compressed-vertices-parity-audit.md).

The immediate dependency order is therefore: (1) keep M2's capacity gate closed until one exact gameplay map and its matching PS2 render pack/resources have a whole-live-set and transition proof; (2) establish one non-overlapping, fenced EE DMA allocation/lifetime contract; (3) add a one-view BSP-only consumer at the completed CE render-frame boundary; (4) compare CE camera/frustum and BSP visibility to the PS2 path; (5) demonstrate nonzero BSP batches/triangles and actual geometry pixels in both PCSX2 modes. Do not expand to object models, first-person weapon drawing, HUD, particles, or scene parity in this first slice.

## Current call graph and why a viewport may remain black

### Retail CE renderer (source behavior)

CE's ordinary [`render_frame()`](../../submodules/halo-ce-universal/source/render/render.c#L594) increments `render.frame_index`, begins the rasterizer frame/window scopes, loops player windows, calls `render_player_frame()`, draws UI, then closes the scopes ([`render.c:594-654`](../../submodules/halo-ce-universal/source/render/render.c#L594)). Each player window computes structure visibility and enters a rasterizer window, then invokes sky, first-person update, object rendering, structure preprocessing/lightmaps, and other passes ([`render.c:306-350`](../../submodules/halo-ce-universal/source/render/render.c#L306)). This is the CE source call chain that the port would normally preserve or translate.

### HCU PS2 adapter (current compiled semantics)

The PS2 port replaces that entry point with its own [`render_frame()`](../../submodules/halo-ce-universal/port/ps2/src/ps2_render.c#L126). It advances `render.frame_index`, chooses a local player's `render_camera`, and updates first-person pose ([`ps2_render.c:94-147`](../../submodules/halo-ce-universal/port/ps2/src/ps2_render.c#L94)). It then fills and commits a pointer-free camera/object/first-person-matrix snapshot ([`ps2_render.c:148-215`](../../submodules/halo-ce-universal/port/ps2/src/ps2_render.c#L148)). The function ends after `hcu_render_snapshot_publish_dma()`; it contains no CE `structure_visibility_compute`, `rasterizer_*`, `render_sky`, `render_objects`, `structure_render_*`, parent `bsp_render_build`, `bsp_render_kick`, or `video_present` call.

The snapshot's documented fields are sequence/frame/time, one camera/window/player, up to 64 first-person matrices, and up to 2,048 object transforms; there is no BSP/cluster/material/texture/geometry reference ([`halo_ps2_render_snapshot.h:8-51`](../../submodules/halo-ce-universal/port/ps2/include/halo_ps2_render_snapshot.h#L8)). Its parent header explicitly says its DMA payload is “not a scene” ([`hcu_render_snapshot.h:39-44`](../../src/stream/hcu_render_snapshot.h#L39)). The packer writes a matrix-oriented VIF payload and reports qword count ([`hcu_render_snapshot.c:213-276`](../../src/stream/hcu_render_snapshot.c#L213)); construction is not VIF submission and has no BSP vertices, cluster batches, material bindings, texture uploads, or GS frame/present boundary.

### Parent PS2 renderer (available, but not integrated in the combined path)

The standalone halo-ps2 viewer demonstrates the missing machine sequence: initialize GIF, `video_init()`, and `bsp_render_init()` once ([`engine/src/main.c:142-161`](../../submodules/halo-ps2/engine/src/main.c#L142)); load a `world_t` and establish the BSP/texture source ([`main.c:157-161`](../../submodules/halo-ps2/engine/src/main.c#L157)); then each frame build the BSP chain, wait for prior GPU work, present, and kick the next chain ([`main.c:238-273`](../../submodules/halo-ps2/engine/src/main.c#L238), [`main.c:307-311`](../../submodules/halo-ps2/engine/src/main.c#L307)). Parent `bsp_render_build()` uses a camera, visibility, clipping, material grouping, and chain buffers ([`bsp_render.c:562-620`](../../submodules/halo-ps2/engine/src/render/bsp_render.c#L562)); `bsp_render_kick()` submits GIF setup/upload and a VIF1 chain ([`bsp_render.c:747-769`](../../submodules/halo-ps2/engine/src/render/bsp_render.c#L747)). Those symbols are currently not in the ordinary HCU combined link per the plan's REA symbol check ([`plans/7.hcu-remake-m2-m4.md:690`](../../plans/7.hcu-remake-m2-m4.md#L690)).

`video_init()` allocates framebuffers/Z/texture window in GS VRAM and enables display output ([`video.c:9-40`](../../submodules/halo-ps2/engine/src/platform/video.c#L9)); `video_present()` waits for vblank and changes scanout framebuffer ([`video.c:94-100`](../../submodules/halo-ps2/engine/src/platform/video.c#L94)). In the combined HCU entry, this is only called by `hcu_m3_render_clear_test()` under `HALO_PS2_M3_RENDER_CLEAR_TEST` ([`hcu_main.c:62-68`](../../src/stream/hcu_main.c#L62), [`hcu_main.c:99-139`](../../src/stream/hcu_main.c#L99)); invocation is similarly conditional ([`hcu_main.c:421-436`](../../src/stream/hcu_main.c#L421)). Normal startup proceeds to `halo_shell_main()` instead ([`hcu_main.c:437-445`](../../src/stream/hcu_main.c#L437)). Therefore a valid viewport rectangle in CE's camera or UI state does not prove that GS output has been initialized or that any frame was drawn/presented.

The plan records a blue PCSX2 clear screenshot for the opt-in diagnostic, and expressly calls it only the first-visible-pixel bring-up—not a gameplay scene ([`plans/7.hcu-remake-m2-m4.md:688`](../../plans/7.hcu-remake-m2-m4.md#L688)). Two independent causes can thus explain black output: the normal ELF lacks the video/present path; and even the clear-test ELF draws only the diagnostic clear, while no production BSP snapshot consumer is present. Separately, the UI map has no gameplay BSP/render pack. The current map-service code rejects every catalog map except `ui` until capacity is qualified ([`hcu_map_service.c:288-311`](../../src/stream/hcu_map_service.c#L288)). The black UI guest viewport is consequently expected and is not evidence of a broken BSP renderer. The plan's artifact boundary correctly distinguishes the black UI capture from the blue clear and from a rendered CE scene ([`plans/7.hcu-remake-m2-m4.md:662`, `683-690`](../../plans/7.hcu-remake-m2-m4.md#L662)).

## BSP vertex/geometry responsibilities

### CE source blob and consumers

The M2 audit established the source format: each compressed rendered vertex is 32 bytes (xyz float32, packed normal/binormal/tangent, diffuse UV float32x2), followed by 8-byte lightmap vertex records (incident radiosity and signed-16 UV) ([`m2-bsp-compressed-vertices-parity-audit.md:21-30`](m2-bsp-compressed-vertices-parity-audit.md#L21)). The blob is not just a draw list.

| Consumer | CE data/path | Consequence for a PS2 replacement |
|---|---|---|
| Frustum visibility | CE `structure_visibility` selects cluster surface IDs/material, computes `vertex_limit = compressed_vertex_data.size / 32`, obtains each triangle corner at `address + vertex_index*32`, then tests its xyz against CE's render frustum ([`structure_visibility.c:551-615`](../../submodules/halo-ce-universal/source/structures/structure_visibility.c#L551)). | HP2 visible-batch visibility may replace only after a stable source-map/BSP binding and CE-vs-PS2 visible-set comparison. It cannot simply discard the CE data while CE visibility still runs. |
| Collision-hit surface/material identity | `structure_render_surface_from_point_and_leaf()` walks leaf surface refs, matches the collision plane, resolves source surface/lightmap/material, fetches each source triangle's compressed vertex through the material accessor, and runs `point_in_triangle3d()` to return surface and barycentric coordinates ([`structures.c:517-620`](../../submodules/halo-ce-universal/source/structures/structures.c#L517)). `structure_test_vector()` reaches this after collision to identify a rendered surface (see M2 report [`:34-36`](m2-bsp-compressed-vertices-parity-audit.md#L34)). | Keep CE's CPU source path authoritative for collision/surface lookup. Current HP2 batches omit the source surface/leaf relation; do not make them a collision replacement. |
| Diffuse/lightmap sampling | World-light queries interpolate source diffuse/lightmap UVs then sample corresponding bitmaps ([`object_lights.c:591-660`, `1455-1490`, `2215-2238`](../../submodules/halo-ce-universal/source/objects/object_lights.c#L591)). | HP2's expanded UV stream is quantized/reordered; require triangle identity and explicit tolerances if it is used as a CPU query provider. A render pack does not imply resident source bitmap bytes. |
| Object-light normal/radiosity | CE decodes source packed normals and the separate radiosity data for CPU object-light evaluation ([`object_lights.c:2484-2524`](../../submodules/halo-ce-universal/source/objects/object_lights.c#L2484)). | HP2's current VU vertex color is not the original directional normal/radiosity input. Preserve CE data or add a measured faithful sidecar. |
| Lens flares | CE reads `uncompressed_vertex_data`, not this compressed blob ([`structure_lens_flares.c:319-325`](../../submodules/halo-ce-universal/source/structures/structure_lens_flares.c#L319)). | Not a reason to retain/remove compressed vertices; account the other data path separately. |

### HP2 `BSPn` output

The converter extracts xyz/diffuse UV/lightmap UV and source surfaces, groups/sorts triangles by cluster/material, expands each triangle to three corners, and serializes VIF batches. The output retains render batch/material/cluster information but not source CE surface IDs, leaf references, or original packed normal/radiosity fields. Positions/UVs are quantized and triangles are reordered; there are documented coverage edge cases (unclustered/unreferenced surfaces, mirror BSPs, portal tie behavior). The M2 audit details the source code/schema citations and why only a render-specific provider is plausible ([`m2-bsp-compressed-vertices-parity-audit.md:40-50`](m2-bsp-compressed-vertices-parity-audit.md#L40)).

An HP2 section existing in an offline converter or in an unrelated standalone asset package is not proof it is available to the HCU guest. The same map SHA, tag offset/extent, scenario BSP index, converter revision/config, HP2 package hash, raw `BSPn` section hash, and dependent texture/lightmap resource hashes must match. The earlier audit found no local retail HP2 package from which to derive a real paired byte extent and specifically disclaimed source/pack identity ([`m2-bsp-compressed-vertices-parity-audit.md:11-17,50`](m2-bsp-compressed-vertices-parity-audit.md#L11)). The current guest ISO is documented as UI-only rather than a gameplay BSP package ([`plans/7.hcu-remake-m2-m4.md:689`](../../plans/7.hcu-remake-m2-m4.md#L689)).

### Whole-resident capacity implications

Do not credit `compressed_vertex_data` bytes as reclaimed merely because a `BSPn` section exists. For a map/BSP live set, account the retained CE tag/query data, HP2 decoded render section and indexes, source surface bridge if used, texture/lightmap source and GS residency, section staging/decode overlap, map-transition overlap, and arena alignment exactly once. If CE visibility or object-light calls still dereference the blob, those bytes remain required; if a render-only mapping is introduced, account the mapping and prove its lease outlives all rendering. The M2 audit's D20 raw-minus-vertex subtraction is explicitly a lower-bound arithmetic projection, not a memory topology or capacity pass ([`m2-bsp-compressed-vertices-parity-audit.md:52-68`](m2-bsp-compressed-vertices-parity-audit.md#L52)).

The DMA issue is independent of BSP payload storage. The renderer's four double-buffered geometry/upload chains total the entire configured `dma_commands` capacity before snapshot payload or packet control data ([`m3-renderer-memory-audit-2026-10-21.md:49-58`](m3-renderer-memory-audit-2026-10-21.md#L49)). Current snapshot binding puts its VIF staging bytes at the beginning of that arena, while the renderer uses its own `memalign()` chain allocator; without a single named, disjoint allocator and lifetime/fence policy, simply linking the BSP renderer could alias DMA-visible data. The memory audit asks for a measured partition, not a silent capacity reduction ([`m3-renderer-memory-audit-2026-10-21.md:10-12,81-95`](m3-renderer-memory-audit-2026-10-21.md#L10)).

## Recommended next implementation slice

### Hard prerequisites (do not bypass)

1. **M2 map admission:** keep the existing fail-closed UI-only preflight until one exact gameplay map's retained CE live set, its matching `BSPn` section(s), texture/lightmap resources, staging peak, and map transition peak all fit their named physical regions with canaries. `hcu_map_service_preflight()` currently enforces the gate ([`hcu_map_service.c:305-311`](../../src/stream/hcu_map_service.c#L305)). Do not open the catalog based on source-size subtraction or a parent-only render test.
2. **DMA ownership:** use one arena-backed 64-byte aligned partition for all four existing parent chains, snapshot input/staging if still needed, and packet metadata; prove non-overlap, capacity and VIF/GIF completion before slot reuse/unload. Do not increase `dma_commands` by consuming the reserve or reduce chain sizes without measured renderer evidence.
3. **Build closure:** make the exact combined ELF retain the required VU1 microprograms and parent `video_init`, `video_present`, `bsp_render_init`, `bsp_render_set_world`, `bsp_render_build`, and `bsp_render_kick`; assert symbol ownership in a repeatable link test. The regular HCU ELF currently dead-strips these renderer paths per plan's artifact check ([`plans/7.hcu-remake-m2-m4.md:690`](../../plans/7.hcu-remake-m2-m4.md#L690)).

### Narrow vertical slice: one CE-controlled static BSP view

After those gates, implement only a one-player, BSP-only frame path:

1. Initialize `video_t`, GIF/VIF1 channels, and BSP renderer exactly once in the combined machine lifecycle, behind validated arena-backed allocations. Keep the blue-clear diagnostic independent and default-off.
2. When a map transaction commits, bind the CE scenario's exact structure-BSP index to the matching HP2 BSP section and texture/lightmap provider from the same map identity; store an explicit map/BSP generation. On teardown or failed switch, wait for GPU/DMA consumers before releasing either side.
3. At the completed CE render boundary, consume one immutable snapshot sequence. Convert CE position, forward/up, FOV, near/far, and viewport to parent `camera_t`; reject degenerate bases, inverted/out-of-range viewport, invalid clip planes, stale snapshot/map generations, and unsupported split-screen rather than invent defaults.
4. Use parent BSP visibility/build/kick for that exact BSP. The initial slice need not draw HCU objects, weapons, skybox parity, HUD, or particles; it must report visible cluster/batch/material/triangle counts and chain occupancy and fail on zero unexpected geometry, truncation or overflow.
5. Wait for both VIF and GS completion before reuse, then call `video_present()` on each accepted frame. Start with blocking fences for correctness; optimize overlap only after slot ownership tests.
6. Keep CE CPU compressed-vertex queries available during this phase. Only after geometry visibility parity passes should a render-only `source surface → BSPS batch/triangle` index be considered; it must not redirect collision/material/lightmap/object-light queries.

This slice establishes “CE's selected map/camera draws static BSP pixels through the PS2 renderer.” It does not claim object animation/model, first-person weapon, particles/effects, UI/HUD, split-screen, or complete Halo CE parity. That boundary is consistent with the current plan's distinction between snapshot publication and scene drawing ([`plans/7.hcu-remake-m2-m4.md:683-697`](../../plans/7.hcu-remake-m2-m4.md#L683)).

## Final recommendation

Do not debug the black UI viewport as though it were a rendering regression: the current ordinary path intentionally produces no PS2 frame, and the only admitted map is not a gameplay scene. The next useful implementation target is the narrow BSP-only vertical slice above, after M2 admission and DMA ownership. Keep CE's compressed source data for all live CPU callers until a consumer-by-consumer replacement is proven; let HP2 `BSPn` serve the PS2 raster path, not the whole CE BSP contract. That delivers one interpretable pixel-level milestone without conflating map loading, snapshot packing, video clear, geometry submission, and full scene parity.
