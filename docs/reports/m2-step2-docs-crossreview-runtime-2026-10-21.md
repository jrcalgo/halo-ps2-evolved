## Verdict

The interpreter evidence now covers the **failure-preservation, CE-unpublish-before-owner-release, post-release preflight refusal, same-process retry, and two clean reload-cycle** subchecks for the UI lifecycle diagnostic. The same ELF still needs its recompiler run to pass before the plan’s interpreter/recompiler lifecycle pair can close. The Step 2 scope should remain limited to this UI lifecycle: it is not a gameplay-map capacity, scene-render, or full M2 pass.

## Remaining qualification / caveats before marking Step 2 complete

1. **Recompiler pair is still pending.** The currently reviewed artifact covers interpreter only. Require the exact same ELF SHA and data assets in recompiler mode, with parser success and no guest-fault marker after the terminal success marker. Capture its independent run directory, settings hash, result/log hashes, source pins, and lifecycle state summary. Until then, the two-mode acceptance is incomplete.
2. **The current result’s placement fields need a durable summary.** `test_hcu_boot.py` only enforces and persists the `physical_memory`/`linked_physical` check inside the M1-boundary/M3-memory-ready branch (`tools/test_hcu_boot.py:384-411`), not the `m2-ui-lifecycle` branch. Although this log independently passes those helpers and the run says `require_physical_placement=true`, that flag alone is not proof for this stage. Preserve the computed evidence in a report/result record or extend the harness before relying on it as a gate.
3. **Stability is a narrow pass.** The interpreter exceeded its requested 2.0-second post-marker window by about 6 ms. That meets this invocation’s configured threshold, but is not a long soak; if Step 2 adopts the older 5-second convention, rerun both modes with the larger threshold. Do not confuse the 132.6-second whole run or guest timestamps through 130 seconds with the post-marker stability interval.
4. **One pre-marker address-error line remains visible.** The log contains `Address Error, addr=0x1ff [store]` at guest time 1.6175, before the later lifecycle trace and terminal marker; the current harness’s post-marker fault scan therefore does not reject it. The guest continues through memory-ready and completes the full lifecycle, so this is not evidence of a lifecycle failure, but its startup origin should be classified (or explicitly documented as an expected PS2 bootstrap quirk) rather than silently treated as absence of all errors. Post-marker fault-free status is supported by the passed harness run.
5. **Do not widen the claim.** The test profile exercises UI `scenario_load`/`scenario_unload` and a small UI B000. It says nothing about retail gameplay CTAG+BSP working-set fit, gameplay scenarios, OPL/optical sources, the black viewport/render adapter, or real-PS2 timing. Those remain separate plan steps/gates, consistent with the PS2 docs’ warning that PCSX2 does not model DMA/cache/VU/GS costs ([`01-ps2-architecture.md:177-181`](../../submodules/halo-ps2/docs/01-ps2-architecture.md#L177), [`06-decisions.md:181-200`](../../submodules/halo-ps2/docs/06-decisions.md#L181)).

**Recommendation:** after the same-hash recompiler run passes, record its evidence plus the parsed physical-layout summary and classify the pre-marker `0x1ff` store. Then Step 2 can be marked complete *only for its UI lifecycle scope* if the plan’s local gate requires no longer stability window. Keep M2 itself open; this evidence does not satisfy gameplay-map capacity/load or rendering.
