# M2 Step 10: exact PCSX2 guest and viewport audit

Date: 2026-10-21. Scope: retained exact-image PCSX2 results, logs, and captures for the current M2 UI stage, the latest attempted rebuilt ELF, the diagnostic clear build, and the data-only ISO. This is a report-only audit; no source, plan, image, or emulator state was changed.

## Finding

There are three different things that must not be conflated:

1. **Latest rebuilt ordinary M2 diagnostic ELF:** SHA-256 `8222e9634d39a7ffa04c5d6d26ed261f7dbc34cd99cd58bb335f36d40763f85f`. The newest retained PCSX2 attempt targets UI stage in interpreter mode but exits with status 127 *before guest startup*. Its launcher log says Qt cannot connect to display `:0.0` and cannot initialize the XCB plugin because `xcb-cursor0` / `libxcb-cursor0` is missing. No guest log, init marker, map marker, or screenshot is produced. This is an environment/frontend launch failure, not evidence of a PS2 guest regression or success.
2. **Earlier ordinary M2 ELF that did execute:** SHA-256 `739076e159c56a5b7715a499a46eb1922ccc3cddf6540643855c1c4345fe9b03`. The retained interpreter and recompiler results both pass the `m2-ui-map-loaded` stage and its stable-marker interval, on the same UI MAP/HP2 inputs and recorded parent/HCU/halo-ps2 commit IDs. Those results prove UI scenario-load execution for that exact, older binary. They do not establish a gameplay BSP load or visible scene. There is no screenshot in those two run directories.
3. **Viewport images:** a retained ordinary-build capture is entirely black with PCSX2 status “No Image” and GPU 0%; it is from ELF SHA-256 `c1e83f7515a7a6a97b68bad75a9811aaf7fddd0564cb3bdd8722d16bab8d6386`, not either of the two hashes above. A separate opt-in renderer-clear diagnostic shows the expected solid blue clear, but it is a third ELF (`1671b5681713c173a260fa0da2734198c0767d0762fae73f0b4a65dc21093dbf`) and is explicitly a hardware bring-up test, not Halo gameplay rendering.

So: if the question is whether a recognizable game scene should appear in the ordinary M2 UI-stage PCSX2 window, the evidence says **not yet**. The last captured ordinary viewport is black. The blue-clear diagnostic proves only that the test GIF packet can clear/present a framebuffer. The latest rebuilt binary has not yet been launched successfully in this environment.

## Why the markers do not imply a picture

The harness defines `m2-ui` as the string `HALO_PS2_LOCAL m2-ui-map-loaded` ([`tools/test_hcu_boot.py:45-52`](../../tools/test_hcu_boot.py#L45)). CE emits that marker from `game_load()` only after `scenario_load()` returns success for `levels\\ui\\ui` and sets `game_globals->map_loaded` ([`game.c:638-648`](../../submodules/halo-ce-universal/source/game/game.c#L638)). Thus it is meaningful UI scenario/tag-load evidence, but not a renderer marker and not a gameplay BSP acceptance marker.

The ordinary image has a CPU-side snapshot path: `render_frame()` advances render state, prepares a snapshot, and calls the parent snapshot publish hook ([`ps2_render.c:94-124`](../../submodules/halo-ce-universal/port/ps2/src/ps2_render.c#L94), [`ps2_render.c:126-216`](../../submodules/halo-ce-universal/port/ps2/src/ps2_render.c#L126)). The captured successful run's log confirms snapshot binding and a five-qword snapshot-DMA record, but those are not evidence of submitting the world’s BSP draw packets to VIF1/GS. The ordinary `hcu_main.c` reaches `halo_shell_main()` after binding snapshots and probing assets ([`hcu_main.c:370-437`](../../src/stream/hcu_main.c#L370)); it does not call the clear test or an M3 gameplay-scene renderer in its normal profile.

By contrast, the opt-in `HALO_PS2_M3_RENDER_CLEAR_TEST` branch in `hcu_main.c` explicitly builds a GIF packet, clears to RGB `(24,72,120)`, sends it on the GIF DMA channel, waits, and calls `video_present()` ([`hcu_main.c:62-139`](../../src/stream/hcu_main.c#L62), [`hcu_main.c:421-436`](../../src/stream/hcu_main.c#L421)). That blue image is intentionally synthetic; it contains no loaded map geometry. The clear capture is an important partial M3 hardware check, but it cannot be used to say that Halo itself renders.

## Why the supplied PlayStation-format-disc screen appears

The mounted ISO `build/hcu-m1-disc-data.iso` is a data volume containing UI assets; it is not a PS2 boot disc and has no `SYSTEM.CNF` / `BOOT.ELF`. Directly selecting/booting that ISO in the BIOS is expected to show the “Please insert a PlayStation or PlayStation 2 format disc” fallback. This does not contradict successful direct-ELF runs: the harness launches PCSX2 with `-elf <machine.elf>` and optionally supplies the ISO after `--` as CDVD data, with `boot_from_disc=false` ([`tools/test_hcu_boot.py:193-215`](../../tools/test_hcu_boot.py#L193), [`tools/test_hcu_boot.py:360-375`](../../tools/test_hcu_boot.py#L360)). The exact screenshot cannot be tied to a launch without a matching run record, but the data-ISO structure explains the BIOS prompt if that image was selected as boot media.

## Step 10 status and next evidence

Step 10 requires a dual-mode run of the exact same rebuilt ELF/package/source pins, first the UI package and then a capacity-approved gameplay map, with logs, marker, high-water data and a rollback/retry case. It also explicitly excludes accepting UI-only success, a BIOS prompt, or an M1 request marker as M2 completion ([`plans/7.hcu-remake-m2-m4.md:656-662`](../../plans/7.hcu-remake-m2-m4.md#L656)). Current evidence meets only the historical UI-stage portion for ELF `7390…`; it does not meet the current-image pair because `8222…` is blocked by the local PCSX2 Qt/XCB launch failure, and no gameplay map is currently authorized by the memory gate. It also does not prove visible scene rendering.

Recommended next pass, without changing gameplay semantics:

1. Re-run the exact latest `8222…` ELF with the working host display / AppImage extraction setup that previously let PCSX2 launch; record the environment/launcher output and retain an actual viewport capture during marker stability. If display libraries are unavailable in the execution context, keep the result classified as host-infrastructure blocked rather than guest failed.
2. Re-run both interpreter and recompiler on that *same* ELF and same package. Record result/log/settings hashes and compare first guest markers and post-marker fault scans.
3. Preserve separate labels for `m2-ui-map-loaded`, diagnostic clear, actual gameplay-BSP-loaded, and visible gameplay-frame evidence. Do not let a blue clear or a CPU snapshot record stand in for the last two.
4. Only advance to gameplay acceptance once M2 Steps 1–9 settle a lossless map-fit/capacity path and the gameplay candidate's physical tag/BSP split is fixed and measured.

No claim is made here that the game is currently visibly rendering. No current guest failure is inferred from the latest Qt/XCB status-127 attempt. No gameplay-map capacity, rollback/retry, or rendered-scene gate is closed by this report.
