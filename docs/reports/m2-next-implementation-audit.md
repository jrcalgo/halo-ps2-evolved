# M2 next implementation audit: UI lifecycle before capacity changes

**Scope:** report-only audit of the current M2 UI/Blood Gulch loader path, cache and arena ownership, and the next sequential M2 item that can advance without selecting new capacities. No runtime implementation was changed for this report.

## Finding

The next sequential incomplete item is **Remake M2 Step 2: prove CE-global scenario unload and same-process reload for the already-qualified UI package**. It is a stronger next slice than changing the tag-cache/BSP split, enlarging `streaming`, or opening a retail-map catalog entry. The current plan calls Step 2 partial: the prior ELF `4a9bcce6…` reached `m2-ui-map-loaded` and remained stable in both PCSX2 modes, but there is no CE-global `scenario_unload` → arena baseline → same-process reload/rollback trace; the latest `20950de9…` ELF was not guest-run. The UI lifecycle test can use the fixed current boot binding and unchanged UI package, and therefore requires no guessed pool size or reserve use. This is a lifecycle qualification, not evidence that Blood Gulch fits or renders.

The immediate implementation should be a bounded, diagnostic-only same-process UI lifecycle fixture that emits/validates lifecycle state markers in the combined guest. Existing host integration already covers the parent-side half, including same-map deferred revalidation, a file mutation between preflight and reload, retry, and a cache-unpublish-before-owner-release negative control. What remains is executing the CE ownership ordering with live scenario/tag/BSP globals in one guest process. This is the first remaining dependency in M2’s numbered sequence that can be advanced without altering the storage contract.

## Evidence and ownership map

### Boot-time spans and arena ownership

* The HCU map service takes its persistent package owner from `MEM_LAYOUT_V2_STREAMING` and its decompression scratch from `MEM_LAYOUT_V2_FRAME_SCRATCH`; these are independently bound arena objects, not permission to resize them (`src/stream/hcu_map_service.c:174-185`).
* The combined machine binds a tag-cache span and a structure-BSP span at boot before CE allocation (`src/stream/hcu_memory_bind.c:41-56`, `src/stream/hcu_main.c:174-183`). The binding API rejects a different late span after `physical_memory_allocate()` (`submodules/halo-ce-universal/port/ps2/src/ps2_memory.c:91-110,147-155`). Preserve the same base and capacity throughout the proposed lifecycle fixture.
* `world_load_section_with_scratch()` reserves the entire decoded section in its owner and the entire encoded section in scratch, releasing scratch on success and both reservations on failure (`submodules/halo-ps2/engine/src/world/section.c:57-89`). Its API cannot stage retail CTAG/B000 through the present arenas: it is a whole-section reader, not a streaming decoder.
* The UI mount retains CTAG and CRNG in the map owner, then retains CBIX there when the BSP catalogue is installed (`src/stream/ctag_mount.c:112-173,199-235`). The mount keeps the source read callback/context alive for CE’s out-of-image cache reads (`src/stream/ctag_mount.c:9-17,156-172`). The UI test measures `streaming=1,550,572/1,572,864` and `frame_scratch high=275,491/393,216`; this is near-capacity UI evidence, not a retail-map sizing prescription (`tests/test_retail_ui_ctag_mount.py`; `tests/ctag_mount_main.c:360-423`).
* The physical tag cache is a distinct final destination: CE’s cache adapter retains the CTAG payload pointer, validates it against the already-bound cache size, then materializes the compact image into the fixed tag-cache base on the exact tag-data cache read (`submodules/halo-ce-universal/port/ps2/src/ps2_cache.c:114-143,358-397`). Thus the payload/metadata owner and final CE tag image have distinct lifetimes. Releasing the transient owner before cache unmount would leave `mounted_payload` dangling; changing the tag-cache address after CE stores pointers would also invalidate live tag/scenario pointers.
* The selected encoded CBSP is loaded into `frame_scratch`, materialized by the CE cache adapter into the fixed structure-BSP span, and released from scratch after the callback returns (`src/stream/ctag_mount.c:67-104`; `submodules/halo-ce-universal/port/ps2/src/ps2_cache.c:380-418`). Blood Gulch’s current B000 whole-section input is 1,303,092 bytes, larger than `frame_scratch`; this known mismatch must remain a blocker for that map until a separately validated streamed CBSP path exists (`plans/7.hcu-remake-m2-m4.md`, M2 Step 7 evidence; `docs/reports/m2-step7-retail-cbsp-validation.md`).

### Required teardown order

CE owns the published scenario/BSP pointers. `scenario_unload()` first calls `scenario_tags_unload()`, clears scenario/BSP/game-global pointers and indices, then calls `ps2_cache_release_map_owner()` (`submodules/halo-ce-universal/source/scenario/scenario.c:364-389`). The parent unloader releases the active BSP callback, unmounts the CE cache, closes the source, rewinds the map owner to its saved transaction mark, and clears mount state (`src/stream/ctag_mount.c:277-290`; `src/stream/hcu_map_service.c:157-172`). This is the governing lifetime ordering for Step 2; a test that only checks arena cursors misses stale CE pointers or premature cache/source release.

The cache layer refuses to release the parent owner if it has no registered unloader, and reports success only after its mounted CTAG pointer is cleared (`submodules/halo-ce-universal/port/ps2/src/ps2_cache.c:179-185`). A lifecycle fixture should observe this as a boundary, rather than manually calling parent teardown without CE’s scenario path.

## Recommended implementation slice: Step 2 lifecycle guest diagnostic

Keep the catalog guard, memory capacities, HCU tag-cache binding, and package format unchanged. Add one bounded diagnostic mode for the exact UI package to the combined `WORLD_HCU_GAMEPLAY=1` guest:

1. Instrument only the lifecycle boundaries needed for proof: before scenario unload; after `scenario_tags_unload()` and after scenario/BSP globals are null; after the parent owner-release callback; before and after the next UI `scenario_load()`; after CE tag/cache validation; after the initial UI BSP callback; and on final-cycle stable completion. Include a cycle number and map identity. Follow the existing marker convention in `scenario.c:381-385` and UI load marker in `source/game/game.c:633-640`; guard any repeated-load harness behind an explicit diagnostic build/test switch so normal menu behavior cannot loop.
2. At each boundary record the exact relevant state: `map_arena.used`, `section_scratch.used`, mount/source active bits, cache-loaded state, current map identity, scenario and BSP indices/pointers, tag-cache and BSP base/capacity (not contents), open-file count if exposed by the test bridge, and a monotonically increasing render-snapshot generation. Record `high` as diagnostic high-water, but test against `cap`; do not expect high-water to return to baseline.
3. Run `UI load → CE scenario unload → owner released → same-process UI reload` for at least two cycles in one guest process, using unchanged physical spans. The reload needs to traverse CE’s registered callbacks and the cache adapter, not call `ctag_mount_unload()` directly from a host test. Require: after unload, owner/source/cache inactive; CE scenario/BSP globals null; owner cursor exactly at the initial baseline; after reload, the same fixed bases are used, UI tag cache is loaded, UI BSP request succeeds, and owner cursor/high-water are bounded by the already measured UI limits.
4. Include a non-destructive failure-before-unload control: corrupt or invalidate a candidate during preflight and assert that the active UI mount, source, arena cursor, and CE pointers are unchanged. The current test already covers parent-side corrupt-source rejection and old-map preservation; the guest assertion closes the CE side.
5. Include one failure-after-unload control only if it can be injected without mutating production package data: fail the diagnostic’s next mount/read callback after CE has unpublished the old map. Require a deterministic no-map/menu-safe state, all old pointers null, source/cache handles closed, arena at baseline, and a subsequent valid UI retry in the same process. Do not call this “restoring the old map”: the current single fixed tag-cache destination cannot preserve the old tag image while overwritten.
6. Extend the boot harness with a distinct terminal lifecycle stage/marker. The current marker table distinguishes `m1-boundary` from `m2-ui`, but no lifecycle terminal stage exists (`tools/test_hcu_boot.py:26-31`). The runner should keep PCSX2 alive until the final cycle marker, validate ordered cycle indices and state deltas, and preserve ELF hash, source pins, mode/settings hashes, full log, and capture. Run the exact same ELF and UI asset hashes in interpreter and recompiler. A black capture is recorded separately and is not failure of a lifecycle-only test or evidence of a visible scene.

### Acceptance and implementation boundary

Step 2 closes only when both exact guest modes demonstrate the required same-process unload/reload and CE-global ownership values, with an injected failure/retry path, no dangling published pointers, stable arena baseline after every teardown, no handle leak, and no post-terminal guest fault. Keep the current Step 10 gate closed: the service explicitly rejects every non-UI map as `capacity-not-qualified` (`src/stream/hcu_map_service.c:214-238`), the physical tag cache remains the diagnostic 2 MiB span, and Blood Gulch CBSP exceeds current whole-section scratch. Do not enlarge any region or modify `config/memory-budget.json` to implement this lifecycle test.

After Step 2, the next viable coding task is Step 9’s host fault-injection matrix at the current UI callback boundaries. Full L0–L6/retail transaction acceptance must wait for the bounded HP2/CTAG and CBSP designs and measured fixed destination layout described in [`m2-streamed-ctag-destination-design.md`](m2-streamed-ctag-destination-design.md). The Step 2 fixture should not imply those later stages are complete.

## Handoff

**Recommended owner action:** implement the M2 Step 2 diagnostic lifecycle path and runner validation first, without changing arena capacities. Existing host tests remain the fast regression layer. Once the latest ELF can be launched, use the UI guest solely to qualify CE/parent ownership order; then proceed to bounded section decoding and a reviewed fixed tag/BSP layout before enabling a gameplay map. This is an actionable way to move the next numbered gap while preserving the 32 MiB budget and the unspent reserve.
