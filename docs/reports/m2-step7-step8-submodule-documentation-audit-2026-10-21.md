# M2 Steps 7–8 — submodule documentation audit

Date: 2026-10-21
Audience: the implementation owner continuing [`plans/7.hcu-remake-m2-m4.md`](../../plans/7.hcu-remake-m2-m4.md), especially Step 7 BSP relocation/consumer correctness and Step 8 capacity, ownership, and target evidence.
Disposition: documentation-derived guidance only. This report does not change product code, plan status, memory budgets, or map admission. Claims about current implementation must be checked against source, tests, and measurements before acceptance.

## Executive summary

The submodule documentation is useful but uneven:

- `halo-ce-universal/docs/` has two documents, about Custom Edition map/cache behavior and PC mods. The cache document gives a detailed validation/conversion sequence and BSP vertex/pointer constraints, but there is no dedicated CE BSP field-consumer, fog/wind, DMA, PS2 memory, or PS2 runtime guide. The pinned CE source remains the authority for those semantics.
- This checkout has no `submodules/halo-64/docs/` directory. The useful Halo-64 documentation is instead `README.md`, `port/n64/README.md`, `port/n64/NOTES.md`, and `port/n64/HISTORY.md` (plus PC-expansion docs). These show real port changes and real memory/performance failures; N64 endian, memory cuts, tick throttling, actor/script omissions, and renderer assumptions must not be copied as PS2 requirements.
- `halo-ps2/docs/` is the strongest PS2-specific design reference. Its architecture/spec/engine, HP2, BSP, animation, audio, hardware-check, and roadmap documents explain the hardware and the bespoke PS2 renderer. They are not proof that HCU’s current CE-data ownership fits. In particular, its 32 MiB plan sums to zero headroom and its converted `BSPS` sizes describe a custom renderer pack, not the full HCU CTAG+CE CBSP+claims owner.
- PS2 SDK/toolchain docs are mostly short installation or module descriptions. They identify the EE/IOP/DVP split and basic services, but do not establish OPL’s exact mounted roots, IOP preservation, runtime service availability, or target throughput. The OPL README documents app launch-path syntax (including `mass:`) and case sensitivity, not an asset-root API for USB/SMB/HDD.

Most actionable sequence: (1) use `halo-ps2/docs/08-bsp-section.md`’s explicit “not verified/not used” ledger as a checklist of risky fields and converter assumptions, but re-resolve every item against CE source; (2) finish source/member inventory and implement the next raw-map-backed valid fog/weather/wind and visibility tests without making size cuts; (3) keep current BSP/map admission closed while Step 8 produces a lossless owner topology and target-sized high-water evidence; (4) qualify playback through the actual CE request → parent/IOP/SPU2 path, not by treating sound-environment/PAS queries as audio evidence.

## 1. BSP field inventory and source-of-truth boundaries

### CE documentation: useful validation model, not a complete BSP contract

[`custom_edition_caches.md`](../../submodules/halo-ce-universal/docs/custom_edition_caches.md#L170) walks the desktop CE loader in stages: verify cache header and tag ranges, validate tag instances, validate each BSP’s header and structure pointer, check lightmaps/material blocks and uncompressed environment/lightmap vertices, then walk resource-held tags. Its later account says the tag validator checks pointer extents, overlap, counts, indices/enums/references, runtime resets, and graph invariants including collision BSPs ([lines 381–414](../../submodules/halo-ce-universal/docs/custom_edition_caches.md#L381)). This is a good checklist for asking whether HCU’s PS2 path validates a field before use, but it describes the CE PC cache path and must not substitute for inspecting the exact PS2-enabled CE code.

The same document says BSP material vertices feed visibility, collision, and lighting after CE compresses them on BSP load ([lines 297–301](../../submodules/halo-ce-universal/docs/custom_edition_caches.md#L297)). That makes a broad “renderer-owned, therefore dead” classification unsafe: the same serialized material data can support CPU-side selection/collision/light consumers before drawing. HCU must establish which exact calls remain rooted and which the PS2 adapter replaces.

`halo-ce-universal/docs/mods.md` covers replacement resource tags and sound/model/bitmap mod behavior, but not BSP schema semantics or a PS2 sound backend. Treat it as Custom Edition mod-system context only.

### halo-ps2 BSP docs: high-value uncertainty checklist

[`08-bsp-section.md`](../../submodules/halo-ps2/docs/08-bsp-section.md#L16) records its Xbox BSP parser’s own survey over 69 BSPs. It is unusually valuable because it labels assumptions explicitly. Examples to carry into the HCU field ledger:

- There are two cluster-to-surface routes (leaf lists and cluster subclusters); they differ on `b40_c1`, and the converter unions them. It reports 4% of surfaces shared by multiple clusters ([lines 26–38](../../submodules/halo-ps2/docs/08-bsp-section.md#L26)). HCU tests should compare each route and preserve source surface identity; a converter’s union is not proof that CE makes the same choice.
- It drops some unreferenced surfaces based on an explicitly unverified inference about Xbox rendering; render `nodes` purpose is unknown; cluster fog bit 15 meaning was unknown in that document; decals, transition BSP, lens-flare ranges, predicted resources, and portal flags were not carried over; mirrors were not converted ([lines 40–59](../../submodules/halo-ps2/docs/08-bsp-section.md#L40)). Those are exact flags for the source-backed inventory: re-trace in CE, test if behavior-bearing, and do not adopt the omissions by analogy.
- Its BSP collision/visibility tree has converter-specific assumptions about plane/tie semantics, front-child selection, convex portalization and solid-space `-1` results ([lines 22–25, 55–59](../../submodules/halo-ps2/docs/08-bsp-section.md#L22)). These are candidate differential fixtures against CE, not authoritative replacements for CE’s own routines.
- Its `bsp_open` validation suite rejects malformed tables/indices and then checks safe walking under ASan/UBSan ([lines 190–199](../../submodules/halo-ps2/docs/08-bsp-section.md#L190)). The testing method—structural mutation plus complete walk—is reusable. The BSPS v2 schema and its “safe to walk” guarantee do not validate CBSP relocation, CE global publication, or arena rollback.

[`05-halo-ce-data.md`](../../submodules/halo-ps2/docs/05-halo-ce-data.md#L43) says Xbox non-BSP tags include animations/collision/AI/scripts, while bitmap pixels, sound samples and BSPs are outside ordinary resident tag data and streamed by the original Xbox system. Its tag-group map assigns structure BSP content to a separate BSP package. This is useful for finding data categories but the proposed PS2 split must be checked against CE direct pointers and HCU’s actual residency contract; Xbox file-offset streaming does not imply a PS2-compatible replacement.

### Test-design implications by consumer family

**Fog, weather, wind.** The PS2 BSP doc’s fog-bit uncertainty and omitted weather/resource fields make it especially important not to treat a fog-free fallback query as coverage of fog regions. The HCU fixture should derive raw map chains for cluster→fog plane→region→palette/tag and test both sides of the signed plane, invalid indices, and weather fallback. For weather/wind, root the actual CE wind selection/update path and compare weather state/current/particle request decisions against CE tag inputs; a `scenario_location_underwater()` query alone is not a wind or particle test. [`03-engine-architecture.md`](../../submodules/halo-ps2/docs/03-engine-architecture.md#L145) describes only the PS2 engine’s approximate per-cluster fog/render mapping, not the CE gameplay contract.

**Geometry/visibility.** Use the source’s cluster surface routes, PVS, portals and lightmap/material ranges as independent ledgers. Verify CE surface-reference/visibility output against raw Xbox records, then join surface IDs to the corresponding HP2 converter output. The PS2 converter’s documented omissions and reordering must be visible in that mapping. Do not compare positions alone: the PS2 geometry pack may omit or reorder source surfaces, while CE CPU consumers use source material/vertex fields.

**Sound.** Separate: (a) CE cluster sound-distance/PVS and environment selection; (b) CE sound event/looping selection and a normalized sound request; (c) resource lookup/streaming; and (d) PS2 IOP/SPU2 playback, voice exhaustion, format decode, and reverb. `03-engine-architecture.md` sketches a PS2 design with 48 voices, 8 reserved and 40 pooled, priority eviction and environment-to-reverb mapping ([lines 200–205](../../submodules/halo-ps2/docs/03-engine-architecture.md#L200)); these are design statements for that engine, not evidence of HCU’s current audio implementation. Assert request identity, position/gain/pitch/loop state and resource lifetime before requiring audible output; then run target/PCSX2 audio tests.

**Collision.** Use CE’s actual vector/pill/sphere wrappers and material/leaf outputs, with independent expectations decoded from the source map. The PS2 BSP notes’ `front >= 0`/tie assumptions are useful for selecting plane-side/tie tests, not a substitute for CE source. In addition to hit tuples, test directional misses, coincident surfaces, shared edges/vertices, invisible/two-sided filters, breakable-state transitions, invalid leaf/index and repeated BSP switches. The submodule BSP docs do not cover CE wrapper filters or HCU collision-owner publication; those require source/test fixtures.

**Relocation failure atomicity.** The PS2 pack design validates offsets/ranges before exposing section views and documents CRC/bounds reader tests in [`07-hp2-format.md`](../../submodules/halo-ps2/docs/07-hp2-format.md#L1); `08-bsp-section.md` illustrates post-open safe-accessor validation. Adopt the principle “validate fully before publication,” but test HCU’s own transaction boundaries: candidate BSP bytes, source/destination non-overlap, parent owner and scratch cursors, CE structure/collision/BSP globals, cache publication, claims, and retry after each injected failure. A format-level parser returning a cleared view does not prove CE/arena rollback.

## 2. Residency, PS2 hardware, streaming and capacity

### Hardware facts and measurement cautions

`01-ps2-architecture.md` provides concrete hardware constraints: EE is 294.9 MHz, in-order with an 8 KiB D-cache and no L2; pointer-heavy/random access can be costly; 16 KiB scratchpad is DMA-able; 32 MiB RDRAM includes a 1 MiB low kernel reservation; and EE, DMAC, GIF and IPU share bandwidth ([lines 29–48](../../submodules/halo-ps2/docs/01-ps2-architecture.md#L29)). For the BSP tree and collision loops, measure realistic access patterns and CPU cycles, not just bytes. Do not copy Halo-64’s N64 tick decimation to hit performance targets; first profile R5900 code and preserve CE cadence/behavior.

The same document says DMA transfers use 16-byte quadwords, describes `REF`/source chains, VIF unpack, and concurrent GIF PATH3 texture uploads/PATH1 drawing ([lines 73–86](../../submodules/halo-ps2/docs/01-ps2-architecture.md#L73)). This supports alignment and ownership requirements for actual DMA command/data buffers and immutable render snapshots—not a blanket 16-byte alignment policy for every CE datum. Check that each DMA span has a single owner, aligned boundaries, and lifetime until completion/fence.

PS2 4 MiB GS eDRAM is also shared between framebuffers/Z and texture window; the document budgets about 2.25 MiB for textures after 512×448 color/Z buffers ([`01-ps2-architecture.md:133-143`](../../submodules/halo-ps2/docs/01-ps2-architecture.md#L133)). This store is not free EE tag capacity. If HCU’s parent owns geometry/texture packs in EE staging or DMA, count that EE staging too; GS-resident texture bytes cannot satisfy arbitrary CE pointer dereferences.

### The PS2 spec is a target proposal, not capacity evidence for HCU

[`02-specs.md`](../../submodules/halo-ps2/docs/02-specs.md#L111) proposes this 32 MiB partition: 1 MiB kernel, 2.5 MiB code/static, 9 MiB resident mission, 7 MiB current BSP, 6 MiB textures, 2.5 MiB dynamic sim, 1 MiB DMA, 1.5 MiB streaming, 0.5 MiB checkpoint, 0.5 MiB audio and 0.5 MiB scratch. It totals exactly 32 MiB with zero headroom, and the document itself says it must be measured/rebalanced ([lines 111–130](../../submodules/halo-ps2/docs/02-specs.md#L111)). Its regions differ from the active HCU plan/memory map. It must not be imported as authorization to enlarge HCU arenas, spend reserve, or classify overlapping stores twice.

The same specification reports original Xbox non-BSP resident tag data of 8.5 MiB (`c20`) to 16.2 MiB (`b40`) before platform conversion and separates raw bitmap/sound/BSP media ([lines 57–68](../../submodules/halo-ps2/docs/02-specs.md#L57)). This corroborates that capacity pressure is real but not the exact PS2 HCU lower bound: the final answer depends on which fields remain CE-addressable, which data has a tested replacement, and simultaneous transition/streaming peaks.

The PS2 `BSPS` renderer section reports largest converted geometry/visibility sections from about 2.47–3.83 MiB among campaigns ([`08-bsp-section.md:201-217`](../../submodules/halo-ps2/docs/08-bsp-section.md#L201)). Those are custom converted VIF packs, not the serialized CE `structure_bsp` image plus collision BSP and claims. Do not use “largest BSPS fits 6/7 MiB” as evidence that HCU’s CE BSP fits. Conversely, if both CE data and BSPS are simultaneously resident, charge both until a source-backed replacement/lifetime test proves one can be released.

The BSP data page’s `LMn` table gives converted lightmap measurements and explicitly assigns them to the shared 6 MiB texture pool, with one BSP’s pages resident at a time ([`09-tex-section.md:118-182`](../../submodules/halo-ps2/docs/09-tex-section.md#L118)). It also says lightmap luminance scale mapping remains unverified. Use these numbers only for that converter output and do not conflate lightmaps, texture cache, DMA upload copies, or raw CE tag/cache data.

### Streaming, DVD, and sound stores

[`07-hp2-format.md`](../../submodules/halo-ps2/docs/07-hp2-format.md#L1) states HP2 payloads are 2048-byte aligned for DVD sector reads, section contents align to 16 bytes, and the reader validates sizes/overlap/CRC before exposing sections. The engine architecture proposes one mission RES, a BSP arena reset on BSP switch, and sound/texture residency ([`03-engine-architecture.md:190-205`](../../submodules/halo-ps2/docs/03-engine-architecture.md#L190)). These provide candidate ownership and transition dimensions to measure: source buffer, decompression scratch, final destination, old-map/BSP lifetime, new candidate lifetime, and pack/texture/audio DMA overlap.

`01-ps2-architecture.md` marks its 4 MB/s average DVD rate as a plan and seeks as 100–300 ms; the ≤8 MB BSP transition is a derived goal, not verified drive throughput ([lines 162–167](../../submodules/halo-ps2/docs/01-ps2-architecture.md#L162)). Likewise, its IOP 5–10 MB/s decompression note is labeled a plan ([lines 145–153](../../submodules/halo-ps2/docs/01-ps2-architecture.md#L145)). Benchmark actual codec, IOP/EE route, OPL source, and map file layout before adopting load-time claims.

SPU2 and IOP have separate capacity: architecture docs give 48 ADPCM voices and 2 MiB sound RAM ([`01-ps2-architecture.md:145-160`](../../submodules/halo-ps2/docs/01-ps2-architecture.md#L145)); `02-specs.md` proposes 1.5 MiB banks, 256 KiB stream ring and ~200 KiB reverb area ([lines 127–130](../../submodules/halo-ps2/docs/02-specs.md#L127)). These stores can move sample residency out of EE only after actual streaming/replay and lifetime interfaces are proven; they cannot replace EE-resident sound tag structures or CE selection state. Record both EE staging and SPU2 allocation once each, not as the same bytes.

### Animation residency experiment: what the docs permit and what they do not

[`12-anim-section.md`](../../submodules/halo-ps2/docs/12-anim-section.md#L25) documents substantial Xbox animation data and quantized PS2 section sizes (e.g. 1.83 MiB `a30`, 2.34 MiB `c10`) with sampled source-frame error figures ([lines 139–160](../../submodules/halo-ps2/docs/12-anim-section.md#L139)). It also expressly says graph state tables and animation sound/frame references are not converted ([lines 43–51](../../submodules/halo-ps2/docs/12-anim-section.md#L43). This is a candidate for *measuring* a typed external/pinned representation, not proof that HCU CE can drop its in-place structures. The reported 5–7 μs per character is extrapolated from an Apple-core sample using a rough 20–30× factor, not an EE measurement; test R5900 cost and exact runtime consumers before accepting it. Any lease experiment must include the animation data’s CE graph/state consumers, active pose/frame pointers, BSP/encounter load overlap, cache pin count, I/O deadline, release on transition/failure, and parity against full resident data.

## 3. Halo-64: useful lessons vs. non-transferable port changes

### What actually changed for Halo-64

`port/n64/README.md` documents the actual platform prefix as big-endian MIPS with 32-bit pointers/longs and 16-bit `wchar_t`, and the source build marks departures with `HALO_N64`; it uses a custom converter, N64 renderer/HUD/particle/sound glue, and explicit generated stubs ([README](../../submodules/halo-64/port/n64/README.md#L264)). The port description states the N64’s 8 MiB budget and the conversion/streaming strategy, and lists severe reductions to simulation update cadence ([README lines 264–286](../../submodules/halo-64/port/n64/README.md#L264)). It also explains code ownership between decomp source, generated stubs, platform layer, and game glue ([lines 290–336](../../submodules/halo-64/port/n64/README.md#L290)).

`NOTES.md` gives a precise reminder that an omitted renderer still has to maintain CE CPU state: frame index, camera/frustum, first-person pose update, HUD timers/sounds, window bounds, and vblank state ([lines 33–62](../../submodules/halo-64/port/n64/NOTES.md#L33)). This is directly useful when deciding whether an HCU rasterizer symbol is draw-only or advances timers/visibility/animation. Reimplement the required state against HCU source and the PS2 renderer interface; do not transplant N64 constants or its video/input choices.

`HISTORY.md` records observed N64 memory fragmentation, cache failures, high CPU costs, and fixes ([e.g. lines 48–61, 398–414, 430–444](../../submodules/halo-64/port/n64/HISTORY.md#L48)). The transferable lesson is to measure largest-free-span/high-water/owner release and capture runtime failures—not to adopt the N64’s 288 KiB object budget, reserve pools, scene culling distances, or tick throttles. It documents update-rate reductions used because four-bot collision/physics exceeded N64 frame capacity ([lines 63–75](../../submodules/halo-64/port/n64/HISTORY.md#L63)); PS2 must profile without changing CE cadence or behavior unless a separately approved parity-preserving policy is proven.

### Non-transferable differences

- Big endian and N64-specific ABI are opposite the PS2’s little-endian R5900 ABI; use Halo-64 only for the general prefix/`HALO_*` convention, not its types or layout flags.
- N64’s 8 MiB RAM, cartridge file model, RSP/RDP, libdragon allocator and renderer are not PS2 limits or APIs. The PS2 has 32 MiB EE RAM, VU/GS/DMAC and separate IOP/SPU2 stores.
- Halo-64 omits/changes features to fit its product. Its README says actor AI except pathfinding, HaloScript, network and Xbox renderer are excluded and game/platform calls use stubs; this project requires campaign AI/scripts and a PS2 rendering/audio adapter. Stub only a call whose source caller is proved outside scope or whose state effect is separately preserved.
- N64 audio formats/mixer, map streaming policy, AI update intervals and ROM/expansion map behavior are not sources of CE parity values.

## 4. Other PS2 submodule documentation: practical value and gaps

### SDK, toolchains, file and boot services

`ps2sdk/README.md` describes separate EE and IOP trees and lists pad/multitap, memory card, USB, HDD, CD/DVD, sound and host network-file capabilities ([lines 15–42](../../submodules/ps2sdk/README.md#L15)). It is a capability inventory, not proof of which modules are mounted under OPL or what the current game initialized. `ps2dev/README.md` and `ps2toolchain/README.md` explain environment/build composition; the EE, IOP and DVP toolchain READMEs state they build separate compiler/toolchain outputs. They are relevant to reproducible builds but contain no application RAM budgets or runtime performance guarantees.

The inspected PS2SDK `sysmem`, `dmacman`, `sifman`, `loadfile`, `ioman`, and `fileio` READMEs are brief. They repeatedly describe IOP modules and note that several are already loaded at IOP boot/need IOPRP integration; `ioman` itself says `iomanx` is likely preferred. This strengthens the requirement to inspect the actual EE↔IOP ABI and OPL boot state; it does not establish that calling module-load/reset APIs is safe under OPL. The `libspu2` and `libsnd2` READMEs only identify PS1-library ports for SPU2, and do not document the HCU mixer, sound DMA ownership, or reverb memory layout. Inspect PS2SDK source/API docs and the game’s actual initialization, then qualify on the target.

`ps2link/README.md` describes a bootloader that downloads/executes EE or IOP programs, loads its IRXs at startup and depends on network modules ([lines 16–39](../../submodules/ps2link/README.md#L16)). `ps2client/README.md` documents `execee`, `execiop`, memory dump, VU and GS debug commands ([lines 41–106](../../submodules/ps2client/README.md#L41)). These can aid target measurements, crash captures and smoke tests, but ps2link is development infrastructure, not a shipping game storage service.

### OPL scope

The checked-in OPL README says apps may be configured with a device identifier and exact ELF path; it gives `mass:APPS/MYAPP.ELF`, says OPL path case is significant, and shows `title.cfg` launch configuration ([`README.md:155-218`](../../submodules/opl/README.md#L155)). It does **not** specify the game process’s post-launch asset-root paths, reliably mounted SMB/HDD prefixes, read semantics, file I/O RPC lifetime, or module-preservation contract. Consequently:

- Treat `mass:` and the exact case as a confirmed example for launching an app only.
- Do not infer `smb:`/`pfs0:`/`mass:` asset access merely because a path appears in other OPL documentation or code. For each source profile, perform real open/stat/seek/read/close after OPL launches the game.
- No documentation inspected here proves `SifIopReset` is safe. The active OPL IOP mount/file services must be queried/reused, and actual OPL launches must verify the selected root; the plan’s no-reset behavior remains a runtime requirement to test.

## 5. Documentation-guided implementation priorities

1. **Finish the raw CE BSP field/member ledger before any field removal.** Start from CE’s `structure_bsp_definitions.h` and schema, enumerate every top-level/nested member, and search all CE source accesses/call paths under the exact PS2 manifest. Use the omissions/uncertainties in `halo-ps2/docs/08-bsp-section.md` as a “must explicitly resolve” list: unreferenced surfaces, render nodes, cluster fog-bit interpretation, decals, transition BSP, lens-flare markers, predicted resources, portal flags, mirror content, triangle winding, ties, concave portals, and solid/outside leaf results. Add explicit columns: CE read/write sites, rooted/live status, PS2 replacement owner, source oracle, runtime test, capacity charge, disposition. The current plan already requires preserving BSP families absent tests; this report adds doc-derived unresolved categories, not new authorization to strip.
2. **Next environment subcheck: test CE source selection, not the converter’s approximation.** Choose raw BSP examples with valid fog plane/reference chains. Add both-sides region selection, fog palette→tag reference, underwater plane distance, region-vs-cluster weather fallback, invalid bounds/failure atomicity. Separately root CE wind and test weather state/vector/current. Use CE source + raw map oracle; the bespoke PS2 renderer’s per-cluster planar fog and global-fog approximation are not CE expected semantics.
3. **Then visibility/material correspondence.** Execute CE CPU visibility/surface preparation on a package-published BSP. Compare list membership, duplicates/shared-cluster surfaces, material intervals, vertex indices, lightmap ranges, portals and PVS to raw Xbox source. Join every retained source surface to converter output; separately report surfaces with no pack representation and data transformed/quantized. No size credit until every enabled CE consumer has a parity-preserving replacement and total bytes/lifetimes are charged.
4. **Close sound as a multi-boundary feature.** First verify CE sound selection and looping/event request for BSP-based environment and location. Then verify sound tag/permutation resource read and expected sample payload, conversion to PS2 ADPCM where applicable, IOP upload, voice allocation/eviction and SPU2 output. Bound concurrent EE staging/SPU2 bank/ring/reverb, and test voice saturation/loop stop/restart. Existing BSP PAS/environment checks do not imply playback.
5. **Keep relocation failure atomicity separate from parser rejection.** Mutation tests should snapshot input, final BSP destination, claims, scratch/owner cursors, CE tag/scenario/BSP/collision globals and selected BSP index. Inject failures before write, after candidate bytes are staged, during pointer relocation, CE schema validation, `structure_bsp_port_verify`, and after activation. Require either the exact prior published state or a specified safe-empty state, followed by successful same-process retry. The PS2 reader’s safe-walk suite suggests exhaustive bounded corruption; only HCU’s real interface test proves HCU rollback.
6. **Design Step 8 from measured simultaneous owners, not spec table arithmetic.** Start with exact current linker/ELF physical placement and the current plan memory map. Measure every campaign map’s CTAG, CE CBSP, claims, persistent render pack/texture ownership, source/decode scratch, transition double-residency, animation pin/high-water, and dynamics. Preserve the existing reserve. A proposal must be lossless and point-aware for CE’s in-place `tag_block`/`tag_data` model, or explicitly replace the CE pointer API with tested indirection. Report per-region current/high-water/peak overlap; include unaligned tails and DMA-visible spans exactly once.
7. **Measure EE cost and DMA hazards on the real build.** PCSX2 interpreter/recompiler are useful correctness checks; `halo-ps2/docs/01` and `06-decisions.md` explicitly caution that PCSX2 may hide cache/DMA/GS behavior. Capture COP0 cycle counts for collision, fog/weather, visibility, compression, sound update and map load; profile cache miss/pointer traversal and DMA fence/wait. Use static linker map, runtime arena sentinels, VIF/GIF completion, and real-hardware profiling where available. Do not reduce update cadence solely by copying Halo-64.
8. **Qualify OPL paths independently from ISO and ps2link.** Use OPL launch examples only to configure `title.cfg`/app paths. On USB, SMB and internal HDD profiles separately, prove the actual post-launch mount root and bounded read APIs with repeated failure/retry/unload. Keep ISO/PCSX2 as other distinct transports. No device path counts as supported until its real operations and IOP-state constraints pass.

## 6. Halo-64 citation use and REA applicability
