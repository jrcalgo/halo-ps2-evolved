## Address math: plausible explanation, not a captured cause

The source layout makes the proposed mechanism technically plausible:

- `struct hs_stack_frame` has `data` at byte offset `0x0e`, while the structure's size is `0x10` on the target (`source/hs/hs_runtime.c:408-415`). The first word in the payload is therefore two bytes off a 4-byte boundary when the frame header itself is aligned.
- A thread's base stack points to `thread->stack_data` (`hs_runtime.c:1354-1363`); `stack_data` begins at offset `0x18` in a `0x218`-byte datum (`hs_runtime.c:424-435`). Game state is allocated on 16-byte boundaries by the parent (`src/stream/hcu_memory_bind.c:47-53`), and the CE bump allocator requires every allocation size to be a multiple of four (`source/saved games/game_state.c:549-581`). The 0x38-byte data-array header and 0x218-byte datum stride are both divisible by four, so a properly initialized thread's base frame is 4-byte aligned.
- On that base frame, raw `frame->data` is at stack_data+`0x0e`, hence address mod 4 = 2. If an earlier allocation leaves `frame->size == 0x14`, the old expression `frame->data + frame->size` yields stack_data+`0x22`, exactly the prior reported target. A `long`/`real` load/store there is halfword-aligned but not word-aligned and can produce the R5900 address error. This is a plausible reconstruction from the base-frame geometry; no trace captured the actual `frame->size` or instruction.
- The new code aligns the *effective result pointer*, not merely the offset: it computes `frame->data + allocation_offset`, adds the zero-to-three-byte correction needed for 4-byte alignment, returns that pointer, and advances `frame->size` through the padding (`hs_runtime.c:2867-2913`). In the example above, it adds two bytes, moving the long from stack_data+`0x22` to stack_data+`0x24`.
- Pushed frame headers now round the previous frame's payload byte-count up to a multiple of four before adding `sizeof(struct hs_stack_frame)` (`hs_runtime.c:1396-1428`). Given an already aligned current frame, this preserves 4-byte alignment for every subsequent frame header. The actual game-state base and run allocation arithmetic meet that initial alignment premise.

The two exact candidate runs no longer reproduce the earlier post-marker address errors or branch-delay message during their 30-second stable windows. This is strong regression evidence that the alignment change plausibly addresses the observed failure. It is not instruction-level proof: the logs still contain no EPC/BadVAddr register frame, and the earlier trace's BadVAddr is not an EPC. A second interacting change or timing-dependent path cannot be excluded.

## Parity and safety assessment

**Positive:** The behavior change is under `#ifdef HALO_PS2`; the normal CE/x86 packed-stack path remains unchanged. The code leaves the tag/datum and scenario layouts intact and aligns only temporary interpreter-stack allocations/headers before the EE consumes word-sized pointers. The correction is calculated from the actual address (using `uintptr_t`), which is more robust than assuming `frame->data`'s base alignment. The generated UI tag data and game-state allocation sequence are unchanged in these runs.

**Important remaining correctness issue:** `expression_get_function_name` reads the first stack payload word directly as `*(long *)thread->stack->data` (`hs_runtime.c:933-962`, especially line 956). Under the new scheme, `hs_stack_allocate` may return `frame->data + 2` for that first word; this raw reader is not updated to skip the padding. Its value can become a blend of the two bytes before the aligned word and two bytes of the stored value, and the raw load itself can still be unaligned. The callsite is reached when debug scripting is enabled and a thread is inside a pushed frame (`render_debug_scripting`, `hs_runtime.c:1025-1075`), so it may be a diagnostic-only/conditional path, but it must be made alignment-aware or explicitly proven unreachable in the shipped PS2 build. This is a real semantic/read-path mismatch in the current patch and should be resolved before calling the change broadly safe.

**Capacity and malformed-state risks:**

- Alignment consumes up to three additional bytes per allocation and up to three per pushed frame. The per-thread scripting stack remains fixed at `0x200` bytes (`hs_runtime.c:311-313,434`); deeply nested or allocation-heavy scripts may now reach overflow sooner than CE/x86. This is a deliberate bounded-memory tradeoff for EE safety, but must be measured against campaign/UI scripts rather than assumed harmless.
- Existing overflow handling should be verified at the new boundaries: `hs_stack_allocate` must reject before writing beyond the inline buffer and return `NULL`; `hs_stack_push` must reject a frame whose header/end exceeds the buffer; and `hs_stack_overflow`/`hs_thread_main` must stop and unwind the script without affecting neighboring thread data (`hs_runtime.c:1410-1447,2867-2913,2760-2789`). Tests should cover exactly-at-limit, one-/two-/three-byte padding pressure, repeated mixed-size allocations, and deep nesting with canaries on the next datum.
- Both functions read the current stack/frame metadata before all validation is complete (`hs_stack_push` reads `thread->stack->size` before its `valid_thread` assertion; `hs_stack_allocate` reads `frame->size` and forms a candidate address before its assertion). That ordering predates much of the current logic, but alignment makes pointer assumptions central. Test or harden invalid/negative `frame->size`, out-of-range/misaligned `thread->stack`, and arithmetic-overflow cases; do not allow a negative size to turn into a candidate pointer before rejecting it.
- `valid_thread` checks the current stack pointer and the payload/fill-mark end but does not assert that a frame pointer is word-aligned (`hs_runtime.c:346-350`). `hs_stack_push` preserves alignment only if the current pointer is already aligned. Add an invariant test (and preferably a validation guard) that every active frame header is 4-byte aligned and lies wholly within this datum's stack buffer.
- Padding changes the byte-level representation of transient script frames. That is appropriate for a target-only ABI adaptation, but saved-game/core snapshots containing active HS threads must either be rebuilt/reinitialized safely or have their stack state validated/rebased; do not assume raw PS2 snapshots remain interchangeable with prior packed-layout states.

## Acceptance tests recommended before wider M2 closeout

1. **Host/EE address arithmetic unit fixture:** exercise payload bases whose address modulo four is 0, 1, 2, and 3; allocate 1-, 2-, and 4-byte values followed by long/real values; assert every pointer used as `long *`/`real *` is 4-aligned, payloads do not overlap, and `frame->size` includes the alignment gaps. Mirror the target's `data`-offset-14/structure-size-16 layout.
2. **Push/pop invariant fixture:** generate prior frame payload sizes in every residue class 0–3; assert the pushed frame address is 4-aligned, `previous` links and script values survive, and pop restores the exact prior frame. Include frames nested until the last representable header and verify no write crosses the 0x200-byte stack boundary.
3. **CE-behavior fixture:** execute representative script bytecode involving global initialization, nested function arguments, short integer + long/real mixtures, begin/if/cond/and/or, sleep/wake/resume, and return values; compare logical results and event order against the CE/x86 path. Specifically enable `debug_scripting` and exercise `expression_get_function_name` so line 956 cannot silently read the pre-padding location.
4. **Overflow/canary fixture:** force `hs_stack_allocate` and `hs_stack_push` to the exact boundary and one byte beyond using varied alignment residue; require a single script-stack-overflow outcome, no null dereference, no neighbor datum/canary mutation, and no resumption of the failed script. Measure high-water/overflow for all UI and campaign script sets that M2/M3 will load.
5. **Guest regression:** retain the exact candidate's interpreter and recompiler 30-second stability results, then run the relevant retail map/script scenario that previously exercised the fault; continue to demand no post-marker EE address error, branch-delay exception, invalid datum access, or memory-canary damage. The current UI-only run is not that broader scenario.

## Conclusion

The alignment mechanism is well motivated and the exact old address has a compelling base-frame derivation: `sizeof(frame)=0x10`, `offsetof(data)=0x0e`, and a payload cursor at `0x14` produce the old `stack_data+0x22` word access. The exact candidate now passes 30-second stable UI-marker windows under both interpreter and recompiler, with the old post-marker faults absent. Thus the patch is a plausible, target-local fix and a meaningful regression improvement, but it is not yet proven as the unique root cause without EPC/watchpoint evidence. It also leaves a direct unaligned/raw payload reader at `expression_get_function_name` and needs explicit stack-capacity, overflow, canary, debug-reader, and CE-parity tests before the HS stack adaptation can be considered complete.
