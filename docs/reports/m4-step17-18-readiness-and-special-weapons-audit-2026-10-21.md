## M2/M3 dependency gate: why M4 runtime acceptance cannot start yet

1. **M2 map admission is still fail-closed.** [`src/stream/hcu_map_service.c`](../../src/stream/hcu_map_service.c#L288) admits only the UI leaf while gameplay working-set/capacity is unqualified. The map-capacity and transaction reports distinguish UI host/guest lifecycle from a gameplay BSP load. A pistol smoke with a synthetic target or UI-only scenario cannot provide the collision surfaces, material identifiers, actor set, scenario weapon tags, or map-owned datum lifetimes required by the M4 rows.
2. **M3's production CE collision owner is not established.** The latest render/collision audits describe a synthetic CE-vs-parent pill fixture, not a production map tick. M3 still needs the real CE object lifecycle and collision result to reach target datum, collision model region/material, and damage resolution as one authoritative path. The M4 ledger explicitly says not to route parent `shot_tick()` into HCU as a shortcut; see [`m4-combat-link-readiness.md`](../hcu-source-backed-review/m4-combat-link-readiness.md).
3. **No integrated CE weapon tick has been demonstrated in the current guest.** The last evidence summarized by the readiness report is an earlier memory-ready run that deliberately stops before `game_initialize_done`; the more recent user-provided M1 observation likewise terminated at memory-ready and did not test weapons. Linked symbols (`game_tick`, `weapon_new`, `projectile_new`) establish compiled closure only. A valid next M4 prerequisite is a current pinned image that initializes a real scenario, creates a CE-owned player/weapon/target, and calls the normal `game_tick` path.
4. **The budget is a runtime gate, not a pool-size guess.** `dynamic_simulation` is 2,621,440 bytes and M4 requires recording its combat high-water while keeping the 5,767,168-byte reserve untouched (plan lines 482–486 and 510). The existing M1 arena observation does not contain projectiles/effects or actor-combat high-water.

These are dependencies, not reasons to rewrite M4 acceptance. Work may continue on report-only source fixtures and a narrow deterministic allocator seam, but do not call a Step 17 row ready or run Step 20 until the M3 production interfaces exist.

## Step 17 audit — ledger is structurally useful, behavior rows are not ready

The ledger currently covers all 23 weapon paths and names the needed axes: trigger cadence/ammo/reload/charge/heat, material and hit region, shields/death, AoE/effect/ownership, exhaustion, replay, and render-schedule invariance. It distinguishes the limited parent smokes from HCU acceptance and keeps vehicle/actor origins separate from camera-fired player tests. The current test `tests/test_m4_weapon_acceptance_ledger.py` is an integrity test: it validates row count/content/open dispositions, not loaded-tag resolution, simulation, object ownership, or weapon parity.

**Concrete Step 17 gap:** there is no machine-readable row-to-fixture/evidence matrix tying each canonical `weap` root to (a) the exact resolved weapon and nested projectile/effect/damage tag hashes, (b) its required trigger/event sequence and expected state fields, (c) the correct firing-origin provider (player marker, actor marker, vehicle/turret mount), (d) CE source oracle, and (e) host and interpreter/recompiler run IDs. The Markdown ledger lists dimensions but not reproducible, per-row readiness artifacts. It must be extended without turning `OPEN` into “ready” just because tags resolve. A row can become ready only after an integrated fixture uses the actual CE datum/update/collision/damage path and supplies exact source and runtime identities.

**Recommended next Step 17 slice:** define one schema-backed ledger manifest and a validator, then populate it for one ordinary projectile weapon (pistol) and the three retained special weapons as *fixture specifications*, not passes. Required fields should include canonical path and tag/content SHA; trigger index and input frames; owning unit/player/actor/seat handle; spawn marker/origin; expected ammo/heat/trigger state; projectile/effect/damage handles; target datum and material/region; RNG state; tick; pool high-water; map+BSP+schema/build hashes; source function references; expected result and tolerances; interpreter/recompiler run IDs. Keep every `runtime_status` OPEN until actual fixture output exists. Then expand to all 23 rows and grenade/objective rows.

Useful CE source anchor set: `game_tick()` ordering in [`source/game/game.c`](../../submodules/halo-ce-universal/source/game/game.c#L331); `weapon_new()` initialization in [`source/items/weapons.c`](../../submodules/halo-ce-universal/source/items/weapons.c#L845); marker/owner/aim selection in `trigger_create_projectiles()` ([`weapons.c:2373-2435`](../../submodules/halo-ce-universal/source/items/weapons.c#L2373)); trigger/ammo/effect/misfire and projectile creation in `weapon_trigger_fire()` ([`weapons.c:2591-2858`](../../submodules/halo-ce-universal/source/items/weapons.c#L2591)); charge/overheat/underwater gate in [`weapon_trigger_begin_firing()`](../../submodules/halo-ce-universal/source/items/weapons.c#L2863); projectile creation/update/detonation in [`projectiles.c`](../../submodules/halo-ce-universal/source/items/projectiles.c#L521), [`:665`](../../submodules/halo-ce-universal/source/items/projectiles.c#L665), and [`:1337`](../../submodules/halo-ce-universal/source/items/projectiles.c#L1337); target material/region and vitality in [`objects/damage.c`](../../submodules/halo-ce-universal/source/objects/damage.c#L1680).

## Step 18 audit — missing fixture, and a source-order correction to its assertion

The required fixture does not exist. The ledger correctly notes that parent `combat_world`, `shot_world`, or a synthetic fixed target would exercise a different allocator and fail to prove CE pool behavior. There is no checked-in, callable CE weapon→projectile→effect path with deterministic failure injection at its actual allocation boundary; adding such a seam is prerequisite work, not permission to rewrite gameplay or make M4's simulator in the parent.

The Step 18 sentence currently asks for a failed extra shot to leave the tick random seed unchanged. **Do not encode that as an unconditional invariant.** Pinned CE source consumes/decrements magazine rounds in `weapon_trigger_fire()` before its later call to `trigger_create_projectiles()`; firing-effect selection / shot-count / misfire RNG can also occur before projectile allocation ([`weapons.c:2620-2646`](../../submodules/halo-ce-universal/source/items/weapons.c#L2620), [`:2660-2745`](../../submodules/halo-ce-universal/source/items/weapons.c#L2660), and [`:2785-2820`](../../submodules/halo-ce-universal/source/items/weapons.c#L2785)). The projectile allocator failure therefore may legitimately follow CE-prescribed weapon-state or RNG changes. A rollback that restores ammo/RNG could itself diverge from CE. The invariant must instead be: the post-failure state equals the pinned source-order oracle for allocation failure at that exact boundary; unrelated live object transforms/vitality and pool links remain intact; no partial projectile/effect datum leaks; and the remainder of the tick remains valid. If the desired product specifically requires atomic rollback, document it as a `port:` deviation and add an explicit parity exception, rather than calling it stock CE parity.

**Concrete Step 18 fixture:** create an opt-in host test seam around the *real* `object_new`/projectile/effect allocation boundary (or the narrow allocator function it calls), with failure injection that does not replace the combat update implementation. Initialize through CE map/tag/object setup, provide a valid weapon and owner, then run `game_tick` with a deterministic seed. Record pre/post canonical state in source order. Cases: projectile pool one-under-capacity then at capacity; effect allocation failure after projectile allocation; simultaneous two explosive events; and follow-up tick proving all surviving handles remain valid. Assert the exact source-prescribed ammo/heat/trigger/RNG changes, and assert non-target object bytes, links/generations, health/shields/transform/velocity are untouched. Run render-publish zero/one/multiple times between ticks and require identical simulation hash. In the plan, replace “random seed unchanged” with “random state matches source-oracle delta; no extra or missing consumption attributable to failure handling.” The fixture only becomes M4 evidence after current M2/M3 ownership exists and its toolchain profile matches target layout.

## Special weapons — required distinctions and next executable fixtures

All three user-retained special weapons remain part of the product. Their current parent profile/presentation code must not be deleted until HCU's integrated path and the presentation adapter replacement pass their scheduled gates. The special weapon host test is source/tag regression only (6 tests per current plan line 504), not simulation.

### Fuel Rod: replace the parent combat implementation with CE's generic path, not a hand-tuned clone

Retail tag audit says handheld `weapons\\fuel rod gun\\fuel rod` uses CE's generic trigger/projectile path, with one projectile, 10 rounds/s, 1.25-second charging, 4 loaded/12 reserve, and a surprising `rounds_per_shot == 0`. Its direct impact damage is null; its material responses choose the tagged effect/detonation route and the linked blast carries the 40/75/75 damage plus owner immunity and “detonate explosives” flags. See the audited tag crosswalk in [`m13-step10-fuel-rod-flight-investigation.md`](../m13-step10-fuel-rod-flight-investigation.md#L246) and detailed projectile/effect notes around [`:1297`](../m13-step10-fuel-rod-flight-investigation.md#L1297).

The codebase currently retains the parent M13 Fuel Rod profile and flight/effect metadata in `src/game/play_fp.c`, `src/game/arsenal.c`, `src/game/shot.c`, and related tests. This is transitional—not proof HCU replaced it. Step 17 must specify the exact CE weapon datum, trigger, projectile definition, owner/ultimate-parent, material response, detonation/effect graph, and victim list. First special vertical slice should compare marker origin/velocity and trigger state with CE tag/source, then surface/material response, then water transition, then exactly-once AoE and owner filtering. Do not decrement one round merely because the parent implementation does so; verify CE's zero-cost semantics and trigger gates from the pinned code.

### Energy Sword: stock CE timing/arbitration baseline plus explicit port lunge extension

CE's ordinary player melee path is biped-owned: `biped_update()` starts melee only when not active, not prevented by the weapon, and not zoomed; the attack frame comes from weapon first-person animation key timing ([`bipeds.c:4355-4412`](../../submodules/halo-ce-universal/source/units/bipeds.c#L4355)). `unit_cause_player_melee_damage()` originates from the head marker, casts a 5×5 ray fan, selects a target with biped/near-target arbitration, and carries material/region and ownership into damage ([`units.c:9004-9075`](../../submodules/halo-ce-universal/source/units/units.c#L9004)). But CE `weapon_melee_attack()` is empty ([`weapons.c:839-843`](../../submodules/halo-ce-universal/source/items/weapons.c#L839)), and the provided Sword tag lacks a stock first-person graph per the prior tag audit.

Therefore split the row oracle: preserve the stock CE melee timing/arbitration/damage semantics where present; specify lunge as a bounded, explicitly marked `port:` addition in HCU, not as a claim that Halo CE contains Halo 2's lunge. Acceptance needs no target, nearer/farther biped versus structure, obstruction, simultaneous request, attack frame, shield/body/death, material response, and render/presentation independence. The retained parent handle pose (`hold_pose`) is presentational and must not move the CE biped or select a collision target.

### Gravity Rifle: its own weapon state over the shared CE flame route

The audited `weapons\\gravity rifle\\gravity rifle` weapon tag is not the Flamethrower weapon tag: the report lists its own 200/200 magazine, 400 total, 3.4-second reload, 30 shots/s, and one projectile per shot, while its trigger references the shared `weapons\\flamethrower\\flame` projectile. The projectile/effect route is persistent/contact-oriented. See [`m13-step10-fuel-rod-flight-investigation.md:247`](../m13-step10-fuel-rod-flight-investigation.md#L247) and [`m4-special-weapons-review.md`](../hcu-source-backed-review/m4-special-weapons-review.md#L100).

Fixture must retain the Gravity Rifle's own weapon datum/cadence/ammo/reload while exercising CE's shared flame projectile/effect contact ticks. Compare one field at a time with Flamethrower: do not import its heat/waste-ammo behavior unless that behavior is selected by the Gravity Rifle tag/source route. Assert bounded contact processing and effect lifetime; never create a gameplay object per visual particle. The parent's carbine-based `hold_pose` is a view-orientation exception only (the HCU/parent boundary is documented in [`plans/5.hcu-remake.md:28-31`](../../plans/5.hcu-remake.md#L28)); it is not authority for weapon simulation.

## Halo-64 comparison and PS2 constraints

Halo-64 is a useful implementation and measurement comparator because it compiles CE weapon/object/projectile code and records concrete profiling practices: collision calls can be counted by caller and GPU waits profiled ([`submodules/halo-64/port/n64/NOTES.md:187-211`](../../submodules/halo-64/port/n64/NOTES.md#L187)); its history distinguishes weapon-marker-origin projectiles from camera firing and describes projectile cost as a ray/map reconnect per tick ([`HISTORY.md:91-98`](../../submodules/halo-64/port/n64/HISTORY.md#L91)). Apply the method—measure actual CE paths, call counts, bounded pools, update cost—not N64 simplifications. Halo-64 explicitly returns no particles/contrails/widgets and uses N64-specific cadence/pool limits ([`NOTES.md:205-211`](../../submodules/halo-64/port/n64/NOTES.md#L205)); those cuts are not acceptable substitutes for PS2's CE effects or the 32 MiB pool budget. Also do not copy N64 lower-frequency simulation or reduced actor behavior without measured EE evidence.

On the parent PS2 side, [`fpview_tick/place()`](../../submodules/halo-ps2/engine/src/sim/fpview.c#L50) is an animation/presentation adapter, and the parent hold-pose tables in `src/game/hold_pose.h` preserve the user's requested sword/gravity orientation. The HCU first-person weapon state is separately advanced in CE's tick (`source/game/game.c:378-383`) and must remain authoritative. The final system should preserve sword, Fuel Rod, and Gravity Rifle while retiring duplicate parent *combat* behavior only after CE traces pass; preserve only the necessary PS2 rendering/presentation adapter.
