# M2 Step 2: isolated optimization/LTO build feasibility

**Scope:** report-only assessment of an isolated compiler-optimization profile for the current ordinary HCU + parent combined ELF. No source, plan, or build artifact was changed or rebuilt for this review. REA was not needed for this question: it concerns compile/link profile mechanics and repository-owned source, not behavior hidden inside a shipped binary. Any candidate must still be checked in the real PCSX2 guest against the exact candidate ELF.

## Finding

An isolated size-optimization experiment is feasible without changing the PS2 memory map or source/ABI contract. The present combined ordinary ELF has only a **388-byte** `elf_static` file-backed overage (`2,097,540 / 2,097,152`), zero undefined symbols, and a modeled minimum reserve headroom of `-822` bytes. Its hash is `147f386d9f34eb6b87254f83c124b4a73ad790855dc0219fe9ae868a1348e66d`; this is the current artifact reported by `build/hcu-parent-link-probe/result.json`, not a claim that the image is accepted. The linker-probe report keeps `acceptance=false` for a successful link and treats the fixed static cap separately from `.bss` and runtime placement (`tools/hcu_parent_link_probe.py:326-335`, `tools/hcu_parent_link_probe.py:354-369`).

The lowest-risk first experiment is **HCU `-Oz` with all other flags unchanged**, because the parent objects in the probe already use `-Oz`, while HCU’s ordinary closure remains `-Os` (`tools/hcu_parent_link_probe.py:199-202`, `tools/hcu_parent_link_probe.py:240-252`, `tools/hcu_ps2_closure.py:137-142`). The existing M2 lifecycle profile already demonstrates a narrowly scoped HCU `-Oz` override on selected diagnostic-only units, but it does not establish that all ordinary HCU units become smaller or that the ordinary guest is equivalent (`tools/hcu_ps2_closure.py:326-328`, `tools/hcu_ps2_closure.py:367-376`).

If HCU-wide `-Oz` is insufficient, **LTO is technically supported by the installed target toolchain and should be attempted as a separate, opt-in profile**, not as a production flag change. The installed compiler identifies as R5900-targeted GCC 15.2.0; the corresponding `lto-wrapper`, `lto1`, and `liblto_plugin.so` are present, and the target GNU ld advertises plugin support. This establishes tool availability, not successful end-to-end LTO linking for this project. PS2SDK’s EE rules already define `EE_FATLTOFLAGS=-flto -ffat-lto-objects` and use the flag during C/C++ compilation (`submodules/ps2sdk/ee/Rules.make:41-46`, `submodules/ps2sdk/ee/Rules.make:90-96`). The parent’s custom `tools/ee-world.mk` rules do not currently apply those flags (`tools/ee-world.mk:206-215`, `tools/ee-world.mk:236-250`).

LTO does **not** require changing the PS2 ABI or fixed memory map, provided the experiment retains current target/ABI and compatibility flags and does not add layout-changing flags. The HCU compile contract includes N32, short `wchar_t`, common-symbol behavior, disabled strict aliasing, wraparound semantics, disabled FP contraction, `-G0`, and section splitting (`tools/hcu_ps2_closure.py:137-142`). The HCU↔parent bridge compile rules also explicitly carry the PS2 prefix and `-fshort-wchar` (`tools/ee-world.mk:132-142`, `tools/ee-world.mk:176-196`). The experimental build must preserve these per-source choices; it must not use `-fwhole-program`, alter `-mabi`, change `-G0`, or modify `config/hcu-ps2-memory-map.json` / the `2 MiB` static limit.

## Why the current closure flow needs an isolated design

The ordinary probe has three build phases: compile HCU closure, generate the typed HCU support object, and compile parent objects into a combined GCC-driver link (`tools/hcu_parent_link_probe.py:227-252`, `tools/hcu_parent_link_probe.py:254-279`, `tools/hcu_parent_link_probe.py:289-310`). Its HCU closure compiles each selected source as a separate object, then uses the **raw target `ld -r`** for both the full layer and rooted closure before `nm`/`objdump` derives live externals and callers (`tools/hcu_ps2_closure.py:358-395`, `tools/hcu_ps2_closure.py:406-417`, `tools/hcu_ps2_closure.py:437-474`). `hcu_ps2_link.py` separately compiles port support and generated typed platform bodies, then links its own standalone ELF (`tools/hcu_ps2_link.py:401-467`).

Consequently, simply appending `-flto` to the final link command is not a valid LTO experiment: the parent and HCU objects must be compiled for LTO, and the final link must invoke the GCC driver with LTO enabled. The raw `ld -r` audit path must not silently become the LTO object aggregator. The installed `ld` advertises the plugin interface, but current code calls it directly with `ld -r` and no explicit LTO plugin (`tools/hcu_ps2_closure.py:410-412`, `tools/hcu_ps2_closure.py:462-466`). Keep the existing non-LTO closure report and its rooted-symbol/caller ledger as the canonical source-backed audit; do not let LTO’s inlining or section folding replace that M0 evidence.

For a machine-image experiment, a safer integration shape is to keep the ordinary closure analysis as-is (to derive its exact live-external set and typed support bodies), create a separate set of LTO-capable HCU translation-unit objects, compile the parent C objects into a distinct output tree with the same profile, then link those object files and the generated support through the target GCC driver with LTO enabled. Add the CE entry roots explicitly (the current combined link forces `halo_shell_main`; the closure’s broader root list is in `tools/hcu_ps2_closure.py:437-461`) and preserve `--gc-sections` and allocation wrappers (`tools/hcu_parent_link_probe.py:300-309`). A second acceptable design is a GCC-driver/plugin-aware partial-link path, but only after a test proves the rooted object retains LTO IR **and** that `nm`/`objdump` still provide trustworthy audit evidence. Avoid relying on raw `ld -r` for a GCC LTO transformation until that is demonstrated.

## Halo-64 comparison: useful build technique, not transferable acceptance

Halo-64 sets `"lto": true` in its N64 port profile (`submodules/halo-64/port/n64/port.json:123-126`). Its build generator uses `-flto -ffat-lto-objects` for game and XDK-facing platform units and passes `-flto=4` to the final link (`submodules/halo-64/tools/n64_build.py:211-215`, `submodules/halo-64/tools/n64_build.py:288-295`, `submodules/halo-64/tools/n64_build.py:315-329`, `submodules/halo-64/tools/n64_build.py:348-355`). Its notes explain that fat objects preserve normal symbols for its `nm`-based link check, and record per-source optimization options through LTO (`submodules/halo-64/tools/n64_build.py:211-215`, `submodules/halo-64/port/n64/HISTORY.md:784-787`).

The caution is equally relevant: Halo-64’s build notes record a 16-job LTO link freezing a 15 GB machine, and now cap the build scope at 9 GB and LTO link concurrency at four (`submodules/halo-64/port/n64/HISTORY.md:947-951`, `submodules/halo-64/port/n64/devtools/build.sh:3-14`; link-job setting at `submodules/halo-64/tools/n64_build.py:352-355`). This port has different R5900/N32 ABI, more retained CE behavior, and a much larger reachable source set than the N64 port; the transferable lesson is *bounded, separately measured LTO*, not an assumed size/performance benefit or an N64 source exclusion. Halo-64 also documents stateful calls that cannot be equated with “drawing-only” stubs (`submodules/halo-64/port/n64/NOTES.md:33-57`); an LTO size win must not be obtained by deleting those semantic owners.

## Minimal profile and implementation requirements

The following is the minimal safe shape for a future implementation; it is not yet implemented here:

1. Add an explicit probe option such as `--optimization-profile {baseline,oz-hcu,lto}` (or an isolated `--lto` switch) and reject mixing the ordinary LTO profile with M2 test macros, non-default cache sizing, or other diagnostic profiles on its first pass. The current probe already builds separate object roots for diagnostic variants and adds suffixes to ELF/map/audit paths (`tools/hcu_parent_link_probe.py:206-218`, `tools/hcu_parent_link_probe.py:296-324`); extend that pattern with an `-oz-hcu` / `-lto` suffix so the candidate cannot overwrite ordinary or prior PCSX2 evidence.
2. Give the HCU closure/build helper its own matching profile directory and record the complete effective compiler flag vector, profile name, compiler version, HCU manifest/prefix hashes, and object hashes in its report (`tools/hcu_ps2_closure.py:299-328`, `tools/hcu_ps2_closure.py:330-355`). For the `oz-hcu` profile, change only the optimization level from `-Os` to `-Oz`. For LTO, add `-flto` to the required C translation units and final GCC-driver invocation; use a single LTO partition/job initially (`-flto=1`) so the build is bounded and deterministic. Retain the exact existing HCU/MSVC ABI and behavior flags.
3. Add a separate `WORLD_OUTPUT` for every parent compile target in the optimization profile, including the standalone parent support-link objects and the gameplay-parent objects; the probe currently uses one `parent-sections-os` directory and one asset-profile keyed gameplay directory (`tools/hcu_parent_link_probe.py:215-219`, `tools/hcu_parent_link_probe.py:240-252`). Ensure all C compile rules pick up the selected flags through `EE_CFLAGS`, while the assembly FileXio module remains an ordinary assembler object (`tools/ee-world.mk:168-174`, `tools/ee-world.mk:206-215`).
4. Enable LTO on the final **GCC driver** command (not raw `ld`) and retain linker script, N32 ABI, `-G0`, page-size, section-GC, memory wrappers, entry roots, and library ordering (`tools/hcu_parent_link_probe.py:300-310`). Make the profile artifact/result names unique and store the selected profile, exact flags, ELF/map/memory-audit hashes, and source pins in the result. Keep the separate normal closure review alongside it.
5. Do not treat `-ffat-lto-objects` as mandatory if the audit closure remains non-LTO. If used for the candidate object set, record the tradeoff and verify it; Halo-64 used it specifically because its link checker inspects symbols in game objects (`submodules/halo-64/tools/n64_build.py:211-215`). Never infer the external-owner review from LTO-folded symbols alone.

## Required tests and acceptance evidence

Before testing a candidate image, add automated tests that verify:

- Baseline arguments still produce the exact existing paths/flags, while each optimization profile writes exclusively to suffixed object/ELF/map/result paths and cannot overwrite or consume baseline objects.
- The baseline non-LTO closure/rooted external ledger is byte-for-byte or semantically identical before/after the profile addition; the candidate profile records all source/object hashes and has no generated unresolved symbol, missing platform owner, or implicit change to root list.
- Every HCU ABI assertion and parent/HCU boundary compilation still passes with the candidate flags. Re-check the combined ELF’s ELF32 little-endian / R5900 / N32 target metadata and all layout assertions; LTO must not be credited with ABI compatibility solely because it linked.
- Candidate link output has zero undefined imports, retains the required entry/callback symbols, preserves `-G0` and current section/arena placement, and passes the complete map-based allocation ownership audit. Compare `.text`, `.rodata`, `.data`, `.sdata`, `.bss`, every `PT_LOAD` file/memory range, `_ftext`, `_fbss`, `_end`, and the `2 MiB` cap to the baseline. Do not alter `config/hcu-ps2-memory-map.json` to make the result pass.
- The candidate is rebuilt from source in fresh suffixed output directories, with parent/HCU/halo-ps2/toolchain pins and all input hashes captured. Confirm no stale object was reused; the existing `-B` rebuild in the probe is a good pattern (`tools/hcu_parent_link_probe.py:240-252`).
- The exact ordinary candidate ELF then passes `tools/test_hcu_boot.py` in both interpreter and recompiler modes through the current M2 Step 2 UI scenario stage, with physical-placement checks and the standard stable interval; record exact ELF, map, ISO/assets, BIOS, PCSX2/settings, and logs. Compare UI/failure/retry behavior with the baseline run, not just the success marker. A successful link or smaller `PT_LOAD` alone is insufficient.
- If runtime behavior is identical and the image fits, separately profile EE frame cost / PCSX2 interpreter and recompiler stability before adopting LTO for production. Static reduction is not proof of acceptable EE CPU cost or hardware behavior.

## Risks and order of operations

| Risk | Containment |
|---|---|
| The 388-byte miss is smaller than the noise from a different source pin or linker order. | Freeze baseline source hashes and full command lines; compare each profile only against that exact baseline. |
| GCC LTO may inline/fold cross-unit CE routines, changing behavior or exposing type/aliasing assumptions despite unchanged ABI. | Preserve all compatibility flags; keep no `-fwhole-program`; run ABI/layout tests and exact guest checks. Do not modify the external owner table based on LTO output. |
| Raw `ld -r` closure path may discard or fail to process LTO IR, invalidating the relocation audit. | Keep baseline closure non-LTO; either link individual candidate LTO objects with GCC driver, or prove a plugin-aware partial link and independent audit. |
| A successful LTO link may increase rather than shrink code or alter initialized data/BSS placement. | Treat size as measured; preserve fixed 2 MiB and arena map; reject if `PT_LOAD`, memory ledger, or physical placement regresses. |
| LTO link resource usage can spike. Halo-64 recorded a machine freeze at 16 jobs. | Start with one LTO link partition/job, existing build concurrency cap, a fresh separate output tree, and process/memory observation. Do not parallelize multiple large LTO builds. |
| Size pressure encourages dropping renderer/CE state or arbitrary stubs. | No behavior cuts are in scope. Retain current CE simulation, render-state owners, parent GS/VU machine layer, and all rooted owners; this experiment changes compiler profile only. |

**Recommended order:** (1) build an isolated HCU-wide `-Oz` candidate, leaving parent `-Oz` and all ABI flags unchanged; (2) if it does not recover the 388 bytes with margin, implement and test a separate LTO profile using the baseline closure for ownership and an LTO-aware GCC-driver link for the candidate; (3) use the same physical placement and exact-ELF PCSX2 gates. The fixed PS2 memory map and source ownership boundaries remain unchanged throughout.

**Review limits:** this assessment inspected the checked-out build scripts/docs and the recorded ordinary probe result. It did not compile an LTO smoke object, produce a candidate ELF, run REA, launch PCSX2, or claim that LTO has already reduced size or preserved behavior.
