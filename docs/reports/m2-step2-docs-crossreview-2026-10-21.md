# M2 Step 2 documentation cross-review — 2026-10-21

Scope: documentation-only cross-review of the CE UI scenario lifecycle and parent CTAG-owner teardown/preflight/retry/reload currently exercised by M2 Step 2 in [`plans/7.hcu-remake-m2-m4.md`](../../plans/7.hcu-remake-m2-m4.md#L199). This report does not change implementation or the plan and does not advance to Step 6.

## Findings that directly constrain Step 2

1. **Keep the test-only lifecycle path isolated from normal CE execution.** Halo-64’s documented approach keeps CE’s own `main_loop` and wraps port-specific behavior in `#ifdef HALO_N64`, rather than replacing the central loop wholesale ([`NOTES.md:27-30`](../../submodules/halo-64/port/n64/NOTES.md#L27)). The same notes say map switching has time-stop/start side effects and the loop later resets `halt_time_scale` ([`NOTES.md:27-31`](../../submodules/halo-64/port/n64/NOTES.md#L27)). For this PS2 diagnostic, an isolated test-only branch that invokes the lifecycle runner and idles is acceptable only if the ordinary branch remains the unmodified production loop, the test macro is opt-in and absent from production manifests, and the diagnostic ELF is separately named/reported. Do not use the diagnostic’s idle-loop stability as evidence that normal gameplay or presentation continues correctly. This is a portability analogy, not a Halo-64 prescription for PS2.

2. **Unpublish CE scenario state before releasing the parent’s backing owner, and validate both sides of that boundary.** Halo-64’s memory history records a concrete failure mode: the old map and its models remained loaded when the menu loaded its logo; freeing the file image alone reclaimed nothing, so its game-specific `n64_game_free_map` teardown had to unload the old map ([`HISTORY.md:301-309`](../../submodules/halo-64/port/n64/HISTORY.md#L301)). It later moved this cleanup before the menu and before freeing the map image ([`HISTORY.md:724-729`](../../submodules/halo-64/port/n64/HISTORY.md#L724)). Its per-map HUD/effect caches also needed explicit release ([`HISTORY.md:400-414`](../../submodules/halo-64/port/n64/HISTORY.md#L400)). Applied here: first run CE’s ordinary scenario-unload path and assert CE scenario/BSP/collision/BSP3D/game-global/index/tag-instance state is unpublished; then run the parent CTAG owner-release callback and assert descriptors, mounted/source state, readers, and arena usage are released; only then permit a fresh CE preflight/load. The diagnostic should observe the legitimate intermediate state: the UI tag cache can remain populated after CE has unpublished its scenario and until the parent owner release runs. A nonzero cache at that first boundary is not by itself a teardown failure; stale CE globals or releasing the parent owner too early are.

3. **Failure/retry must pass through CE’s actual map-load caller, not a parent-only helper.** Halo-64’s startup notes identify the relevant ordering constraints around `main_setup_connection`, map-name selection, and `main_menu_scenario_loaded` ([`NOTES.md:13-20`](../../submodules/halo-64/port/n64/NOTES.md#L13)); its README also describes menu-driven cycle testing that returns to the menu and starts the next map ([`README.md:342-350`](../../submodules/halo-64/README.md#L342)). These are useful evidence that lifecycle behavior is coupled to CE main/menu state, but they do not specify the PS2 rollback contract. For Step 2, inject the post-owner-release/preflight failure at the production CE `main_load_ui_scenario` call site, assert it fails closed with CE globals still unpublished and the parent service reset, then retry through that same CE entry point and require a successful reload. Keep the existing pre-unload refusal case separate: that case should preserve the still-live UI state because teardown has not begun. Avoid a test-only direct call to `map_loader` or a helper that skips `main_load_ui_scenario`; such a test cannot prove the real caller handles failure and retry correctly.

4. **Treat UI scenario loading as a lifecycle test, not a renderer or gameplay-map result.** The Halo-64 README distinguishes the UI map’s content from gameplay maps: menu assets are extracted from `ui.map`, while gameplay maps and the game-side adapter have separate responsibilities ([`README.md:307-335`](../../submodules/halo-64/README.md#L307)). Accordingly, two clean UI cycles can prove CE unpublish/parent-owner release/retry/reload and stable owner base/capacity, but cannot prove a gameplay BSP fits, a scene renders, or game simulation is valid. This agrees with the active M2 plan’s explicit distinction at [`plans/7.hcu-remake-m2-m4.md:195-197`](../../plans/7.hcu-remake-m2-m4.md#L195).

## Platform and guest-test caveats

- **PCSX2 interpreter and recompiler runs are separate evidence, both bound to exact artifacts.** The pinned PS2 engine documentation says PCSX2 is forgiving about DMA timing, cache behavior, and VU hazards and does not model GS fill or DMA contention ([`01-ps2-architecture.md:177-181`](../../submodules/halo-ps2/docs/01-ps2-architecture.md#L177)). The ADR says interpreter runs are the closest emulator mode to exposing timing issues hidden by JIT, but still not hardware timing ([`06-decisions.md:90-100`](../../submodules/halo-ps2/docs/06-decisions.md#L90)); its later qualification keeps the interpreter as the milestone gate and documents unmodeled divergence ([`06-decisions.md:181-200`](../../submodules/halo-ps2/docs/06-decisions.md#L181)). For Step 2, keep the required interpreter and recompiler traces independently tied to the same ELF hash, source pins, settings, data-image hashes, and complete logs; do not treat agreement between modes as physical-hardware certification.
- **A data ISO is not necessarily a bootable disc; test how the harness launches the image.** The current plan already documents that its extracted UI ISO is an asset carrier and that PCSX2 should launch the ELF directly while the ISO is mounted only as data ([`plans/7.hcu-remake-m2-m4.md:203-205`](../../plans/7.hcu-remake-m2-m4.md#L203)). A BIOS “insert disc” screen in that configuration is not CE guest evidence. This distinction should remain visible in each lifecycle run report.
- **OPL/storage documentation is not a prerequisite for this lifecycle step.** The OPL README documents app ELF paths and supported storage families (for example, `mass:` and the HDD configuration) ([`opl/README.md:72-93`](../../submodules/opl/README.md#L72), [`opl/README.md:155-178`](../../submodules/opl/README.md#L155)); PS2SDK’s FILEIO notes describe its service’s IOP boot integration ([`fileio/README.md:1-17`](../../submodules/ps2sdk/iop/fs/fileio/README.md#L1)). These are useful later for storage-root qualification, but they do not establish that OPL-mounted devices are available to this ELF, nor do they affect CTAG owner teardown. Do not expand Step 2’s acceptance to USB/SMB/HDD or optical-media qualification based on these docs.
- **The PS2 machine constraints argue against “fixing” lifecycle by hidden heap allocations or arbitrary arena rewind.** The PS2 architecture doc records the 32 MiB EE RAM and 2 MiB IOP distinction ([`01-ps2-architecture.md:14-23`](../../submodules/halo-ps2/docs/01-ps2-architecture.md#L14)); the engine ADR specifies no heap after load and arena/fixed-pool ownership ([`06-decisions.md:37-40`](../../submodules/halo-ps2/docs/06-decisions.md#L37)). Keep teardown owner-driven and measurable: explicit release, stable bases/capacities, expected used/high-water transitions, and no test-only forced reset of allocator state.

## Documentation coverage and applicability

- The requested HCU `docs/` directory currently has only `mods.md` and `custom_edition_caches.md`; those describe Custom Edition cache/mod formats, not the retail Xbox UI tag cache lifecycle. The cache document does provide a transferable safety principle—validate all offsets/counts/sizes before consuming untrusted map data ([`custom_edition_caches.md:149-188`](../../submodules/halo-ce-universal/docs/custom_edition_caches.md#L149))—but it is not direct evidence for Step 2 teardown ordering.
- Halo-64 has no repository-root `docs/` directory. Its relevant documentation is under `port/n64/` (`NOTES.md`, `HISTORY.md`, and README), cited above. Its successful memory cleanup lessons are useful comparison evidence, but the N64’s memory manager, display transition, and map-free implementation are not code to transplant into this 32 MiB PS2 integration.
- Reviewed other PS2-related submodule documentation where it touched current lifecycle boundaries. OPL/PS2SDK/ps2client docs concern launch, storage, or platform services and are outside Step 2’s acceptance unless a guest trace demonstrates a concrete dependency. No reviewed document authorizes bypassing CE’s scenario-load caller, suppressing a failed preflight, resetting IOP, or claiming a rendered scene from a lifecycle trace.

## Recommended Step 2 acceptance wording

Keep Step 2 open until one exact diagnostic ELF completes all required guest cases in both PCSX2 modes: (a) pre-unload refusal preserves the current valid UI; (b) CE’s ordinary unload unpublishes all tracked globals; (c) the parent owner is then released without an unsafe arena rewind; (d) the injected post-release failure is observed at CE’s real preflight caller and leaves no published/staged stale state; (e) retry through that caller reloads the UI; and (f) two successful unload/reload cycles preserve expected arena base/capacity and return used bytes to the measured baseline. Include normal-production-profile UI qualification separately. The test-only loop must not be counted as normal-game-loop proof. A black UI viewport remains non-render evidence; gameplay map fit, rendered geometry, OPL/optical storage, and real-console hardware behavior remain distinct gates.
