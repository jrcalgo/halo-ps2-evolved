## Actual simultaneous owners and exact contradictions

### 1. Preflight peak: streaming owner is too small for the current algorithm

`hcu_map_service_preflight()` allocates HMAP, CTAG, CRNG, then CBIX from the same map/`streaming` arena and holds all four pointers until validation finishes ([`hcu_map_service.c:283-310`](../../src/stream/hcu_map_service.c#L283)). Their frozen Longest payload sum is:

```text
HMAP       72
CTAG  4,339,096
CRNG       9,380
CBIX          44
          ---------
          4,348,592 bytes, before arena alignment
```

The `streaming` cap is 1,572,864 bytes ([`memory-budget.json:14-20`](../../config/memory-budget.json#L14)); raw payload alone exceeds it by 2,775,728 bytes. The map-service gate currently rejects Longest before these allocations, so this is a proof that the existing algorithm cannot be enabled as-is, not an observed failed Longest run. Preflight's later full retail-source SHA pass uses a separate scratch lease (up to the remaining scratch capacity, capped at 262,144 bytes) and releases that lease before returning ([`hcu_map_service.c:26-53`](../../src/stream/hcu_map_service.c#L26)); it is not simultaneously added to the four retained section payloads, but is a distinct high-water phase that must remain measured.

### 2. Post-unload mount peak: CTAG alone dominates the owner

The current mount loader retains CTAG and CRNG; its BSP-catalog variant adds CBIX and registers their backing pointers for later CE cache/resource callbacks ([`ctag_mount.c:112-173,199-235`](../../src/stream/ctag_mount.c#L112)). For Longest that is at least 4,348,520 raw bytes (`4,339,096 + 9,380 + 44`), before allocation padding, in a 1,572,864-byte `streaming` owner: a raw deficit of 2,775,656 bytes. HMAP is loaded and released in a separate verified-source pass, so it does not belong in this mount-resident sum ([`ctag_map_source.c:97-153`](../../src/stream/ctag_map_source.c#L97)).

The bounded section visitor has an already-open-reader variant, and the production HCU service now calls it for BSP sections through `visit_section()`; the ordinary `load_section()` callback remains the **whole-output** `world_load_section_with_scratch()` for CTAG, CRNG, HMAP, and CBIX ([`hcu_map_service.c:56-83`](../../src/stream/hcu_map_service.c#L56), [`hcu_map_service.c:88-96`](../../src/stream/hcu_map_service.c#L88), [`section.c:141-235`](../../submodules/halo-ps2/engine/src/world/section.c#L141), [`section.h:12-32`](../../submodules/halo-ps2/engine/src/world/section.h#L12)). The visitor leases 65,536-byte history plus 16,384-byte input and 16,384-byte output = 98,304 bytes, and only reports success after the section CRC; its sink may already hold a prefix on failure ([`section.c:79-138`](../../submodules/halo-ps2/engine/src/world/section.c#L79)). The Longest retail-backed CTAG host fixture is a different path: it retains CTAG relocation rows in the same host scratch arena and uses `malloc` for the expected image and staged image, with a 393,216-byte scratch array ([`tests/hp2_ctag_stream_main.c:98-140`](../../tests/hp2_ctag_stream_main.c#L98), [`tests/test_ctag.py:237-329`](../../tests/test_ctag.py#L237)). Its 173,760-byte high-water is a measured requirement of that fixture's allocation strategy, not a measurement of the newly wired production B000 visitor path.

### 3. Frame scratch: snapshot banks leave a 124,224-byte service lease

`hcu_main()` permanently binds two presentation snapshot banks at the start of `frame_scratch` and initializes `render_section_scratch` over the tail for map operations ([`hcu_main.c:331-354`](../../src/stream/hcu_main.c#L331)). Deriving the bank size from the published C layout gives:

```text
snapshot struct = 24-byte header + 64-byte camera
               + (64 × 52-byte first-person matrices)
               + (2048 × 64-byte object records)
               = 134,488 bytes
aligned bank     = 134,496 bytes
two banks        = 268,992 bytes
frame_scratch    = 393,216 bytes
tail lease       = 124,224 bytes
```

The sizes follow [`halo_ps2_render_snapshot.h:8-51`](../../submodules/halo-ce-universal/port/ps2/include/halo_ps2_render_snapshot.h#L8), `hcu_render_snapshot_storage_required()` ([`hcu_render_snapshot.c:28-31`](../../src/stream/hcu_render_snapshot.c#L28)), and the current v2 budget. The 98,304-byte visitor lease by itself fits the tail; with a 64-byte allocation it needs at most 98,367 bytes and leaves at least 25,857 bytes. The exact retail-backed CTAG host fixture, however, allocates its 75,420-byte relocation table from the same scratch arena before the visitor's 98,304-byte workspace. Its measured high-water is **173,760 bytes** ([`hp2_ctag_stream_main.c:121-140,207-209`](../../tests/hp2_ctag_stream_main.c#L121), [`test_ctag.py:324-329`](../../tests/test_ctag.py#L324)). That is **49,536 bytes above** the production tail. Therefore the tested implementation shape cannot be copied into the current `section_scratch` lease, even though the full nominal `frame_scratch` cap of 393,216 B would accommodate it.

An arithmetic alternative is possible but not implemented: hold the 75,420 relocation bytes in a separate persistent owner (the candidate tag span has 213,496 unused bytes after the final Longest tag image, or `streaming` can hold the relocation list plus CRNG/CBIX/HMAP metadata), and leave only the visitor lease in `render_section_scratch`. The header is 52 B and can be a fixed local record or part of that tail metadata. This alternative is conditional: it needs a checked reservation/rollback contract, no alias with the staged image, accurate owner high-water, correct object lifetime through validation/fixups, and assurance that CE cannot treat tail metadata as tag/BSP payload. The current helper which validates the complete split spans is not the production sink or lifecycle integration ([`ps2_ctag.c:93-153,265-307`](../../submodules/halo-ce-universal/port/ps2/src/ps2_ctag.c#L93), [`ps2_ctag.h:33-54`](../../submodules/halo-ce-universal/port/ps2/include/ps2_ctag.h#L33)).

The sub-arena has its own `used/high` fields and is not the parent `frame_scratch` arena object. Target telemetry that reports only `layout.regions[FRAME_SCRATCH].high` will not include this tail lease; the measured peak must report both the parent-reserved snapshot banks and the child arena high-water. Currently `hcu_main()` prints the child base and cap, not its high-water ([`hcu_main.c:345-352`](../../src/stream/hcu_main.c#L345)). For the production B000 visitor now wired in the working tree, the HP2 visitor's 98,304-byte lease fits the 124,224-byte tail, leaving 25,920 bytes by raw arithmetic; `arena_alloc(..., 98,304, 64)` can consume alignment padding, so target/test high-water must still confirm the exact margin. The 173,760-byte CTAG fixture peak remains a separate incompatibility if its same-arena relocation-row allocation were copied into this child.

### 4. B000 CBSP: direct-to-final-span route is now wired, not yet qualified

For a streamed B000, the payload metadata is 36 B header + 214 relocation rows × 12 B = 2,604 B. With the 98,304-byte visitor workspace, raw co-live scratch is 100,908 B; two 64-byte arena alignments add at most 126 B, so the conservative arithmetic peak is 101,034 B, leaving at least 23,190 B of the 124,224-byte tail. This is the useful B000-specific result from the split parser tests; the 374,784-byte image then fits inside the 1,814,336-byte final BSP span. The host fixture confirms Longest B000 splits into 138 BSP-internal and 76 CTAG-name fixups and matches the Python materializer ([`test_cbsp.py:208-257`](../../tests/test_cbsp.py#L208), [`ps2_cbsp.c:76-169,240-320`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cbsp.c#L76)).

The current dirty tree has implemented this proposed shape. `map_loader()` passes the section-scratch child as the BSP metadata/scratch arena when mounting the catalog, then registers the service's reader-backed visitor and clears the old whole-section BSP loader ([`hcu_map_service.c:145-157`](../../src/stream/hcu_map_service.c#L145), [`ctag_mount.c:264-293,316-338`](../../src/stream/ctag_mount.c#L264)). On the CE side, `cache_file_read()` selects that visitor for exact structure-BSP-cache requests and marks completion true only after `stream_cbsp_for_read()` succeeds ([`ps2_cache.c:509-555,570-589`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L509), [`ps2_cache.c:580-592`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L580)). The sink keeps the 36-byte header in a fixed stack state, writes the 374,784-byte decoded image at the final BSP base, and puts 2,568 relocation bytes into its tail; B000's final image+rows consume 377,352 of the 1,814,336-byte span, leaving 1,436,984 bytes. `ps2_cbsp_open_parts()` checks the separated header/image/table and the adapter rebases in place only after the visitor reports HP2 success, then clears Xbox vertex/index buffer fields before CE observes success ([`ps2_cache.c:390-506`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L390), [`ps2_cbsp.c:76-169,240-320`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cbsp.c#L76)). This avoids a B000-sized wire staging allocation and the former owner/scratch alias.

This is implementation evidence only, not qualification. In the current tree the retail Longest test exercises `ps2_cbsp_open_parts()`/rebase against Python materialization, while the `ps2_cache.c` host fixture's new visitor-failure/retry case is synthetic and does not compose `ctag_mount`, HCU's `visit_section()`, the retail HP2 package, and CE `scenario_switch_structure_bsp()` ([`test_cbsp.py:208-257`](../../tests/test_cbsp.py#L208), [`ps2_cache_cbsp_main.c:219-233`](../../tests/ps2_cache_cbsp_main.c#L219), [`test_cbsp.py:311-380`](../../tests/test_cbsp.py#L311)). I found no test that covers the complete newly wired Longest route. Also, the sink writes directly into final fixed BSP memory before outer HP2 CRC is known; the scenario completion flag/global publication remains withheld on failure, but bytes can be partially overwritten. Failure/retry must prove CE does not read this unpublished destination and that a subsequent visitor fully overwrites it before commit. The 98,304-byte workspace fits the 124,224-byte child in arithmetic, subject to measuring its 64-byte alignment overhead and confirming the scratch lease is otherwise idle during synchronous `cache_file_read()`.

## Transition phases and rollback constraints

These phases must not be summed indiscriminately as if all temporary payloads coexist; they also must not be treated as one peak without checking the exact CE callback order.

1. **Preflight while the old map may still be live.** The current service whole-loads section payloads and therefore cannot accommodate Longest in `streaming`. A new preflight may stream HMAP/CTAG envelope and HP2 CRC data, verify map identity, and stage only small metadata. It must not write into old-map tag/BSP caches: CE preflight happens before unload. The full relocation-target check cannot be claimed until the complete CTAG image words are available. The HP2 visitor supports a caller-owned reader to make serial passes over one open file, but the production service currently calls the path-opening whole-output loader; pin/check the HP2 package identity across preflight and post-unload passes ([`section.h:24-32`](../../submodules/halo-ps2/engine/src/world/section.h#L24), [`hcu_map_service.c:56-79`](../../src/stream/hcu_map_service.c#L56)).
2. **Unload old scenario and quiesce consumers.** CE's scenario unload clears scenario, BSP, and tag/global state before parent map-owner release ([`scenario.c:370-412`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L370)); tests cover the UI same-map unload/revalidate/fail/retry path, not Longest direct-to-cache corruption/retry. The parent render snapshot is pointer-free but contains datum/definition indices. Before overwriting old tag/BSP bytes, invalidate old snapshot publication and wait for every frame/DMA reader that could still interpret those IDs or matrices. Current production scene submission is absent, so this fence requirement is not yet runtime demonstrated.
3. **Post-unload CTAG stage/commit.** The final tag-cache span is valid only as private staging until HP2 outer CRC, CTAG image CRC, all relocation rows/targets/address arithmetic, CE header/tag schema checks, and source/package identity checks succeed. The visitor's callback prefix is not commit evidence. On failure, clear HCU cache mount state, release map/scratch marks exactly once, keep CE tag globals unpublished, and make same-process retry rewrite from offset zero. If relocation rows live in tag tail or streaming, preserve them until the rebase and any needed validation completes; don't silently let them become part of CE's tag-data schema region.
4. **Post-tag B000 read/commit.** The BSP final span is similarly unpublished while visitor writes. CE `cache_file_read()` initially sets completion false and only marks true after the B000 payload has been materialized/validated; scenario code publishes the global BSP/collision pointers after the read and `structure_bsp_port_verify()` succeed ([`ps2_cache.c:375-447`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L375), [`scenario.c:1101-1184`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L1101)). Keep this ordering, including the PS2 reset of Xbox-only vertex/index buffers, and ensure callback failure releases temporary leases and leaves the destination invalid.
5. **Normal resident scene.** Once commits finish, the decoded tag/BSP images remain in their fixed cache spans; CRNG/CBIX (and possibly CTAG relocations) remain in map metadata ownership; tag validation claims remain in `resident_gameplay`; renderer consumes pointer-free snapshots and separately owned textures/geometry/DMA. These map-lifetime allocations coexist. A map unload can release the map metadata owner only after CE cache callbacks and renderer/DMA readers stop; current `ctag_mount_unload()` calls BSP unmount, then cache unmount, then source close, then arena rewind ([`ctag_mount.c:277-290`](../../src/stream/ctag_mount.c#L277)).

Halo-64 offers a useful **lifetime pattern**, not a PS2 budget or a reason to adopt N64 cuts: its level unload waits for RSP work before freeing level data (`submodules/halo-64/port/n64/src/n64_render.c:1716-1755`), and its model-room routine only drops entries no longer referenced by frames in flight before waiting for the processor (`n64_render.c:1239-1280`). The PS2 equivalent should be an explicit renderer/DMA quiesce fence and counted lease; do not import the N64 heap size, reduced simulation, or resource eviction policy as evidence of PS2 fit.

## What the current evidence proves—and what it does not

- **Proves:** package dimensions and Longest B000 relocation census; source-derived caps; exact snapshot-bank and scratch-tail arithmetic; production callback ownership; current no-op/default map admission boundaries; host parser parity; host streamed-CTAG corruption and prefix failure behavior; the test's 173,760-B CTAG-fixture scratch peak; the newly wired production B000 visitor/cache path by source inspection only; derived validator claims formula; and the parent renderer's future DMA ownership conflict.
- **Contradicts:** the claim that the current HCU CTAG whole-load path fits Longest under the current owner/scratch topology, and that the CTAG stream fixture's current same-arena allocation pattern fits the production child scratch slice. The former B000 whole-output alias failure is corrected in current source by the visitor route, but the replacement has not yet earned behavior/runtime evidence.
- **Does not prove:** the candidate split's physical guest placement or real claims allocation; a target CTAG/CBSP stream; Longest map-load, scenario/BSP globals, collision, resource reads, object/AI startup, texture/lightmap/audio residency, peak under reload/failure/retry, scene DMA submission, rendered geometry, or M2 acceptance. A UI-only lifecycle test, a host malloc-backed stream fixture, a parser test with fake bases, or an ELF link cannot close these claims.
