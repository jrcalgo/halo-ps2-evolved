# Retail map payload inventory for HCU M2

Generated by the pinned Halo-PS2 tag inventory parser against the 24 decompressed
retail maps retained in `data/retail/weapon-audit-maps/`:

```sh
python3 -I submodules/halo-ps2/tools/halo2ps2/inventory.py data/retail/weapon-audit-maps/*.map
```

The report contains aggregate metadata only; the retail maps remain ignored and
no tag or payload bytes are copied here. “Bitmap MiB” and “sound MiB” are raw
Xbox payload sizes referenced by tag records, not PS2 converted sizes and not
simultaneous EE residency requirements. They establish the scale and codec
coverage required of the converter and streaming design.

## M2 implications

- Raw bitmap data ranges from 18.6 to 56.5 MiB per map. The texture converter
  must inventory format/mip/depth details, convert to GS-compatible data, and
  report each pack's bytes in EE RAM, GS eDRAM, and disc staging separately.
- Raw sound data ranges from 11.5 MiB on some multiplayer maps to 164.5 MiB on
  `a50`; campaign maps contain thousands of permutations. The project must
  audit each encoding and conversion/transcode path against SPU2 playback, then
  stream bounded banks rather than imply the 512 KiB EE staging buffer stores
  an entire map's sound set.
- Campaign script-node counts range from 4,557 (`b30`) to 17,516 (`a10`), with
  127–238 built-in uses. The runtime tag-image path must retain all script
  syntax/string data and preserve its relation to tag validation; excluding
  those as presentation payload would break campaign scope.
- Inventory is source-size evidence only. It does not prove codec quality,
  streamed working-set size, cache hit behavior, or memory fit. M2 still needs
  representative simultaneous-load measurements and corrupt/truncated payload
  tests.
