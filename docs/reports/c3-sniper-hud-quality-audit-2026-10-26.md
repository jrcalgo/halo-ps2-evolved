## Highest-confidence all-HUD-loss path

The CE HUD emits screen quads through `hud_draw_bitmap_internal()` in `submodules/halo-ce-universal/source/interface/hud_draw.c`. Weapon HUD static elements, overlays, and crosshair images go through the same `rasterizer_psuedo_dynamic_screen_quad_draw()` seam. CE's weapon-HUD code also draws multitexture overlay entries from `hud_draw_weapon_overlays()` in that file and `hud_weapon.c`.

The PS2 capture seam rejects any quad with a second or third texture map as `HALO_PS2_BITMAP_UNSUPPORTED_MULTITEXTURE` (`submodules/halo-ce-universal/port/ps2/src/ps2_bitmap_requests.c`, `bitmap_request_unsupported_reason`). It records the rejection instead of emitting a partial request. At the end of the frame, `src/stream/hcu_bitmap_frame.c::batch_fault()` treats any `unsupported_count` as a batch fault, and `drop_batch()` discards the entire frame's captured bitmap batch. The consumer deliberately does not fail CE's simulation frame for that dropped batch.

This is a concrete mechanism for the report that *all* bitmap HUD disappears with the sniper, zoomed and unzoomed: a single unsupported weapon-HUD overlay can suppress every otherwise-supported HUD quad in that frame. The implementation should check the private run's `c3-bitmap` diagnostics for `unsupported-reasons` bit 2 and flags `0x2` or `0x4`, paired with nonzero `bitmap-frames-dropped` and `drop-cause` bit `0x2`. The current quiet desktop ELF does not include those detailed telemetry rows, so it cannot prove this runtime trigger.

Do not relax the all-or-nothing failure rule before the consumer can preserve request ordering, coverage, and upload/draw fence ownership. A targeted fix should either implement the actual CE overlay composition in the parent quad path or omit only a specifically identified optional overlay while keeping the primary scope bitmap and the rest of the HUD. If the runtime counters instead show invalid identity, full queue, or unsupported UV/transform, use that recorded cause to select the fix.

## Zoom-state and scope layout path

`hud_multitexture_overlays_follow_zoom()` in `hud_draw.c` identifies elements whose overlays have a zoom-level effector. `render_weapon_hud()` in `hud_weapon.c` uses that predicate to draw zoom-following static elements in a centered 640-wide layout on wider screens. Crosshair elements separately select a state from the live zoom state and preserve the scope image's placement when applying the display-FOV reticle scale. This makes the private run's actual `NONE -> 0 -> 1` control trace important: it should also log the selected weapon HUD tag/state and the bitmap tag/index for each emitted quad, so a missing scope asset can be distinguished from an entire rejected frame.

`interface_draw_screen()` handles the weapon HUD's screen-effects mask separately from HUD quads. It chooses full-screen versus split-screen mask by window count, and gates the effect by CE zoom state. I decoded the retail Blood Gulch sniper WPHI tag `3860989102`, `weapons\\sniper rifle\\sniper rifle`: it has one screen effect with `mask_flags=0x1` (only when zoomed), `convolution_flags=0x1` (warp), full-screen mask `ui\\hud\\bitmaps\\sniper\\sniper_scope_mask2` (BITM tag `3861513398`, image 0, 512x256 A8Y8, mip count 0, flags `0x89`, 262144 source bytes), and split-screen mask `sniper_scope_mask_sm` (tag `3861578935`, image 0, 256x256 AY8, mip count 0, flags `0x89`, 65536 bytes). It also sets light-enhancement and desaturation intensities to 1.0 with mask-related flags. `interface_draw_screen()` selects convolution type from the radius: a positive radius chooses the Xbox warp path. That path samples the current render target and convolution mask in multipass; the `convolution_flags` bit only gates it on zoom. A missing or unimplemented screen-effect mask explains the missing scoped vignette, but it does not alone blank unzoomed weapon-HUD bitmaps.

The same map's WPHI references the non-mask scope images separately: `hud_reticles_scope` (BITM tag `3815309813`, image 0, 64x64 A8Y8, mip count 0) and `sniper_scope_crosshairs2` (tag `3861316787`, image 0/1, 64x256 AY8 plus narrow 128x8/8x128 pieces, mip count 1). The small crosshair variant `sniper_scope_crosshairs_sm` (tag `3861382324`) has 32x128 and narrow component images. Thus the 512x256 over-limit image is specifically the fullscreen **screen-effect mask**, while authored crosshair pieces are within the 256-pixel limit. Confirm whether PS2's screen-effect entrypoint consumes the mask at all before changing `hcu_bitmap_dispatch.c`; that entrypoint is distinct from `rasterizer_psuedo_dynamic_screen_quad_draw()` and should not be assumed to pass through the current bitmap request queue.

## Filtering, dimensions, and pixelation

The parent quad emitter encodes linear minification and magnification when `point_sampled` is false, and point sampling when true (`src/stream/hcu_bitmap_quad.c::hcu_bitmap_quad_emit_validated`, `GS_TEX1`). CE sets `point_sampled` in `hud_draw_bitmap_internal()` only when a meter parameter is present and the game is one-player. Ordinary static/crosshair scope images have no meter, so this path requests linear sampling; changing it globally to linear would not address those images.

The current bitmap dispatcher explicitly selects mip level 0 with `tex_mip(..., 0)` and accepts only power-of-two PSMT4/PSMT8 images up to 256 by 256 (`src/stream/hcu_bitmap_dispatch.c::dispatch_request_impl`). It does not choose a lower-resolution mip or resize the source. The specific 512x256 mask has no authored mip, but it is the fullscreen screen-effect input rather than a screen quad. The scope crosshair sprite images are 64x256 and 64x64, so their low authored dimensions and their placement relative to the 512x448 PS2 framebuffer can contribute to the user's pixelation report. The private run should capture lossless framebuffer pixels and log source bitmap dimensions, PSM, mip count, HUD screen bounds, and `point_sampled`; the available retail tag data gives the corresponding source identities and dimensions above.

The faithful quality target is to preserve the highest authored source mip and CE's per-element filter choice, while checking HUD geometry against the native 512x448 frame. Do not enlarge the GS framebuffer or change filtering globally based only on the desktop-scaled screenshot.
