# D20 CE actor, player, tick, and skeletal-pose path audit

Date: 2026-10-21  
Scope: source-backed investigation only; no production or test code was changed for this audit.

## Finding in one sentence

The current D20 host oracle proves real CE scenario/tag/BSP loading and unload/switch lifecycle, but it does not initialize the CE game systems, create a player or authored AI actor, run `game_tick()`, advance an animation, or build a skeletal pose. The next useful test is a separate host-only gameplay oracle that calls the real CE lifecycle in retail order and uses adapters only at machine-service boundaries.

## Evidence boundary and test outcome

`run_d20_host_oracle()` starts with a catalog check and preflight, waits for CE precache, calls `scenario_load("levels\\d20\\d20")`, checks the scenario/BSP/collision/tag globals and parent owner, injects a partial-write failure during the B001 switch, restores B000, switches through the remaining BSPs, and unloads (`tests/hcu_ce_map_lifecycle_main.c:431-536`). Its build deliberately links the real scenario/tag loader, schemas, PS2 CTAG/CBSP/cache service, parent map service, and halo-ps2 HP2 section/file readers—but not CE `game.c`, `players.c`, `objects.c`, `ai.c`, `units.c`, or model-animation implementation (`tests/test_hcu_ce_d20_oracle.py:61-103`). Thus successful `scenario_load` is not evidence of CE gameplay startup.

The exact default-sandbox invocation is currently expected to skip at execution: the test detects `SIGSYS`/return codes `-31` or `159` and reports `sandbox blocks native ILP32 execution with SIGSYS` (`tests/test_hcu_ce_d20_oracle.py:120-128`, also `:143-147`). Separately, the elevated host run completed successfully: one test passed, with all four noninitial BSP switches (B001–B004) and the B001 late-write rollback/recovery check. The test's own pass conditions require four switch records, the B001 rollback marker, and complete unload (`tests/test_hcu_ce_d20_oracle.py:124-128`); its retained manifest identifies the result as host-only and expressly denies an EE-capacity/gameplay-fit claim (`tests/test_hcu_ce_d20_oracle.py:162-180`). The host fixture uses an explicitly enlarged BSP destination, which its source labels as not an EE placement proposal (`tests/hcu_ce_map_lifecycle_main.c:501-504`).

The D20 admission exception is narrowly compiled behind `HCU_M2_D20_HOST_ORACLE`; normal production preflight still rejects maps other than UI (`src/stream/hcu_map_service.c:305-317`). Do not carry this define into the PS2 manifest or use this fixture as evidence that D20 fits EE RAM.

## Smallest source-backed production call path

The correct way to extend the fixture is not to call `scenario_load()` and then fabricate a partially initialized game around its globals. The normal CE transition begins after CE's process-wide game initialization and then goes through `game_load()`, which owns the scenario load and `game_globals->map_loaded` transition (`submodules/halo-ce-universal/source/game/game.c:281-329`, `:616-657`). A host test that wants the actual production path should therefore begin with `game_initialize()`, construct `game_options` for D20, and call `game_load(&options)` rather than duplicating `scenario_load()` in its harness.

After `game_load()` succeeds, retail's `main_new_map()` performs `game_initialize_for_new_map()`, creates the local player(s), starts game time, and dispatches `game_initial_pulse()` (`submodules/halo-ce-universal/source/main/main.c:1475-1497`). `game_initialize_for_new_map()` resets/initializes the map-dependent systems, marks the game active, places scenario objects, and invokes `ai_place()` (`submodules/halo-ce-universal/source/game/game.c:663-730`). The local-player helper chooses a local controller and calls `player_new()` before associating the player with a local-player slot (`submodules/halo-ce-universal/source/main/main.c:788-872`); `player_new()` allocates and initializes the CE player datum and machine association (`submodules/halo-ce-universal/source/game/players.c:1225-1272`). `game_initial_pulse()` visits the player data and emits game-engine start events (`submodules/halo-ce-universal/source/game/game.c:432-443`).

For a deterministic one-tick oracle, call the real `game_tick()` once after asserting the game's active state. This is the function the game-time scheduler invokes for each CE simulation tick (`submodules/halo-ce-universal/source/game/game_time.c:472-487`); its substantive order includes `units_update()`, local-host `ai_update()`, player updates, effects, first-person, engine, HaloScript, objects, and post-player/HUD work (`submodules/halo-ce-universal/source/game/game.c:334-410`). Directly invoking one tick from the isolated host harness avoids needing a wall-clock/frame loop; do not replace the bodies of these gameplay systems with success-shaped stubs.

### Expected authored player and actor branches

- **Player biped:** `players_update_before_game()` is called inside `game_tick()` (`game.c:373`). When a local solo player has no unit, it calls `player_spawn()` (`submodules/halo-ce-universal/source/game/players.c:4802-4850`). In the non-engine solo branch, `player_spawn()` obtains a scenario starting location, reads the scenario's player-unit reference, builds `object_placement_data`, and calls `object_new()` (`players.c:1417-1488`). This is the source-backed player-creation path; asserting only a `player_datum` is not enough.
- **Scenario AI:** `ai_place()` calls `encounters_create_for_new_map()` (`submodules/halo-ce-universal/source/ai/ai.c:548-554`). CE iterates the scenario's encounter definitions and creates those not marked “not initially created” (`submodules/halo-ce-universal/source/ai/encounters.c:1730-1753`). Encounter placement eventually associates a real unit and calls `actor_create_for_unit()`, which validates the biped and actor variant, then creates/attaches an actor datum (`submodules/halo-ce-universal/source/ai/actors.c:2523-2605`). `actor_new()` resolves the variant's actor definition and allocates the actual CE actor datum (`actors.c:2213-2259`). An actor count without a valid actor↔unit↔object identity chain does not prove authored actor placement.
- **Ticked pose:** unit animation updates call `animation_update_internal()` for active unit animation state (`submodules/halo-ce-universal/source/units/units.c:10145-10168`, usage at `:10308-10325`). The normal object update then calls `object_compute_node_matrices()` (`submodules/halo-ce-universal/source/objects/objects.c:3866-3905`). That routine chooses the current animation frame and obtains node orientations from `animation_get_node_orientations()` (`objects.c:2526-2575`). The decoder accesses animation frame bytes through `animation_get_frame_data()` and `tag_data_get_pointer()` (`submodules/halo-ce-universal/source/models/model_animations.c:854-875`, `submodules/halo-ce-universal/source/models/model_animation_definitions.c:504-539`). This supports a CPU skeletal-pose assertion (valid authored graph/frame data, finite node orientations/matrices, expected frame progression); it does not prove GS/VU scene rendering.

## Minimum real dependency closure

The minimum **behavior path** that must remain real is:

```text
game_initialize
  -> game_load -> scenario_load -> tag/scenario + D20 BSP lifecycle already exercised
  -> game_initialize_for_new_map
     -> game_state / objects / units / player-control / AI / HaloScript map init
     -> objects_place + ai_place -> encounters -> actor/object placement
  -> CE local-player creation + game_initial_pulse
  -> game_tick
     -> units_update -> ai_update -> players_update_before_game/player_spawn
     -> objects_update -> object_compute_node_matrices
        -> animation_get_node_orientations -> animation data accessor/tag range
```

The actual compile/link closure will be broader than this call chain: the initializers are intentionally shared engine lifecycle and cannot safely be reduced by replacing subsystem initializers with stubs. Start with a full PS2-selected HCU source closure under a host-compatible ABI profile and use section GC only after confirming each path remains rooted. The current map-only binary is explicitly smaller and its link-map assertions list scenario, tag, map service, and file-reader symbols only (`tests/test_hcu_ce_d20_oracle.py:75-111`). Preserve a generated link map and unresolved-symbol inventory for the new executable so test adapters are auditable.

Only machine-boundary services are candidates for host adapters (e.g. timer/input publication, physical-memory arena binding, file/device access, sound playback, and drawing submission). Adapters must be observable and fail loudly when a required gameplay call reaches an unimplemented path. Do not stub `object_new`, `unit_spawn`, encounter placement, `actor_new`, `actor_create_for_unit`, `game_tick`, `animation_get_node_orientations`, `animation_get_frame_data`, or tag-data reads: these are the behaviors under test.

## Authored data and pose limits

The current host fixture has validated the D20 scenario tag, selected initial collision BSP, all five BSP references and switches, but not that encounter placement completes. The D20 host package is a tag/BSP lifecycle artifact; its packaging removes model vertex/index payload (the converter audits `removed_model_vertex_index_bytes` at `tools/convert_retail_ctag.py:96`). The parent HP2 render pack and GS/VU renderer are separate from this map-only CE test. Animation tag/frame data may be in the tag image and be usable for simulation, but that must be verified by walking the actual D20 biped → model/animation-graph tag references and proving frame-data extents resolve inside the mounted tag image. Do not infer actor pose success from presence of an animation tag, observed accessor requests, or node-matrix allocation alone.

An actor can be authored in a scenario encounter while not initially instantiated (the encounter flag gates `encounters_create_for_new_map()` at `encounters.c:1740-1749`). Select a known encounter that is initially created and whose actor variant resolves to supported actor type/tag references. Record the encounter and actor tag identities, relevant object/unit datum indices, model/animation graph indices, current animation index/frame, and node-matrix digest. If D20's selected initial authored encounter is delayed or requires a script/trigger, state that explicitly and use the smallest appropriate D20 fixture/trigger instead of fabricating an actor record.

## Incremental host-only test design

1. **Preserve the existing map oracle.** Keep its D20-only admission macro private and its success assertions unchanged. Retain the current package, map, executable, link map, and runtime log hashes with the test result. The normal production profile must continue to reject D20 at preflight (`src/stream/hcu_map_service.c:305-317`).
2. **Add a separate gameplay-oracle executable.** Give it a unique test source/target and a separate macro from the map-lifecycle oracle. Initialize the required host-owned arenas and platform-service adapters, call real `game_initialize()`, create options with `map_name = "levels\\d20\\d20"`, then call real `game_load()`. Assert the map-loaded flag and CE scenario/BSP/tag globals. Avoid pre-calling `scenario_load()` so the test exercises the actual CE wrapper and does not double-mount/reload.
3. **Run the real map initialization.** Call `game_initialize_for_new_map()`. Assert `game_globals->active`, object/actor/encounter data readiness, and exact initial placement counts. Check that object creation and AI placement stay within host-side instrumented high-water bounds. Exercise failure and cleanup paths if initialization aborts; do not let fixture assertions leave a mounted owner or CE globals behind.
4. **Create a local CE player.** Mirror the production sequence (`player_new`, `local_player_set_player_index`, `game_time_start`, `game_initial_pulse`) from `main.c:788-872` and `:1475-1497`. Prefer actual input boundary adapters publishing neutral controls. After one real `game_tick()`, require a valid player datum and spawned biped object/unit from the authored D20 start/player-unit tag, including matching player/unit/object indices and finite position/orientation.
5. **Prove authored AI actor creation.** Choose an initially-created D20 encounter with a valid supported actor type and verify its scenario encounter → squad/platoon → actor variant → actor definition → biped/object definition references. After `ai_place()`/one tick, assert `actor_get()` is valid, actor unit index resolves to a living unit/object, and the actor's encounter/squad ownership matches the selected authored encounter. Treat pools full, unsupported type, not-initially-created encounter, and missing tag references as explicit test failures or documented skips with source evidence—not successful zero-actor results.
6. **Prove animation data and CPU pose.** Trigger/select a real animation through CE unit/object APIs; after sufficient deterministic ticks, assert animation state and frame index change as expected. Run the real node orientation/matrix path and assert node count matches the referenced model, matrix/orientation values are finite and non-default where the authored frame dictates change, and every animation frame accessor range is within the current mounted tag data. Check trace observer data only as a supplementary witness; it records range requests, not pin/lifetime ownership.
7. **Keep host claims bounded.** Label all buffers overprovisioned host memory and report exact capacities/peaks. The new test proves CE lifecycle and gameplay semantics on a host ABI only. It does not prove PS2 capacity, R5900 behavior, retail hardware timing, geometry availability, GS/VU presentation, or a visible gameplay scene.
8. **Default sandbox and elevated execution.** A local `pytest -rs` run may skip native ILP32 execution due SIGSYS; that is an environment restriction, not a test pass. The elevated host run must execute the same exact test binary/inputs and capture the stdout, executable/link-map/source/package hashes. Keep those statuses distinct in CI and in milestone evidence.

## Completion criteria for this investigation's follow-on

Call the next D20 gameplay-oracle step complete only when the test demonstrates all of: real CE `game_initialize`/`game_load`/`game_initialize_for_new_map`; one actual player biped; one actual authored AI actor with valid unit/object relationship; at least one real `game_tick()`; at least one real animation frame-data decode and resulting CPU node pose; bounded/recorded host resource use; deterministic teardown; a production-profile D20 rejection check; and clear separation of adapter stubs from real gameplay code. Until then, describe the completed result as the real D20 scenario/BSP host lifecycle oracle only.
