# C3 path to 30 rendered FPS — twelve-agent review

This is the review before the renderer changes were implemented. The later measured results are in the [controlled multiview A/B report](c3-multiview-fps-ab-2026-10-25.md).

Twelve GPT-6 Luna agents, all at low reasoning, reviewed separate areas of the running C3 implementation. A thirteenth examined the reported movement change after falling. The performance review made no further engine or emulator-setting changes. The preceding fixed-tick implementation is documented [separately](c3-realtime-simulation-2026-10-25.md).

The strongest next implementation target is the object adapter's **128 KiB table clear for each single-object submission**. The next investigation target is work outside the parent renderer callback, including a **32,872-byte binding-table hash on every CE frame**. Both are confirmed work; neither has a measured optimization speedup yet.

## What is measured

The latest timing executable is `97f489c7bcf106a4de7812a2999a6392f447ba4dafdcac14d431dba81b456370`, running one player/view on Blood Gulch in PCSX2 2.8.2 with recompilers and Vulkan. Scripted firing is disabled. The [retained scheduler proof](../../build/c3/perf/realtime-simulation-20261025-r1/scheduler-proof.json) measures 750 gameplay ticks and 374 rendered frames over 24.992 wall seconds: **30.0096 gameplay ticks/s and 14.9648 rendered FPS**. Movement and looking were exercised without a detected guest failure.

Warm samples from that run show approximately:

| Scope | Observed value | Interpretation |
|---|---:|---|
| Parent render callback | 30–33 ms | Guest timer duration; includes the following phases |
| View construction | 26–28 ms | Includes BSP and object work; not a BSP-only measurement |
| Presentation | 2.5–5.9 ms | Includes waiting for the next vertical blank |
| Frame-end/HUD/submission | about 1 ms | Resident HUD work is already cheap |
| Sampled BSP/video completion waits | 0.000 ms | Rounded samples, not proof that all waits cost zero |
| Simulation | 30.01 ticks/s | Calculated from host log timestamps and completed game ticks |
| Rendering | 14.96 FPS | Calculated from host log timestamps and completed render frames |

The older resident-HUD A/B recorded a 40.64 ms callback and 13.28 ms presentation phase. Those values should not replace the newer run's measurements. Presentation depends on phase relative to vertical blank. Guest timer milliseconds and host wall milliseconds are different measurement domains; subtracting them does not establish an exact unmeasured CPU cost.

There is **no explicit 15 FPS cap** in the scheduler. It renders once after the due fixed steps. Roughly two simulation steps per rendered frame are the observed result of the current workload and timing. Removing a supposed half-rate switch is not an available fix.

|---|---|---|---|
| 1 | Remove full viewer-table initialization from single-object drawing | Source and compiled EE instructions request 131,092 zero bytes per accepted submission | High confidence in wasted work; exclusive time and FPS gain unmeasured |
| 2 | Measure CE capture, binding validation and snapshot publication separately | Full binding digest and repeated snapshot searches occur outside the measured parent callback | High confidence these operations run; unknown share of frame time |
| 3 | Hoist object-pass setup and batch compatible submissions | C3 invokes the generic object pass separately for individual objects and first-person models | High confidence in repetition; API/order changes require validation |
| 4 | Reduce BSP grouping, visibility and clipping overhead | Repeated metadata access, per-view sorting and bounded insertion sorting in the view path | Source-confirmed; profile subphases before choosing the algorithm |
| 5 | Separate expensive qualification bookkeeping from quiet rendering | Pose hashing, pose tracking and parity bookkeeping still execute in several paths | Must distinguish evidence collection from safety and residency logic |
| 6 | Test selected presentation TUs at `-O2` | Parent build uses size-oriented optimization; exact timing ELF has 110,460 B static headroom | Conditional; code growth, ABI and visual results must be checked |
| 7 | Controlled PCSX2 VU-setting comparisons | Instant VU1 and MTVU are disabled in the retained settings | Emulator-specific experiment; no proven gain or correctness equivalence |

### 1. Clear one object, not a 1,024-object table

[`object_pass`](../../src/stream/hcu_render_objects.c) creates an `object_table_t`, clears the whole structure, fills its first object, sets `count = 1`, and invokes `obj_render_pass`. It does this inside the selected-object loop and again for first-person submissions. The relevant source is around lines 1523–1577 and 1606–1685.

[`sim/objects.h`](../../submodules/halo-ps2/engine/src/sim/objects.h) defines 1,024 `object_t` entries. Each entry is 128 bytes on the EE ABI; the table adds five 32-bit metadata fields. The clear is therefore **131,092 bytes**, not just the one 128-byte object. For illustration, 64 such submissions request about 8 MiB of zeroing per view. The actual submitted-object count must be recorded before assigning a per-frame total.

This is present in the production object file, not just source that an optimizer might remove. In the retained `object_pass` disassembly, offset `0x2c0` loads `s5 = 0x20000`; `0x310` passes `a2 = s5 + 20`; `0x314` calls `memset`. The first-person path repeats the size at `0x8b8`–`0x8c4`. [Disassembly](../../build/c3/perf/fps-review-20261025/object-pass-disassembly.txt) and the [object hash/fact record](../../build/c3/perf/fps-review-20261025/review-facts.json) retain the evidence. The table also creates roughly 128 KiB of local stack pressure; that is a peak scratch size, not an accumulating allocation for every object.

The preferred correction is a renderer API accepting a single object or an explicit object span. A smaller first change can initialize only the object and metadata actually consumed, after auditing every reader of the generic table. Preserve all fields currently read, submission order, model/texture selection, identities and counters. Neither approach requires removing any object or changing CE simulation.

This should be the first isolated implementation/A/B because it removes substantial repeated work with a narrow visual contract. Record object-pass time, number of submissions, bytes cleared and whole-loop/render rate before and after; do not assume it alone doubles FPS.

### 2. Account for CE work before the parent callback

The real-time branch in [`halo-ce-universal/source/main/main.c`](../../submodules/halo-ce-universal/source/main/main.c) samples input and advances CE for each fixed step, then calls `main_game_render` to produce the latest snapshot before the parent callback. Consequently the parent callback timer does not include all simulation, HUD capture or snapshot-publication work.

There is a concrete hidden digest in [`hcu_bitmap_frame.c`](../../src/stream/hcu_bitmap_frame.c): `profile_unchanged()` calls `bindings_digest()` from the frame-begin callback. The pinned HCM metadata contains **587 bindings × 56 bytes = 32,872 bytes hashed per CE frame**. This is a different hash from the texture-payload hashes eliminated by resident HUD dispatch, so warm HUD counters reporting zero hashes do not measure it.

Time this operation first. A possible optimization is a verified, sealed binding generation with explicit lifetime and revision checks, while retaining strict checking for mutable metadata. Computing the digest only at bind changes the current mutation-detection contract. A `const` pointer alone is insufficient evidence of immutability. Any replacement needs ownership, invalidation and corruption/mutation tests; simply deleting the check is not an equivalent optimization.

Snapshot construction also repeats linear searches. [`ps2_render.c`](../../submodules/halo-ce-universal/port/ps2/src/ps2_render.c) interns resources, resolves attachment parents, finds each view's unit, and re-interns objects while building references to objects already in the snapshot. [`hcu_snapshot_bank.c`](../../src/stream/hcu_snapshot_bank.c) performs linear object interning. Some of this is bounded quadratic work, including repeated work across views.

A bounded per-publication identity index can replace those searches. Use complete generation-safe identities, exact collision checks, and explicit full-table behavior. Direct references to already-interned object indices can avoid re-searching them. Charge scratch to an existing fixed owner. Retain immutable banks, reader pins and map-generation invalidation. Do not reuse stale palettes or add another animation simulation.

### 3. Reuse object and camera preparation

After the table-clear fix, C3 still calls `obj_render_pass` once per selected object. That repeatedly prepares camera basis/FOV values, generic pass state, model information, permutations and palette state. A per-view begin/draw/end interface can reuse camera setup while preserving per-object model bindings and ordering. Grouping draws across models is a larger change because transparency and state order matter.

Other candidates are repeated palette conversion/copies, per-object pose hashes, and duplicate node output into `world` and `skin` arrays. Inspect consumer contracts before removing an array write. The existing static-pose helper already documents that its `world` array need not be populated in one path, but this does not prove every pose consumer has that contract.

Squared-distance range tests can avoid some object `sqrtf` calls. Reusing per-view trigonometric results can avoid repeated camera conversions. These are useful smaller experiments, behind the large table clear and pass setup. Keep floating-point boundary behavior and rendering output checks.

### 4. BSP visibility, grouping and clipping

[`bsp_render.c`](../../submodules/halo-ps2/engine/src/render/bsp_render.c) groups visible batches by material each view, repeatedly decodes batch/material records, and sorts used materials. Immutable batch-to-material and decoded metadata can be prepared at world bind. Stable bucket ordering may replace repeated comparison sorting if it preserves the required draw order.

The clipped-batch path tests bounds, insertion-sorts up to 256 unsafe batches, transforms triangle vertices and clips polygons. Existing counts and timers include visibility, clip batches/triangles/polygons, skipped work, dropped work and emitted chains. Split unsafe-batch selection, ordering, transform/clip and emission before selecting a replacement such as bounded nearest-first selection.

Preserve near-plane and portal correctness. Conservative portal handling may increase visible work, but tightening it without correct homogeneous clipping can cause missing geometry. The existing clipping time/size caps already have visual consequences; reducing those caps is not a fidelity-preserving way to reach 30 FPS.

The active C3 world already uses **prebaked BSPS packets through DMA REF**. `hcu_render_world_bind` calls `bsp_open`, which clears `source_ops`; it does not call `bsp_bind_source`. The alternative `source_ops` packet-copy branch and borrowed CE packet builder are not the active path. Prebaking that dormant path cannot explain or improve the measured run.

### 5. Presentation, compiler and emulator experiments

The active entry is `src/stream/hcu_main.c`, not the standalone viewer's `engine/src/main.c`. The viewer's two-vblank pacing loop does not explain this C3 run. C3 waits for previous completion as needed, presents through `graph_wait_vsync`, then seals/submits. Presentation time includes phase-dependent waiting; the latest 2.5–5.9 ms cannot be treated as a fixed cost that can simply be subtracted from every frame.

Keep exact DMA/GS completion, idle-chain selection, source leases and snapshot readers. Warm completion-wait samples are mostly zero; there is no measured basis for blind fence removal. Timestamp callback entry, simulation batches, snapshot publication, prior-fence observation, presentation and submission against render/snapshot IDs to establish the actual critical path.

The exact timing ELF has **2,379,908 file-backed PT_LOAD bytes against a 2,490,368-byte allowance**, leaving **110,460 bytes**. This was independently parsed from the active ELF. A different machine-only link report has more space and must not be used as this executable's headroom. Try size/performance flags only on measured presentation hot translation units, retain the ABI and floating-point rules, and rebuild in fresh output directories. Broad `-O3`, `-ffast-math`, LTO or VU rewrites are not justified first steps.

The actual PCSX2 profile uses native resolution, EE/IOP/VU recompilers, Fastmem, no EE cycle-rate/skip adjustment, MTVU off and Instant VU1 off. The log identifies Vulkan and an RTX 4070; it does not establish host CPU utilization. Separate, repeated A/B trials of MTVU or Instant VU1 may be informative, but timing-sensitive VIF/GS behavior and captured output must pass. Emulator VPS, 100% emulation speed, turbo and cycle hacks are not substitutes for 30 game render frames/s at correct gameplay speed.

## Implementation and acceptance sequence

1. Add bounded full-loop and subphase timing: fixed-step CE cost, input/sound, CE bitmap validation, snapshot construction, object adapter/setup, BSP phases, presentation and submission. Keep sparse output outside measured intervals. Record distributions and slow frames rather than five averages alone.
2. A/B the one-object adapter/table-clear correction in isolation. Then test per-view object setup reuse and measured capture/snapshot hot spots separately. Treat the binding-generation optimization as an explicit integrity-contract design.
3. Optimize the measured dominant BSP/object phases. Test compiler and emulator variations independently, after source changes have a stable baseline.
4. Require sustained **30 rendered FPS and 30 gameplay ticks/s**, no warm scheduler drops, bounded memory/chain use, stable lifetimes and complete required content. Compare equal simulation ticks and inputs, or replay an identical immutable snapshot: matching rendered frame numbers alone is insufficient once rendering cadence changes.
5. Qualify one view first, then repeat for two, three and four independent views and the required maps/scenes. Camera-independent metadata and poses may be shared; visibility, LOD, clipping, HUD placement and draws remain camera-specific. Current data does not measure a linear view-count multiplier.

New caches must fit fixed storage: frame scratch is 393,216 bytes, DMA commands 1,179,648 bytes, and the bitmap owner 400 KiB. The measured resident bitmap allocation leaves 25,616 bytes within its usable owner; that is not a blanket allowance for unrelated caches. Keep one cache-age/budget advance and one submission/present per frame.

## Separate live movement assessment

The thirteenth agent checked the current quiet process group `674841` and ELF `2d7cf30c8ee5c2b41d1ba8ea0403644a037e6a34982e572889fc7f3aef1a03ce`. It captured the focused PCSX2 window, held forward briefly and released the key. The [before](../../build/c3/perf/fps-review-20261025/movement-current.png) and [after](../../build/c3/perf/fps-review-20261025/movement-after-forward.png) images show a changed view, approximately 14–16 FPS, about 60 VPS and 100% emulation speed. They do not supply player coordinates or velocity, and neither captures the user's earlier slow-to-normal falling transition. The nearby `Unknown device 'd'` messages do not establish input failure.

Source review rules out one specific theory: a crouch **command bit** cannot remain latched merely because its update condition is skipped. `player_action_clear` clears the input blob each update, and `player->control_flags` is replaced from that rebuilt input. This does not prove the live biped's crouch proportion, animation state or collision state is correct.

Actual remaining candidates include the biped's alert animation seat, which forces walking speed and zero sideways speed (`bipeds.c:3875`), crouch/sneak speed blending (`:3853`), and grounded collision/acceleration and pill resolution (`:2573`, `:2639`). These are hypotheses, not observed runtime states. Proving the fall-dependent issue needs paired input, position, velocity, crouch proportion, animation seat, airborne/slipping flags and contact surface across the transition, plus simulation-rate data. Those values are not exposed in the current quiet log. No restart or source/settings change was made for the assessment, and no cause is claimed from screenshots alone.

## Review coverage

All twelve requested review agents used GPT-6 Luna with low reasoning: (1) measured budget and clocks, (2) BSP visibility/clipping, (3) presentation/fences, (4) CE simulation, (5) snapshot publication, (6) objects/poses/first person, (7) packets/VU/DMA, (8) textures and binding validation, (9) EE code generation/size, (10) PCSX2 configuration, (11) multi-view scaling/storage, and (12) independent critical-path review. The movement assessment was a separate thirteenth task. Recommendations were checked against the combined C3 call path; unrelated viewer and alternate CE-engine paths were excluded.

No proposed change has yet established 30 rendered FPS. The quiet fixed-tick build is running with normal simulation cadence, manual controls and diagnostic output disabled. The oversized/intersecting first-person geometry remains a separate correctness defect.
