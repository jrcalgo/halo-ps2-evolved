# Step 8 multiplayer capacity audit and next action — 2026-10-21

## Scope and disposition

This is a Step 8 capacity audit for the currently declared product only: the 13 stock multiplayer maps, with multiplayer co-op and AI bots in scope. Campaign missions/maps are excluded by the scope decision already recorded at [`plans/7.hcu-remake-m2-m4.md:3`](../../plans/7.hcu-remake-m2-m4.md#L3). Old campaign-capacity lower bounds and d20 experiments are not Step 8 acceptance requirements; they are not used below to reject this multiplayer target.

**Disposition: Step 8 remains open.** Newer evidence does establish a production-sized host allocation and PCSX2 UI-startup placement for the selected streaming split, and two small multiplayer maps pass a CE lifecycle/collision/PVS host fixture under that split. It does not establish a complete 13-map owner ledger, representative runtime peak for bots/co-op/game modes, successful admission of any multiplayer map in the production guest, or the exact retained-resource/cache high-water for the two fixture maps. The highest-priority next action is a map-by-map, source-pinned allocation experiment against the real production tag/BSP/claims bindings, beginning with Sidewinder and the exact CE materialization path. Keep all non-UI admission closed until that and the all-map/live-owner checks pass.

## Current code-owned capacities

Budget v2 commits 27,787,264 bytes of the 33,554,432-byte EE RAM and leaves 5,767,168 bytes as an uncommitted reserve ([`config/memory-budget.json:1-20`](../../config/memory-budget.json#L1)). Relevant fixed regions are `resident_gameplay` 6,815,744; `current_bsp` 6,291,456; `texture_cache` 4,194,304; `dynamic_simulation` 2,621,440; `streaming` 1,572,864; `audio` 524,288; and `frame_scratch` 393,216 bytes. None of those values is free capacity merely because a particular smoke test leaves a buffer unused.

At boot, `hcu_memory_bind_parent_v2()` allocates CE game state from `resident_gameplay`, a single tag-cache span at the start of `current_bsp`, the BSP span from the remainder of `current_bsp`, and the validator-claims bitmap from the remaining `resident_gameplay` ([`src/stream/hcu_memory_bind.c:19-72`](../../src/stream/hcu_memory_bind.c#L19)). These are distinct simultaneous owners. CE’s PS2 memory provider rejects overlapping ranges and refuses late rebinding after allocation ([`ps2_memory.c:91-110,147-155`](../../submodules/halo-ce-universal/port/ps2/src/ps2_memory.c#L91)); the chosen addresses/capacities therefore have to be decided and validated before `physical_memory_allocate()`, not patched after loading a map.

The production entry separately partitions `streaming` into a 1,048,576-byte map-owner child and a disjoint 524,288-byte section-scratch child, while the 268,992-byte render-snapshot banks stay in `frame_scratch` ([`src/stream/hcu_main.c:372-401`](../../src/stream/hcu_main.c#L372), [`hcu_map_service.c:355-397`](../../src/stream/hcu_map_service.c#L355)). The map service checks child containment and rejects overlap. This resolves the specific old scratch mismatch for the current code path; it does not create capacity in `current_bsp`, prove memory-map-wide simultaneous ownership for a gameplay workload, or make the 124,224 bytes left in `frame_scratch` transferable to the BSP cache. That remaining frame span is non-contiguous with `current_bsp` and is not currently an input to the CE BSP cache binding.

These raw numbers are more useful for the immediate design than the compressed-vertex projection, but still not whole-runtime fit. In particular, the catalog’s retained sidewinder BSP extent is 1,984,512 bytes ([`hcu_map_catalog.c:93`](../../src/stream/hcu_map_catalog.c#L93)); the matching report records Sidewinder CTAG 4,378,160 and an unverified projected BSP 1,417,680 bytes ([`retail-map-minimum-working-set-current.json:417-433`](retail-map-minimum-working-set-current.json#L417)). The current `current_bsp` arrangement cannot hold that CTAG plus raw BSP: it misses by 71,216 bytes before any additional alignment/guard requirements. The projection would make the subtotal 5,795,840 bytes and appear to leave 495,616 bytes, but it is not an accepted saving: BSP compressed-vertex data feeds CE lighting and surface queries, and Step 7 has not approved a behavior-preserving replacement ([`plans/7.hcu-remake-m2-m4.md:258-261`](../../plans/7.hcu-remake-m2-m4.md#L258)).

For comparison, the host MP fixture deliberately allocates the largest multiplayer CTAG 4,477,120 bytes and a BSP span 1,814,336 bytes, whose sum exactly equals `current_bsp`; its claims buffer is 786,432 bytes. Those are the candidate *global fixed split* used for the Longest/Blood Gulch fixture, not the Sidewinder-specific raw requirement ([`tests/hcu_mp_capacity_main.c:54-65,82`](../../tests/hcu_mp_capacity_main.c#L54)). A fixed split sized for the two tested maps therefore cannot be assumed to cover Sidewinder.

## What the current host/guest evidence does establish

The retained host run reports Longest and Blood Gulch each completing two actual CE scenario load/query/unload cycles using the real production-sized 1 MiB owner + 512 KiB section-scratch streaming children. Owner high-water was 85,000 and 89,164 bytes; scratch high-water was 262,144 bytes. The test compares exact full PVS rows and independent collision tuples, verifies an unqualified `a30` request does not mutate the active-map snapshot, and asserts cleanup after unload ([`m2-multiplayer-production-capacity-host-2026-10-21.md:9-24,32-38`](m2-multiplayer-production-capacity-host-2026-10-21.md#L9)). This is good host semantic evidence and supports those two maps’ *specific exercised owner and scratch operations*. It does not measure EE allocator/placement, does not include the full renderer/texture/audio/AI/co-op runtime peak, and does not mean their 4.2–4.5 MiB CTAG images reside in the fixture’s 1 MiB map-owner child; the tag and BSP are separate CE cache bindings.

The same report binds one exact R5900 ELF and PCSX2 UI-map boot to source pins and confirms physical non-overlap/canaries plus the 1 MiB/512 KiB split. That test reaches stable `m2-ui-map-loaded`, not a multiplayer map, so it verifies boot partition placement only ([`m2-multiplayer-production-capacity-host-2026-10-21.md:26-30`](m2-multiplayer-production-capacity-host-2026-10-21.md#L26)). It is not evidence that a retail multiplayer scenario was admitted, materialized, queried, or rendered on PCSX2.

The earlier `m2-candidate-map-capacity-audit.md` and some earlier Step 8 notes predate the streaming-destination changes. Their statements that preflight still materializes all CTAG into the 1.5 MiB streaming arena and therefore cannot pass must be treated as stale for the present streamed visitor path; the current implementation streams sections and retains only relocation metadata in the map owner ([`hcu_map_service.c:199-239`](../../src/stream/hcu_map_service.c#L199), [`:292-299`](../../src/stream/hcu_map_service.c#L292)). Conversely, that improvement does not solve the stable CE tag-cache requirement: the 2 MiB default cannot contain any MP CTAG, and the opt-in 4.477 MiB diagnostic split has only been physically checked at boot, not against a loaded MP map. Therefore do not repeat the old preflight blocker, but keep the map-binding and all-owner blockers open.

## Lossless owner-topology experiment to run next

The immediate experiment should answer whether an exact map-specific CE tag/BSP binding is sufficient for all 13 maps *without* losing bytes, compressing schema data, or borrowing reserve:

1. Freeze one MP-only input tuple: current retail map/package/source hashes, CTAG/BSP audit/schema ELF identities, parent/HCU/halo-ps2 exact working-tree hashes, production compiler flags/manifest, memory-budget hash, current map loader and cache binding sources. Re-run the 13-map raw extent extraction from this tuple. The older report rows are candidate guidance until their exact source/schema tuple is revalidated.
2. For each MP map independently calculate 16-byte-aligned CTAG image span, exact maximum individual BSP span (not the sum of all BSPs when CE only publishes one at a time), validator claims bytes using the actual configured spans, relocation/CBSP/scratch peak, and any interval/canary gaps. Check `tag_span + active_bsp_span <= 6,291,456` under the current single-region CE contract. This first-pass check passes for all listed maps except Sidewinder by 71,216 bytes. Then include resident game-state + claims in `resident_gameplay`, tag/BSP old-new overlap behavior, and static render/texture/audio/dynamic owners in the full interval ledger.
3. Try the smallest honest lossless topology change first: map-specific tag-cache capacity (rather than one map’s maximum) and a per-map active BSP capacity, bound once before CE allocation. This can recover the unused portion left by maps whose CTAG+BSP are smaller than the global maximum; however it cannot rescue Sidewinder merely by shrinking its CTAG to its own 4,378,160 B because the raw sum remains 71,216 B over. Keep the host test of real `physical_memory_bind_*` rejection/overlap and add a production-path allocation test for each resulting split.
4. For Sidewinder, compare two explicit safe candidates using actual consumer/API constraints: (a) establish whether any already committed *contiguous EE span* can be reassigned to the BSP cache while preserving the minimum proven texture, audio, dynamic simulation (including bots/co-op), snapshots, renderer DMA, and streaming owners; or (b) extend the BSP destination API to a bounded multi-span/address translation contract. Candidate (b) is a real CE/HCU architecture change, not a simple arena resize: every BSP-relative schema pointer, validator-range check, and direct consumer must resolve with CE-correct semantics across spans. Do not count noncontiguous leftover bytes as a contiguous BSP cache today. Neither candidate may borrow the 5.5 MiB reserve or treat GS/IOP/SPU2 storage as EE pointer memory.
5. Only if those lossless candidates fail should Step 7 consider a compressed/external BSP representation. It must preserve exact lighting/surface/material consumers and collision/PVS/sound results; the existing projection is not a capacity credit. Halo-64 is relevant only as an example of port-specific access seams and measured caches, not as evidence for PS2 cache size, acceptable BSP omissions, or N64-style simulation cuts ([`submodules/halo-64/port/n64/NOTES.md:65-75`](../../submodules/halo-64/port/n64/NOTES.md#L65)). REA is not applicable to this source/raw-map capacity audit; the relevant evidence is inspectable CE schemas, package bytes, allocator bindings, and target execution.
6. Turn the passing Longest/Blood Gulch host harness into a parameterized 13-map fixture with package/source-derived expected map extents, real CE load/unload and query operations, per-map chosen capacities, fault/rollback checks, and one active-map transition between every pair. Add target-query coverage only after each map has a justified production binding; log bound addresses, actual bytes, every arena high-water, cache claims span, and canaries.
7. Exercise the simultaneous multiplayer workload separately from map decode: 1–4 local players, bots at agreed high-water, co-op objective/rule state, vehicles, weapon projectiles/effects, BSP queries, renderer snapshots, texture/lightmap upload, and sound staging. Record per-owner high-water and phase overlap on the exact production ELF. Keep all map admission closed until each map and this common worst-case workload fit together with guard/headroom, no double-accounting, and reserve untouched.

## Specific acceptance gaps

- No retained 13-map measured capacity matrix currently combines each source CTAG, active raw BSP, claims, map-owner/scratch, render/texture/audio/DMA, and dynamic simulation under one exact source tuple.
- Only Longest and Blood Gulch have the reported real CE host collision/PVS query fixture; the other eleven maps have package/corpus arithmetic, not runtime capacity qualification.
- Sidewinder’s raw tag+BSP pair contradicts the 6 MiB current single-span allocation by 71,216 bytes before alignment, and its projected compressed-BSP candidate is not parity-qualified.
- The existing all-map working-set JSON is a lower-bound/projection corpus; excluded owners are explicitly listed and its schema artifact is a named historical hash. Re-run and bind this data to current exact sources before using it to set capacities.
- Existing guest evidence exercises UI map load and boot partition placement, not gameplay admission. No current result proves target/PCSX2 multiplayer live-set high-water, AI bot/co-op capacity, or all-map switch behavior.
- UI/bootstrap catalog entries remain separate. Do not count campaign-only map rows or campaign workloads against this multiplayer Step 8 gate.

**Step 8 should remain incomplete until** the exact MP source tuple is regenerated; a lossless stable owner topology covers every one of the 13 maps, including Sidewinder; the complete common multiplayer workload fits with measured high-water and rollback/transition ownership; and the exact integrated image demonstrates target/PCSX2 placement and gameplay-map query/load evidence without reserve borrowing. The top-level plan’s milestone state remains authoritative; this report is supplemental evidence, not a change to it.
