# M2 Step 6 — Feasibility of executing the real CE BSP switch

**Scope:** report-only review of build/test options for executing HCU's actual `scenario_switch_structure_bsp()` in a deterministic host test or a PCSX2 diagnostic. No production source, test, build script, or shared plan was modified. Findings use the current worktree and existing build artifacts; the stored EE objects prove that the function compiles for the target, but no new ELF or guest run was produced for this report.

## Recommendation

The most practical first seam is a host ILP32 executable that compiles the real `source/scenario/scenario.c` and roots only the `scenario_switch_structure_bsp` function section using `-ffunction-sections` plus `--gc-sections`. Start with narrow test shims for unrelated platform/simulation calls and use the real transaction body. Then expand the link closure to include the real `scenario_structure_bsp_load()` / `scenario_structure_bsp_unload()` from `source/cache/cache_files.c`, the HCU `port/ps2/src/ps2_cache.c` adapter, `ps2_cbsp.c` / `ps2_ctag.c`, and the parent package loader/backend, stubbing only unrelated schema/render/audio/system leaves. This second stage would make the transaction test meaningfully end-to-end at the CPU/owner level.

The source/build setup supports this approach: HCU's production closure already compiles `scenario.c` successfully with per-function sections, and the target link uses `--gc-sections`; the repository also has an ILP32 host ABI toolchain and a real host test for `tag_validate.c`. The challenge is not compiling the switch body but resolving and correctly modeling its small reachable dependency closure and source structures. A separate test-side transaction model, even when paired with the adapter fixture, is not a substitute.

PCSX2 diagnostics are the eventual target validation, not the most efficient first seam. The normal HCU machine image uses the actual CE/HCU code and parent adapter, but current M2 status says there is no capacity-qualified multi-BSP gameplay map; the UI package has one BSP and cannot exercise replacement. A guest test requires a supported scenario with at least two BSP references, realistic tag/BSP residency, and diagnostic fault injection. Do not add test-only guest hooks before the deterministic host seam is working and M2 capacity enables a candidate map.

## Evidence that section-level host execution is feasible

1. The closure compiler applies `-ffunction-sections` and `-fdata-sections` in [`tools/hcu_ps2_closure.py:137-142`](../../tools/hcu_ps2_closure.py#L137), compiles one source object per manifest path, and records the object artifact ([`tools/hcu_ps2_closure.py:276-322`](../../tools/hcu_ps2_closure.py#L276)). The current no-bootstrap build result records `source/scenario/scenario.c` as compiled, zero failed units overall, and the source/object hashes ([`build/hcu-ps2-closure/all-no-bootstrap-memory/result.json`](../../build/hcu-ps2-closure/all-no-bootstrap-memory/result.json)). This confirms that the checked-out CE source is accepted by the production R5900 compile profile.
2. The target linker already uses `-Wl,--gc-sections` in the parent-link probe ([`tools/hcu_parent_link_probe.py:230-244`](../../tools/hcu_parent_link_probe.py#L230)); a rooted host executable can use the same dead-section elimination principle. Unlike the production `rooted.o`, a host fixture must compile source with the host ILP32 ABI, not link the n32 R5900 object.
3. A host ILP32 prefix exists: [`tools/host_abi32.py:10-19`](../../tools/host_abi32.py#L10) points to the locally prepared 32-bit sysroot and emits `-m32`/sysroot/linker arguments. Existing tests use this in a runnable executable for the real validator ([`tests/test_hcu_ps2_closure.py:35-57`](../../tests/test_hcu_ps2_closure.py#L35)). `scenario_globals` has an explicit 0x100 layout assertion at [`scenario.h:65-86`](../../submodules/halo-ce-universal/source/scenario/scenario.h#L65), and BSP references are asserted to 0x20 bytes at [`scenario_definitions.h:147-157`](../../submodules/halo-ce-universal/source/scenario/scenario_definitions.h#L147). A 32-bit host test can therefore match the pointer/long layout required by CE instead of attempting an invalid LP64 harness.
4. The real transaction has a compact externally visible control boundary: it calls the old/new BSP load and unload routines, capacity verifier, `tag_get`, time/collision controls, menu fallback, and disconnect/reconnect operations ([`scenario.c:1088-1195`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L1088)). Its per-function relocation table was inspected from the existing production object using `mips64r5900el-ps2-elf-objdump -r -j .text.scenario_switch_structure_bsp`; the live edges are limited to CE globals, `tag_block_get_element_fast`, load/unload, `structure_bsp_port_verify`, `tag_get`, `error`, stop/start time, collision logging, main-menu fallback, and the static disconnect/reconnect call chains. The unrelated 129 undefined symbols in the whole `scenario.c.o` object include dead-function references; they are not the switch function's actual link closure.

## Host options and their evidence strength

### Option A — Real CE transaction caller, narrow shim leaves (recommended first)

Compile the actual `scenario.c` for ILP32 with `HALO_PS2`, the PS2 prefix and CE include paths. Link the test main, `scenario.c.o`, and shims with function/data sections and `--gc-sections`; force-retain `scenario_switch_structure_bsp` as the root. The test supplies actual `struct scenario` / `struct scenario_structure_bsp_reference` blocks and allocates/publishes a stable `struct structure_bsp` + collision block for each successful shim load. Stubs record timing, disconnect/reconnect, `error`, and menu calls. The fake `scenario_structure_bsp_load()` / `_unload()` at this stage should be labeled as seam fakes, not production cache evidence.

This executes HCU's exact guard, unload/load ordering, verification rejection, global nulling, old-index retry, publication, return value and menu fallback. It closes the largest gap in today's `switch_bsp_reference()` model while keeping the first test manageable. The current model's same-index behavior differs: it returns success (`1`), but CE returns its initialized `FALSE` without entering the switch body. The new harness should assert CE's actual result convention, not copy the model ([`ps2_cache_cbsp_main.c:91-110`](../../tests/ps2_cache_cbsp_main.c#L91), [`scenario.c:1091-1105,1190-1195`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L1091)).

**What Option A does not prove:** cache tag-instance publication, CE `cache_file_globals.structure_bsp_header`, production CE header/schema checks, the actual PS2 `cache_file_read` adapter, parent scratch/source lifetime, or package-derived CBSP selection. It is a CE caller execution test only.

### Option B — Real CE switch + CE load/unload + PS2 adapter (target host acceptance)

Expand Option A to include the actual `scenario_structure_bsp_load()` and `scenario_structure_bsp_unload()` sections from `source/cache/cache_files.c`. Those sections' relocations were inspected in the current production object with `objdump -r -j .text.scenario_structure_bsp_load` and `..._unload`. The reachable load function references `cache_file_read`, `physical_memory_*`, header-range checking, `tag_validate_structure_bsp`, cache tag-instance lookup, vertex-buffer registration, Custom Edition hooks, and a thread/time/audio wait branch; unload references vertex-buffer deregistration, tag-instance lookup and cache globals ([`cache_files.c:1376-1534`](../../submodules/halo-ce-universal/source/cache/cache_files.c#L1376)). On the PS2 build the blocking read is expected to complete synchronously, so a faithful fixture should assert that completion is true and the `SwitchToThread` wait is not entered.

Add production `port/ps2/src/ps2_cache.c`, `ps2_cbsp.c`, and `ps2_ctag.c` plus `src/stream/ctag_mount.c`, `ctag_ps2_backend.c`, `cbsp_catalog.c`, and the package/section reader needed by its callbacks. Reuse existing test seams where they already supply physical-memory spans and host file operations ([`tests/ps2_cache_cbsp_main.c:11-52`](../../tests/ps2_cache_cbsp_main.c#L11); [`tests/ctag_mount_main.c:448-570`](../../tests/ctag_mount_main.c#L448)). Keep the destination address fixed, and use two distinct CBSP records selected by catalog extents.

The first iteration may shim `tag_validate_structure_bsp` and `structure_bsp_port_verify` behind deterministic counters (pass/fail per requested datum). This still executes CE's actual read/materialize/header/cache-tag registration path and the actual switch algorithm, while giving the test precise fault control. Once that seam passes, replace the validation shims with the production validators where their dependencies and scratch binding are available. Clearly distinguish those tiers in test names/output.

This is feasible without modifying production code if the combined live dependency closure is small enough to shim. If not, the next-smallest safe production adaptation is to add a test-configuration seam around *external side-effect leaves only* (timing/audio/render registration/error/UI) while keeping both CE transaction functions and the PS2 adapter bodies unchanged. Do not move or copy the transaction algorithm into a helper just to make it link; that would create another behavior implementation.

### Option C — Current guest image with instrumentation (required target confirmation, later)

The machine path already links HCU CE and the parent services; `WORLD_HCU_GAMEPLAY=1` adds `hcu_main` and streaming bridges in [`tools/ee-world.mk:45-68`](../../tools/ee-world.mk#L45), and `hcu_parent_link_probe.py` builds the combined `WORLD_HCU_GAMEPLAY=1` target ([`tools/hcu_parent_link_probe.py:217-244`](../../tools/hcu_parent_link_probe.py#L217)). The PCSX2 boot harness has UI and playable-stage markers ([`tools/test_hcu_boot.py:26-31`](../../tools/test_hcu_boot.py#L26)). But current M2 plan evidence says the accepted catalog remains UI-only for runtime and gameplay maps are rejected while tag/BSP capacity is unqualified; the UI package has one BSP. Thus current UI PCSX2 runs cannot reach the switch branch.

After a multi-BSP campaign map is capacity-qualified and actually loaded, add diagnostics under an explicit test-only compile define around CE's actual sequence: old unpublish, new read/materialize, CE validation, new publication, rollback attempt, and rollback-failed safe menu. The diagnostic should log old/requested/result indices, CE global addresses as offsets within their owning arenas (not raw unstable host addresses), tag-instance/cache-header publication, arena used/high marks, source handles, and callback counts. Add controlled injections at actual seam results (read/CBSP materialization, CE schema/header checks, `structure_bsp_port_verify`, and old-BSP reload), but do not make injection affect retail builds. Run the identical ELF/package in interpreter and recompiler; require a guest trace that proves each targeted branch and no post-marker fault. Host tests remain the fast exhaustive fault matrix; PCSX2 confirms target integration, not exhaustive corruption enumeration.

Keep the existing synthetic adapter test as a lower-level codec/cache test. Add these new **test files only** first:

| New file | Responsibility |
|---|---|
| `tests/hcu_scenario_bsp_switch_main.c` | ILP32 test main and initialized real CE scenario/reference/global fixtures; invokes `scenario_switch_structure_bsp()` directly; controlled test-side dependencies and full transaction snapshots. |
| `tests/hcu_scenario_bsp_switch_shims.c` | Shim only out-of-scope platform/render/audio/error services and, for tier A, load/unload/verification/tag lookup; each shim records calls and can inject a named failure. Split into multiple files if source ownership stays clearer. |
| `tests/test_hcu_scenario_bsp_switch.py` | Build command using `tools.host_abi32.flags()`, current HCU manifest include dirs and `halo_ps2_prefix.h`; compile real `scenario.c` with `-ffunction-sections -fdata-sections`; link root `scenario_switch_structure_bsp` with `--gc-sections`; execute the test binary; assert deterministic stdout trace and SHA/pin manifest. |
| `tests/hcu_scenario_bsp_switch_fixture.h` | Shared fixture definitions for test shims: scenario references, tag identities, fake stable BSP/collision blocks, failure plan and state-snapshot types. Do not redefine CE structs; include CE headers and assert their sizes. |

Tier B should extend that same harness rather than create a second transaction model. Add actual source inputs to its compile command: `source/cache/cache_files.c`; `port/ps2/src/ps2_cache.c`, `ps2_ctag.c`, `ps2_cbsp.c`; `src/stream/ctag_mount.c`, `ctag_ps2_backend.c`, `cbsp_catalog.c`; then only the actual reader/catalog/arena/CRC pieces the linker reports as live. Root CE switch and CE load/unload; use `--print-gc-sections` or map output as an audit artifact so a shim cannot accidentally replace a transaction function. Test names should state exact retained production owners, e.g. `test_real_ce_switch_with_real_ps2_cache_adapter`.

Potential challenge: `scenario.c`'s section's disconnect/reconnect helpers call the CE BSP procedure tables, whose targets include AI, cluster, contrail, effect and object subsystems. Keep the real helper/table code if the fixture can stub its leaf calls. Do not replace `scenario_call_disconnect_from_structure_bsp_procs()` itself with a no-op if acceptance includes disconnect/reconnect ordering; record and assert those leaf calls instead. The source table and direct references are in [`scenario.c:294-...`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L294), and the switch invokes them before unload and after publication ([`scenario.c:1116-1125,1183-1189`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L1116)).

## Build feasibility detail / closure caveats

- **Do not link the existing R5900 object into the host executable.** It is ELF32 little-endian MIPS/n32 and host ABI test binaries are x86 ILP32. Recompile the current HCU source with the host ABI flags and short wchar while preserving the PS2 prefix/defines. This catches source behavior with matching CE 32-bit layouts but is not a target run.
- **Do not compile on LP64 and cast down pointers.** The actual scenario/reference structures contain pointers and use `long`; the declared sizes (0x100 globals and 0x20 BSP reference) are ABI-sensitive. A 64-bit host would produce misleading memory and pointer arithmetic.
- **`--gc-sections` helps but does not make the closure zero-cost.** The actual switch calls static disconnect/reconnect helpers and the load/unload routines. The object-wide undefined list is misleadingly large: the function-section relocation list is the correct dependency source. Build the executable and use linker errors plus map/GC output to drive the shim list.
- **Avoid script-generated copies of the C function.** Current `tests/test_cbsp.py:250-312` text checks the CE function and `ps2_cache_cbsp_main.c:72-110` has a separate model. Generating/extracting the CE body into another C file would preserve the same split and can silently diverge. The harness should compile the real source file or use the actual production object.
- **Schema tests need explicit tiering.** A passing fake `tag_validate_structure_bsp` proves branch selection, not production validation. Run with deterministic fail/pass shims first to cover every transaction branch; separately link production validators with the exact claims/scratch binding and package tag image to claim schema-path coverage.
- **Section garbage collection can hide required behavior if the root is wrong.** Force-root only `scenario_switch_structure_bsp` and inspect the resulting map/GC log to confirm the transaction section, cache load/unload (Tier B), adapter `cache_file_read`, CBSP materializer and parent callback are all live. Reject an executable that silently discarded any owner the test claims to exercise.

## Proposed sequential work (no plan edits made here)

1. Prototype a throwaway/non-committed ILP32 host link in a temporary directory with `scenario.c` + real CE transaction root + shim leaves; do not copy the transaction body. Confirm the harness hits real compiled CE branches for same index, invalid index, candidate success, candidate load failure, candidate verify failure, old reload success, old reload failure, and first-load failure.
2. Add the reusable test files above and make the test emit a deterministic trace. Snapshot all CE index/global pointers, tag-instance/header ownership once Tier B is linked, active CBSP/parent owner identity, arena cursors, open handles, and call counters. Pointer values should be checked for exact restoration/target allocation identity, not hashed alone.
3. Add Tier B and use one Step 5 package-derived map with two BSPs; the corpus's 82/82 catalog references are provenance, not evidence that every candidate fits. For host feasibility, the package sections can be actual but loaded into an overprovisioned host-owned arena; make no EE-capacity claim from that test.
4. Run `tests/test_cbsp.py`, the new harness, `tests/test_retail_ui_ctag_mount.py`, and adjacent reader/validator tests under sanitizers where supported. Preserve current test and failure counts; do not claim guest transaction proof.
5. After M2 Step 8/10 proves a stable production backing and a real gameplay map loads in PCSX2, add the diagnostic-only injection and event trace. Then run the exact same ELF/package and settings in both interpreter and recompiler, covering both successful switch and failure/rollback branches. Keep the milestone partial until host actual-function + target guest evidence and state invariants all meet Step 6.

## Bottom line

There is no technical reason to settle for a source-order test: compiling the real CE switch function as a host ILP32 object with GC-sections is practical, and a production R5900 object already shows a compact per-function relocation closure. The lowest-risk path is tiered. Tier A first executes actual CE control flow with explicit leaf shims; Tier B integrates the actual CE cache loader/unloader with the PS2 adapter/parent owner; a later PCSX2 run proves target interaction on a capacity-qualified multi-BSP map. Do not count Tier A alone as Step 6 complete, because it leaves the exact integration risks the step calls out.
