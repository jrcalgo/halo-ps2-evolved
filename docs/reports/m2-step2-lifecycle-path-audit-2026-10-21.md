# M2 Step 2 guest lifecycle fault/retry path audit

Date: 2026-10-21  
Scope: report-only audit of the opt-in `HALO_PS2_M2_UI_LIFECYCLE_TEST` guest profile. This reviews its CE menu preflight, teardown/global clearing, deferred parent-loader failure, retry, validator, and build isolation. It does not claim a current guest run passed.

## Verdict

The path is useful and substantially stronger than a synthetic owner test: it starts after the ordinary CE UI map is loaded, observes a rejected preflight while the old map is live, reaches CE's real `scenario_unload()` and parent-owner release, injects failure inside the real `hcu_map_service_preflight()` reached from the production `map_loader()`, retries through `main_load_ui_scenario()`, and runs two ordinary menu unload/load cycles. Its opt-in compile definition is isolated to a diagnostic HCU closure plus matching parent objects; it is not enabled by the default production make variables.

It is **not yet a complete CE failure/retry transaction test**. The deferred failure is entered by calling `hcu_map_service_lifecycle_consume_deferred_failure()` directly, which invokes the private `map_loader()` callback itself. It does not exercise the failure result returning through `cache_files_precache_map_begin()` → `game_precache_new_map()` → `scenario_load()` / `main_new_map()`. The retry does use `main_load_ui_scenario(FALSE)`, but because the injected callback failure bypasses that CE call chain, this proves parent callback cleanup and later UI recovery—not CE's actual response to an unload-then-map-load refusal. The source validator also checks only a subset of CE globals, and its event-order checks do not fully assert the injected-marker ordering.

Recommendation: keep Step 2 **partial** until a second fault case drives the deferred failure through CE's real map-load callback path (or explicitly narrow the acceptance wording to “parent service owner cleanup + normal UI recovery”), and strengthen the guest marker to verify all CTAG-backed CE globals and event order. Do not promote the black viewport or UI diagnostic into scene-render evidence.

## Path traced

1. The lifecycle code runs after `game_initialize()`, `main_setup_connection()`, and `main_initialize_time()`, before the steady `while (TRUE)` loop. It first requires the real UI scenario, main-menu state, UI cache mount, and tag/BSP bases to be present ([`main.c:3481-3490`](../../submodules/halo-ce-universal/source/main/main.c#L3481)). This is a valid live-owner baseline, though it is a UI/bootstrap profile only.
2. The pre-unload fault arm makes one call to the normal `ps2_cache_preflight_map("levels\\ui\\ui")`; the parent callback returns false before taking any new owner. The test compares `game_map_loaded`, menu-loaded state, scenario pointer, structure-BSP pointer, and cache-mounted state before/after ([`main.c:3492-3503`](../../submodules/halo-ce-universal/source/main/main.c#L3492), [`hcu_map_service.c:418-427`](../../src/stream/hcu_map_service.c#L418)). This correctly tests refusal before CE starts teardown.
3. To set up the deferred boundary, the path calls `main_menu_unload()`, then preflights the already-mounted same UI map. The active-owner shortcut marks `reload_pending` without overwriting the live package ([`main.c:3506-3511`](../../submodules/halo-ce-universal/source/main/main.c#L3506), [`hcu_map_service.c:444-455`](../../src/stream/hcu_map_service.c#L444)).
4. It calls `game_unload()` and `game_dispose_from_old_map()`. `game_unload()` reaches the real `scenario_unload()` when `map_loaded` is set ([`game.c:754-783`](../../submodules/halo-ce-universal/source/game/game.c#L754)). `scenario_unload()` clears scenario indices, `global_scenario`, `global_structure_bsp`, `global_collision_bsp`, `global_bsp3d`, and `global_game_globals` before calling `ps2_cache_release_map_owner()` ([`scenario.c:378-403`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L378)). The parent unloader then releases the active CTAG mount and source, clears `preflight_ready`, and preserves only the deferred request state ([`hcu_map_service.c:329-349`](../../src/stream/hcu_map_service.c#L329)). This ordering is sound: CE pointers are unpublished before their backing bytes are released.
5. The test arms the post-unload injection and invokes the diagnostic bridge. That bridge checks the request is pending and no mount/source remains, then calls the actual `map_loader()` ([`hcu_map_service.c:563-578`](../../src/stream/hcu_map_service.c#L563)). Because `map_unloader()` reset `preflight_ready` but preserved `reload_pending`, `map_loader()` enters `hcu_map_service_preflight()` again ([`hcu_map_service.c:258-273`](../../src/stream/hcu_map_service.c#L258)). The injection is applied after the normal preflight predicates all succeeded but before publication of `identity`, `ctag_info`, or `preflight_ready`; the failed preflight closes the source and clears staged fields ([`hcu_map_service.c:489-520`](../../src/stream/hcu_map_service.c#L489)). This exercises a realistic late-validation failure seam and confirms the parent service can return to its empty state.
6. The key coverage gap is at this point: `map_loader()` is called directly by the diagnostic bridge, not by CE's registered `cache_files_precache_map_begin()` route ([`ps2_cache.c:396-426`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L396)). No `game_precache_new_map()` or `scenario_load()` observes that failure. The subsequent retry does take the ordinary `main_load_ui_scenario(FALSE)` route and checks the UI scenario and owner are restored ([`main.c:3528-3538`](../../submodules/halo-ce-universal/source/main/main.c#L3528)); the two later ordinary menu reload cycles also use `main_menu_unload()`/`main_menu_load()` ([`main.c:3541-3563`](../../submodules/halo-ce-universal/source/main/main.c#L3541)).

## Validator and evidence quality

`validate_m2_ui_lifecycle_log()` requires both failure injections, preservation/safe-empty/retry markers, two completed reload cycles, CE unpublication markers, parent-owner release, and identical fixed owner footprint across the two loaded cycles ([`test_hcu_boot.py:95-162`](../../tools/test_hcu_boot.py#L95)). Its phase snapshots include arena base/cap/used/high-water, mount/source activity, descriptor, preflight/reload flags, and staged map.

Three limitations should be corrected before calling the test fully source-backed:

- Runtime predicates and `m2-ui-lifecycle-ce-unpublished` / `owner-released` log records verify `global_scenario` and `global_structure_bsp` are null, plus cache-unmounted. The source clears five scenario-backed global pointers, but the guest diagnostic does not print/assert `global_collision_bsp`, `global_bsp3d`, or `global_game_globals` after unpublish ([`scenario.c:382-386`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L382), [`scenario.c:393-409`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L393)). The code path is correct by inspection; the claimed runtime proof is narrower than the teardown claim.
- Required markers are checked for presence. The validator orders “pre-unload preserved” before “post-unload safe-empty” before “retry complete,” but it does not enforce that `preflight-before-unload` precedes preservation, or that `preflight-after-unload` and `postunload-failure-injected` precede safe-empty. Add an exact ordered event sequence check.
- The source trace uses a dictionary keyed by phase for cycle-0 rows. Current phase names happen to be unique for the rows consumed, but the validator would silently overwrite a repeated phase instead of rejecting duplicate/unexpected records. Parse an ordered event list and reject duplicate phase names where uniqueness is required.

The existing native ILP32 fixture is a separate, useful complement: it snapshots all CE scenario/cache/tag pointers and owner bytes, injects late streamed visitor and BSP writes, and verifies rollback/retry ([`test_hcu_ce_map_lifecycle.py:51-99`](../../tests/test_hcu_ce_map_lifecycle.py#L51), [`hcu_ce_map_lifecycle_main.c`](../../tests/hcu_ce_map_lifecycle_main.c)). It does not close the guest CE entry-path gap because it links selected scenario/cache/service code with host shims, not the guest `main_load_ui_scenario()` flow.

## Build-profile audit

The guest profile is properly opt-in and kept separate from other diagnostic variants:

- `tools/hcu_parent_link_probe.py --m2-ui-lifecycle-test` assigns profile-specific closure/output directories and rejects incompatible render-clear or animation-trace variants ([`hcu_parent_link_probe.py:176-215`](../../tools/hcu_parent_link_probe.py#L176)).
- It passes `--m2-ui-lifecycle-test` to both closure and link generation, and forwards `WORLD_HCU_M2_UI_LIFECYCLE_TEST=1` only to the combined gameplay object build ([`hcu_parent_link_probe.py:224-249`](../../tools/hcu_parent_link_probe.py#L224)).
- HCU closure applies `HALO_PS2_M2_UI_LIFECYCLE_TEST` only when compiling `source/main/main.c` and `source/scenario/scenario.c`, while the corresponding parent make rule applies it to `hcu_map_service.c` ([`hcu_ps2_closure.py:349-363`](../../tools/hcu_ps2_closure.py#L349), [`ee-world.mk:148-156`](../../tools/ee-world.mk#L148)). The linker helper enforces that the lifecycle profile also uses `--no-bootstrap-memory` ([`hcu_ps2_link.py:380-394`](../../tools/hcu_ps2_link.py#L380)).
- The default `WORLD_HCU_M2_UI_LIFECYCLE_TEST` is zero ([`ee-world.mk:45-49`](../../tools/ee-world.mk#L45)), so production compilation does not execute this diagnostic block. The bridge function definitions and injection sites in `hcu_map_service.c` are compiled only under the test define ([`hcu_map_service.c:553-579`](../../src/stream/hcu_map_service.c#L553)).

For reproducibility, the lifecycle run report must bind the exact diagnostic ELF hash and the generated closure report/source hashes; git commit IDs alone are insufficient because both HCU and parent worktrees are dirty. The current boot runner records exact ELF hash and submodule commit IDs, while the closure report records per-source hashes and profile defines. Preserve both artifacts together for each accepted guest result.

## Halo-64 / REA applicability

This is a source-level lifecycle/callback audit, not a binary behavior reconstruction. Halo-64 is not the authority for CE's map-load failure semantics, and its N64 cuts/ABI should not be copied into this PS2 lifecycle path. REA is not needed to establish these source call edges; use it only if a failing shipped/build artifact must be compared at machine-code or runtime level. The decisive evidence here is the CE/parent source path plus a guest run bound to its exact ELF.

## Actionable closure criteria

Verify CE returns to the intended unloaded/menu-safe state after refusal, then issue the same-map retry through the normal menu path.
2. Print and assert all CTAG-backed scenario globals after `scenario_unload()`: `global_scenario`, `global_structure_bsp`, `global_collision_bsp`, `global_bsp3d`, `global_game_globals`, scenario/BSP indices, `global_tag_instances`, and cache-mounted/tag-loaded state. Include the globals that are actually backed by the mounted CTAG, and document any intentionally persistent state.
3. Make the boot-log validator assert the full ordered marker sequence and reject duplicates/missing per-cycle teardown/reload events.
4. Rebuild the distinct host-profile lifecycle ELF; record source-rooted closure report/hash, combined ELF/hash/map, exact assets, emulator settings and logs; run interpreter and recompiler. Keep the Step 2 gate partial until both the intended CE failure route and post-failure retry pass.
