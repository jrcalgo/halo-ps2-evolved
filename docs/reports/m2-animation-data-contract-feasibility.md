# M2 step 4 — animation data contract feasibility

**Decision: no runtime or tag-format change yet.** The source audit identifies every current consumer of `animation.data` and the retail range audit measures the in-image payloads well enough to reject a naïve “make it external and stream it through the existing accessor” change. It does not identify a safe cache capacity, a complete stable identity for every animation record, or a target-measured access pattern. Keep the existing in-image `TAG_SCHEMA_DATA` contract for M2; treat external animation data as a later, explicitly gated design item, not as a completed optimization.

This is a report-only investigation for M2 step 4. No runtime code or plan was changed. Source baseline: parent `70e2ed0cf2145a45d23aa07414a3a88c05155d4c`, HCU `6933490b2d16bb1c637295b6a0f3880ba23a7d56`, halo-ps2 `71183bb0a9adc586cd267b2780c82bbc12cfd95b`. The retail range artifact is tied to schema ELF SHA-256 `2fba411b7244b20fdf31f0b1e540fc2b6f5598891f53a64f8b12f850a0cda0aa`; the JSON report SHA-256 is `92a1d32f79f77a83ce1125dddb9b73c5a3c57ec94632ad0963e3602018b4f47a`. These identities matter: results from different schema ELFs must not be combined.

## What `animation.data` means in the current CE port

The HCU animation graph (`antr`, version 4) caps a graph at 256 animations, each animation at 2,048 frames and 64 nodes. The animation record keeps three distinct payload descriptors: `frame_info`, `default_data`, and `data`; `compressed_data_offset` is an offset within `data`, not a separate file reference. `animation_get_default_data()` is a separate accessor for `default_data`, so changing `data` must not accidentally externalize or reinterpret either neighboring payload. See [model_animation_definitions.h:20–29, 62–97](../../submodules/halo-ce-universal/source/models/model_animation_definitions.h#L20) and [the frame accessor declarations](../../submodules/halo-ce-universal/source/models/model_animation_definitions.h#L196).

The schema caps one `animation.data` blob at `2048 × 64 × 24 = 3,145,728` bytes (3 MiB), `default_data` at 1,536 bytes, and `frame_info` at 32,768 bytes. `animation_fields` declares all three as `TAG_SCHEMA_DATA` and runs `animation_check` after them; the animation graph schema reaches those records through its `animations` block. These are not interchangeable field types. See [tag_schema_models.c:59–64](../../submodules/halo-ce-universal/port/linux/game/tag_schema_models.c#L59), [animation_fields and animation_schema](../../submodules/halo-ce-universal/port/linux/game/tag_schema_models.c#L1197), and [animation graph schema](../../submodules/halo-ce-universal/port/linux/game/tag_schema_models.c#L1230).

`TAG_SCHEMA_DATA` is an in-image pointer/size claim. The validator verifies that the referenced bytes lie in the tag image and claims the extent for overlap/ownership validation; it is not a generic external-file descriptor. Switching a field to `TAG_SCHEMA_FILE_DATA` would change validation to file-offset semantics but would not, by itself, update CE runtime accessors, pinning, lifetime, or the animation validator. See [`TAG_SCHEMA_DATA`/`TAG_SCHEMA_FILE_DATA`](../../submodules/halo-ce-universal/port/linux/game/tag_schema.h#L145) and [tag_validate.c:748–780](../../submodules/halo-ce-universal/port/linux/game/tag_validate.c#L748).

The frame accessor obtains `animation->data.address` through `tag_data_get_pointer`, then returns either `address + compressed_data_offset` or `address + frame_index * frame_size`. The pointer is raw and has no acquire/release or pin lifetime. `tag_data_get_pointer` bounds-checks against `data->size` and returns an address inside that data block; the current contract is a stable in-memory pointer for the tag-data lifetime. See [animation_get_frame_data](../../submodules/halo-ce-universal/source/models/model_animation_definitions.c#L500) and [tag_data_get_pointer](../../submodules/halo-ce-universal/source/tag_files/tag_groups.c#L91).

Validation is substantial and must remain behaviorally equivalent. For compressed animations, `animation_data_problem` validates the compressed offset/header, default arrays, node-header extents, keyframe and frame-index extents, strictly increasing frame indices, and the last keyframe’s frame number. For uncompressed data it checks computed frame size, total frame bytes, and base-animation defaults. A malformed animation is corrected to a no-node animation rather than being handed unchecked bytes. See [compressed keyframe validation](../../submodules/halo-ce-universal/port/linux/game/tag_schema_models.c#L817), [animation data validation](../../submodules/halo-ce-universal/port/linux/game/tag_schema_models.c#L862), and [animation_check](../../submodules/halo-ce-universal/port/linux/game/tag_schema_models.c#L933). Any future external-data path must validate the same logical byte view before runtime use, including offsets relative to the external record and cross-extent failure behavior.

## Direct consumer inventory

The source audit and the repository’s focused test enumerate these raw consumers:

| Consumer path | How it reads `animation.data` | Contract consequence |
|---|---|---|
| `animation_get_frame_data()` | Returns a raw pointer for a compressed animation blob or a selected uncompressed frame. | A temporary-copy cache cannot evict or reuse its backing storage until every pointer derived from that call has finished. [`model_animation_definitions.c:500–515`](../../submodules/halo-ce-universal/source/models/model_animation_definitions.c#L500) |
| `animation_get_node_orientations()` | Calls the frame accessor, then walks frame bytes across the node decode. It also reads the separate `default_data`. | Data must stay pinned for the full node loop; keep `default_data` unchanged. [`model_animations.c:843–880`](../../submodules/halo-ce-universal/source/models/model_animations.c#L843) |
| `replacement_animation_apply()` and overlay application variants | Decode one frame directly; interpolation paths can hold current and next frame pointers while comparing/decoding them. | Both frames must remain simultaneously valid where the routine retains both pointers. [`replacement_animation_apply`](../../submodules/halo-ce-universal/source/models/model_animations.c#L1016), [`overlay_animation_apply` and scaled/continuous variants](../../submodules/halo-ce-universal/source/models/model_animations.c#L1101) |
| `aiming_screen_apply()` | Computes four neighboring yaw/pitch frames, acquires four raw pointers (`data00`, `data10`, `data01`, `data11`), then decodes/interpolates. | A one-slot staging buffer is observably unsafe: each later read could invalidate an earlier pointer. Four distinct frames may alias at grid edges, but the API must not rely on that to reduce capacity without proving the alias rules. [`model_animations.c:1756–1883`](../../submodules/halo-ce-universal/source/models/model_animations.c#L1756) |
| `animation_get_keyframe_rotation()`, `animation_get_keyframe_translation()`, `animation_get_keyframe_scale()` | Each obtains a pointer starting at `compressed_data_offset` and directly reads the compressed header, node headers, defaults, keyframe values, and frame-index tables. | The compressed blob must be resident/pinned across each helper’s full operation; per-node random I/O is unacceptable. [`model_animations.c:2145–2164`](../../submodules/halo-ce-universal/source/models/model_animations.c#L2145), [`translation`](../../submodules/halo-ce-universal/source/models/model_animations.c#L2289), [`scale`](../../submodules/halo-ce-universal/source/models/model_animations.c#L2428) |
| Shared validity helpers | `animation_data_contains()` and `animation_frame_valid()` inspect `data.size`, computed offsets, flags, and `frame_size`; they do not themselves read bytes. | A new descriptor must preserve logical size and overflow-safe range semantics even when bytes are external. [`animation_data_contains`](../../submodules/halo-ce-universal/source/models/model_animations.c#L2571), [`animation_frame_valid`](../../submodules/halo-ce-universal/source/models/model_animations.c#L2638) |

The higher-level animation paths include base-object node pose and root transform/velocity, first-person weapon animation pose, replacement/overlay/continuous overlays, and aiming-screen interpolation. For example, object transforms call `animation_get_node_orientations` in [objects.c:2532](../../submodules/halo-ce-universal/source/objects/objects.c#L2532), first-person weapon pose calls it at [first_person_weapons.c:1240](../../submodules/halo-ce-universal/source/interface/first_person_weapons.c#L1240) and again at [first_person_weapons.c:1262](../../submodules/halo-ce-universal/source/interface/first_person_weapons.c#L1262), and root velocity decodes current and prior poses serially in [model_animations.c:813–840](../../submodules/halo-ce-universal/source/models/model_animations.c#L813). These uses mean animation-data access is part of gameplay/presentation tick work, not merely an optional rendering upload.

`frame_info` and `default_data` are nearby but separate contracts. `animation_get_frame_info()` has independent bounds/fallback behavior ([model_animation_definitions.c:518–530](../../submodules/halo-ce-universal/source/models/model_animation_definitions.c#L518)); unit movement reads frame info in [bipeds.c:3668–3699](../../submodules/halo-ce-universal/source/units/bipeds.c#L3668). Do not count those bytes as `animation.data` in a range report or silently fold them into an animation-data cache.

The textual consumer regression test checks the direct `tag_data_get_pointer(&animation->data, ...)` call sites and `animation_get_frame_data` use, but it is not a semantic or dynamic call-graph proof. See [test_animation_data_ranges.py:10–39](../../tests/test_animation_data_ranges.py#L10). A source change that introduces aliases, helpers, or new direct address arithmetic must extend this inventory test and rerun the search-based audit.

The hard memory boundary remains 32 MiB, with the 5.5 MiB reserve unspent; `resident_gameplay` is 6,815,744 bytes, `current_bsp` 6,291,456 bytes, and `streaming` only 1,572,864 bytes. See [memory budget](../../config/memory-budget.json#L1) and [memory accounting notes](../memory.md#L3). A c10-sized 4.97 MB candidate cannot reside in the streaming region. A maximum single 167,560-byte record could fit as one cache entry, but one entry is not a capacity proof: `aiming_screen_apply` requires four simultaneously valid frame pointers from one animation, while multiple actors/players and first-person poses can use different animations during a tick. Current evidence does not establish peak distinct records, reentrancy, read frequency, or whether all active objects’ animation references must remain available.

If the full bytes are still copied/mapped into EE RAM and exposed as pointers, “external” only changes packaging, not the memory cost: c10’s payload remains about 4.74 MiB, plus other tags, staging, and alignment. If instead they are streamed from DVD/OPL storage, synchronous random reads from each compressed node helper would violate the current pointer assumptions and risk stalling simulation. The EE has a 30 Hz tick budget; no measured PS2/PCSX2 cache-miss latency, bytes-read-per-tick, peak lease count, or four-player/campaign animation workload is in these artifacts. A correct access layer must bulk-load/pin a whole animation record (or equivalent contiguous decode unit), never issue per-node storage reads, and demonstrate misses do not create unbounded tick stalls. The ranges are extent statistics, not evidence of decoder working sets.

## Why no faithful bounded external-data contract is selected

A viable future contract would need, at minimum, a typed record identity and a lifetime-bearing accessor. The identity must be stable across conversion and runtime load—e.g. map source hash + tag index + animation-block element index + field identifier—and bind the original logical size, compression flag, compressed offset, payload hash, and external source extent. Runtime acquisition must return the exact original logical byte view and guarantee its lifetime through the complete caller decode; release occurs only after all derived raw pointers are dead. `aiming_screen_apply` must be able to hold four pointers; interpolation paths must hold both frames. Cache exhaustion must fail deterministically before use or block only at a documented safe point, never return a valid-looking recycled pointer.

Schema validation has to validate the external payload before publishing the tag graph, with the same checks currently performed by `animation_data_problem`. A generic file-data descriptor is not enough: existing model animation code reads `animation->data.address` directly, and schema validation currently claims `TAG_SCHEMA_DATA` extents inside the tag image. The format must also distinguish unavailable/corrupt resource, short read, failed hash, and capacity exhaustion, and must cleanly unload/reload while invalidating every lease. The proposal must not change behavior for in-image data: it should be a bounded provider behind the same logical byte contract, with the in-image provider remaining the reference implementation.

The existing range report lacks a unique animation-record key in the emitted summary needed to construct that mapping. The schema walker outputs in-image field records with field, size, and target, but not a stable graph/tag/animation-element identity for each record. See [ctag_schema_walk.py:211–243 and 335–344](../../tools/ctag_schema_walk.py#L211). The extractor’s offsets and hashes are useful for source integrity, but not enough to bind runtime CE pointers to external resource IDs without extending conversion output and proving the map/tag traversal identity.

Therefore the evidence supports **no-change now**: preserve `TAG_SCHEMA_DATA`, existing `animation->data.address` pointers, validation/correction behavior, and the tag-image lifetime. Do not set a cache cap from the largest observed record or the 1.5 MiB streaming pool. M2 can close the investigative question as “no safe externalization contract approved”; actual externalization remains unimplemented and must not be represented as a milestone implementation or acceptance pass.

## Required future tests and target evidence before reconsidering

1. **Schema identity and source manifest:** extend the retail extractor to emit stable map/tag/graph/animation-element/field IDs and exact logical size, source offset, source hash, payload hash, flags, `frame_count`, `frame_size`, `node_count`, `compressed_data_offset`, and compression mode. Test determinism across repeated conversion, different map load orders, duplicate animation names, aliases/shared ranges, and corrupted/missing source ranges. Include all 24 source maps and bind each to its SHA-256.
2. **Validation parity:** exercise compressed and uncompressed animations from `c10`, `d40`, `b40`, and `bloodgulch`, including the largest record and all edge shapes; compare acceptance/correction and decoded output between in-image and external providers. Mutate header offsets, node counts, truncated keyframe tables, descending/duplicate frame indices, wrong final frame, default arrays, size overflow, short reads, bad payload hash, out-of-map source extent, and record aliasing. Require the same no-node fallback and diagnostics as CE for malformed logical data.
3. **Whole-consumer decode equivalence:** on each fixture compare every node’s translation, rotation, and scale over every frame for base, replacement, overlay, scaled/continuous overlay, aiming-screen interpolation (all four corners and interior weights), root matrix/velocity, object animation, and first-person weapon pose. Include current/previous-frame and repeated-call cases; compare deterministic float bit patterns where the existing path is deterministic, otherwise use documented CE tolerances. Confirm `frame_info` and `default_data` remain byte-identical and separately owned.
4. **Lease/lifetime adversarial tests:** make cache capacity deliberately one, two, then four record slots; force eviction between acquisition and decode; test `aiming_screen_apply` with four distinct frames and concurrent requests from two animation records, multiple objects, and multiple first-person views. Assert no stale pointer, premature eviction, use-after-unload, or silently altered pose. Test nested/reentrant access if any call path can recurse. The API must provide explicit acquire/release or equivalent scoped lifetime, and the test should instrument leases/high-water.
5. **Target memory and I/O qualification:** measure resident tag bytes, external cache/staging high-water, and simultaneous leases on EE/PCSX2 for representative campaign and multiplayer scenes, including 1–4 local players, active actors, and first-person weapons. Preserve the 5.5 MiB reserve and account each byte once in the named budget regions. Measure cold/warm IOP/DVD/OPL reads, seek count, bytes/read, misses/tick, longest blocked tick, and 30 Hz deadline misses; use the actual USB, SMB, HDD, ISO, and optical profiles in scope. PCSX2 wall time alone is not physical EE qualification.
6. **Failure and reload behavior:** test absent device, unavailable source root, interrupted/short reads, corrupt directory/index, cache exhaustion, map unload while leases exist, failed map switch, and retry. No partially published map or dangling animation pointer may survive failure; previous-map rollback must preserve the prior provider and tag references.
7. **Closure/regression:** expand `tests/test_animation_data_ranges.py` beyond textual call counts to assert every newly introduced direct reader is registered in the consumer inventory. Run the complete HCU schema, animation, map conversion, memory ledger, and guest startup suites against the exact manifest/ELF hashes. Only after these pass and measured working-set/tick-budget evidence exists should M2 reconsider replacing `TAG_SCHEMA_DATA` with a typed external record.

## Assessment summary

The sources show a tightly coupled raw-pointer interface, including one four-pointer interpolation path and three compressed direct readers; the schema validator owns and checks the bytes as in-image tag data. Retail reports quantify useful per-map payload bounds and source fragmentation, but neither stable runtime identities nor concurrency, I/O, cache, or tick measurements. Under the PS2 32 MiB ceiling and fixed 5.5 MiB reserve, the available 1.5 MiB streaming region cannot retain every animation byte for the largest maps, while an all-resident external mapping saves no RAM. The safe result is to preserve the current contract and defer externalization until a complete typed lease design is proven against every listed consumer and target workload.
