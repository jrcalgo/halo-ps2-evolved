# M2 C2 r8 runtime evidence (2026-10-24)

Lane: runtime (C2.2 and C2.4 production profile runtime registration).
Build directory: `build/m2-c2-r8-runtime/` (the EE object build is in `build/m2-c2-r8-runtime/ee-gameplay/`, the link in `build/m2-c2-r8-runtime/link/`).
Row: `sidewinder_marine_shotgun_4p4bot` (profile 26, map `sidewinder`).

## Changed files

- `tools/c2_profile_image_header.py` (new): emits the generated row header. It pins the package path (asset-root relative), exact size and SHA-256 (checked against the manifest's `package_sha256`), the HCM1 metadata blob as a const array with its SHA-256 and decode storage bytes, the five source maps (path, size, SHA-256, each checked against the manifest), and an `output_datum` to source-map table from the manifest's chunk bindings. A datum that maps to two source maps is an error.
- `src/stream/hcu_main.c`: when `HALO_HCU_PROFILE_IMAGE_HEADER` names the generated header, `hcu_register_selected_runtime(service, owner, scratch)` opens the package and source maps through `hcu_file_bridge` at their pinned sizes. It then builds the `hcu_map_profile_runtime` (package reader, compatibility gate, metadata, source reader, relocation and stream scratch, `renderer_drained = hcu_renderer_drained`, the row's residency span) and calls `hcu_map_service_register_runtime`. Without the header it keeps the fail-closed refusal, with a new message that names the missing define. The call site passes `map_owner_storage` and `render_section_scratch`.
- `tools/ee-world.mk`: `WORLD_HCU_PARTITION_PROFILE ?=`. When set, the `hcu_main.o` rule adds `-DHALO_HCU_PARTITION_PROFILE`, `-DHALO_HCU_PROFILE_IMAGE_HEADER="<row>.h"` and `-I$(WORLD_OUTPUT)/c2`. A pattern rule generates `$(WORLD_OUTPUT)/c2/<row>.h` with the tool.
- `tests/test_hcu_main_wiring.py`: adds `HcuProfileImageTest` (source inspection of the refusal and registration paths, a generator pin check against the manifest, an EE compile with the generated header, and a makefile check).
- `tests/hcu_map_service_profile_main.c`: adds registration case 1d (a compatibility gate that rejects the profile leaves nothing registered).
- `tests/test_hcu_map_service_profile.py`: the fixture's PASS count moves from 25 to 26 for case 1d.

## Storage placement (named owners)

| Input | Bytes | Owner | Notes |
| --- | ---: | --- | --- |
| HCM1 metadata decode storage | 51,092 | `streaming_map_owner` (1 MiB) | `metadata_bytes - 32` |
| Relocation storage | 131,764 | `streaming_map_owner` | manifest `ctag_relocation_table_bytes`, rounded to 4 |
| Stream scratch | 65,536 | `streaming_section_scratch` (512 KiB) | one 64 KiB HCP segment |
| Residency span | 1,048,576 | row residency span (`s_partition.residency_base`) | 16 slots of 64 KiB |

Metadata and relocation storage fit in the 1 MiB map owner with room to spare. The stream scratch comes from the section arena, not frame scratch, because the mount keeps it until unload.

Build issues found and fixed during the run: the first include of the header by full path failed, because GCC resolves a quoted include relative to the source file and the `-I` paths, not the working directory. The makefile now passes the header by basename with `-I$(WORLD_OUTPUT)/c2`. The first link also lacked `libfileXio` (now `-lfileXio`) and then `-lsbv_patches`, which does not exist in this SDK; the link adds `-lfileXio` and `-lpatches` (`sbv_patch_*` is provided by `libpatches.a`).

## Full-link command and limitation

`tools/hcu_parent_link_probe.py` has no option for a partition row, and it is outside this lane's ownership, so it was not edited. The link was run directly, using the probe's own link line (`mips64r5900el-ps2-elf-gcc -mabi=n32 -G0 -T ps2sdk/ee/startup/linkfile ...`) over the 62 objects of `build/m2-c2-r8-runtime/ee-gameplay`, plus the six closure objects from `build/hcu-ps2-closure/all-no-bootstrap-memory/`. The equivalent make command for the objects is in `run_objects.py`. A probe option `--partition-profile` would be the cross-lane change that makes this reproducible.

## Open gaps (C2.4 partial; not closed)

- Not executed. The ELF was linked, but nothing booted it on PCSX2 or hardware, so the registration log line and the package and source reads are untested at run time. The `HALO_PS2_LOCAL profile-runtime` line is produced only on a successful registration.
- `frame_owner` is NULL. The bitmap frame owner is not wired into `hcu_main.c`, so unload and successor staging fail closed. A later step must pass the owner.
- Source maps are checked by size on the EE, not by SHA-256. The SHA-256 check is a host step in the generator, so a changed map on the device is caught only by the size check.
- The datum table covers the 569 datums of the chunk bindings. A resource whose datum is not in that table is refused (the reader returns 0). The resource records have no `output_datum`, so the 896 resources cannot yet be checked one by one against the table.
- The package is read through `hcu_file_bridge`. Its relative paths resolve under the file layer's default root, which is assumed to be the repository root (the ps2link `host:` root). This is not verified on the device.
- The 16-entry residency table is ELF static storage, outside the CE budget (as recorded in r5). The budget lane still has to decide whether to charge it.
- The relocation and metadata storage are carved from the 1 MiB streaming map owner. The partition's total committed bytes are unchanged, and no committed budget or reserve value was changed.
- No steady-state heap use was added. The registration allocates only from the two arenas, once.
- The compatibility gate checks the map name and profile id. It does not re-run the manifest's full dependency checks on the EE.

## Verdict

C2.2: the registration path is wired for a selected row and compiles and links with the generated image. Host tests pass. Not verified at run time.
C2.4: the production runtime registration is built for the sidewinder row. It fails closed on every missing input. Registration itself is untested on hardware or PCSX2, and the frame owner, datum coverage and bridge root remain open.
