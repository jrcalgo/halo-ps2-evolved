# M2 next capacity design review: the first real map and the all-map path

**Disposition:** M2 has a plausible bounded-memory path to *attempt* a first retail multiplayer map, with **Longest** the best first candidate. It does not yet have a qualified gameplay map, and this first-map path is not an all-map solution. The present code cannot load Longest: the tag-cache binding is 2 MiB, CTAG preflight needs a full section larger than the 1.5 MiB streaming arena, the mount retains full CTAG/CRNG section buffers in that arena, and the CBSP loader needs a full encoded section in a 384 KiB scratch arena. Fix those owners/transactions without changing the 32 MiB partition or reserve, then measure all parent-renderer assets and CE validation/runtime peaks before claiming a fit.

This report is report-only. It does not approve cutting map support, removing simulation/tag fields, resizing memory regions, or using the reserve. The map-and-BSP numbers below retain each complete compact CTAG image and the complete raw active CE BSP image; **no hypothetical compressed-vertex projection is used**. “Compact CTAG” already reflects the converter's represented PS2 CTAG format. Any data the converter moves to another representation still needs an explicit destination, consumer mapping, and parity proof; this report does not treat removed source bytes as free.

## Hard memory ledger: capacities are fixed owners, not fungible free RAM

The 32 MiB budget is `27,787,264` committed bytes plus `5,767,168` reserve bytes. The reserve remains unavailable. The exact region definitions are in [`config/memory-budget.json`](../../config/memory-budget.json#L1-L21) and [the memory record](../memory.md#L1). The PS2 GS has 4 MiB of eDRAM, but it is a separate hardware store, not CPU-addressable EE RAM that can back CE pointers; IOP and SPU2 RAM are separate stores too ([`docs/memory.md`](../memory.md), “GS VRAM”; [`config/hcu-ps2-memory-map.json`](../../config/hcu-ps2-memory-map.json)).

| EE region | Capacity | Current/provisional owner and capacity implication |
|---|---:|---|
| `system_kernel` | 1,572,864 | Kernel, stacks, IOP/EE buffers. Keep the measured stack/kernel reservation; not map RAM. |
| `elf_static` | 2,097,152 | Allocated machine ELF/code/constants. The inspected ELF's earlier parent-link report is already slightly over its cap; rebuild and close M0/M1 placement before using any slack assumptions. |
| `resident_gameplay` | 6,815,744 | CE game-state allocation and validator claims are already charged here. The M2 run evidence records `4,214,784` bytes for those two allocations, leaving `2,600,960` bytes in that region at that boot boundary. Object-pool bytes nested in game state must not be charged again. Current claims size depends on the bound tag+BSP spans. |
| `current_bsp` | 6,291,456 | Current single contiguous tag-cache span followed by the active CE structure BSP span. `hcu_memory_bind_parent_v2` binds the tag cache at this region's start and the BSP to its remaining tail ([`hcu_memory_bind.c:41-56`](../../src/stream/hcu_memory_bind.c#L41)). Default tag cache is 2,097,152 bytes, leaving 4,194,304 for the BSP; the binding is not sized for retail CTAG. |
| `texture_cache` | 4,194,304 | HCU EE texture/lightmap cache capacity; do not treat as spare BSP RAM while textures are live. GS texture pages are another store and don't make this region disappear. |
| `dynamic_simulation` | 2,621,440 | Combined allocator for dynamic object/actor/effect/projectile allocations; do not shrink based on UI-only or N64 pool figures. |
| `dma_commands` | 1,179,648 | Two frame chains plus upload chains measured by the parent renderer. It is DMA-facing, not map scratch. |
| `streaming` | 1,572,864 | HP2/map-service arena; current implementation uses it for full decoded map sections and retains some section owners after mount. |
| `checkpoint` | 524,288 | Reserved parent checkpoint/save owner; no current map fallback. |
| `audio` | 524,288 | HCU EE sound staging. SPU2's 2 MiB is separate and not an EE cache for arbitrary tag data. |

`resident_gameplay + current_bsp` totals 13,107,200 bytes gross. Subtracting the observed 4,214,784-byte CE game-state/claims baseline leaves at most 8,892,416 bytes in those two regions for tag/BSP data **if** those stores could be repartitioned freely. That is only a useful lower-bound screen: it excludes parent-renderer pack residency, alignment, other resident owners, map-load overlap, texture/audio peaks, and additional claims if the spans change. It is not a proposed memory map. Moving a byte between regions is an explicit ownership/layout change, not proof that the source region is unused.

Consequences:

1. **Longest is the correct first capacity experiment, not a qualified solution.** It has the smallest multiplayer CTAG+BSP lower bound (4,638,408 bytes) and one active BSP. Its retail source SHA is `e045…`; the compaction audit records a 4,263,624-byte image and 4,339,096-byte CTAG payload, SHA `0e3765…`. The CBSP audit records 374,784 raw BSP bytes and a 377,388-byte encoded CBSP envelope. It fits the raw tag+BSP pair in `current_bsp` with 1,653,048 bytes left on paper, but the remainder must still pay for every parent-render representation and staging/accounting item not in the pair.
2. **Sidewinder is the nearest hard counterexample for a one-region tag+BSP placement.** Its intact pair is 71,216 bytes over `current_bsp` before alignment or renderer data. This is not proof it cannot be represented across other legitimate owners; it proves current single-region ownership is insufficient.
3. **Campaign is a different memory problem.** c20 is the smallest compact-CTAG-plus-largest-raw-BSP sum among the ten campaign maps but is 6,414,996 bytes over the optimistic two-region free remainder after the observed permanent allocation; it is also 2,200,212 bytes over the gross 13,107,200-byte resident+BSP sum. No repartition of those two regions alone can fit the preserved pair. Its four scenario BSPs are loaded one at a time; the largest is `levels\\c20\\c20_3`, 9,039,872 bytes raw, with 9,073,100 bytes encoded in CBSP. More campaign rows are still larger.
4. The `retail-map-minimum-working-set-current.json` is explicitly an optimistic projection that externalizes compressed BSP vertex data and omits its destination. Its “fits” bits must not be used for this no-loss requirement. The animation externalization column is also a hypothetical and is not a safe current optimization; see [`m2-budget-proposal-animation-data-v1.md`](m2-budget-proposal-animation-data-v1.md#L1-L68) and [`m2-animation-data-contract-feasibility.md`](m2-animation-data-contract-feasibility.md).

## Why the current path fails before any real-map capacity result

The current path is bounded for the UI fixture, not for the stock map set:

1. `hcu_memory_bind_parent_v2` accepts a requested `tag_cache_bytes`, allocates that entire span from `current_bsp`, and binds the BSP cache to the remaining tail ([`hcu_memory_bind.c:41-70`](../../src/stream/hcu_memory_bind.c#L41)). The active `hcu_main.c` default remains 2 MiB. Longest's 4,263,624-byte image exceeds that binding by 2,166,472 bytes.
2. `hcu_map_service_preflight` rejects every non-UI entry until capacity is qualified, then decodes HMAP, full CTAG, CRNG, and CBIX into `streaming` at once and releases the transaction only after validation ([`hcu_map_service.c:177-230`](../../src/stream/hcu_map_service.c#L177)). Longest's CTAG payload alone is 4,339,096 bytes—2,766,232 bytes above the full 1,572,864-byte streaming arena. A larger tag destination does not fix preflight.
3. Section loading allocates the full raw output in the owner arena and the full stored section in scratch, reads it, and calls `hp2_load_stored` ([`section.c:23-90`](../../submodules/halo-ps2/engine/src/world/section.c#L23)). It is not a streaming decode API.
4. The actual mount reloads and retains decoded CTAG and CRNG section payloads in `map_arena` for the mount lifetime ([`ctag_mount.c:112-165`](../../src/stream/ctag_mount.c#L112)). Therefore even a successful temporary preflight would not work by merely increasing the arena cap: the CTAG section's 4.339 MiB raw payload plus CRNG exceeds streaming, although the final CTAG image is separately intended for `current_bsp`.
5. CE reads the CTAG image as one exact extent and `ps2_ctag_materialize` copies the entire image and rebases all listed pointers ([`ps2_cache.c:338-355`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L338), [`ps2_cache.c:358-385`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L358), [`ps2_ctag.c:159-180`](../../submodules/halo-ce-universal/port/ps2/src/ps2_ctag.c#L159)). This means the published tag image needs one contiguous, stable EE span until CE unloads; a segmented destination is **not** an implementation shortcut unless every pointer consumer and schema validator is redesigned together.
6. `ctag_mount` requests a full encoded CBSP section into `frame_scratch` before invoking the BSP materializer; its map-level BSP catalog correctly limits residency to one active BSP, but the whole-envelope scratch path is incompatible with even Blood Gulch's 1,303,092-byte CBSP payload and 393,216-byte frame scratch ([`ctag_mount.c:67-104`](../../src/stream/ctag_mount.c#L67), [`m2-step7-retail-cbsp-validation.md:10-13`](m2-step7-retail-cbsp-validation.md#L10)). Longest's 377,388-byte CBSP envelope is just under the whole 393,216-byte arena, but leaves too little for any concurrent frame scratch and still shares it with source-hash/decode work. Do not generalize that numeric “fits” to the current actual loader because stored bytes, metadata, alignment, and owner lifetimes must also be charged.
7. The CE/parent handoff already has the right broad ownership concept—one active BSP and a stable mounted tag image—but no real gameplay map has passed the path. The real Blood Gulch test proves byte-identical Python/PS2-C CBSP materialization only; CE `structure_bsp_port_verify`, simulation queries, physical placement, all render assets, and map-level acceptance remain open ([`m2-step7-retail-cbsp-validation.md:1-31`](m2-step7-retail-cbsp-validation.md#L1)).

The solution is not to remove the UI guard. It is to replace the full-section staging topology while preserving the existing CE contiguous-pointer contract for the first map.

## Recommended implementation path, without spending reserve or dropping maps

### Track A — qualify one intact multiplayer map as a first vertical slice

1. **Freeze one coherent artifact bundle.** Re-run CTAG compaction, schema-footprint, CBSP materialization/catalog generation, and the working-set join with the exact same retained schema ELF and pinned retail map hashes. Keep the ELF, source manifest, all report JSON, actual Longest HP2 package, produced render/texture/audio packages, and hashes together. Fix the current b3f59 embedded-vs-on-disk ELF mismatch first. Retain parent/HCU/halo-ps2 commits plus working-tree patch hashes.
2. **Get the actual Longest target footprint, not only the CE pair.** Generate the same parent BSP/mesh/collision, texture/lightmap, object/scenery, animation, and sound packs used by the runtime path. For every pack, distinguish compressed source bytes, decompressed EE destinations, GS allocations, and any source-backed data. Measure whether parent rendering's BSP0 and HCU's full CE structure BSP coexist and where each goes. The renderer and HCU cannot claim the same bytes/region. Current evidence has no Longest pack high-water, so the 4,638,408 subtotal is only a candidate bound.
3. **Introduce HP2 metadata preflight.** Read and validate the bounded HP2 header/section table and source identity without allocating each full decoded section. Validate section extents/codecs/CRCs, bounds, duplicate tags, and arithmetic overflow. Stream the source-file SHA with the existing bounded hash scratch; keep only HMAP and compact parsed CRNG/CBIX metadata. Make preflight a read-only validation pass; do not mutate active CE pointers or publish new owners.
4. **Stream-decode CTAG to the final contiguous tag span.** First change the binder to accept a map-specific, measured pair of contiguous tag and BSP spans whose sum plus alignment/guards fits `current_bsp`. For Longest the strict lower bound is tag `4,263,624` + BSP `374,784` = `4,638,408`; round and reserve only from measured owner requirements. Implement a decoder sink/iterator with fixed bounded scratch (initial 16–64 KiB is a test candidate, not an accepted capacity) and incremental stored/raw checks. Validate CTAG envelope/image CRC/relocation ordering before publication; then materialize/rebase directly into the final tag span without a second full CTAG image in `streaming`. Keep a distinct staging/publication state so CE cannot observe partially decoded bytes.
5. **Replace persistent wire-section ownership with compact metadata.** Decode CRNG into a bounded index or preserve only a measured, compact wire copy in a named owner; decode CBIX into a bounded catalog. Do not leave the raw CTAG package section in `streaming` for the life of the map. Prove every tag-data resource read still maps through the original source extents and fails closed on short reads/corruption. This preserves information and the source-backed cache behavior; it does not silently make external resources resident for free.
6. **Stream the selected CBSP to the final BSP span.** Give the CBSP decoder/materializer a bounded read/parse interface so it does not need the entire envelope in `frame_scratch`. Validate the envelope, CRC, CBSP relocation domains, CTAG string targets, and all source extents before exposing CE BSP globals; materialize into an unpublished BSP span and publish only after success. Preserve the original raw CE BSP bytes exactly after declared pointer fixups. Maintain CE's one-active-BSP lifetime while switching among campaign BSPs.
7. **Define safe destructive switching before trying CE map transitions.** With one tag/BSP slot, preflight can prove the candidate's source/structure/capacity, but can't promise old-map restoration after overwriting the same spans. Verify CE unload releases all pointers before destination writes. On late read/decode/schema failure, return to a defined menu/unloaded state with a specific diagnostic and allow retry; if product requires old-map rollback, budget and implement an additional real staging slot without touching reserve. Test each transition and injected failure.
8. **Measure all simultaneous owners on target.** Instrument arena high-water and address/canaries for tag span, BSP span, HCU game state/claims, HP2 read/decode scratch, compact metadata, texture/lightmap residency, parent renderer packs/DMA, dynamic pools, and audio staging. Run Longest in exact PCSX2 interpreter/recompiler and then PS2 hardware when available. The M2 UI screenshot or `m2-ui-map-loaded` marker is not a gameplay map or render pass.
9. **Acceptance for Longest only:** source/package hashes match; all CE tag/schema and BSP checks pass; CE collision/material/cluster/path/sound queries pass; parent renderer sees the correct same map; at least one gameplay tick runs; no region overlaps, heap growth, stale pointers, or canary damage occur; measured peaks fit named regions, ELF fits its cap, and all 5,767,168 reserve bytes remain untouched. Record this as a *first-map vertical slice*, not reduction of the 24-map product target.

### Track B — preserve the complete retail map set under the fixed 32 MiB contract

The lower-bound screen shows that reallocating only `resident_gameplay` and `current_bsp` cannot qualify campaign c20, much less all campaign missions: even before permanent game state, its CTAG+largest raw BSP pair is 15,307,412 bytes versus 13,107,200 gross; after the observed game-state/claims floor the deficit is 6,414,996 bytes. Therefore the completed design must either (a) show, by measured ownership and no-loss mapping, how currently committed but transient regions contribute to map phases without violating their concurrent runtime contracts; or (b) change the runtime data-access architecture so only a measured simultaneously-needed subset of complete, losslessly recoverable tag/resource/BSP data is resident. It may not claim that source data deleted by a converter, unmeasured unused pools, GS eDRAM, IOP RAM, or reserve bytes are free EE memory.

1. **Build a field-level residency/consumer map for all 24 maps.** Extend the existing per-map CTAG/schema/resource audits to classify each byte range by authority and lifetime: CE object/gameplay metadata, physics/collision/path, runtime effects/AI/script data, texture/lightmap/geometry, audio, animation, and source-backed file data. Bind every range to consumers and pointer lifetime, not just schema owner. Preserve opaque/unknown fields resident until proven safe. Include all ten campaign missions and all thirteen multiplayer maps; current audit reports already carry map hashes, tag counts, CTAG sizes, source ranges, and active BSP extents.
2. **Prefer lossless typed backing over arbitrary stripping.** For candidate data classes to be source-backed/paged (e.g., large animation/material/visual resources), add stable `(map hash, tag identity, field/element, logical offset, size, digest)` identities and a CE API with explicit pin/lease lifetime. Retain the current in-image pointer path as reference until all consumers—including raw pointer helpers and multi-frame interpolation—are converted and parity-tested. Existing animation findings reject a one-slot cache: `aiming_screen_apply()` can hold four frame pointers concurrently, and direct helpers read the `animation.data` pointer; the recorded 4.97 MiB c10 payload total is not a cache-size proof ([`m2-animation-data-contract-feasibility.md`](m2-animation-data-contract-feasibility.md), [`m2-budget-proposal-animation-data-v1.md:39-68`](m2-budget-proposal-animation-data-v1.md#L39)).
3. **Keep essential simulation data authoritative in HCU.** Do not copy Halo-64's constrained N64 cuts into this EE build. Halo-64's notes say it can skip some far-AI work and substitute N64-specific pool policy because of its target; that is comparison evidence, not a permissible PS2 feature policy ([`submodules/halo-64/port/n64/NOTES.md:200-208`](../../submodules/halo-64/port/n64/NOTES.md#L200)). PS2 retains campaign AI, scripts, effects, local-player gameplay, and all stock maps in scope. Pool changes require EE measurements and parity fixtures.
4. **Measure full runtime coexistence, not startup-only spare bytes.** Use representative authored encounters and 1–4 local players to record data pins, collision queries, actor/object/effect pool high-water, animation leases, texture working set, DMA buffers, sound staging, checkpoint reserve, streaming scratch, and tick/I/O latency. A region is not “available” just because its startup used count is zero. Tie measurements to PCSX2 mode and exact hashes; emulator wall time alone is not EE performance qualification.

### Provisional boot-fixed tag/BSP split: Longest and Blood Gulch

This is a bounded arithmetic experiment inside the unchanged `current_bsp` region, not an accepted allocation or M2 pass. `config/memory-budget.json:12` fixes `current_bsp` at 6,291,456 bytes. `src/stream/hcu_memory_bind.c:41-56` places the tag cache at the start of that arena and binds the remaining tail to the CE BSP cache; `src/stream/hcu_main.c:16-18,180` currently asks for a 2,097,152-byte tag cache. The CE validation bitmap is a separate owner in `resident_gameplay`: `claims_address_space_capacity()` sums the configured tag and BSP spans, and `tag_validate_claims_buffer_size()` computes `ceil(span/32) * sizeof(unsigned long)` (`submodules/halo-ce-universal/port/linux/game/tag_validate.c:239-284`); on the PS2 ILP32 ABI this is one bit per addressable byte. Keeping the combined span fixed at 6,291,456 bytes therefore keeps claims at 786,432 bytes, exactly the current observed baseline. Game state is 3,428,352 bytes, making game-state-plus-claims 4,214,784 bytes charged once to `resident_gameplay`; neither claims nor the game-state object pool should be double-counted in `current_bsp` (`submodules/halo-ce-universal/port/ps2/include/halo_ps2_limits.h:18-22`, `src/stream/hcu_memory_bind.c:47-61`).

Using the exact `2fba…` CTAG/BSP reports, a single boot-fixed split that can hold either map's entire CTAG image is:

| Candidate map | CTAG image in tag span | CTAG wire payload (not resident image) | Largest active raw BSP | CBSP encoded envelope | Remaining BSP-span bytes after raw BSP |
|---|---:|---:|---:|---:|---:|
| Longest | 4,263,624 | 4,339,096 | 374,784 | 377,388 | 1,439,552 |
| Blood Gulch | 4,477,116 | 4,556,496 | 1,296,384 | 1,303,092 | 517,952 |

The fixed tag span is `align_up(max(4,263,624, 4,477,116),16) = 4,477,120` bytes; the fixed BSP span is `6,291,456 − 4,477,120 = 1,814,336` bytes. This preserves every byte represented in the compact CTAG image and every byte in the selected raw active BSP; it does not change global region budgets, borrow reserve, or externalize/strip data. The CTAG wire payload is larger than its final image because the CTAG stream includes header/relocation encoding. The current map path's HP2 section load and mount ownership still operate on encoded section payloads before materialization (`src/stream/hcu_map_service.c:88-101`, `src/stream/ctag_mount.c:112-170`; `submodules/halo-ps2/engine/src/world/section.c`), so wire/staging peaks cannot be treated as equal to the final resident-image requirement.

This split is a plausible **first bounded experiment** for Longest and Blood Gulch only. It assumes the existing CE binding accepts the larger contiguous tag cache and leaves a usable single active BSP span; it is not yet wired into the product boot profile or exercised through target map loading. It does not solve: full CTAG/CRNG wire decode and retained mount-owner pressure in the 1.5 MiB `streaming` region, full CBSP encoded-section decode pressure in 384 KiB `frame_scratch`, BSP materialization/validation/query and unload lifetimes, parent render geometry/lightmap/texture residency, audio/animation/resource staging, simultaneous peak accounting, any campaign mission (including c20), or visible scene rendering. It is not evidence of a playable or rendered map. The next executable implementation should parameterize the boot allocation locally for the two-map fixture (without changing `config/memory-budget.json`), add canaries/high-water reports for the tag/BSP/claims owners, then run actual CTAG and CBSP materialization and schema/query fixtures; only after those pass should the end-to-end loader/render trial begin.
