## What the controlled 30 FPS result actually tests

The most useful retained controlled data is `docs/reports/c3-multiview-fps-ab-2026-10-25.md` and its machine record under `build/c3/perf/multiview-ab-20261025-r2/report.json`. The optimized condition changes exactly four compile-time settings from zero to one: `HCU_C3_OBJECT_FASTPATH`, `HCU_C3_OBJECT_VIEW_CACHE`, `HCU_C3_BINDING_SEAL`, and `HCU_C3_SNAPSHOT_INDEX`. `HCU_C3_REALTIME_SCHEDULER=1` and `HCU_C3_BITMAP_RESIDENT=1` are common to both conditions. Thus this comparison does not measure scheduler or resident-bitmap benefits.

The matched one-view result is 14.959 to 29.968 rendered FPS, with game rate 30.052 to 30.035 Hz, zero drops, full RGB equality, canonical snapshot equality, and bitmap queue parity. Quiet one-view observation separately showed 29.97 FPS / 59.94 VPS / 100% emulation speed. This restores normal NTSC presentation at approximately 30 FPS for the tested Blood Gulch workload. At 2/3/4 views the optimized rates are 18.705 / 14.535 / 9.990 FPS, so split-screen is not at 30.

The four-setting bundle cannot identify the contribution of each individual switch from the matched matrix. The earlier isolated one-view sequence in that report is explicitly directional and from separate sessions: fast path ~19.983, binding sealing ~19.402, snapshot indexing ~14.977, view setup cache ~19.982, combined ~29.972. It is not a controlled component-wise causal estimate. The companion [flag correctness audit](c3-fps-flag-correctness-fresh-2026-10-26.md) establishes that r1's severe black crop is capture-origin error in a rejected matrix; r2 one-view baseline and optimized PNGs are byte-identical. It also finds a latent cached-setup reservation failure bug: setup can be marked valid although its chain reservation failed. That is a failure-path correctness issue requiring a fix/fixture, but it was not established as the cause of r1's crop and does not contradict the r2 pixel-identical capture. Where other archived baseline/current framebuffer hashes differ, a detailed visual diff is still needed; animation timing or other dynamic state could explain the difference, and a hash alone proves neither regression nor equivalence. The controlled matrix's exact parity applies to its own matched captures and tuple, not every asset, camera, map, and later first-person state.

## Runtime/compiled evidence boundaries

1. The earlier known baseline is ~14.96 render FPS with ~30 Hz simulation, not a scheduler-imposed 15 cap. The controlled one-view improvement is associated with the four optimized renderer settings, and the baseline already has realtime scheduling and resident bitmaps.
2. The controlled matrix runs one fixed Blood Gulch package/workload and supports exact RGB/canonical snapshot/queue parity for those runs. It is strong evidence of tested behavior, not a universal no-regression guarantee.
3. The generic frozen-link probe is diagnostic and does not itself establish runtime acceptance. A separate run of the same ELF establishes production Blood Gulch map load and CE ticks, and the desktop launch has a user-observed ~15 FPS/rendered content. That live observation is not a controlled FPS benchmark or matched A/B against the 30 FPS ELF.
4. The current checkout has extensive uncommitted source/test/config changes. Commit IDs and submodule pins alone do not identify the bytes of the dirty working tree; report comparisons must use retained manifest source hashes and ELF hashes. The r2 matrix records 27 pinned paths matching across all eight cases. Its v1–v4 labels mean view counts, not source revisions.
5. Static memory of the controlled matrix: `elf_static` used 2,385,156–2,386,308 bytes of 2,490,368, headroom 104,060–105,212; PT_LOAD NOBITS was 1,987,792 bytes in all eight. The current c258 ELF's guest manifest records its own load segment FileSiz 2,402,692 / MemSiz 4,398,244 and a guest high byte below its reserve; these are different ELF/accounting numbers. The snapshot index's additional 8 KiB is separately charged to bounded frame scratch in the controlled report. None of these static values alone is a whole-run runtime peak.
6. Newer split-screen profiling in `c3-rfps-ai2-runtime-2026-10-26.md` has two-view phase diagnostics and one v9 instrumented run. It reports `game-time` median 16.724 ms and publication 9.809 ms, but it is one two-view run, not a matched comparison with the known 15 FPS executable. Its 2/3-view preliminary runs are explicitly from a hook-broken tuple and must not be combined with v9.
7. The durable cleanup record `build/c3/fps-runtime-fresh/cleanup-20261026T1855Z/cleanup-manifest.json` (SHA-256 `b9dd0c2df2f2392a6d48888c8f62805f392a4155d8453d8f4cc0dfc365abbca8`) identifies twelve stale private emulator groups by PID/PGID, AppRun child, display, data path, and log path/hash. All twelve groups and their private Xvfb servers exited after identity-revalidated SIGTERM; no SIGKILL was used. The same-PGID AppRun children consumed 837.1% aggregate CPU (54–80% per child in the earlier sample). The separate visible user Board group PID 386252 / AppRun 386253 on `:0.0` was not signaled. This establishes significant host load relief, not that it caused the full FPS shortfall. The cleanup record's Board OSD observation is 15.98 FPS / 59.94 VPS / 100% speed for an unrelated Boarding Action session; it is a host sanity check, not Blood Gulch candidate evidence.
8. These stale groups were attributable to abandoned runtime harnesses only at the mechanism level: the cleanup diagnosis finds wrappers can return after the direct launcher exits without verifying detached AppRun descendants have drained. It does not prove which historical harness created every group. The groups' logs are now stable: a read-only SHA-256 recheck after cleanup matched all twelve hashes in the cleanup manifest. However, a hash taken by the old runner before an AppRun descendant exits would only identify a point-in-time prefix, not prove a complete run log. The source cleanup fix in progress at `tools/c2_guest_run.py` (`_stop_owned_process` / `run_guest`) tracks owned process identities and descendants, waits for group drain, and refuses final log hashing while any tracked writer remains. This raises confidence in *future* run manifests; it does not retroactively validate a historical manifest's completion claim or hash timing.
9. Resource pressure could bias only runs that overlapped those children. No paired measurement isolates their FPS effect, and the known 14.96→29.97 renderer matrix predates this Oct 26 orphan inventory. Do not attribute the measured doubling or the current ~15 FPS observation to the orphan processes. Once new matched runs use the process-drain fix, compare under clean host conditions and retain CPU/GPU and writer-exit evidence with the timing artifact.

## Recommendations supported by this evidence

- Attribute the measured one-view near-doubling to the combined object fast path, view setup cache, binding seal, and snapshot index. Report the fast path and view cache as the strongest measured work reductions; do not claim exact per-flag FPS shares.
- Treat v4 as a build-capacity change and fixed-tick scheduling/resident HUD as shared baseline features. They explain build acceptance or stable simulation/warm HUD behavior, not the controlled render FPS delta.
- Keep duplicate-name resolution and spawn-overlap fixes in correctness/gameplay categories until exact source diffs plus a matched runtime test establish another effect.
- Keep package packing and bitmap batching claims separate from source flags. To assess their impact, compare the same executable/source with only the package/profile or batching revision varied, pin package digest and source hashes, and retain per-view RGB plus queue/fence/canary checks.
- Use the post-first-person-fix source as the next visual/performance baseline. Run a quiet, pinned current production ELF at one view and then 2–4 views, recording ELF/package/pin hashes, game ticks, completed render frames, drops, full-frame parity at matched states, and memory high-water. Current diagnostic link cannot fill this gap.
- For split-screen, focus on measured remaining phases rather than asserting 30 FPS: the retained 4-view data remains 9.99 FPS. Newer profiling suggests publication and game-time also matter beyond the renderer callback; first collect a matched frozen tuple with whole-batch timing before selecting code changes.
