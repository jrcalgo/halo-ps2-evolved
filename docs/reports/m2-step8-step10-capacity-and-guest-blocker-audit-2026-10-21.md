## Step 8 — What is actually blocking capacity

The configured budget is 27,787,264 committed EE bytes out of 33,554,432, with the 5,767,168-byte reserve untouched. Named stores include 6,815,744 B `resident_gameplay`, 6,291,456 B `current_bsp`, 2,621,440 B `dynamic_simulation`, 4,194,304 B texture cache, 1,179,648 B DMA commands, 1,572,864 B streaming, 524,288 B audio, and 393,216 B frame scratch ([`config/memory-budget.json:1-23`](../../config/memory-budget.json#L1)). CE cannot use GS eDRAM, IOP RAM, or SPU2 RAM as ordinary EE pointers.

The strongest current blocker is not section decode scratch; it is the representation’s complete, stable pointer-addressable images:

* The exact-schema D20 CTAG image is 10,046,996 B (16-byte span 10,047,008 B). Its largest referenced raw BSP, `d20_hangar`, is 8,517,632 B after span alignment. Together they need 18,564,640 B before validation scratch or renderer replacement data. Current budget v2 provides only 6,291,456 B in `current_bsp` for tag plus one active BSP ([`hcu_memory_bind.c:41-70`](../../src/stream/hcu_memory_bind.c#L41)).
* `tag_validate_claims_buffer_size()` sizes its bitmap from the configured tag+BSP capacities; at the cited d20 spans it adds 2,320,580 B. Adding only fixed known lower-bound owners—system/kernel 1,572,864 B, ELF LOAD 2,086,532 B, ELF `.bss` 2,114,588 B, CE game state 3,428,352 B, tag+BSP 18,564,640 B, and claims 2,320,580 B—gives 30,087,556 B. This exceeds the entire committed budget by 2,300,292 B **before** dynamic actors/AI/scripts/effects, textures/lightmaps, DMA, audio, streaming, scratch, renderer state, alignment, and transition overlap. The reproducible calculation and current caveats are in [`m2-campaign-capacity-topology-review-2026-10-21.md`](m2-campaign-capacity-topology-review-2026-10-21.md) and [`m2-2026-10-21-budget-repartition-review.md`](m2-2026-10-21-budget-repartition-review.md).
* This is a lower-bound contradiction for the present fully resident image contract, not a complete proof that no lossless topology could ever fit. It does prove that moving region boundaries, streaming only HP2 codec output, choosing a smaller BSP, or citing nominal unused arenas cannot solve d20. Even the sensitivity calculation that removes all d20 animation payloads at zero cache/metadata/provider cost leaves only 2,751,784 B for every other omitted owner and pinned animation. That number is not available spare memory: it is below the nominal dynamic-simulation reservation, whose actual phase high-water still needs measurement.
* The normal cache/map contract explains the difficulty. `tag_block.address` and `tag_data.address` are fixed raw pointers ([`tag_groups.h:87-145`](../../submodules/halo-ce-universal/source/tag_files/tag_groups.h#L87)); `tag_data_get_pointer()` returns direct `address + offset` pointers rather than consulting a paging provider ([`tag_groups.c:91-114`](../../submodules/halo-ce-universal/source/tag_files/tag_groups.c#L91)). CE reads and validates a complete tag image before publishing its globals ([`cache_files.c:1262-1332`](../../submodules/halo-ce-universal/source/cache/cache_files.c#L1262)); it does the same for a complete active BSP before publication and can roll back a BSP switch ([`scenario.c:1116-1192`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L1116)). A file-backed field therefore needs a lifetime-bounded EE lease or a redesigned pointer-consumer contract, not just a new file reader.
* HP2 bounded visitation is still useful: it removes duplicate encoded section staging, and the production CBSP visitor now has host UI-path and retail-package transaction coverage. It does not reduce the complete CE tag/BSP final images or automatically make the d20 residency contract fit. The current service still rejects every non-UI map before package access ([`hcu_map_service.c:288-311`](../../src/stream/hcu_map_service.c#L288)); preserve that gate.

4. **Instrument all candidate bytes and lifetimes, not just animation requests.** The existing inventory finds direct animation schema-validation reads, three compressed keyframe helpers, the default-pose path, melee frame-info and four simultaneous aiming-frame pointers ([`m2-animation-live-set-access-inventory-2026-10-21.md`](m2-animation-live-set-access-inventory-2026-10-21.md)). If the full all-campaign set still cannot fit with the reserve untouched, stop the lease line and produce the measured architecture decision / alternate lossless residency design; do not reduce campaign, AI, scripts, effects, or hardware reserve to force a green result.

This slice can unblock a truthful Step 8 design decision, not Step 8 completion by itself. ## Halo-64 comparison boundary

Halo-64 demonstrates a method, not a PS2 budget solution: its `n64_anim.c` stores animation graph files on cartridge and services frames from sixteen 4 KiB chunks (64 KiB total), using cartridge DMA and a boot-reserved block to avoid later map-allocation fragmentation ([`n64_anim.c:1-12,22-24,48-63,108-177`](../../submodules/halo-64/port/n64/src/n64_anim.c#L1)). The source documents its constrained N64 environment; those byte counts and cartridge semantics do not transfer to the 32 MiB PS2 EE, DVD/OPL/FileXio path, or this product’s campaign/AI/script/effect scope.

The seam is especially incomplete if copied mechanically. HCU's accessor has direct compressed-data paths; CE schema validation dereferences animation bytes, and aiming interpolation can keep four frame pointers live at once. A PS2 solution must retain the CE acceptance/correction and pose result, provide contiguous EE leases for the full nested lifetime, and measure I/O latency/60 Hz CPU cost. Do not import Halo-64's cache size, eviction semantics, ABI, or gameplay cuts.
