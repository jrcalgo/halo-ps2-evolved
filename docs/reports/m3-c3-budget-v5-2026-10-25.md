# C3 memory budget v5 (2026-10-25)

Budget v5 moves 524,288 bytes (512 KiB) from the uncommitted reserve into the C3 object residency pool, as approved by the user on 2026-10-25. The 32 MiB EE map remains 33,554,432 bytes.

## Owner chain

The C3 object pool is the rest of the level arena. The level arena is the `render_texture` owner of the selected partition row, after the BSPS and TEXS+LM spans (`hcu_render_media_pack_plan`). `render_texture_bytes` is the row's render span, and `render_parent` is the texture parent `texture_cache` minus its map share. The boot backing is `MEM_LAYOUT_V2_BYTES`, the sum of the nine region rows in `submodules/halo-ps2/engine/src/core/mem.c`.

Growing the pool by 524,288 therefore grows the owner chain at each level:

1. `texture_cache` region row, 4,194,304 -> 4,718,592 (`mem.c`).
2. `MEM_LAYOUT_V2_BYTES`, 24,117,248 -> 24,641,536 (`mem.h`).
3. Every partition row's `render_texture_bytes` (28 rows) += 524,288. The C3 row is `bloodgulch_mounted_gunner_4p4bot`: 3,338,064 -> 3,862,352.
4. Level arena cap for that row: 1,877,392 -> 2,401,680. The pool, after the unchanged 329,712 bytes used and the 16-byte alignment pad, is 1,547,648 -> 2,071,936 (the 64-byte rounding in `hcu_render_objects_load` is unchanged).

## Why every row

`hcu_memory_profile_plan_v1`, `hcu_memory_partition_guards_intact` and `tools/audit_hcu_c2_partition_budget.py` require every row to fill the map and render backing exactly. The backing is now 11,010,048 bytes. Raising the texture cap alone would leave an unallocated gap in the 27 non-C3 rows and in the bots candidate, so all 28 rows gain the same 524,288 bytes. Non-C3 rows never allocate the level arena, so they only gain unused render span.

The partition rows (`hcu_memory_profile.c`) changed as follows: `render_texture_bytes` += 524288 for every row, `tag_cache_bytes`, `structure_bsp_bytes` and `residency_bytes` unchanged.
