# M2 Step 6 — CE BSP replacement and rollback transaction audit

**Scope:** report-only investigation of Step 6 in [`plans/7.hcu-remake-m2-m4.md`](../../plans/7.hcu-remake-m2-m4.md#L502). No production source or plan edits are proposed here. This report distinguishes three different evidence levels: (1) static inspection of the real decompiled CE transaction, (2) host execution of the PS2 cache/CBSP adapter plus a test-side model of CE's transaction, and (3) actual CE scenario execution in a guest. Current evidence reaches levels 1 and 2; it does not reach level 3 for a BSP switch or rollback.

## Finding

The Step 6 transaction has a useful and nontrivial host model, but the acceptance claim is not yet demonstrated by executing CE's `scenario_switch_structure_bsp()` with the production PS2 cache adapter. The existing C fixture performs the adapter's real `cache_file_read()` and relocation/materialization, while its `switch_bsp_reference()` independently models unload, candidate verification, index publication, and retry. The Python test separately checks selected source-order properties in CE. Neither fixture drives CE globals or the CE call graph, and the fixture's CBIX/CBSP records are synthetic, not drawn from a retail map package. Consequently the tests do not prove that CE's cache tag instance, `cache_file_globals.structure_bsp_header`, `global_structure_bsp`, collision pointers, `scenario_globals->structure_bsp_index`, the parent mount owner, and the cache adapter remain mutually consistent across all failure edges.

The main architectural concern is now sharper than a generic rollback question: CE unloads and reloads the old BSP through the *same fixed BSP destination* that the rejected candidate has just overwritten. That is a valid reload strategy only if the old CBSP remains independently available from the package and every CE-side pointer/registration is unpublished before the destination is reused. The source paths implement this strategy, and the host fixture models an old-payload reload; no current guest trace proves that ownership choreography under the production transaction.

## Ownership and mutation order

The BSP switch spans multiple owners, and Step 6's “old index/global state restored” needs to be checked as an aggregate transaction rather than one index variable.

1. **CE scenario owner:** `scenario_switch_structure_bsp()` owns the request guard, stop/restart timing, disconnect/reconnect of BSP procedures, CE's `global_structure_bsp_index`, `scenario_globals->structure_bsp_index`, and publication of `global_structure_bsp`, `global_collision_bsp`, and `global_bsp3d` ([`scenario.c:1088-1195`](../../submodules/halo-ce-universal/source/scenario/scenario.c#L1088)).
2. **CE cache/tag owner:** `scenario_structure_bsp_load()` owns validation of the reference/header/schema, `cache_file_globals.structure_bsp_header`, vertex-buffer registration, and the referenced tag instance's `base_address`; unload deregisters buffers, clears the tag-instance base address, and clears the header pointer ([`cache_files.c:1376-1534`](../../submodules/halo-ce-universal/source/cache/cache_files.c#L1376)). These records must not point to a candidate after rollback begins.
3. **HCU PS2 cache adapter:** `cache_file_read()` owns the mounted CTAG/CBSP views and invokes the parent BSP loader only for the exact requested BSP cache destination; it rejects extent mismatch and releases newly loaded CBSP payload if materialization fails ([`ps2_cache.c:219-257,358-418`](../../submodules/halo-ce-universal/port/ps2/src/ps2_cache.c#L219)). The adapter's single `mounted_cbsp` view is a staging lease, not the CE materialized BSP's long-term owner.
4. **Parent package/mount owner:** `ctag_mount` finds the exact CBIX row, checks overlap against CTAG/resource extents, loads the chosen HP2 section into `bsp_scratch`, asks the adapter to mount it, and releases that scratch on `unmount_bsp` ([`ctag_mount.c:54-104`](../../src/stream/ctag_mount.c#L54)). Whole-map unload releases the BSP lease, unpublishes the cache, closes the read source, and rewinds the map owner in that order ([`ctag_mount.c:277-290`](../../src/stream/ctag_mount.c#L277)).

The required invariant at each observable boundary is: **either** the CE cache/tag/global state and parent map owner jointly describe one fully loaded, verified BSP with all registered references pointing into its current materialization, **or** they describe no active BSP and no CE/cache pointer references an arena that has been released or overwritten. During replacement, old materialized bytes cannot remain valid after the shared BSP cache is overwritten. Recovery must therefore reload the prior *package section* into the same stable destination before republishing old CE pointers/index; it cannot merely restore old pointers.

## Existing tests: reuse value and limits

### `tests/ps2_cache_cbsp_main.c` + `tests/test_cbsp.py`

This is the most relevant reusable adapter fixture. The Python harness compiles the real PS2 `ps2_cache.c`, `ps2_ctag.c`, and `ps2_cbsp.c`; the C executable mounts a synthetic CTAG, loads/materializes two synthetic CBSPs at different extents, checks relocation results, injects bad extents/tag overlap, loader failure and a candidate-verification rejection, and verifies it can fetch the old CBSP payload again ([`test_cbsp.py:205-248`](../../tests/test_cbsp.py#L205), [`ps2_cache_cbsp_main.c:131-169`](../../tests/ps2_cache_cbsp_main.c#L131)). This is valuable execution of the adapter seam and should remain.

Limit: the fixture's own `switch_bsp_reference()` is explicitly a contract model, not CE execution ([`ps2_cache_cbsp_main.c:72-76`](../../tests/ps2_cache_cbsp_main.c#L72)). Its “verify” is `bsp_cache[4] == 0x42` ([`ps2_cache_cbsp_main.c:79-88`](../../tests/ps2_cache_cbsp_main.c#L79)); its publication is assignment to `current_bsp_index`. Thus its passing rollback checks establish adapter rematerialization and the model's behavior, not CE's schema verifier, globals, tag instance, callback registration, or rollback branch.

### `tests/test_cbsp.py::test_ce_structure_bsp_switch_preserves_verify_and_rollback_order`

Keep this regression guard for control-flow drift. It checks guard/disconnect/unload/load ordering, two verification call sites, retry before global publication, explicit nulling, and the safe-menu call ([`test_cbsp.py:250-312`](../../tests/test_cbsp.py#L250)). It is a text-based structural assertion and cannot establish branch execution, pointer correctness, cleanup side effects, or target runtime.

### `tests/ctag_mount_main.c` real UI service transaction

Reuse its snapshots, real retail UI package source, `open/close` accounting, owner-release callback, corruption between preflight and deferred load, and retry pattern ([`ctag_mount_main.c:448-570`](../../tests/ctag_mount_main.c#L448)). It demonstrates a parent map-service transaction and package reader, but the UI map has one BSP and this fixture calls the cache read path directly. It does not invoke CE's BSP switch/verify/unload path, so it must not be relabeled as BSP rollback coverage.

### Package matrix / retail package audit

Reuse Step 5's exact package hashes and 82-entry catalog mapping as fixture provenance. Select a retail map with at least two BSP references and ensure each transaction case names the actual package SHA, scenario tag, reference order, CBIX row, CBSP section, file extent, and tag datum. The package matrix proves that the catalog payloads correspond; it does not prove CE switch semantics or that those payloads fit the current BSP destination.

## Concrete gaps to close

1. **No live CE transaction execution.** The current C driver duplicates rather than calls CE's switch function. Source-order assertions can coexist with wrong data flow or unhandled side effects.
2. **No package-derived switch fixture.** The two active CBSP fixtures are small synthetic images. There is no test where CE's actual scenario reference and package catalog select an actual second retail BSP.
3. **Failure points are coarsely modeled.** Existing execution has adapter loader failure and post-materialization “reject” cases. It lacks separately controlled failures at section open/read, CBSP parse/relocation, CE header-range check, tag schema validation, port BSP-capacity verification, and old-BSP retry.
4. **No complete CE state snapshots.** No test captures before/after values for both BSP indexes, all global pointers, `cache_file_globals.structure_bsp_header`, tag-instance `base_address`, registered vertex-buffer state/count, disconnect/reconnect calls, selected CBSP lease, owner arena cursors/high-water, file handles, and release counts.
5. **Rollback failure is not executed.** We need prove deterministic null/safe-menu semantics and cleanup with old BSP reload unavailable or rejected, not only the source contains `main_goto_main_menu()`.
6. **First load and same-index contracts are only partial.** No CE execution proves first-load failure leaves no state, and current model's same-index return value does not match CE's false “no transition” result. Explicitly define expected boolean semantics in the fixture.
7. **Unresolved candidate-staging assumption.** `ctag_mount.load_bsp_extent()` first calls `release_mounted_bsp()` and then reserves candidate bytes at a scratch mark ([`ctag_mount.c:87-104`](../../src/stream/ctag_mount.c#L87)); this is correct for the old encoded payload lease, but the EE destination itself is a single mutable BSP buffer. Tests need assert no CE pointer or registered draw/collision state is consumed between unpublish and candidate verification, and old package data can be reloaded after candidate overwrite.
8. **Current capacity prevents a retail runtime switch.** Step 8 notes the current production tag/BSP bindings are not sufficient for gameplay map residency; Step 10 properly keeps non-UI entries rejected. Therefore a real retail guest switch is downstream of capacity and a BSP-bearing gameplay map load. This is a dependency, not a reason to declare Step 6 done via synthetic host tests.

## Safe next implementation slice

Keep the current synthetic adapter test intact, then add a **test-only deterministic transaction seam that calls the actual CE transaction code**. Preferred order:

1. Inspect whether `scenario.c` can be compiled as a host test object with its normal PS2 source prefix and section garbage collection. If its unresolved closure is manageable, compile the real CE scenario/cache files against test shims for unrelated services/globals; do not copy/reimplement `scenario_switch_structure_bsp()` into the test. If the closure is too broad, isolate only side-effect boundaries behind narrow `HALO_PS2` test hooks that production binds to the current functions. The transaction algorithm must remain the production body.
2. Build a two-BSP synthetic CE scenario/tag image and mount it through production `ctag_mount` + production PS2 cache backend. Track a single stable BSP destination, a bounded parent scratch owner, open/close counts, and release/unmount counters. Ensure the second package row is selected by the exact `(file_offset,file_size)` pair, not by test-local index alone.
3. Capture a transaction snapshot before every call: requested and published CE indices; scenario index; `global_structure_bsp`, collision/BSP3D pointers; tag instance and cache-header pointer; vertex-buffer registration state; mounted CBSP view; owner/scratch cursors/high-water; descriptor counts; and callback counts. Compare it after success, each failure, and retry.
4. Add deterministic fault injection at the loader and CE-validation boundaries: fail source open/read; reject CBSP parse/relocation; produce malformed CE header/pointers; fail tag schema validation; fail `structure_bsp_port_verify`; then fail old-BSP reload (separately as read failure and verification failure). At each failure, assert either full old-BSP republish after re-materialization or the specified safe null/menu state; prove no released arena pointer remains published.
5. Derive at least one fixture from a real audited package with two BSPs when available. Bind the fixture to current package/audit hashes. Until it fits actual PS2 arenas and is run in PCSX2, label it host CE transaction evidence only.
6. After M2 Steps 8–10 provide a capacity-qualified guest scenario, add diagnostic-only markers/counters around actual CE unload, adapter materialization, CE verification, republish/rollback, and owner baseline. Run one successful switch, candidate failure→rollback, rollback failure→safe menu, and a retry in interpreter and recompiler on the exact same ELF/package pins. These are required for the plan's guest acceptance; do not create a guest marker that claims a branch without observing the actual branch.

Do not begin by replacing the CE algorithm or by adding a generic parent transaction API: the current ownership division is appropriate. CE must own scenario/global publication; HCU's PS2 cache adapter owns cache-read and transient CBSP-view behavior; the parent mount owns package payload/scratch and its source handle. The missing piece is executable cross-owner evidence and then capacity-qualified guest confirmation.

## Gate recommendation

Keep Step 6 `partial`, as the plan currently records. The existing model tests are meaningful adapter/contract coverage, but do not satisfy the plan's explicit package-derived transaction execution and aggregate-state invariants. Step 6 can advance to host-transaction-complete only after the actual CE switch body is exercised with the production adapter and the full state snapshot/fault matrix passes. It cannot reach guest-complete before M2's stable BSP backing/capacity and accepted gameplay-map load exist.
