# M3 renderer audit alignment to remake plan — 2026-10-21

## Scope and conclusion

Report-only comparison of [`m3-renderer-submission-audit-2026-10-21.md`](m3-renderer-submission-audit-2026-10-21.md) with the remaining M3/M4 instructions in [`plans/7.hcu-remake-m2-m4.md`](../../plans/7.hcu-remake-m2-m4.md) and governing exits in [`plans/5.hcu-remake.md`](../../plans/5.hcu-remake.md). No code or plan was changed. The renderer audit identifies a material gap: M3 currently specifies snapshot publication and consumer-only simulation ownership, but not the concrete CE-snapshot → gameplay render-pack → halo-ps2 BSP renderer → GS presentation path. The plan should add the audit's F1 BSP-only slice as an explicit dependent M3 substep, without treating a blue clear, UI load, or free-camera viewer as game rendering.

The hard dependency is M2 gameplay-map admission and measured pack residency, not simply the existence of `bsp_render`. The audit reports that the linked BSP renderer is not initialized or called from the combined HCU machine image and no admitted gameplay BSP/texture callbacks are supplied ([audit §§1–3, 24–38](m3-renderer-submission-audit-2026-10-21.md#L9)). Thus M3 can continue host-side camera, snapshot, arena, ownership, and synthetic BSP tests in parallel, but cannot pass the visible-gameplay-scene gate until M2 provides an admitted map and a coherent physical memory layout.

## Prioritization and dependencies

1. **Now, in parallel with M2:** camera conversion and DMA partition/fence host fixtures; map/render-pack inventory; build-link audit; snapshot immutability under rendering schedule. These use no unadmitted gameplay map and can expose API/ownership errors early.
2. **Hard gate before target F1:** M2 has one exact gameplay scenario whose CTAG, required CE BSP/collision data, HP2 render pack, textures/lightmaps and validation scratch have measured simultaneous physical owners. The renderer audit specifically warns that the retail lower bound excludes renderer-pack and transition costs ([audit lines 13–14, 68–74](m3-renderer-submission-audit-2026-10-21.md#L13)).
3. **First target render:** implement one viewport and BSP-only scene, use CE camera, same admitted scenario/BSP index, complete real GS/VU/DMA submission, fence and present. The deterministic fixed camera may debug; the acceptance run must use a real CE gameplay-tick camera and exact package/image, interpreter and recompiler.
4. **Only after F1:** object/model/animation, first-person weapon pose, particles/effects/HUD, then split-screen/view ordering and complete parity. Keep M4 simulation work advancing with host fixtures; gate presentation-specific claims separately.
5. **M3/M4 cannot close from current evidence:** currently demonstrated artifacts are CE snapshot production, independent PS2 renderer capability, blue clear diagnostic, and UI lifecycle. None establishes production HCU BSP rendering. The audit explicitly recommends leaving Steps 13–14 and Group F incomplete ([audit lines 101–103](m3-renderer-submission-audit-2026-10-21.md#L101)).

## Governing-plan consistency

The additions should elaborate, not replace, `plans/5.hcu-remake.md`. Preserve its ownership model: HCU CE datums own gameplay identity/state; parent/halo-ps2 supplies PS2 presentation machinery; parent `src/game` remains a comparison oracle until parity. Its M3 exit remains movement/collision parity and render-schedule invariance ([`plans/5.hcu-remake.md:417–425`](../../plans/5.hcu-remake.md#L417)), while M4 still requires all combat/objective rows and identical interpreter/recompiler traces ([`plans/5.hcu-remake.md:427–435`](../../plans/5.hcu-remake.md#L427)). The renderer audit's F1 BSP-only gate is a missing presentation acceptance item—not permission to relax the all-map M2 capacity gate, omit CE camera authority, remove `src/game` early, or claim full M3/M4/CE parity.
