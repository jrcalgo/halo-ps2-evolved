# Remake M3 Step 11 — CE tick-order and render-schedule fixture review

**Scope:** report-only review of Remake M3 Step 11 in `plans/7.hcu-remake-m2-m4.md`. This review distinguishes source-text assertions, host-executed CE code, integrated guest evidence, and real gameplay evidence. No implementation or plan files were changed.

## Finding

The current test suite does **not** execute `game_tick()`. `tests/test_hcu_ps2_input.py::test_ce_game_initialization_and_tick_phase_order_is_preserved` extracts the source text for `game_initialize()` and `game_tick()` and checks substring order/count. It compiles and executes an extracted `input_frame_begin()` fragment in a separate test, but the tick check is source-order-only. The passing “9 tests and 2 subtests” is therefore not evidence that a real CE tick ran, that one `game_tick()` occurred per requested simulation tick, or that render/snapshot publication cannot advance simulation.

The production HCU path does use CE’s actual scheduler and tick: parent `src/stream/hcu_main.c::main()` initializes the machine services and ends by calling `halo_shell_main()` (`src/stream/hcu_main.c:155-303`); HCU’s PS2 port renames the CE shell entry to `halo_shell_main` (`submodules/halo-ce-universal/port/ps2/src/ps2_main.c:1-30`, build configuration in `tools/hcu_ps2_closure.py` and the HCU PS2 manifest); `source/shell/shell_xbox.c::main()` initializes the shell and calls `main_loop()` (`.../source/shell/shell_xbox.c:110-132`). The native `main_loop()` calls `input_frame_begin`, `input_update`, `input_abstraction_update`, `player_control_update`, and then `game_time_update` before its render path (`.../source/main/main.c:3620-3738`). `game_time_update()` schedules zero or more CE ticks from elapsed fixed-step time and invokes `game_tick()` inside its `server_updates` loop (`.../source/game/game_time.c:384-493`).

`src/game/play_ee.c` is not this production path: it implements the separate parent `WORLD_PLAY=1` diagnostic and the makefile adds it and parent movement/combat/collision sources only under that option (`src/game/play_ee.c:1-30`; `tools/ee-world.mk:70-79`). The `WORLD_HCU_GAMEPLAY=1` branch selects `hcu_main.o` and the HCU services (`tools/ee-world.mk:45-65`). A test of `play_ee`’s callback or tick counter cannot stand in for HCU’s `game_tick`.

## What current checks establish—and do not establish

The current test’s tick block obtains source bodies with `extract_function`, asserts ordered phase substrings and a first-person RNG lock/unlock bracket, then scans `main_loop` source for a call ordering (`tests/test_hcu_ps2_input.py:128-176`). It does not compile either extracted `game_tick()` or `game_time_update()`, link their CE dependencies, call them, capture a tick sequence, or hash state. The assertions are useful regression alarms for a source edit but can pass while the linked runtime chooses a different preprocessor branch, is never scheduled, gets called multiple times, or has a render callback that schedules a tick indirectly.

The input tests *do* execute meaningful host code: `input_frame_begin()` is extracted, compiled, and run with call recorders for pad polling, device snapshot, and mutex acquisition (`tests/test_hcu_ps2_input.py:91-126`); the surrounding suite exercises the parent bridge and PS2 XInput code. These are input/frame-boundary checks, not a CE simulation tick fixture. Likewise, the current PCSX2 UI test logs mentioned in the plan do not prove a gameplay tick: they load the UI map and publish/pack a render snapshot, with no guest tick counter or deterministic gameplay-state hash.

## Runtime boundaries and tick semantics

1. The HCU shell owns production loop scheduling. `main_loop()` calls `player_control_update()` once for an active frame, then passes a scaled elapsed-time delta to `game_time_update()`; it does not call `game_tick()` directly (`source/main/main.c:3688-3708`).
2. `game_time_update()` computes `floor((time_delta_sec + leftover_dt) * speed * TICKS_PER_SECOND)`, caps local advancement to seven ticks per frame, updates local/server clock state, and loops calling `game_tick()` once for each eligible server-time increment (`source/game/game_time.c:384-487`). Therefore a main-loop/frame count is not a simulation-tick count: one frame may run zero or multiple ticks.
3. `game_tick()` itself owns the CE phase sequence. The current body performs pre/post data-array checks and light recovery, then cheat/client cleanup, allegiance, units, AI-or-network actor driving, player-before, effects, antennas, locked first-person/rumble, game-engine, editor, HaloScript under its existing condition, recorded animations, objects, player-after, HUD, player effects, and closing profile/collision calls (`source/game/game.c:331-403`). An expected call ledger must model the local PS2 branch: `network_game_distributed_client()` is false, so the AI branch runs; coop/network-client branches should be asserted unreachable for local smoke, not silently treated as ordinary local tick behavior.
4. CE input is currently sampled at **frame** boundary, not independently before each internal tick. `input_frame_begin()` runs once in `main_loop`, and `input_update`/abstraction/player control precede `game_time_update` (`source/main/main.c:3620-3708`; `source/input/input_xbox.c` and existing extracted fixture). Since one frame can contain 0–7 ticks, Step 12’s literal “poll sequence number equals CE tick sequence number” would be false for valid catch-up scheduling. Preserve one frame sample consumed according to CE’s existing held/pressed/released semantics unless a CE source audit proves a different tick-input contract; test the frame sample ID and the tick(s) it feeds, including zero- and multi-tick frames.
5. RNG is shared CE state with a lock-depth counter. `random_math.c` stores global and local seeds and increments/decrements the global-seed lock (`source/math/random_math.c:79-124`); global seed access asserts the lock while a game engine runs (`:132-140`). `game_tick` brackets `rumble_update()` and `first_person_weapons_update()` with this lock (`game.c:378-382`). Rendering also locks the global seed around `main_game_render` and its frame calls (`source/main/main.c:3312-3404`). A deterministic test must initialize fixed seeds and verify the lock is balanced at phase/tick exit; it must not assume the whole tick leaves the random seed unchanged. Hash the resulting seed as part of the repeatability tuple.
6. The production render path is sequenced after `game_time_update` in the same loop (`main.c:3707-3738`). HCU’s PS2 `render_frame()` advances frame/camera presentation fields, calls `first_person_weapon_render_update()` for a selected player, builds a copied snapshot, commits it, and optionally packs its DMA payload (`port/ps2/src/ps2_render.c:91-190` and `:272+`). This function does not itself call `game_tick`, but it is not wholly side-effect-free: first-person render pose and render globals deliberately advance. The invariant should cover authoritative simulation state and tick/time/RNG scheduling while explicitly excluding documented render-owned pose/cache/frame fields. Independently instrument tick entry so a render callback cannot hide an indirect call.

### Relevant code obligations and external-call surface

A real `game_tick` link/run necessarily traverses more than the phase names asserted today. Its direct semantic boundary includes `profile_tick_start/end`, collision-log period begin/end, `real_math_reset_precision`, profile enter/exit, `match_assert`, `game_state_check_data_arrays`, `lights_port_recover`, and each phase function in the list above. Conditional reads include `game_globals->active` / `players_are_double_speed`, `network_game_distributed_client()`, and `network_coop_active()`. Any host fixture that replaces phase functions with recorders can prove dispatch order only; it does not prove each subsystem’s gameplay behavior. A full initialized tick additionally depends on valid CE game-state/data arrays, map/scenario globals, timer state, player/object/AI/effect/weapon/script pools, and the corresponding source-backed externals from M0.

`game_time_update` adds its own setup/clock boundary: active game-time globals (`speed`, `leftover_dt`, `local_time`, `server_time`), `game_connection()`, local clock update (`update_client_local_ticks`), maximum-server-time selection (`update_client_get_maximum_possible_server_time`), `render_interpolation_tick`, `network_distributed_tick`, and post-tick `render_interpolation_frame_begin` / `game_frame` (`game_time.c:382-507`). A host fixture stubbing these services must label itself scheduler/dispatch coverage, not a complete CE tick. The M0 rooted-external owner table should be consulted before using any generated or no-op implementation for a call reachable from this local path; no simulation-affecting external may be converted to a success-shaped stub merely to make a fixture link.

## Smallest valid increment

Keep the existing static source-order assertions as cheap structural regression checks, but add two explicitly labeled layers rather than claiming they already test runtime:

### Layer A — Execute the real CE `game_tick` function, narrow dispatch harness

- Compile the pinned HCU `source/game/game.c` for a host test using the same HCU headers, ABI definitions that are safe on host, and the same preprocessor branch (`HALO_PS2`, local connection) as production. Link the real `game_tick` object/function; use wrappers only for non-simulation boundary services and phase calls that are deliberately being counted. If whole-file link closure is too broad, compile production `game.c` with function sections and garbage collection so the test roots only `game_tick`, then enumerate every unresolved call in the test executable/map. Do not synthesize a copied version of the function body.
- Supply an initialized `game_globals` fixture (`active=TRUE`, normal player speed) and deterministic local/network conditions. Each phase wrapper appends `{tick_id, phase_id}` and updates a small explicit counter. Assert the exact local phase trace, each required phase count once, AI taken and network actor branch not taken, HaloScript condition expected for local/non-coop, and first-person lock depth returns to zero on exit. Include begin/end sentinels and verify one invocation of the actual function produces exactly one ordered trace. This layer proves execution of the real CE dispatcher, not realistic subsystem state.
- Use source-derived wrappers only for the first narrow test. Classify each stub/wrapper in the report/result as “dispatch fixture only”; fail if the selected root unexpectedly pulls a gameplay function into the stub list. The fixture should assert link-symbol and selected-object identities so it cannot silently test a local reimplementation.

### Layer B — Exercise real scheduler count; then real gameplay state when M2 permits

- Add a `HALO_PS2_M3_TICK_TEST` diagnostic hook at the **real `game_tick` entry/exit** (or use a link-time wrapper that calls `__real_game_tick` and records around it). It must be compiled only in the explicit test profile, retain the original function, and log monotonic tick sequence plus CE `game_time_get()` and seed values. In the PS2 guest, drive `game_time_update` with deterministic deltas or expose a tightly scoped test-only fixed-step driver: 0 seconds → 0 tick; one tick interval → 1; two intervals → 2; local cap case → at most 7, with clocks advancing consistently. Keep floating-point boundary vectors away from representational ambiguity or assert against the pinned source arithmetic.
- For the initial UI-map runtime test, only claim scheduling/dispatch if an actual game-progress state can be initialized; UI-map load or render snapshot alone is insufficient. After M2 supplies a capacity-approved gameplay map, initialize a deterministic local game/player/object state and run N real `game_time_update` ticks in both interpreter/recompiler. Record a compact canonical hash over local/server tick, stable datum indices/generations and selected authoritative transforms/velocities, weapon/ammo/projectile/vital state as available, and both RNG seeds. Sort by stable datum identity; exclude profile counters, padding, render frame/camera/interpolation caches, presentation-only first-person render pose, audio, and wall-clock fields. Repeat from identical initial state and require identical per-tick hashes in each mode; compare modes according to the established float/ABI tolerance policy, not an unexamined raw-memory hash.
- Render-schedule test: fork/reset the same fixture state, run the same N game ticks with 0, 1, and 2 invocations of the production `render_frame`/snapshot-build-and-pack path between ticks, then compare each authoritative simulation hash and tick counter. Record render frame/snapshot sequence separately. Assert render callback count changes while CE tick count and authoritative state do not; instrument `game_tick` at the actual symbol so accidental direct/indirect calls fail immediately. Include render callback calls that actually publish/pack a snapshot (not only snapshot API unit tests).
- Make traces host/target distinctions explicit: Layer A is host execution of the CE production function with selected boundary wrappers; Layer B is PCSX2 on the exact combined ELF and source/package pins; physical four-pad evidence is a separate controller qualification. Do not call host phase wrappers “gameplay parity,” and do not call UI-menu frame rendering a gameplay scene.

### Acceptance and dependency conditions

- Step 11 can close its *tick-order contract* only after a real `game_tick` function invocation produces the expected local ordered trace and the implementation is bound to the production CE object/source. Its *scheduler/render-schedule* clause still requires a real scheduler count test proving zero/one/multiple ticks and zero/one/multiple render callbacks do not spuriously advance CE tick state.
- M3’s full exit remains dependent on M2 providing a capacity-approved resident gameplay BSP and player/object fixture. A black UI viewport, UI `snapshot-dma` marker, or game initialization marker does not satisfy movement/collision or gameplay-tick parity.
- Reconcile Step 12 wording: because CE polls at frame begin but game_time_update may execute multiple ticks per frame, document a single sampled input frame feeding zero/multiple simulation ticks according to CE timing semantics. Require monotonic poll-frame IDs and explicit tick-to-frame association, not poll ID == tick ID.
- No M0 owner-table row or unresolved external can be waived on the strength of the narrow dispatch harness. Every target-required scheduler/phase callback must use its real HCU/PS2 owner or be proven unreachable under the exact local product path.

## Halo-64 comparison (not a behavior template)

Halo-64’s `n64_game_tick()` wraps and calls the real `game_tick()` and adds timing/campaign/firefight hooks (`submodules/halo-64/port/n64/game/n64_game.c:1326-1450`). Its notes specifically preserve CE’s main loop, noting that rendering and ticks are separate, and list render-state hooks still required after drawing was removed (`submodules/halo-64/port/n64/NOTES.md:1-31`). That supports the instrumentation seam and the distinction between presentation callbacks and simulation. Do not import its N64 pool/timing/feature cuts or treat its wrapper as evidence for the PS2 build. On PS2, the native HCU main loop currently calls the unwrapped CE `game_tick()` from `game_time_update()`.

## Evidence status

- **Source audit:** current production source path and CE scheduler/tick/render ordering verified at the citations above.
- **Host test evidence:** `tests/test_hcu_ps2_input.py` has a source-order assertion for game initialization/tick phase order and an executed extracted `input_frame_begin` fixture. It does **not** invoke `game_tick`; no real tick hash or render-schedule test was found in the test tree searched for `game_tick`, `tick hash`, `render_schedule`, and snapshot scheduling.
- **Target evidence:** current plan artifacts include a UI-map load and snapshot CPU-packing marker on an earlier exact ELF, but no gameplay tick trace, deterministic state hash, render-schedule comparison, or accepted gameplay-map simulation. A fresh target run is needed after the M2 accepted map/runtime owner becomes available.
- **Status recommendation:** keep M3 Step 11 partial. The smallest meaningful next implementation is Layer A, followed by the Layer B scheduler hook/test; do not represent Layer A’s wrappers as simulation behavior parity.
