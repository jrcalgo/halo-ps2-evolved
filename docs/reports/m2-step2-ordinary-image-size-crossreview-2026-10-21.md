## Finding

The associated link map is SHA-256 `b8fd1647545ce056bccf933842b769f17bde995aecc61cd7eb2e3a187c7ba85f`. Its section totals are `.text=1,631,704`, `.rodata=392,408`, `.data=73,140`, `.ctors=24`, `.dtors=8`, `.sdata=4`, and `.bss=2,116,772`. These values and the ELF identity are recorded in the exact result artifact; the probe computes the accepted file-backed amount from PT_LOAD headers ([`hcu_parent_link_probe.py:300-324`](../../tools/hcu_parent_link_probe.py#L300)).

There is a smaller, separate accounting difference worth preserving: the memory-audit candidate ledger counts `elf_static=2,097,312` (160 bytes over), while the PT_LOAD gate counts 2,097,540 (388 over). Do not substitute the ledger sum for the executable's PT_LOAD `p_filesz` criterion; resolve the 228-byte accounting delta when the owner ledger is refreshed. Neither metric currently passes.

## Source-backed size-reduction assessment

The obvious generic section-GC optimization is already active. The HCU link-probe profile compiles parent code with `-ffunction-sections -fdata-sections` and links with `--gc-sections` ([`ee-world.mk:211-215`](../../tools/ee-world.mk#L211)); the production gameplay link also directly uses `--gc-sections` ([`hcu_parent_link_probe.py:300-309`](../../tools/hcu_parent_link_probe.py#L300)). The probe fixes parent optimization at `-Oz` ([`hcu_parent_link_probe.py:199-202`](../../tools/hcu_parent_link_probe.py#L199)). Therefore “turn on dead-code elimination” is not an identified solution, and the map already reflects retained sections after GC.

I tested one linker-only candidate against the exact current object list, writing only temporary outputs under `/tmp`: adding `-Wl,--relax` to the same `-Oz`, `--gc-sections`, N32 link produced a PT_LOAD file size of **2,125,188 bytes**, 27,648 bytes larger than the current 2,097,540-byte image. It does not solve this overflow for this link/toolchain, so do not adopt it as a size fix. The experiment preserved the existing object and library inputs; it was not run in PCSX2 and is not a candidate ELF.

The map also identifies a tempting but behavior-affecting cut: `fileXioInit` pulls `__fileXioOpsInitializeImpl`, which in turn references `fileXioWrite` and `__fileXioWriteHelper` (map references at lines 55-100); the linked `fileXioWrite` text is 0x1b8 bytes and its helper is 0x48 bytes ([current link map: lines 55-100 and 7091-7102](../../build/hcu-parent-link-probe/hcu-gameplay-machine.map#L55)). This is not a safe automatic deletion. The PS2 stream reader itself deliberately opens files read-only and exposes bounded `open/read/seek/stat/close` operations ([`file.c:66-87,99-169`](../../submodules/halo-ps2/engine/src/stream/file.c#L66)), but generic CE file APIs include writers and other HCU/CE callsites may depend on them. Removing write support or replacing the SDK's operation table would alter file-service semantics, and the currently read-only asset-loader contract is not evidence that every gameplay/save/debug caller is unreachable. Only consider it after an explicit product-scope decision, rooted-caller audit, and regression tests for every retained file operation; it is not source-backed as semantics-preserving today.

Other apparently easy changes do not establish the required reduction:

- Stripping debug/symbol metadata or `.comment` cannot be counted as a PT_LOAD reduction; the gate is based on load-segment bytes, not the host-side file length.
- Removing parent object files or renderer/service sections without a root/call-site audit can drop machine behavior. The combined source deliberately includes the PS2 renderer, platform services, stream readers, HCU entry, and map services ([`ee-world.mk:5-44,49-65`](../../tools/ee-world.mk#L5)). Retaining their parent objects is not itself proof that every section is live, but section GC already operates at function/data-section granularity; any further exclusion needs symbol-root and parity evidence.
- Changing optimization, ABI/code-generation flags, or CE implementation to save a few bytes is unproven. It may be a useful measured experiment, but must be treated as a new executable and re-run through source parity tests, target ABI checks, and both PCSX2 modes—not described as a no-semantics-change fix in advance.

**Recommendation:** the current evidence does **not** establish a source-backed, semantics-preserving change guaranteed to recover at least 388 PT_LOAD bytes while holding the memory map and lifecycle-test profile fixed. Keep the ordinary image diagnostic-only until a measured candidate passes the PT_LOAD gate. Continue with an exact section/root audit to find code or data that is provably unreachable from the intended gameplay path, or evaluate a controlled compiler/linker profile experiment; bind every result to new object, ELF, and map hashes. Do not shrink the PS2 memory map or borrow the lifecycle-only profile's smaller closure to make the ordinary profile appear to pass.
