# Remake M3 Step 14 ownership audit — 2026-10-21

## Scope and conclusion

This is a report-only audit of Step 14 in [`plans/7.hcu-remake-m2-m4.md`](../../plans/7.hcu-remake-m2-m4.md#L619), focused on authoritative CE state versus the parent `sim/objects`, `sim/skeleton`, and `sim/fpview` code. It does not change shared code or claim M3 completion.

The intended ownership boundary is already stated in the parent headers: in an HCU-integrated game CE owns object identity, transforms, animation simulation, and first-person state; the parent should consume a copied immutable render snapshot. The source supports that boundary, but it is not yet demonstrated end-to-end in the production guest. The key Step 14 risk is broader than duplicate writes: parent helpers can independently advance viewer animation and generate poses from a separate object table, while CE's render callback intentionally updates *render-only* first-person caches inside CE-owned data. The acceptance invariant must therefore distinguish simulation-authoritative fields from documented presentation caches instead of asserting that no CE bytes ever change during render.

## Ownership and call-path findings

### CE is authoritative for object identity, world transform, and simulation animation

CE stores its objects in `object_header_data` and iterates those datums in the PS2 render adapter. The adapter obtains a world matrix using `object_get_world_matrix` and copies the datum index, definition, type, render flags, and matrix into the parent snapshot; it does not write the object datum in this loop ([`ps2_render.c`](../../submodules/halo-ce-universal/port/ps2/src/ps2_render.c#L185-L204)). The source implementation of `object_get_world_matrix` reads the CE datum's position/axes and, when parented, composes the parent node matrix into its output ([`objects.c`](../../submodules/halo-ce-universal/source/objects/objects.c#L2133-L2147)).

Conversely, CE movement/physics call `object_set_position` after computing movement results. That setter writes position and orientation, recomputes node matrices, and reconnects the object to the map ([`objects.c`](../../submodules/halo-ce-universal/source/objects/objects.c#L3375-L3413)). Representative callers are unit movement ([`units.c`](../../submodules/halo-ce-universal/source/units/units.c#L3249-L3250), [`units.c`](../../submodules/halo-ce-universal/source/units/units.c#L3853-L3854)), vehicle movement ([`vehicles.c`](../../submodules/halo-ce-universal/source/units/vehicles.c#L1196)), and physics integration ([`physics.c`](../../submodules/halo-ce-universal/source/physics/physics.c#L1523), [`physics.c`](../../submodules/halo-ce-universal/source/physics/physics.c#L1587)). These are the correct state writers to include in a simulation-state hash/trace. `object_set_position` also performs derived node/map bookkeeping, so tests should capture relevant node/membership results as well as the obvious position fields.

### The parent object table is viewer/demo simulation, not an HCU mirror

The parent `object_table_t` is an independent fixed array of `object_t` records with its own position, root transform, animation graph/index, and frame ([`objects.h`](../../submodules/halo-ps2/engine/src/sim/objects.h#L21-L43)). The header explicitly says these helpers are for the standalone viewer/host tests, and must not become a simulation mirror in HCU mode ([`objects.h`](../../submodules/halo-ps2/engine/src/sim/objects.h#L1-L5)). `objects_spawn_bsp` and `objects_spawn_def` create identities and initialize roots in that table ([`objects.c`](../../submodules/halo-ps2/engine/src/sim/objects.c#L10-L53), [`objects.c`](../../submodules/halo-ps2/engine/src/sim/objects.c#L141-L179)); `objects_tick` advances its own animation frame ([`objects.c`](../../submodules/halo-ps2/engine/src/sim/objects.c#L55-L68)). Those routines should not receive CE objects or be called by the HCU game tick.

In the default viewer, `main.c` deliberately advances `objects_tick` and `fpview_tick` at its 30 Hz simulation cadence, then places the first-person view and renders ([`main.c`](../../submodules/halo-ps2/engine/src/main.c#L248-L256)). The HCU-enabled target uses a different conditional object list: it includes HCU bridges under `WORLD_HCU_GAMEPLAY=1`, while the `WORLD_PLAY=1` block that adds `play_ee.c` and its wrappers for `objects_tick`, `objects_pose_model`, and `fpview_tick/place` is separate ([`ee-world.mk`](../../tools/ee-world.mk#L45-L80)). This is useful structural isolation, but object-file inclusion alone is not proof of runtime exclusion: HCU also compiles `sim/objects.o`, `sim/skeleton.o`, and `sim/fpview.o` in the common viewer object list ([`ee-world.mk`](../../tools/ee-world.mk#L14-L17)). The combined image's rooted call graph/link map should prove which sections are live, and runtime instrumentation should prove the viewer mutators are not invoked.

`objects_pose_model`/`objects_pose` and `skel_world` are different: they derive node matrices into caller-provided output arrays. `skel_world` writes only `world[]` outputs and its stack-local `done[]`, with no object-table pointer ([`skeleton.c`](../../submodules/halo-ps2/engine/src/sim/skeleton.c#L4-L26)); `objects_pose_model` reads model/animation data and writes the `object_nodes_t` result ([`objects.c`](../../submodules/halo-ps2/engine/src/sim/objects.c#L70-L139)). This is safe as a pure presentation helper only when its inputs are immutable CE snapshot/model data and its output is frame-local. Today the CE snapshot carries object root matrices and first-person node matrices, not full node palettes for each animated world object; so calling parent `objects_pose` on its own `object_t` table would render a different/duplicate simulated world, while calling `objects_pose_model` on copied CE animation state would require an explicit adapter input contract not yet present.

### First-person CE presentation has a deliberate render-only write path

CE's `render_frame()` selects a camera, calls `first_person_weapon_render_update()`, copies CE first-person nodes into the snapshot, and iterates object datums to copy their world transforms ([`ps2_render.c`](../../submodules/halo-ce-universal/port/ps2/src/ps2_render.c#L134-L204)). The first-person render update mutates CE's private first-person presentation state: it updates visibility and builds node matrices ([`first_person_weapons.c`](../../submodules/halo-ce-universal/source/interface/first_person_weapons.c#L649-L670)). Matrix building reads the selected camera and updates `render_facing`, `render_position`, `render_forward`, `rendered`, and last-render tracking ([`first_person_weapons.c`](../../submodules/halo-ce-universal/source/interface/first_person_weapons.c#L1172-L1198)). The adapter then copies node matrices out through a bounded interface without exporting a live CE pointer ([`first_person_weapons.c`](../../submodules/halo-ce-universal/source/interface/first_person_weapons.c#L832-L850)).

This is a CE-owned *presentation cache*, not a parent mutation and not a gameplay weapon-pose update. Step 14 should whitelist these fields as render-derived state and separately assert that weapon datum state, unit/object transform, simulation animation state, tick/time, and RNG are invariant under render scheduling. If visual camera sway uses prior render-facing data to influence the next render pose, the test must compare rendered outputs under a fixed camera sequence and avoid treating the expected cache update as a gameplay mutation.

### Current snapshot test is useful but only tests a stubbed boundary

`tests/test_hcu_render_frame_invariance.py` extracts the production `render_frame` function text ([test lines 11-29](../../tests/test_hcu_render_frame_invariance.py#L11-L29)) and runs it against synthetic object/matrix arrays and stub functions ([test lines 32-95](../../tests/test_hcu_render_frame_invariance.py#L32-L95)). It performs 0/1/2 render builds and checks that those synthetic arrays and a sentinel remain byte-identical, while checking snapshot contents and DMA packing ([test lines 157-180](../../tests/test_hcu_render_frame_invariance.py#L157-L180)). It does not link CE object datums, CE physics/unit tick, CE RNG/weapon state, real first-person cache storage, parent `objects_tick`, or the target call graph. Therefore it validates the adapter's copy semantics but does not yet satisfy Step 14's stronger live CE state invariant.

The live production rendering call path is structurally connected in CE: `source/main/main.c` calls `render_frame` from `main_game_render` and UI transitions ([`main.c`](../../submodules/halo-ce-universal/source/main/main.c#L3311-L3392), [`main.c`](../../submodules/halo-ce-universal/source/main/main.c#L2960-L2990)). However, the current parent HCU diagnostic screenshot exercises only an isolated GS clear, and prior M3 evidence says the full snapshot consumer/scene is not live yet. A code-level function being linked is not evidence that the current guest drives it.

## Recommended Step 14 seam and test order

1. **Define state partitions before asserting invariance.** Build an explicit test inventory with (a) authoritative gameplay state: object datum identity/generation, position/axes, parent relation, node-matrix simulation data, unit/weapon datums and animation state, game tick/time, RNG; (b) allowed CE presentation state: `render` camera/frame and first-person render caches; (c) immutable inputs and outputs: committed snapshot bank and frame-local parent render work. Add byte offsets/source names for each class rather than hashing opaque whole global arenas.
2. **Make current target reachability observable.** Add test-only wrappers/counters around `objects_tick`, `objects_spawn_*`, `fpview_tick`, `fpview_place`, and CE `object_set_position`; inspect the production HCU ELF map and rooted symbols to verify no parent viewer mutator is called from CE runtime. Keep this diagnostic-only and default-off. `tools/ee-world.mk` separates `WORLD_PLAY` from `WORLD_HCU_GAMEPLAY` already, so assert that target distinction in the build test.
3. **Strengthen host fixture from adapter stubs to a CE-owned miniature world.** Use actual CE datum structs, object iterator/world-matrix routines, and representative physics/unit movement routines (or link the smallest source-extracted functions with faithful dependencies). Apply a fixed tick/input sequence, save authoritative-state digest, render 0, 1, and 2 times using `render_frame`, commit/copy/pack snapshots, then assert the digest and next-tick result match a no-render control run. Separately assert that the explicitly allowed frame/cache/snapshot fields do change as expected.
4. **Exercise invalidation and identity lifecycle at the actual snapshot boundary.** Delete/reuse an object handle and unload/rebind the map between publications; require generation-aware snapshot rejection or consumer invalidation before rendering. Current snapshot entries carry `datum_index` but no demonstrated generation field in the copied object record, so the audit must establish where generation is encoded or add one before this can pass. Include stale bank/map generation checks.
5. **Do not route the viewer table into HCU.** The safest implementation seam is a parent snapshot consumer API that accepts only `const halo_ps2_render_snapshot *` plus immutable model/tag views and writes only frame-local renderer buffers. Initially consume root transforms and test exact record identity/capacity; add animation-node palette production only after CE animation matrices are exported through a bounded snapshot field. Do not call `objects_tick`, `fpview_tick`, `objects_spawn_*`, or mutate parent `object_t` roots in the HCU runtime.
6. **Target evidence follows host invariance.** Once renderer arena partition and snapshot consumption are implemented, run the same deterministic scene/tick schedule on PCSX2 with render disabled, one render per tick, and extra presentation frames. Compare CE state hashes at tick boundaries and compare image/snapshot hashes only under fixed renderer settings. M3 still also needs resident gameplay BSP and actual GS/VU submission; the blue-clear diagnostic does not satisfy this.

## Disposition

The ownership design is sound and already reflected in `objects.h`/`fpview.h` comments, but M3 Step 14 remains incomplete. The immediate gap is **evidence and runtime reachability**, not a need to migrate the viewer's `object_table_t` into CE. The existing extracted `render_frame` test is a good first adapter test; extend it around authoritative CE tick/object state and explicitly permit CE-owned first-person render-cache updates. Do not close Step 14 until the actual HCU production link and runtime show no parent simulation writers and render cadence leaves all gameplay-authoritative CE state and the next tick result unchanged.
