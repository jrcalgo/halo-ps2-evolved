# M2 Step 7: second retail map selection for the package transaction fixture

## Recommendation

Use the audited retail campaign map **`a50`** as the second package-backed CE/PS2 BSP transaction fixture, after retaining `a30` as the current baseline. It is the best next structural stress case in the locally audited corpus: `a30` has two scenario BSP references, while `a50` has four; `a50` therefore exercises a larger reference/catalog cardinality and a different set of BSP images while keeping a bounded, reproducible package. Do not claim that either package is a complete playable map or that `a50` fits PS2 memory based on this test.

## Why `a50` is the right next case

1. **It changes scenario/catalog structure, not merely bytes.** Four `scenario_structure_bsp_reference` rows and four matching CBIX sections exercise tag-index lookup, section selection, active datum publication, and unload/reload across more than the fixed two-entry sequence now present in the `a30` fixture. The code under test is CE's `scenario_switch_structure_bsp()` and load/unload lifecycle, not just the standalone CBSP decoder (`tests/hcu_scenario_bsp_switch_main.c`; `source/scenario/scenario.c`).
2. **Its BSP images are non-identical and cover more than one size class.** `a50` references `levels\\a50\\a50_exterior` (3,835,904 B), `a50_muster` (6,983,680 B), `a50_hangar` (7,157,760 B), and `a50_control` (7,159,808 B). All four CBSP sections are present in the audited package and map to the four source extents. This tests catalog integrity and repeated owner-arena allocation/release with a small and three near-maximum payloads. The per-BSP source details are in `docs/reports/retail-bsp-cbsp-audit-current.json` under the `a50` row; CBIX completeness is checked by `tools/audit_retail_cbsp_catalogs.py`.
3. **It is large enough to expose assumptions in CTAG validation.** The current compacted CTAG audit reports `a50` image size 11,174,776 B, payload size 11,339,176 B, and 3,311 tag instances, compared with `a30` 9,689,096 B, 9,843,008 B, and 3,215 instances (`docs/reports/retail-ctag-compaction-audit-current.json`). This tests CE's real `tag_validate_tags()` and PS2 normalization against another actual scenario/tag table, not only another BSP byte array.
4. **It is still tractable as a host diagnostic.** Each raw `a50` BSP is below the fixture's current 8 MiB `BSP_CACHE_BYTES`; each CBSP envelope is below 8 MiB; and CTAG is below the current 16 MiB tag-cache/owner test buffers. Those are host fixture bounds only. The current BSP arena/scratch are 16 MiB each, and are deliberately oversized. Their actual high-water and transient overlap must be recorded; if the candidate section exhausts the fixture arena, increase/rework only the host test-owned capacity with explicit measurements rather than weakening production bounds.
5. **It remains a meaningful contrast with the `a30` validation.** The two-map test should keep `a30` to protect the already-working B000↔B001 rollback case, then parameterize a second invocation for `a50`. `a50` broadens map/reference diversity but does not establish campaign loading, runtime collision/PVS use, target memory fit, or rendering.

`a10` is a later, stronger multi-BSP campaign stress test (nine BSPs, 38,887,424-byte HP2 package, 9,622,260-byte compact CTAG image, per-map figures in the same catalog/CTAG reports), but it has substantially more sections and larger per-BSP/aggregate data. `b40`/`c40` each have thirteen BSPs. Those should follow once the fixture is count-agnostic and memory high-water is measured; they are not the best *next* transaction regression while the existing fixture is hard-coded for two BSPs. Blood Gulch is useful for the existing standalone CBSP parity and collision work, but its single-BSP scenario does not stress multi-entry scenario switching; see `docs/reports/retail-bsp-cbsp-bloodgulch.json` and `docs/reports/m2-step7-retail-cbsp-validation.md`.

## Required fixture changes

The current package test is specifically `test_retail_ctag_and_cbsp_flow_through_ce_transaction_and_ps2_cache()` in `tests/test_hcu_scenario_bsp_switch.py`. It hard-codes package `a30`, asserts exactly two entries `B000/B001`, reads only two CBSP payloads, and passes exactly two extents to the executable. The C integration path in `tests/hcu_scenario_bsp_switch_main.c` repeats those assumptions. Make the fixture data-driven before adding `a50`:

1. **Parameterize package identity and catalog.** Pass map name, package path, HMAP identity (file length/tag offset/tag size), catalog count, and every catalog row to the child fixture. Prefer the already-audited manifest as the source of expected package hash/source hash; compare it to actual package and HMAP bytes at test time. Require contiguous unique `B000...B00N` rows, sorted non-overlapping source extents, and exact CBIX-to-HMAP source extent agreement before executing C.
2. **Remove two-element globals.** Replace `references[2]`, `retail_offset[2]`, `retail_size[2]`, and the test's two static tag instances with bounded arrays sized to an explicit maximum (e.g. 16) or scenario-derived storage. Ensure real CE tag instances remain authoritative for the package path; only the fixture's scenario/reference indexing should be generalized. Do not accidentally set `global_tag_count` to the number of BSPs—the real `tag_header->tag_count` is 3,311 for `a50`.
3. **Make the section provider recognize all catalog entries.** `load_package_section()` currently recognizes only `B000` and `B001`; parse the `B` suffix strictly, range-check it against the actual catalog, record each successful/failed selection, and reject unknown or non-catalog tags. Avoid bit shifts on a potentially unbounded integer; use a failure-index field/set or a bounded bitset. Keep section name, index, catalog extent, returned raw size, and decoded CBSP extent in one-to-one agreement.
4. **Exercise the complete four-BSP path.** For `a50`, perform initial loads and transitions that visit each reference, e.g. B000→B001→B002→B003→B000, checking after each step: active `scenario_globals` index, global BSP pointer, matching tag datum `base_address`, prior datum cleared on unload, owner/scratch marks returned to expected state, and the loaded bytes/source offset match the selected catalog row. Include at least one nonadjacent transition (B000→B003) so the implementation is not accidentally relying on adjacency.
5. **Extend rollback/failure injection per index.** At minimum inject owner-section read failure and verifier/schema rejection for a non-first index (prefer B002 or B003), then prove CE restores B000 and leaves exactly the previous datum active. Also fail restoration of the previous BSP and prove CE enters the existing safe-null/menu path with all CE globals cleared. Confirm every injection is actually reached by asserting the selected-section trace.
6. **Run the real validators per package.** Bind the claims bitmap with `tag_validate_claims_buffer_size()` and run real `tag_validate_tags()` on the `a50` CTAG. For each visited BSP, run real `tag_validate_structure_bsp_actual()`/CE BSP schema verification on materialized data, retaining the Xbox-only vertex/index header canonicalization at the PS2 adapter boundary (covered by `tests/hcu_scenario_bsp_switch_main.c` and `submodules/halo-ce-universal/port/ps2/src/ps2_cache.c`). Do not replace CE validation with a success stub. Release validator claims state between package invocations and test for clean re-bind.
7. **Measure allocation peaks rather than simply enlarging buffers.** Record mount owner used/high-water after CTAG materialization and again while each BSP is active; record scratch high-water during every selected BSP conversion; exercise unload and prove no monotonic growth across repeated switches. `a50`'s 11,339,176-byte CTAG payload plus a ~7.18 MB CBSP envelope is a useful transient overlap probe, but do not assume both are charged to the same arena without reading the ownership path. Host fixture values remain explicitly non-production.
8. **Keep output identity-bearing.** Emit map name and package/source hashes with `refs`, `selections`, successful section count, validator results, owner/scratch high-water, and status. A successful `a30` output must remain unchanged or be updated deliberately; `a50` must report four catalog sections and demonstrate each index was selected. Do not print just `bsp-sections=8` if that number conflates expected catalog entries with load events.

## Pre-run and acceptance checks

Run these checks before accepting `a50` transaction results:

1. Recompute package SHA-256 and verify it equals the `a50` row in `docs/reports/retail-cbsp-catalog-package-audit-e4a97218.json` (`9359e0...21941a`); verify HMAP source-map hash equals `d7a3...70f38d` and that source file length/tag offset/tag size agree with the row from `docs/reports/retail-ctag-compaction-audit-current.json` (250,138,624 / 234,469,376 / 15,668,928 bytes).
2. Decode `CTAG`, `CBIX`, and all four CBSP sections with the shipped Python validators (`tools/ctag.py`, `tools/cbsp.py`, HP2 reader). Assert catalog count 4 and extents exactly `(2048,3835904)`, `(3837952,6983680)`, `(10821632,7157760)`, `(17979392,7159808)`; assert every CBSP envelope declares the same extent and materialization passes relocation bounds and CTAG-name checks.
3. Run real CE tag validation and all four BSP schema validations with the test's actual source pins. Preserve validator output and package hashes. If CTAG validation fails, investigate unsupported Xbox-only serialized/runtime fields and apply only source-backed canonicalization in the PS2 cache adapter; do not bypass CE's schema/claim checks.
4. Run both `a30` and `a50` invocations in the approved host ILP32 environment, then related parser/cross-domain/schema tests (`tests/test_cbsp.py`, `tests/test_hcu_reader_fault_matrix.py`, `tests/test_ctag_schema_walk.py`, `tests/test_hcu_scenario_bsp_switch.py`). The fixture's >16 MiB test arrays and host libc file reads are not PS2 evidence.
5. Separately rebuild the R5900 closure and run the current exact PS2 ELF/package through PCSX2/device-backed storage once the M2 memory/load path supports it. A host package transaction is not a substitute for PS2 destination placement, source I/O, collision/PVS/sound consumers, or rendered-scene proof.

## Resource and product caveats

`a50` has four BSPs, but the transaction fixture should load only one active BSP image at a time, matching CE's unload-before-load lifecycle. The complete package includes all four CBSP sections; do not allocate all four simultaneously for convenience and then call that runtime behavior. The current capacity audit reports `a50`'s largest raw BSP as 7,159,808 B and its hypothetical projected BSP after compressed-vertex externalization as 4,360,680 B (`docs/reports/retail-map-minimum-working-set-current.json`). The same audit says compact CTAG is 11,174,776 B; even after its hypothetical animation-data externalization the CTAG candidate is 6,617,194 B, above the current 4,701,212-byte resident-gameplay span. The BSP projection is arithmetic only, does not prove that removing those bytes is safe, and excludes validator scratch, other runtime data, and required PS2 render packs.

Therefore this selection is specifically for **map diversity and CE transaction correctness**. It does not close M2 Step 7. Continue to require separately: PS2 memory destination/peak proof; device-backed package reads; actual CE collision, surface/material, cluster-PVS, sound-cluster and pathfinding consumers; malformed pair handling on target; a current-build PCSX2 run; and evidence that any externalized/render-only data is safe and represented in the PS2 renderer. These remain open under `plans/7.hcu-remake-m2-m4.md` Step 7 and the broader source/ownership boundary in `plans/5.hcu-remake.md`.
