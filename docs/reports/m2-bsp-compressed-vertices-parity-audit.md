# M2 BSP compressed-vertex replacement/parity audit

Status: investigation only. No production code or plan was changed for this report. This is not approval to strip `structure_material.compressed_vertex_data`, not a capacity acceptance, and not evidence that a retail BSP renders in the integrated guest.

## Finding

The `halo-ps2` HP2 `BSPn` section contains a useful equivalent for a subset of CE's BSP render inputs: per-cluster batches with expanded triangle positions, texture UVs, lightmap UVs, and vertex colors, directly consumable by the VU1 renderer. It does **not** currently preserve the full CE `compressed_vertex_data` contract or enough identity to replace all CPU reads. In particular, it does not serialize the CE source surface index/leaf relationship, source material vertex indices, packed vertex normal/tangent/binormal, or packed incident-radiosity vector. It quantizes positions and UVs, reorders triangles, and omits some source surfaces. Thus it is a candidate for a narrowly defined render-visibility adapter only after parity tests; it is not a drop-in for CE collision-hit surface/material resolution or CE object-light sampling.

The current capacity arithmetic (subtracting the vertex blobs from the raw BSP) is only a lower-bound projection. A valid whole-resident calculation must charge the HP2 `BSPn` bytes, alignment and runtime metadata, any externalized/sidecar CPU data, streaming buffers, and transition overlap exactly once in the actual physical region(s). If a `BSPn` payload is already loaded for rendering, it might serve as the backing store for a render-only query without a second copy, but that fact and lifetime are not established by this audit.

## CE data layout and consumer call tree

### Record and byte layout

`structure_material` carries separate `uncompressed_vertex_data` and `compressed_vertex_data` tag-data descriptors (`submodules/halo-ce-universal/source/structures/structure_bsp_definitions.h:50-66`). On retail BSPs audited by the PS2 converter, the latter is a concatenation of:

| Portion | Source record | Bytes per element | Semantics read by CE |
|---|---|---:|---|
| Rendered vertex array | `environment_vertex_compressed` | 32 | xyz float32 (12), packed normal/binormal/tangent (12), diffuse UV float32x2 (8) |
| Lightmap vertex array | `environment_lightmap_vertex_compressed` | 8 | packed incident radiosity (4), lightmap u/v signed 16-bit (4) |

The definitions are at `submodules/halo-ce-universal/source/objects/object_lights.c:270-284`. The lightmap accessor begins at `compressed_vertex_data.address + vertices.count * 32` and indexes 8-byte records thereafter (`object_lights.c:258-266`). `halo-ps2/tools/halo2ps2/bsp.py:101-125` states the source `structure_material` stride as 256 bytes and the render `surfaces` records as 6 bytes. The corresponding converter reads each material's vertex counts at material offsets `+0xB4` and `+0xC8`, compressed-data size/pointer at `+0xEC`, and requires `size == rendered_count*32 + lightmap_count*8` (`submodules/halo-ps2/tools/halo2ps2/bspconv.py:129-145`).

### Consumer categories

1. **CE CPU frustum/visibility triangle test.** `structure_visibility` iterates cluster surface-index lists, selects the material, treats each surface vertex index as a 32-byte stride into `compressed_vertex_data`, reads the first 12 bytes as an `real_point3d`, bounds-checks all indices using `data.size / 32`, and calls `render_frustum_triangle_visible` (`submodules/halo-ce-universal/source/structures/structure_visibility.c:551-615`). This direct CPU path is the strongest candidate for redirecting to the existing PS2 VIF geometry, but it still needs a mapping from a CE surface to its source triangle(s) and must handle omitted source faces correctly.
2. **Collision-hit to source render surface/material/barycentrics.** `structure_test_vector` calls CE collision (`collision_test_vector`) with a structure/front-facing filter, then invokes `structure_render_surface_from_point_and_leaf` with collision point, leaf, and plane (`submodules/halo-ce-universal/source/structures/structures.c:838-911`). The callee walks that leaf's source surface references, matches each reference's collision BSP3D plane, resolves its source `structure_surface` and lightmap/material, reads xyz from each indexed 32-byte compressed vertex, and calls `point_in_triangle3d` to return source surface ID and barycentric `s,t` (`structures.c:517-615`). HP2 BSPS has no serialized source surface ID or leaf->surface association, so its present records cannot reproduce this identity lookup directly.
3. **Diffuse/lightmap texture-coordinate sampling.** `sample_diffuse_texture` interpolates the three source diffuse UVs; `sample_lightmap` interpolates source lightmap UVs and samples the bitmap (`submodules/halo-ce-universal/source/objects/object_lights.c:591-660`). The world-light query obtains collision hit/material/surface via `structure_test_vector`, then calls these samplers (`object_lights.c:1455-1490`, `2215-2238`). The PS2 BSPS packet has both UV sets, but its values are quantized and its records are expanded/reordered, so exact source triangle identity and an accepted texel-equivalence tolerance are needed.
4. **Per-surface object-light normal/radiosity sampling.** The object-light path also decodes packed source normals for the triangle and interpolates/normalizes them; it reads incident-radiosity values from the separate lightmap-vertex records (`object_lights.c:2484-2524`). The current BSPS packet contains neither source normal/tangent/binormal nor incident-radiosity vectors. It stores a precomputed color stream for the GS/VU render path, which is not a general substitute for these directional CPU values.
5. **Non-applicable similarly named consumers.** Lens flare construction reads `material->uncompressed_vertex_data`, not the compressed blob (`submodules/halo-ce-universal/source/structures/structure_lens_flares.c:319-325`). Model compressed vertices in `source/rasterizer/rasterizer.c` are a different tag family and not part of this BSP capacity question.

## What HP2 `BSPn` does preserve—and does not

The parent pack format has one `BSP0..BSPZ` section per converted structure BSP; the section includes per-cluster VU batches, cluster/portal data, and a point-location tree. Its documentation explicitly treats collision, lightmap atlases, and textures as separate concerns (`submodules/halo-ps2/docs/08-bsp-section.md:1-7`). The BSPS material table stores shader tag ID, lightmap page, UV shift, batch count, and triangle count; batch records identify material and VIF extent, but neither table carries CE surface ID (`docs/08-bsp-section.md:75-101`).

`bspconv.read_materials` reads xyz and diffuse UV from each 32-byte source rendered vertex, lightmap UV from the 8-byte lightmap vertex when present, and source triangle vertex indices/surface IDs in converter-side objects (`submodules/halo-ps2/tools/halo2ps2/bspconv.py:117-165`). `build_section` groups triangles by cluster set and material, sorts them spatially, and serializes batches (`bspconv.py:338-350`). The source surface-ID list lives only in `Material.surfaces` (`bspconv.py:68-72`); it is not emitted in the serialized BSPS directory/tables (`docs/08-bsp-section.md:75-101`).

Each VIF packet contains center/scale constants, signed-16 relative xyz, signed-16 diffuse/lightmap UV, and u8 RGBA. Each triangle is expanded to three corners; batches contain at most 24 triangles (`bspconv.py:31-42`, `232-266`). The C reader decodes position as `centre + s16*scale` and returns four signed-16 UV components plus RGBA (`submodules/halo-ps2/engine/src/world/bsp.c:182-220`; `bsp.h:69-94`). This differs from CE's float xyz/UV and requires numeric parity tolerances. Rendering references the VIF packet directly (`submodules/halo-ps2/engine/src/render/bsp_render.c:395-402`).

Coverage caveats are material: the converter groups only triangles with at least one cluster surface route and drops no-cluster triangles; its documentation reports 21/69 audited BSPs with unreferenced surfaces (195 surfaces total) and says their non-draw status is an inference. Mirrors occur in `b40_c` and are marked but not converted. The same document reports 2 concave portal polygons replaced by convex hulls and unresolved tie behavior for exactly-on-plane cluster lookup (`submodules/halo-ps2/docs/08-bsp-section.md:40-59`). These facts do not alone prove a mismatch with CE, but they prevent a blanket equivalence claim.

The shared campaign mission/BSP set and the source maps behind the report must be paired with matching HP2 outputs. A tag path like `levels\\d20\\d20_hangar` is not sufficient provenance: require exact map SHA, tag file offset/extent, BSP index/path, converter code/config hash, HP2 package SHA, `BSPn` tag/index and raw-section SHA, plus the material/bitmap/lightmap resource package identities. This report found no local retail HP2 packs to inspect, so it cannot state per-map BSPS output sizes or claim the 3,311,136 source bytes are replaced without a duplicate.

## Capacity/accounting consequences

The v4 audit's arithmetic formula is `raw BSP extent - sum(compressed_vertex_data extents)` (`tools/audit_retail_bsp_schema.py:24-34`, `107-127`). For `d20_hangar`, that is 8,517,632 − 3,311,136 = 5,206,496 bytes, which is less than the 6,291,456-byte `current_bsp` cap. It is not an allocation topology: it omits the replacement BSPS payload, adapter indexes, live CE data needed for collision/light queries, section/table alignment, staging and decompression overlap, texture/lightmap storage, and map-transition lifetime. The audit itself marks it arithmetic-only and says there is no proven HP2 equivalent and no charge for an external copy (`tools/audit_retail_bsp_schema.py:27-34`, `114-127`, `181-188`).

Use an explicit whole-resident equation for each maximum live map state, e.g.:

```text
current_bsp live bytes = retained CE BSP schema extents
                       + resident BSPS section(s) including VIF and tables
                       + source-surface/triangle bridge index (if added)
                       + bounded staging/decompression overlap and alignment
                       + any remaining collision/query BSP payloads
```

Then account the full image as distinct, non-overlapping physical stores: ELF/static/BSS, retained gameplay/tag arena, current BSP, texture/lightmap cache, dynamic simulation, DMA command arena, streaming scratch, audio/checkpoint/scratch, kernel/system reservation, and 5.5 MiB reserve. If the CE render blob is moved to a separate HP2 section but still needed for hit/light sampling, it remains resident or pinned somewhere and must be counted there; moving it does not reduce whole-resident RAM. If its rendered-vertex floats are genuinely replaced by the already-resident BSPS packet, subtract only after proving the packet is already charged once, its same-map lifetime covers every caller, its error is acceptable, and a surface-index bridge has a measured size. Do not charge the full CE blob and BSPS packet twice, and do not give the BSPS section zero cost because it is “render data.”

`d20_hangar` is one BSP, not necessarily the peak map image. The per-map report lists 82 BSPs across 24 maps and the scenario can refer to multiple BSPs. Capacity acceptance must use the actual scenario/map residency policy: simultaneously resident BSPs, any old/new BSP transition overlap, and whatever section set CE keeps alive. A per-BSP lower-bound pass is not a whole-map proof.

Preserve raw rows, not only aggregate pass/fail. Repeat over every structure BSP in the accepted campaign corpus and any simultaneous/multi-BSP scenario.

## Recommended implementation boundary if pursuing this path

Keep CE's collision BSP and authoritative source-surface identity path intact until the hit-to-surface and lighting rows above pass. First prototype a **render-only** provider keyed by `(map SHA, BSP index, material index, source surface index)` that can fetch decoded triangle vertices from the exact active BSPS section; fail closed to CE source data when no mapping exists. The converter must serialize a validated source-surface mapping (and any CPU data required for CE lighting) or demonstrate that an already resident distinct source-data lease is cheaper. Measure its actual section bytes and index bytes across the corpus. Do not assume a VU VIF packet is CPU dereference-equivalent: direct packet access is possible, but it expands and quantizes vertex streams and has no IDs.

Once the render-only provider passes parity, evaluate whether the original float xyz array may be removed while retaining normal/tangent/binormal, UV precision, source topology, and lightmap records. Then evaluate whether any light-sample record can be precomputed without changing CE behavior. Each removal is a separate data migration with its own payload checksum, consumer audit, and same-ELF guest evidence. This sequence preserves the requested Halo CE semantics while allowing measured PS2-specific storage repacking.
