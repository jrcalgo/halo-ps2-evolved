# C3 first-person asset and pose-stage audit (R3) — 2026-10-26

## Findings

There is no evidence that the PS2 model converter swaps the viewmodel axes, changes handedness, or applies a model-unit/origin conversion. Xbox MODE vertices are parsed as `f32 position[3]`; `read_model` preserves those values, `pack_batch` quantizes each same-axis coordinate around a batch center, and `decode_batch` restores `centre + s16 * scale` (see `submodules/halo-ps2/tools/halo2ps2/modelconv.py:61-65, 414-430, 605-628, 1038-1058`). The VU1 model path decodes XYZ and skins with the uploaded node palette (`submodules/halo-ps2/engine/src/vu1/model.vsm:28-66`). It does not insert a coordinate permutation.

The retained actual MODL chunks also have plausible Halo-unit bounds, not a conspicuous unit-scale error. Decoding all packed batches with `modelconv.parse_section`/`decode_batch` gives the selected assault rifle bind-space AABB `x=[-0.0215,0.0907], y=[-0.0105,0.0105], z=[-0.0429,0.0477]`, model radius `0.0657`; selected hands AABB `x=[-0.0020,0.2907], y=[-0.1275,0.1275], z=[-0.0336,0.0430]`, radius `0.1936`. These values are computed from the retained package's packed PS2 asset, so they validate its decode/bounds but are not an independent byte-for-byte comparison against an unavailable raw retail MODE cache.

Halo 64's separate model converter likewise does not establish an axis mismatch: it reads `(px,py,pz)`, applies only each owning node's inverse default transform to produce node-space vertices, then stores coordinates multiplied by `MODEL_SCALE=1024` (`submodules/halo-64/tools/n64/models.py:669-694, 873-874`). At draw time Halo 64 applies the CE matrix basis at `WORLD_SCALE/MODEL_SCALE` and its translation at `WORLD_SCALE` (`submodules/halo-64/port/n64/src/n64_render.c:3570-3576`; constants at `:39,334`). That is a matched unit conversion for its own pretransformed vertex format, not evidence for a Y/Z swap. Halo 64 and PS2 use different vertex representations; neither source path gives a basis correction to apply to current PS2 MODL coordinates.

## CE pose/render order

CE advances the first-person weapon state for every local player in `game_tick` (`submodules/halo-ce-universal/source/game/game.c:388`; implementation at `source/interface/first_person_weapons.c:2117+`). Normal CE rendering sets the selected window's player and camera before `first_person_weapon_render_update` (`source/render/render.c:322-340`). That call selects visibility for that player and rebuilds its matrices from the selected camera (`first_person_weapons.c:659-680, 1348-1793`), using current state, moving and overlay animations plus interpolation. The normal draw then remaps those matrices separately for gun/hands and calls `render_model`; that path applies each model node's runtime default inverse (`first_person_weapons.c:529-615`, `models/models.c:1028-1038`). There is no later model-space scale/origin/axis transform in that route.

The camera-local selected runtime root is genuinely non-identity and weapon-specific: in the retained movement trace, model graph node 7 for weapon datum 1161 is remapped as the gun root, with posed `F=(0.5956,0.0904,0.7982)`, and parent-relative root `P=(0.0809,-0.0967,-0.0249)` (`build/c3/first-person-fix/runtime/quiet-baseline-v1/run-20261026T063340Z-7a41b5cf118c/emu.txt`, `HALO_PS2_FPPOSE` near emulator time 102.648). The parent clip diagnostic reports that the bundled rifle's projected weapon bounds are entirely offscreen, `x=[1.81996,6.16745]`, `y=[-2.42419,2.08202]` (`docs/reports/c3-fp-i1-pose-2026-10-26.md`). A non-identity authored pose is therefore an observed input, not proof of a parent axis error.

## Remaining stage and a concrete freshness hole

CE's optional first-person projection stage is `viewmodel_projection_begin` in the transparent-geometry/model rasterizers. The port hook selects `display.viewmodel_fov` or, when a widened world FOV was requested, `render_fov_authored_vertical`; otherwise it leaves the current projection unchanged (`submodules/halo-ce-universal/port/linux/game/view_fov.c:186-235`; call sites include `source/rasterizer/rasterizer_transparent_geometry.c:591-619`). Existing runtime records do not state whether this conditional branch applied or its selected angle. The parent report's FOV equivalence only covers the captured render-camera FOV, not an active separate authored viewmodel FOV. Add an explicit bounded record of selected angle/applied bit before claiming that branch is ruled out; do not change FOV without that observation.

There is a source-backed stale-pose possibility in the C3 publisher. `ps2_bitmap_frame_run` builds poses only inside its successful per-window loop, after all preflight checks and successful `begin`, immediately before `set_view` (`port/ps2/src/ps2_render.c:405-479`). Preflight or begin failures return/skip without any pose rebuild; a `set_view` failure updates that view, then stops later views. `render_frame` nevertheless continues to `ps2_c3_publish_frame_snapshot` (`:1145-1243`), whose view loop sets player/camera but copies existing weapon/hands matrices without calling `first_person_weapon_render_update` (`:996-1110`). The C3 bitmap owner is normally bound by `hcu_main.c:1544-1557`, and successful windows each get their pose update before HUD callbacks, so downstream request/HUD batch-drop errors do not cause this issue. The source hole is specifically optional bitmap-frame preflight/begin/partial-view failure followed by snapshot publication. A targeted C3 per-view pose rebuild in the snapshot loop, after setting render context and before copying models, would make the snapshot independent of bitmap callback success; ensure successful bitmap path does not introduce undesirable duplicate state updates.

## Evidence boundary and next capture

The retained runtime log has the CE-remapped pose and parent clip matrix, but it does not record the exact first-person animation state/frame, nor whether the optional viewmodel projection branch was selected. The requested next diagnostic fields are: local-player and window indices; game tick; first-person state and state animation index/frame; moving animation index/frame; overlay index; interpolation index/count; root graph node and quaternion/translation; relative root F/L/U/P; selected camera position/forward/up/FOV; and `viewmodel_projection_begin` selected angle/applied flag. Also record bitmap-frame preflight/begin/per-view callback status alongside whether each per-view pose rebuild ran. These fields discriminate current authored animation, stale export, and a missing projection stage without fitting an arbitrary offset or scale.

No production source was edited and no emulator or guest/build run was performed for this audit.
